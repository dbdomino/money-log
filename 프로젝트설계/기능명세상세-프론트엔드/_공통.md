## 필드 설명 작성 규칙 (누락)

화면 상세 문서의 표(입력·표시·동작) **설명 칸은 그 칸만 보고 의미가 읽혀야** 한다.

- `_공통.md`에 같은 내용이 있어도 **화면 문서 표에 의미를 다시 적는다**.
- 다음만 적는 것은 **누락**이다: `동일`, `위와 같음`, `공통 참고`, `생략`, 빈 칸, `요청 에코`.
- 링크는 **보조**일 뿐, 설명 칸을 대체하지 않는다.

## 표시방식 (페이지 / 모달)

| 구분 | 대상 | 표시 | URL |
|------|------|------|-----|
| **페이지** | 목록·허브·auth·본인정보·엑셀·목표·통계 | 풀페이지 (`templates/**/*.html`) | 대표 URL만 |
| **모달** | 등록·수정·상세 (및 고정지출 월별) | 부모 페이지 위 모달 (`fragments` / `th:fragment`) | 부모 URL + `?m=` (+ `id` 등) |

규칙:

- 사이드바「지출 등록」「소득 등록」「고정지출 등록」은 **전용 페이지가 아니라** 부모로 이동 후 모달 오픈.
- **구 경로는 부모 + `?m=` 로 redirect 한다.** 대상이 두 갈래이고 확정 목록은
  [007 url-map 계약](../../specs/007-frontend-foundation/contracts/url-map.md)에 있다.
  - **실재했던 레거시 주소**: `/mem/login`(GET) → `/auth/login`, `/mem/ind` → `/`.
    `/mem/login`(POST)와 `/api/ammounts/**` 는 **redirect 하지 않고 없앤다** — POST 는 본문
    형식이 백엔드 계약과 다르고, `/api/**` 는 화면 URL 이 아니다. 프론트가 REST 를 노출하면
    브라우저가 화면 모듈을 API 처럼 부르는 길이 생긴다.
  - **관례상의 등록·수정·상세 주소 16건**: `/payments/new`·`/payments/{id}/edit`·
    `/ledger/expenses/new` 처럼 실재한 적은 없지만 사용자가 손으로 칠 법한 주소다.
    수단 3 · 지출유형 3 · 지출 2 · 소득 2 · 고정지출 4 · 회원 2 이며 전부 부모 목록 +
    `?m=`(+ `id`)로 보낸다.
  - 상태 코드는 구 주소가 `301`, 루트 분기가 `302` 다. `id` 가 없으면 `?m=` 없이 부모
    페이지로만 보낸다. 목록에 없는 주소는 redirect 하지 않고 404 다.
  - **`/expend-groups/icons/{filename}` 은 redirect 대상이 아니다.** 아이콘 프록시 주소이며
    `/expend-groups/{id}` 보다 **먼저** 매칭되어야 한다. 순서를 잘못 두면 아이콘 요청이 상세
    모달 redirect 로 새어 나가고, 증상은 "아이콘이 하나도 안 보인다"로만 나타난다.
- 삭제·정지·중도상환 확인은 공통 `fragments/confirm-dialog`.
- 기획·프로토: [화면기획/01-화면구성.md](../화면기획/01-화면구성.md)

모달 딥링크 예:

| `?m=` | 의미 | 부모 |
|-------|------|------|
| `create` / `detail` / `edit` | CRUD | 해당 목록 (수단·유형·회원·고정지출) |
| `expense-create` / `expense-edit` | 지출 | `/ledger` (5.1) |
| `income-create` / `income-edit` | 소득 | `/ledger` (5.1) |
| `monthly` | 고정지출 월별 | `/fixed-expenses` (4.2) |

## 인증·토큰 (화면 공통)

로그인 API 응답의 토큰을 저장한다. API 호출 시 `Authorization: Bearer <accessToken>`.

### 토큰은 서버 세션에 둔다

**저장 위치는 `money-app` 의 `HttpSession`이다.** 브라우저(로컬 스토리지·JS 메모리)에 두지
않는다.

`money-app` 은 서버 렌더링 화면이고 백엔드 호출도 **서버가** 한다
(`*WebController → BackendApiClient`). 토큰이 브라우저에만 있으면 서버가
`Authorization` 헤더를 붙일 수 없어 그 구조 자체가 성립하지 않는다.

| 항목 | 값 |
|------|-----|
| 저장 키 | 세션 속성 (`accessToken` · `refreshToken` · 표시용 회원 정보) |
| 브라우저가 들고 있는 것 | **`JSESSIONID` 쿠키뿐.** JWT 원문은 브라우저에 내려가지 않는다 |
| 세션 만료 | `server.servlet.session.timeout: 30m` (30분). 만료되면 토큰을 잃은 것이므로 미로그인으로 보고 `/auth/login` 으로 보낸다 |
| 로그아웃 | `MemberTokenRevoke` 호출 후 **세션 무효화**(`invalidate`) |

**세션 만료 시간에 단위를 반드시 붙인다.** 값만 적으면 초로 읽힌다 — 현재 설정의 `60` 은
1분이고, 명세가 값을 비워 둔 탓에 그것이 의도된 값으로 읽혔다. Access 토큰이 1일인데 화면
세션이 1분이면 사용자에게는 "1분마다 재로그인"으로 관측되고, Access 만료 재발급 흐름은
세션이 먼저 죽어 **한 번도 일어나지 않는다.**

이 선택의 결과가 셋이다.

- **브라우저가 `:8081` 을 직접 부르지 않는다.** 그래서 백엔드에 CORS 설정이 필요 없다.
- **JWT 가 JS 에서 읽히지 않는다.** XSS 로 토큰이 새지 않는다.
- **화면 JS 는 토큰을 모른다.** `modal.js` 같은 클라이언트 스크립트는 화면 조작만 하고
  API 호출을 하지 않는다.

**토큰 원문을 로그·화면·HTML 에 남기지 않는다** (헌장 원칙 IV 의 마스킹).

| 시점 | 처리 | 호출 API |
|------|------|----------|
| 로그인 성공 | 응답의 `accessToken`·`refreshToken` 을 **세션 속성에 담는다**. 브라우저에는 `JSESSIONID` 만 나간다 | `MemberLogin` |
| 보호 화면 진입 | 세션에 토큰이 있는지 보고, 있으면 그 토큰이 아직 유효한지 백엔드에 확인한다. 세션이 비었으면 확인 없이 `/auth/login` 으로 보낸다 | `MemberTokenValidate` |
| Access 만료 (`resCode` 1001) | 세션의 `refreshToken` 으로 재발급을 시도하고, 받은 새 토큰으로 **세션 속성을 덮어쓴 뒤** 원래 요청을 다시 부른다. 재발급도 실패하면 아래 줄로 넘어간다 | `MemberTokenRefresh` |
| 다른 곳 로그인·세션 무효 (`1001`·`1006`) | **세션을 무효화**(`invalidate`)하고 `/auth/login` 으로 보낸다. 「다른 곳에서 로그인되어 로그아웃되었습니다」를 함께 보여 준다 | — |
| 로그아웃 | 백엔드에서 JWT 를 비활성화한 뒤 **세션을 무효화**하고 `/auth/login` 으로 보낸다 | `MemberTokenRevoke` |
| 세션 만료 (백엔드 토큰과 무관) | 세션이 사라져 토큰을 잃은 것이므로 미로그인으로 보고 `/auth/login` 으로 보낸다 | — |

### 로그인 필요 여부

| 구분 | 화면번호 | 화면 |
|------|----------|------|
| **로그인 불필요** | 1.1~1.6 | 로그인, 회원가입, 아이디 찾기, 비밀번호 찾기, 비밀번호 변경, 권한 없음 |
| **로그인 필수** | 1.7 및 Phase 2~6 전부 | 본인 정보, 수단·유형·가계부·고정지출·목표·통계 등 |
| **관리자 필수** | 1.8~1.10 | 회원 목록·추가·수정 |

- 미로그인 시 **로그인 필수** URL → `/auth/login` redirect.
- **일반 회원**에게 회원 관리 메뉴·URL 비노출. 관리자 URL 직접 접근 → `/error/forbidden` (1.6, 로그인 불필요).
- **본인 가계부 화면만** 제공 (타인 가계부 없음).

## API 호출 규칙

| Method | Path | Query | Body | 프론트 규칙 |
|--------|:----:|:-----:|:----:|-------------|
| GET | ✅ or ✅ | ✅ or ✅ | ❌ | Path **또는** Query **중 하나만** (혼용 금지) |
| POST | ❌ | ❌ | ✅ | Body만 (JSON/multipart) |
| PATCH | ✅ | ❌ | ✅ | Path(키) + Body(변경분만). **PUT 미사용** |
| DELETE | ✅ | ❌ | ❌ | Path만 |

**예외:** `StatisticsMonthlyGet`만 Path 연·월 + Query `view?`(`saved`\|`live`) 허용.

### 실패 표시

- API 실패 시 `resCode`·`data.message`를 화면(alert 또는 폼 상단)에 표시한다.
- 컨트롤러에서 try-catch로 응답을 제각각 만들지 말고, 공통 클라이언트·에러 처리에 맡긴다.

### 페이징 UI

요청: Query `offset`·`limit` — **둘 다 필수이고 기본값이 없다.** 빠뜨리면 `9001` 이다.
응답: `offset`·`limit`·`totalCount`로 현재 페이지·전체 페이지 수 환산.

**`offset` 은 `limit` 의 배수여야 한다.** 아니면 `9001` 로 목록이 통째로 실패한다.
페이지 버튼은 `offset = (페이지 번호) × limit` 으로만 만들고, 사용자가 임의 `offset` 을
넣을 수 있는 입력을 두지 않는다. `limit` 을 바꿀 때 `offset` 을 그대로 두면 배수가
깨지므로 **첫 페이지로 되돌린다**.

## 이름은 어디서 오는가 — 화면마다 다르다

같은 `paymentMethodName`·`expendGroupName` 이라도 **어떤 API 에서 왔느냐에 따라 의미가 다르다.**

| 출처 | 이름의 성격 | 원본 이름을 바꾸면 |
|---|---|---|
| 지출·소득 (3.x) | **등록 당시 스냅샷** | 과거 내역은 **옛 이름 그대로** |
| 고정지출 설정 (4.1~4.4) | **조회 시점 현재 이름** | 과거 조회 결과도 **새 이름으로 바뀐다** |
| 통계 상세 (5.5·5.6) | **저장 당시 스냅샷** | 저장본은 **옛 이름 그대로** |
| 목표금액 (5.1·5.2) | **조회 시점 현재 이름** | 새 이름으로 바뀐다 |

**가계부 목록(4.8)은 한 응답 안에서 두 규칙이 섞인다.**

| 행 종류 | `paymentMethodName`·`expendGroupName` |
|---|---|
| `EXPENSE` · `INSTALLMENT` · `INCOME` | 등록 당시 **스냅샷** |
| **`FIXED`** | 조회 시점 **현재 이름** |

수단 이름을 바꾼 뒤 가계부를 열면 **고정지출 행만 새 이름으로 보인다.** 버그가 아니라
설계다 — 고정지출은 "지금 유효한 설정"이고 지출·소득은 "이미 일어난 일의 기록"이다.
화면에서 이 차이를 숨기려고 이름을 다시 조회해 덮어쓰지 않는다.

## 합계는 필터와 무관하다

목록 위 요약 카드의 합계는 **그 달 전체 기준**이며 필터를 걸어도 바뀌지 않는다.

| API | 합계 필드 | 기준 |
|---|---|---|
| 4.8 월별 가계부 | `expenseTotal` · `incomeTotal` | 그 달 전체 |
| 4.5 월별 고정지출 내역 | `total` | 그 달 전체 |

**필터를 걸면 목록의 합과 상단 합계가 달라지는데 그것이 의도다.** 합계는 화면 상단
요약이고 필터는 아래 목록을 좁히는 도구다. 화면이 합계를 직접 다시 더해 맞추려 하면
"필터를 걸었는데 합계도 같이 줄어드는" 다른 화면이 된다.

## 연·월 입력 범위

| 대상 | 연도 | 월 | 위반 |
|---|---|---|---|
| 목표금액·통계 (5.1·5.2·5.4·5.5·5.6) | **2000 ~ 2100** | 1 ~ 12 | `3603` |
| 월별 고정지출 내역 (4.5·4.6·4.9) | **1900 ~ 9999** | 1 ~ 12 | `3403` |
| 월별 가계부 (4.8) | **1900 ~ 9999** | 1 ~ 12 | `3501` |
| 고정지출 적용 기간 (4.1·4.4) | **1900 ~ 9999** | 1 ~ 12 | `3401` |

**목표·통계 화면의 연도 select 는 2000~2100 으로 끊는다.** 그 밖의 값을 고를 수 있게
두면 사용자가 화면에서 고른 값이 서버에서 거절된다.

**005 와 006 의 연 범위가 다르다.** 005(고정지출·가계부)는 1900~9999, 006(목표·통계)은
2000~2100 이다. 같은 화면에서 두 API 를 함께 부르면 좁은 쪽에 맞춰야 한다.

**같은 "연·월 범위 오류"의 코드가 자원마다 다르다.** 자원별 코드 대역 배정의 결과이며
의도된 차이다 — 화면이 하나로 묶어 처리하지 말고 그 화면이 부르는 API 의 코드를 쓴다.

## 연·월을 보내는 형식이 둘이다

| 대상 | 형식 |
|---|---|
| 할부 등록의 `startYearMonth` | 문자열 `"2026-01"` |
| **고정지출의 적용 기간** | **정수 네 칸** — `startYear`·`startMonth`·`endYear`·`endMonth` |
| 그 밖의 연·월 (Path·Query·Body) | 정수 두 칸 — `year`·`month` |

정수 칸이 기본형이고 할부만 문자열이다. 폼에서 `<input type="month">` 하나로 받았다면
고정지출은 **보내기 전에 연·월로 쪼개야** 한다.

## 지출 등록은 API 가 둘로 갈린다

| 사용자가 고른 것 | 부르는 API | 금액 필드 |
|---|---|---|
| 일시불 | `ExpenseCreate` | `amount` |
| 할부 | `ExpenseCreateInstallment` | `monthlyAmount` + `installmentMonths` + `startYearMonth` |

한 폼에서 토글로 고르지만 **제출되는 API 자체가 다르다.** 금액 필드 이름도 달라서
일시불 폼 그대로 할부를 보내면 `9001` 이다.

| 코드 | 언제 | 화면이 할 일 |
|---|---|---|
| `3003` | 수단이 없거나·타인 것이거나·사용 안 함이거나·삭제됨이거나 **용도가 안 맞음** | "다른 수단을 고르세요". 존재를 감추려 한 코드라 원인을 더 캐지 않는다 |
| `3103` | 지출유형이 없거나·타인 것이거나·사용 안 함이거나·삭제됨 | "다른 유형을 고르세요" |
| `3201` · `3301` | 지출·소득의 값 오류 — 금액 0 이하, 날짜 형식, 장소 100자·내용 255자 초과 | 어느 칸이 틀렸는지 폼에 표시 |
| `3401` | 고정지출의 값 오류 **또는 수단 용도 불일치** | 3.x 와 달리 **용도 불일치가 여기로 온다** — 수단은 실재하므로 "지출용 수단을 고르세요" |
| `9001` | 요청 형식 오류 — 필수 누락, 페이징 규칙 위반 | 폼·페이징 입력을 다시 본다 |

**용도 불일치의 코드가 갈린다.** 지출·소득 등록(3.x)에서는 `3003`, 고정지출 등록(4.1)
에서는 `3401` 이다. 004 는 수단의 존재를 감추려고 `3003` 으로 묶었고, 005 는 사용자가
자기 목록에서 고른 것이라 감출 이유가 없다고 봤다.

## 수정 화면에서 빈 칸의 뜻 (008 확정)

수정 폼에서 사용자가 칸을 비웠을 때 **칸마다 뜻이 다르다.** 1.7 본인 정보와 1.10 회원 수정이
이 규칙을 세웠고, 009~012 의 수정 화면이 그대로 따른다.

| 칸 | 비워 두면 | 요청에 |
|---|---|---|
| **새 비밀번호** | **바꾸지 않는다** | **싣지 않는다** |
| 그 밖의 선택 칸 (이메일·폰·소개 등) | **비운다** | `null` 로 싣는다 |
| 필수 칸 (닉네임·권한 등) | (비울 수 없다) | 언제나 싣는다 |

새 비밀번호만 다른 이유는 **그 칸만 현재 값이 채워지지 않은 채 뜨기 때문**이다. 비어 있는 것이
기본 상태이므로 "비웠다"가 아니라 "건드리지 않았다"로 읽는 것이 맞다. 나머지는 현재 값이 채워진
채로 뜨므로 사용자가 지웠다면 지우려는 뜻이고, 이것을 "유지"로 읽으면 사용자는 이메일을 지우고
저장했는데 그대로 남아 있는 화면을 보게 된다.

**새 비밀번호 칸에는 「변경할 때만 입력」을 함께 적는다.** 비어 있는 것이 정상 상태라는 것을
사용자가 알아야 한다.

백엔드 수정 API 의 omit 규칙: [기능명세상세-백엔드/_공통.md § PATCH Body 규칙](../기능명세상세-백엔드/_공통.md#patch-body-규칙)

## 목록 검색 칸이 여럿일 때 (008 확정)

검색 칸을 여럿 둔 목록에서 **두 칸을 함께 넣으면 둘 다 맞는 행만** 나온다. 백엔드가 조건을
`AND` 로 묶기 때문이다.

- **화면에 그 사실을 한 줄로 적는다.** 적지 않으면 사용자는 "또는"으로 기대하고, 결과가 비었을
  때 데이터가 없다고 읽는다. 그 오작동은 오류가 아니라 **빈 결과**로 나타나 원인을 짐작하기
  어렵다.
- **칸 하나에 받아 여러 조건에 똑같이 싣지 않는다.** "아이디에도 있고 닉네임에도 있는" 행만
  걸려 사용자 기대와 정반대로 동작한다.
- 검색 폼은 **페이지 번호를 싣지 않는다.** 새 검색은 언제나 첫 페이지에서 시작한다 — 싣고
  다니면 3페이지에서 검색했을 때 결과가 한 페이지뿐인데도 3페이지를 요구해 빈 화면이 뜬다.
  페이지 번호는 **페이지 이동 링크만** 싣고, 그 링크는 **검색어를 함께** 싣는다.

1.8 회원 목록이 이 규칙을 세웠다.
