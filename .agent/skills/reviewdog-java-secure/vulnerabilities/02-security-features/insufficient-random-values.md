# Use of Insufficiently Random Values (CWE-330)

**Severity**: 🟠 HIGH
**Category**: Security Features
**OWASP Top 10**: A02:2021 – Cryptographic Failures

---

## Overview

### Attack Description

Use of insufficiently random values occurs when predictable random number generators are used in security-sensitive contexts. Weak PRNGs (like `java.util.Random`, `Math.random()`, C `rand()`) generate predictable sequences that can be guessed by attackers, compromising session tokens, cryptographic keys, CSRF tokens, password resets, and other security features. If predictable random numbers are used where unpredictable numbers are required, an attacker can predict the next number generated by the software and exploit the system.

### Impact

**Potential consequences:**
- Session hijacking (predictable session IDs)
- Authentication bypass
- CSRF token prediction
- Password reset token guessing
- Cryptographic key prediction
- Account takeover
- Random number exhaustion attacks

---

## Security Measures

### Key Principles

A computer's random number generator produces the same sequence of random values if the seed is fixed. To avoid this, Java's `Random()` and `Math.random()` use the current time as the default seed via the `java.util.Random` class, and in C, the `rand()` function uses a default seed that changes each time. However, seeds should be set based on encrypted cryptographic keys.

For security verification purposes such as session IDs and encryption keys, you must not use `Random()` or `Math.random()` in Java. Instead, use the cryptographically protected `java.security.SecureRandom` class, which produces nearly unpredictable output.

**Primary Defenses:**

1. **Use Cryptographically Secure PRNGs**
   - **Java**: `java.security.SecureRandom` (NOT `java.util.Random`)
   - **C/C++**: `/dev/urandom`, `CryptGenRandom()`, `getrandom()`
   - **C#**: `System.Security.Cryptography.RNGCryptoServiceProvider`
   - **Python**: `secrets` module (NOT `random`)

2. **Proper Seeding**
   - `SecureRandom` auto-seeds from OS entropy
   - Never use fixed/predictable seeds
   - Never use current time as seed for security
   - Let cryptographic library handle seeding

3. **Security-Sensitive Use Cases**
   - Session IDs/tokens
   - CSRF tokens
   - Password reset tokens
   - Cryptographic keys/IVs
   - Nonces
   - Salt for password hashing

4. **When Weak RNG is OK**
   - Simulations
   - Games (non-gambling)
   - Load balancing
   - Non-security random sampling

## Code Examples

### Attack Scenario

When using the `random()` method of the `java.util.Random` class, setting a fixed seed causes the same random values to be generated every time, which is not safe. Even when using a changing seed, it is still unsafe for security verification purposes.

**Attack:**
```java
// Attacker observes sequence of "random" values
Random random = new Random();
int token1 = random.nextInt();  // 12345
int token2 = random.nextInt();  // 67890
int token3 = random.nextInt();  // ?

// Attacker can predict token3 by:
// 1. Determining seed from observed outputs
// 2. Using same algorithm to generate next value
// 3. Hijack session or bypass security check
```

### ✅ Secure Code

#### Java - SecureRandom

```java
import java.util.Random;
import java.security.SecureRandom;
...

public Static int getRandomValue(int maxValue) {
    // Use setSeed to set a changing seed value, or use the default current-time-based changing seed.
    // For security-related random number generation, use java.security.SecureRandom.
    Random random = new Random();
    return random.nextInt(maxValue);
}

public Static String getAuthKey() {
    // For security verification, use SecureRandom which is cryptographically protected
    // and produces nearly unpredictable output.
    try {
        SecureRandom secureRandom = SecureRandom.getInstance("SHA1PRNG");
        MessageDigest digest = MessageDigest.getInstance("SHA-256");
        secureRandom.setSeed(secureRandom.generateSeed(128));
        String authKey = new String(digest.digest((secureRandom.nextLong() +
            "").getBytes()));
    } catch (NoSuchAlgorithmException e) {
        ...
    }
}
```

**Security Features:**
1. `SecureRandom` with SHA1PRNG algorithm
2. Cryptographically secure random generation
3. Self-seeding with 128 bytes of entropy
4. Combined with SHA-256 for auth key
5. Unpredictable output

#### ✅ Better Practice - Modern SecureRandom Usage

```java
import java.security.SecureRandom;
import java.util.Base64;

public class SecureRandomGenerator {

    private static final SecureRandom secureRandom = new SecureRandom();

    /**
     * Generate cryptographically secure random bytes
     */
    public static byte[] generateRandomBytes(int length) {
        byte[] randomBytes = new byte[length];
        secureRandom.nextBytes(randomBytes);
        return randomBytes;
    }

    /**
     * Generate secure session token
     */
    public static String generateSessionToken() {
        byte[] tokenBytes = generateRandomBytes(32);  // 256 bits
        return Base64.getUrlEncoder().withoutPadding().encodeToString(tokenBytes);
    }

    /**
     * Generate CSRF token
     */
    public static String generateCSRFToken() {
        byte[] tokenBytes = generateRandomBytes(32);  // 256 bits
        return Base64.getEncoder().encodeToString(tokenBytes);
    }

    /**
     * Generate password reset token
     */
    public static String generatePasswordResetToken() {
        byte[] tokenBytes = generateRandomBytes(48);  // 384 bits (extra security)
        return Base64.getUrlEncoder().withoutPadding().encodeToString(tokenBytes);
    }

    /**
     * Generate random alphanumeric string (for verification codes)
     */
    public static String generateVerificationCode(int length) {
        String chars = "ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789";
        StringBuilder code = new StringBuilder(length);

        for (int i = 0; i < length; i++) {
            int index = secureRandom.nextInt(chars.length());
            code.append(chars.charAt(index));
        }

        return code.toString();
    }

    /**
     * Generate random number in range [min, max)
     */
    public static int generateSecureRandomInt(int min, int max) {
        if (min >= max) {
            throw new IllegalArgumentException("max must be greater than min");
        }

        int range = max - min;
        return secureRandom.nextInt(range) + min;
    }
}
```

**Usage Examples:**
```java
// Session token
String sessionId = SecureRandomGenerator.generateSessionToken();
// Example: "X9k3mP_vQr2nL8jY4wT6fA"

// CSRF token
String csrfToken = SecureRandomGenerator.generateCSRFToken();
// Example: "rY8kP2vN6mL4jW9qT3sX7fA=="

// Password reset token (expires in 1 hour)
String resetToken = SecureRandomGenerator.generatePasswordResetToken();
// Example: "aB3cD4eF5gH6iJ7kL8mN9oP0qR1sT2uV3wX4yZ5"

// 6-digit verification code
String verifyCode = SecureRandomGenerator.generateVerificationCode(6);
// Example: "K8M3P9"
```

**Security Features:**
1. `SecureRandom` for all generation
2. Auto-seeding from OS entropy
3. 256+ bit tokens
4. URL-safe Base64 encoding
5. No predictable patterns

## 🚨 Common Mistakes

1. **Using Random for Session IDs**
   ```java
   // DON'T: Predictable session ID
   Random random = new Random();
   String sessionId = String.valueOf(random.nextLong());

   // DO: Secure session ID
   SecureRandom secureRandom = new SecureRandom();
   byte[] tokenBytes = new byte[32];
   secureRandom.nextBytes(tokenBytes);
   String sessionId = Base64.getUrlEncoder().encodeToString(tokenBytes);
   ```

2. **Time-Based Seeding**
   ```java
   // DON'T: Time is predictable
   Random random = new Random(System.currentTimeMillis());

   // DO: Let SecureRandom handle seeding
   SecureRandom secureRandom = new SecureRandom();
   ```

3. **Insufficient Token Length**
   ```java
   // DON'T: Too short (only 32 bits)
   int token = secureRandom.nextInt();

   // DO: At least 128 bits (16 bytes)
   byte[] token = new byte[16];
   secureRandom.nextBytes(token);
   ```

## 💡 Best Practices Summary

1. **Always use SecureRandom** - For all security-sensitive randomness
2. **Never use Math.random()** - Not cryptographically secure
3. **Never use rand()** - Predictable and weak
4. **Sufficient token length** - Minimum 128 bits (16 bytes)
5. **No fixed seeds** - Let SecureRandom auto-seed
6. **One instance** - Reuse single SecureRandom instance
7. **Base64 encode** - For string representation of random bytes
8. **Test randomness** - Use statistical tests in QA
9. **Code review** - Scan for weak RNG usage
10. **Update entropy** - Ensure OS has sufficient entropy
