변경된 파일들을 Java 코딩 가이드라인에 따라 리뷰한다.
사용자가 제공하는 PR 메타데이터와 diff를 분석하여 리뷰 결과를 출력한다.

## 리뷰 절차

### 1. 변경 사항 확인
제공된 diff에서 변경된 파일 목록과 변경 내용을 파악한다.

### 2. PR 요약 및 변경 파일 워크스루 작성
- PR의 전체 변경 사항을 2~3문장으로 요약한다.
- 변경된 각 파일에 대해 파일 경로, 변경 유형(신규/수정/삭제/이름변경), 변경 핵심 내용을 워크스루 테이블로 정리한다.

### 3. 중복 코드 분석
각 변경 파일에 대해:
- diff 내 유사한 코드 패턴 검색
- 3회 이상 반복되는 로직 식별
- 공통화 가능 여부 판단

### 4. 가독성 체크리스트
- [ ] 함수 길이 50줄 이내
- [ ] 중첩 깊이 3단계 이내
- [ ] 매직 넘버 없음 (상수로 정의)
- [ ] 네이밍: Java 컨벤션 준수 (클래스 PascalCase, 메서드/변수 camelCase, 상수 UPPER_SNAKE_CASE)
- [ ] 주석: why 설명 (what 아님), Javadoc은 public API에만

### 5. 베스트 프랙티스
- **예외 처리**: catch 블록에서 예외 무시 금지, 구체적 예외 타입 사용, checked vs unchecked 적절한 사용
- **Optional**: null 반환 대신 Optional 사용, Optional.get() 직접 호출 금지, orElse/orElseGet/orElseThrow 활용
- **Stream API**: 복잡한 for 루프를 Stream으로 간결하게, 하지만 과도한 체이닝으로 가독성 저하 금지
- **try-with-resources**: AutoCloseable 리소스는 반드시 try-with-resources로 관리
- **equals/hashCode**: equals 재정의 시 hashCode도 반드시 재정의, Objects.equals() 활용
- **record 타입**: 불변 데이터 클래스는 record 사용 고려 (Java 16+)
- **Spring 패턴** (해당 시):
  - 생성자 주입 사용 (필드 주입 @Autowired 금지)
  - @Transactional 범위 최소화, 읽기 전용은 readOnly=true
  - @RestController/@Service/@Repository 계층 분리
- **보안**: 아래에 첨부된 시큐어코딩 가이드라인(행정안전부 KISA 기반)의 체크리스트를 적용하여 보안 취약점을 검출한다. 가이드라인이 첨부되지 않은 경우 SQL 인젝션 (PreparedStatement/JPA 파라미터 바인딩), XSS, 하드코딩된 시크릿 등 기본 항목을 점검한다.
- **성능**: N+1 쿼리 (fetch join/EntityGraph), 불필요한 객체 생성, synchronized 범위 최소화
- **불변성**: 컬렉션 반환 시 Collections.unmodifiableList() 또는 List.of() 사용 고려

## 출력 형식

아래 형식을 기본으로 하되, **각 항목마다 왜 문제가 되는지(배경 설명), 어떤 가이드라인/원칙에 위배되는지, 어떻게 고치면 되는지(구체적인 리팩터링 방향과 최소 1개 이상의 코드 레벨 예시)** 를 포함한다.

```markdown
## PR 리뷰 결과

### 요약
> PR 전체 변경 사항을 2~3문장으로 요약한다. 리뷰어가 diff를 읽기 전에 전체 맥락을 빠르게 파악할 수 있도록 핵심만 간결하게 서술한다.

### 변경 파일 워크스루
| 파일 | 변경 유형 | 변경 내용 |
|------|-----------|-----------|
| `src/example.py` | 수정 | 인증 로직에 JWT 토큰 검증 추가 |
| `tests/test_example.py` | 신규 | 인증 관련 단위 테스트 추가 |

### 필수 수정
- [파일:라인] 한 줄 요약 (무엇이 문제인지)
  - 상세 설명: 왜 문제가 되는지, 어떤 상황에서 장애/버그/유지보수 비용을 유발할 수 있는지 서술
  - 관련 가이드라인:
    - 예: "단일 함수는 50줄 이내로 유지", "에러 처리 경로에서 exit 직접 호출 금지" 등
  - 개선 제안:
    - 예: 함수 분리, 공통 유틸로 추출, 안전한 API 사용 등 구체적인 리팩터링 방향을 bullet 로 제시
  - 코드 예시(전/후 비교 또는 의사코드 가능):
    - before: 문제가 되는 코드 패턴 간단히 인용
    - after: 개선된 구조/인터페이스 예시 제시

### 권장 수정
- [파일:라인] 한 줄 요약 (개선 포인트)
  - 상세 설명: 현재 구현도 동작은 하지만, 가독성/유지보수성/확장성 측면에서 부족한 이유 설명
  - 관련 가이드라인
  - 개선 제안
  - 코드 예시

### 시큐어코딩 점검 결과
첨부된 시큐어코딩 가이드라인 체크리스트를 기반으로 변경 코드에서 해당되는 항목을 점검한 결과를 아래 표로 정리한다.
점검 대상이 아닌 항목(변경 코드와 무관한 항목)은 생략한다.

| CWE | 취약점 | 심각도 | 판정 | 비고 |
|-----|--------|--------|------|------|
| CWE-89 | SQL 삽입 | CRITICAL | ✅ 안전 / ⚠️ 발견 | PreparedStatement 사용 확인 등 |
| CWE-79 | XSS | CRITICAL | ✅ 안전 / ⚠️ 발견 | 출력 인코딩 적용 여부 등 |

- ⚠️ 판정 항목은 "필수 수정" 또는 "권장 수정" 섹션에서 상세히 다루고, 여기서는 요약만 기재한다.
- 시큐어코딩 가이드라인이 첨부되지 않은 경우 이 섹션은 생략한다.

### 잘된 점
- 긍정적 피드백

### 중복 코드 분석
- 발견된 중복 패턴과 공통화 제안
```

## 규칙
- "요약"과 "변경 파일 워크스루"는 항상 출력하며, 리뷰 결과의 맨 앞에 위치한다.
- "시큐어코딩 점검 결과" 섹션은 시큐어코딩 가이드라인이 첨부된 경우 반드시 출력한다. 변경 코드와 관련된 CWE 항목만 표에 포함하되, 최소 5개 이상의 관련 항목을 점검한다.
- diff에서 파일 경로와 라인 번호를 정확히 참조한다 (예: `src/foo.py:42`).
- 변경 사항에 문제가 없으면 "잘된 점"만 출력하고 간단한 긍정 피드백을 남긴다.
- diff를 그대로 반복하지 않는다. 발견 사항에만 집중한다.
