# D·E·F 계층·중분류 그룹핑 참조

자체시험 결과서에서 **시험항목(대분류)·시험항목(중분류)·시험목적**은 3단계 계층이다.  
**중분류(E)는 여러 행에 반복**되고, **행마다 달라지는 것은 시험목적(F)** 이다.

정본 예시: 사용자 편집 `TC_001-010_merged_20260610.xlsx` — **회원가입 이메일 인증** 구간.

**xlsx D~H에는 FR-/NC/Txxx 등 Speckit 전용 식별자를 쓰지 않는다.**  
**연동규격 API 번호(6.22, 12.3 등)는 TC에 써도 된다.**

## 계층 요약

| 컬럼 | 역할 | 행 단위 |
|------|------|---------|
| **D 시험항목(대분류)** | 기능·업무 영역 (사용자 관점 이름) | 동일 기능 TC는 **같은 값** |
| **E 시험항목(중분류)** | **기능 단계·API·처리 구간** | 같은 단계의 TC는 **같은 값**(반복) |
| **F 시험목적** | **개별 검증 시나리오** (성공/실패·코드·DB) | **행마다 다름** |

```text
대분류 (1개 기능명)
 └── 중분류 A (단계/API 그룹) ── 시험목적 행 1
 │                              ├── 시험목적 행 2
 │                              └── 시험목적 행 3
 └── 중분류 B
      └── ...
```

## 잘못된 패턴 vs 올바른 패턴

### 잘못됨 — 중분류에 시나리오 문장

| D | E (잘못) | F |
|---|---|---|
| 회원가입 이메일 인증 | 이미 사용 중인 ID로 6.22 호출 시 resultcode 701로 실패 | (비어 있거나 중복) |

→ E와 F 역할이 뒤바뀌었거나 E에만 모든 내용이 들어간 형태.

### 잘못됨 — 시험목적에 Speckit 전용 식별자

| F (잘못) |
|----------|
| FR-012 위반 시 refreshToken 필수 실패를 확인한다. |
| NC에 따라 aud 검증 실패를 확인한다. |
| plan·smoke-phase7 시나리오 1~9 통합 확인을 수행한다. |

→ Speckit 문서를 보지 않는 수행자가 이해할 수 없다. **연동규격 번호·업무 기능명·path**로 서술한다.

### 올바름 — specs/001 기준 (회원가입 이메일 인증)

**D** (전 행 동일): `회원가입 이메일 인증`

| E 중분류 | F 시험목적 (예) |
|----------|----------------|
| **인증 이메일 발송** | 유효한 ID·이메일로 6.22 호출 시 발송이 성공(resultcode 200)하는지 확인한다. |
| **인증 이메일 발송** | 이미 사용 중인 ID로 6.22 호출 시 resultcode 701로 실패를 확인한다. |
| **인증 이메일 발송** | 만료된 flow_token으로 6.22 호출 시 resultcode 713으로 실패를 확인한다. |
| **인증 이메일 발송** | SMTP 장애로 발송 실패 시 resultcode 740으로 실패를 확인한다. |
| **인증 이메일 발송** | 동일 이메일주소 재발송 제한 조건이 있어도 6.22 호출 시 tbl_email_auth_send 행이 생성되는지 확인한다. |
| **인증 이메일 발송** | 발송 메일 본문에 FRONT_HOST 기반 인증하기 URL과 payload 정보가 포함되는지 확인한다. |
| **이메일 인증요청** | 최신 이메일·5분 이내·유효 payload로 6.23 호출 시 인증 성공(resultcode 200) 및 프론트 콜백 status=OK 1회를 확인한다. |
| **이메일 인증요청** | 인증 완료된 이메일 payload로 6.23 재호출 시 resultcode 734 및 콜백 미호출을 확인한다. |
| **이메일 인증요청** | sent_at 기준 5분(300초) 초과 후 6.23 호출 시 resultcode 735로 실패를 확인한다. |
| **이메일 인증요청** | 신규 발송 후 이전 만료 payload로 6.23 호출 시 resultcode 736으로 실패를 확인한다. |
| **이메일 인증요청** | 변조된 payload로 6.23 호출 시 resultcode 741 및 콜백 status=NOK를 확인한다. |
| **이메일 인증요청** | delivery_status=발송 실패 상태 payload로 6.23 호출 시 실패를 확인한다. |
| **이메일 인증요청** | 첫 인증 성공 시 tbl_email_auth_send에 email_auth_yn, email_auth_at, client_id가 기록되는지 확인한다. |
| **이메일 인증결과 확인** | 6.23 성공 후 6.24 호출 시 인증 완료를 확인한다. |

| **이메일 인증결과 확인** | 이미 인증 완료된 (email, flow_token)으로 6.24 호출 시 resultcode 734로 실패를 확인한다. |

## 중분류(E) 도출 규칙

산출물을 읽은 뒤 **먼저** 대분류·중분류 스켈레톤을 잡고, 그 아래에 시험목적 행을 배치한다.  
**FR-/NC 등 Speckit 식별자는 그룹핑 판단에만 쓰고 xlsx에는 넣지 않는다.** 연동규격 API 번호는 xlsx에 써도 된다.

1. **HTTP path·operationId** — `contracts/`·`openapi.yaml`에서 동일 엔드포인트·동일 처리 단계는 하나의 E.
2. **User Story·업무 단계** — 발송 / 인증 요청 / 결과 확인 등 흐름 경계.
3. **제공자·채널** — 동일 대분류 안에서 제공자별 흐름이 다르면 E에 제공자를 넣을 수 있다.  
   - 예: `네이버 연동 해제 알림 수신`, `카카오 연동 해제 알림 수신` (006)
4. **검증 유형** — 인바운드 웹훅 / 내부 API / DB·ActionLog 확인 등 처리 구간이 다르면 E를 나눈다.

### 중분류 명명 원칙

- **짧은 명사구** — 동사형 시나리오 문장·resultcode 나열은 **F(시험목적)** 에 둔다.
- **2~8어절** — `인증 이메일 발송`, `이메일 인증요청`, `SNS aud 검증`, `Google RISC 수신`
- **한 행 = 한 중분류 그룹**이 아니다. **한 중분류 = 여러 행**이 정상이다.
- 산출물에 없는 단계 이름을 임의로 만들지 않는다.

## 대분류(D) 도출 규칙

- `spec.md` Feature 제목·User Story를 **사용자 관점**으로 짧게 정리한다.
- 한 spec이 여러 업무 영역이면 **대분류를 나눈다** (002: 회원 탈퇴 / SNS 연동 설정 등).
- 산출물 내부 번호·식별자만으로 대분류를 만들지 않는다.

## 시험목적(F) 문체

- 성공: `…하는지 확인한다.`
- 실패: `…실패를 확인한다.` / `…으로 실패를 확인한다.`
- **거절·거부** 대신 **실패·성공**을 쓴다.
- resultcode·HTTP·DB는 **F에** 구체적으로 적는다 (산출물에 있는 값만).
- API 지칭: **연동규격 번호(6.22 등)·업무 기능명·HTTP path** — **FR-/NC/Txxx 등 Speckit 식별자 금지**.

## 기능별 중분류 스켈레톤 (산출물 기준 힌트)

아래는 **생성 시 참고용**이다. 실제 행 수·명칭은 `spec.md`·`contracts/`를 우선한다.

| spec | 대분류 예 | 중분류 그룹 예 |
|------|-----------|----------------|
| 001 | 회원가입 이메일 인증 | 인증 이메일 발송 / 이메일 인증요청 / 이메일 인증결과 확인 |
| 002 | 회원 탈퇴, SNS 연동 설정, … | 탈퇴 처리 / SNS 설정·조회 API별 업무 구간 |
| 006 | SNS 연동 해제 | 제공자별 연동 해제 알림 수신·HMAC 검증·DB 반영 |
| 007 | 해외 로그인 차단, 해외 로그인 차단 OTP | 차단 판정·OTP 발송·OTP 검증 |
| 008 | 구글 SNS 연동, SNS 연동 목록, … | 구글 연동·해제·로그인·회원가입·목록 조회 |
| 009 | SNS aud 검증, 구글 refresh_token | aud 검증·refresh_token 처리 |
| 010 | Google RISC 수신 | JWT 검증·이벤트 처리·연동 해제 |

## 생성 절차에서의 적용 순서

1. spec 산출물에서 테스트 가능 요소 목록 작성 (시나리오 단위).
2. **대분류** 목록 확정.
3. 각 대분류 아래 **중분류 그룹** 확정 (여러 시나리오가 같은 E를 공유하도록).
4. 각 (대분류, 중분류) 그룹에 **시험목적** 행을 1건씩 배치 — **Speckit 식별자 없이** 서술.
5. 시험절차·시험내역은 기존 규칙대로 행마다 작성.

## 통합 시나리오 (plan·smoke → xlsx)

`plan.md`·`references/smoke-*.md`에서 **통합 1행**을 만들 때:

| 나쁨 (xlsx) | 좋음 (xlsx) |
|-------------|-------------|
| F: `plan·smoke-phase7 시나리오 1~9 통합 확인…` | F: `12.1·12.4·6.25·6.26·11.5를 순서대로 호출하여…` |
| G: `smoke-phase7.md 체크리스트 1~9…` | G: 12.1·12.4·6.25·6.26·11.5 단계 + resultcode (703, 742, 743, 737, …) |

상세 예시는 `SKILL.md` §통합 시나리오·스모크(plan) TC 참고.
