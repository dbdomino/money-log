변경된 마크다운 스펙/문서 파일을 문서 품질 가이드라인에 따라 리뷰한다.
이 리뷰는 코드가 아닌 **스펙/문서**를 대상으로 하므로, 코드 품질(함수 길이, 성능, 메모리 등)이 아닌 **문서 품질**에 집중한다.

## 입력 소스 (스킬과 동일)

- **Bitbucket Cloud PR 웹 URL**이 있으면: 상위 스킬(`SKILL.md`)대로 **`bb_get`** 등으로 `GET …/pullrequests/{id}/diff` 통합 diff를 확보한 뒤, 아래 절차의 **입력 diff**로 쓴다. (로컬 워크스페이스와 PR이 다른 리포여도 동일.)
- **PR URL이 없으면**: 로컬 `git diff`·`git show` 등으로 얻은 통합 diff 또는 사용자가 붙인 diff를 입력으로 쓴다.

두 경우 모두 **동일한 출력 형식·품질 기준**을 적용한다. 전체 diff를 리뷰 결과에 재붙여 넣지 않는다.

## 리뷰 절차

### 1. 변경 사항 확인
제공된 diff(또는 PR API에서 받은 통합 diff)에서 변경된 파일 목록과 변경 내용을 파악한다.

### 2. PR 요약 및 변경 파일 워크스루 작성
- PR의 전체 변경 사항을 2~3문장으로 요약한다.
- 변경된 각 파일에 대해 파일 경로, 변경 유형(신규/수정/삭제/이름변경), 변경 핵심 내용을 워크스루 테이블로 정리한다.

### 3. 명확성 검증
각 변경 내용에 대해:
- **모호한 표현 탐지**: "적절히", "필요 시", "등", "충분한", "빠르게", "일부" 같은 정량화되지 않은 표현 식별
- **다의적 해석 가능성**: 두 사람이 읽었을 때 서로 다르게 해석할 수 있는 문장 식별
- **주어/동작 누락**: "~해야 한다"에서 주체가 명시되지 않은 경우, "처리한다"에서 구체적 동작이 없는 경우

### 4. 완전성 검증
- **정상 시나리오**: 기본 흐름(happy path)이 명확히 기술되어 있는지
- **예외/에러 시나리오**: 실패, 타임아웃, 잘못된 입력 등 예외 상황에 대한 기술 존재 여부
- **경계값**: 최솟값, 최댓값, 빈 값, null 등 경계 조건의 동작 명시 여부
- **전제 조건과 사후 조건**: 기능의 선행 조건과 결과 상태가 명시되어 있는지

### 5. 일관성 검증
- **용어 통일**: 같은 개념을 다른 이름으로 부르는 경우 (예: "사용자"와 "유저", "삭제"와 "제거")
- **문서 간 정합성**: 다른 스펙 문서에서 참조하는 내용과 모순이 없는지
- **포맷 일관성**: 헤딩 레벨, 리스트 스타일, 표 구조 등이 문서 내에서 통일되어 있는지

### 6. 구조 검증
- **필수 섹션 존재 여부**: 목적/개요, 범위, 요구사항, 제약사항 등 핵심 섹션 포함 여부
- **마크다운 문법**: 깨진 링크, 잘못된 헤딩 계층, 닫히지 않은 코드 블록 등
- **논리적 흐름**: 섹션 순서가 자연스럽고, 상위 개념에서 하위 상세로 전개되는지

## 출력 형식

아래 형식을 기본으로 하되, **각 항목마다 왜 문제가 되는지(배경 설명), 어떤 원칙에 위배되는지, 어떻게 고치면 되는지(구체적인 수정 문구 예시)** 를 포함한다.

```markdown
## PR 리뷰 결과

### 요약
> PR 전체 변경 사항을 2~3문장으로 요약한다. 어떤 스펙이 추가/변경되었는지, 주요 의도가 무엇인지 간결하게 서술한다. (PR 번호·브랜치·리포는 URL 또는 메타에서 한 줄로만 언급해도 된다.)

### 변경 파일 워크스루
| 경로 | 유형 | 한 줄 의도 |
|------|------|------------|
| `specs/.../spec.md` | 수정 | … |

### 필수 수정
- [파일:라인] 한 줄 요약 (무엇이 문제인지)
  - 문제 유형: 모호한 표현 | 시나리오 누락 | 용어 불일치 | 구조 오류 | 논리적 모순
  - 상세 설명: 왜 문제가 되는지, 이 문서를 기반으로 구현할 때 어떤 혼란/오류가 발생할 수 있는지 서술
  - 관련 원칙:
    - 예: "스펙 문서는 구현자가 추가 질문 없이 구현 가능해야 한다", "모든 예외 상황은 명시적으로 기술한다" 등
  - 수정 제안:
    - before: 문제가 되는 현재 문구 인용
    - after: 구체적으로 수정된 문구 예시 제시

### 권장 수정
- [파일:라인] 한 줄 요약 (개선 포인트)
  - 문제 유형: 가독성 | 구조 개선 | 보완 권장 | 포맷 통일
  - 상세 설명: 현재도 이해는 가능하지만, 명확성/유지보수성 측면에서 개선이 필요한 이유
  - 수정 제안:
    - before/after 형태로 개선된 문구 제시

### 용어 일관성 분석
- 동일 개념에 대해 문서 내에서 다르게 사용된 용어 목록
  - 예: "사용자" vs "유저" → 하나로 통일 권장
  - 예: "요청" vs "리퀘스트" → 한글 또는 영문 중 하나로 통일
```

## 규칙
- **「요약」→「변경 파일 워크스루」→「필수 수정」→「권장 수정」** 순서를 지킨다. `### 변경 파일 워크스루`는 표 형식으로 항상 출력한다(변경이 없으면 “없음” 한 줄).
- diff에서 파일 경로와 라인 번호를 정확히 참조한다 (예: `specs/auth.md:42`).
- 코드 품질 관점의 리뷰(함수 길이, 성능, 보안 취약점 등)는 하지 않는다.
- 변경 사항에 문제가 없으면 "잘된 점"만 출력하고 간단한 긍정 피드백을 남긴다.
- diff를 그대로 반복하지 않는다. 발견 사항에만 집중한다.
- 모호한 표현을 지적할 때는 반드시 구체적인 대안 문구를 함께 제시한다.
