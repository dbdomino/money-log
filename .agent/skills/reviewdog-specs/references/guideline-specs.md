# PR 스펙·문서 diff 리뷰 (서브 에이전트용)

리뷰 **절차·출력 형식**의 규범은 본 문서다. **프로젝트 팀과 저장소의 합의**는 저장소 루트 **`CLAUDE.md`** 에 정리되어 있으므로, 서브는 리뷰 전에 **`CLAUDE.md`를 반드시 Read** 하고, diff·스펙 문구가 그 내용과 **모순·누락**되지 않았는지 점검한다. `CLAUDE.md` 는 보통 **Claude Code** 용으로 두는 **일반 마크다운** 파일이며, 파일명은 **관례**일 뿐 **다른 에이전트·도구가 읽는 데 기술적 제한이 없다** (UTF-8 텍스트).

서브는 **저장소를 쓰지 않으며**, **MCP·git을 호출하지 않는다.** (단, `CLAUDE.md` **읽기**는 `reviewdog-specs` 스킬이 허용한다.) 입력으로 메인이 전달한 **통합 diff**(및 회차 2 이상이면 메인이 함께 붙인 **로컬 미커밋 diff** 블록)를 사용한다.

> **reviewdog-pr-specs** 를 쓰는 경우: 메인이 Bitbucket PR 통합 diff를 넘기면, 아래 “Diff” 항목만 PR 본문으로 이해하고 **베이스/HEAD** 맥락은 PR 메타 한 줄로 대체해도 된다.

## 입력

- **비교 맥락 (reviewdog-specs)**: 로컬 베이스 브랜치명 `<BASE>`, 현재 브랜치명(또는 `HEAD` 설명), 비교식 **`<BASE>...HEAD` (three-dot)** 를 메인이 프롬프트에 한 줄 이상으로 포함한다.
- **Diff**: `git diff <BASE>...HEAD` 로 얻은 통합 diff 문자열(메인이 수집). 추가로 `git diff HEAD` 워킹 트리 블록이 붙어 있으면 “커밋된 범위 대비 변경 + 로컬 미반영 변경”을 합쳐 해석한다.
- 전체 diff를 **리뷰 결과에 다시 붙여 넣지 않는다.**

## 프로젝트 계약 (`CLAUDE.md`)

서브는 **`CLAUDE.md` Read 후** diff 리뷰를 수행한다. 없거나 비어 있으면 본 문서 절차만 적용한다.

**활용 예** (저장소마다 다름 — 실제 목차를 열어 확인):

- **API·응답 스키마**: 예) 목록 응답 `content` / `totalElements`, 페이지 메타 등 constitution과 동일한지.
- **인증·권한**: 앱 레벨에서 금지된 패턴(헤더 직접 파싱 등)을 스펙이 요구하고 있지 않은지.
- **시드·menu_api_mapping**: 신규 API가 스펙에만 있고 시드 반영 언급이 빠졌는지(해당 절이 있을 때).
- **예외·에러 모델**: `ServiceException` / `ErrorCode` 등 팀 규약과 스펙 서술이 맞는지.

**충돌 시**: 스펙 문서 품질(모호함 등)은 본 문서 §3~6을 따르되, **팀 계약 위반**은 **`### 필수 수정`** 으로 올린다. `관련 원칙`에 **CLAUDE.md 의 어떤 절·규칙과 충돌하는지** 한 줄을 적는다(파일명·섹션명 수준).

## 리뷰 절차

### 0. `CLAUDE.md` 반영 (선행)

`CLAUDE.md` 를 Read 한 뒤, 이후 단계에서 그 계약을 **체크리스트처럼** 참조한다.

### 1. 변경 사항 확인

제공된 diff에서 변경된 파일 목록과 변경 내용을 파악한다.

### 2. 요약 및 변경 파일 워크스루 작성
- **브랜치 대비** 전체 변경 사항을 2~3문장으로 요약한다(의도·영향 범위).
- 변경된 각 파일에 대해 파일 경로, 변경 유형(신규/수정/삭제/이름변경), 변경 핵심 내용을 워크스루 테이블로 정리한다.

### 3. 명확성 검증
각 변경 내용에 대해:
- **모호한 표현 탐지**: "적절히", "필요 시", "등", "충분한", "빠르게", "일부" 같은 정량화되지 않은 표현 식별
- **다의적 해석 가능성**: 두 사람이 읽었을 때 서로 다르게 해석할 수 있는 문장 식별
- **주어/동작 누락**: "~해야 한다"에서 주체가 명시되지 않은 경우, "처리한다"에서 구체적 동작이 없는 경우

### 4. 완전성 검증
- **정상 시나리오**: 기본 흐름(happy path)이 명확히 기술되어 있는지
- **예외/에러 시나리오**: 실패, 타임아웃, 잘못된 입력 등 예외 상황에 대한 기술 존재 여부
- **경계값**: 최솟값, 최댓값, 빈 값, null 등 경계 조건의 동작 명시 여부
- **전제 조건과 사후 조건**: 기능의 선행 조건과 결과 상태가 명시되어 있는지

### 5. 일관성 검증
- **용어 통일**: 같은 개념을 다른 이름으로 부르는 경우 (예: "사용자"와 "유저", "삭제"와 "제거")
- **문서 간 정합성**: 다른 스펙 문서에서 참조하는 내용과 모순이 없는지
- **포맷 일관성**: 헤딩 레벨, 리스트 스타일, 표 구조 등이 문서 내에서 통일되어 있는지

### 6. 구조 검증
- **필수 섹션 존재 여부**: 목적/개요, 범위, 요구사항, 제약사항 등 핵심 섹션 포함 여부
- **마크다운 문법**: 깨진 링크, 잘못된 헤딩 계층, 닫히지 않은 코드 블록 등
- **논리적 흐름**: 섹션 순서가 자연스럽고, 상위 개념에서 하위 상세로 전개되는지

## 출력 형식 (메인으로 되돌려줄 유일 본문)

아래 형식을 기본으로 하되, **각 항목마다 왜 문제가 되는지(배경 설명), 어떤 원칙에 위배되는지, 어떻게 고치면 되는지(구체적인 수정 문구 예시)** 를 포함한다.

**출력은 반드시 아래 블록으로 시작**하고, **그 블록만** 출력한다(앞뒤 인사·JSON·중복 헤더 없음).

```markdown
## PR 리뷰 결과

### 요약
> diff 전체(베이스…HEAD 대비) 변경을 2~3문장으로 요약한다. 어떤 스펙이 추가/변경되었는지, 주요 의도가 무엇인지 간결하게 서술한다. (PR·브랜치·리포는 메인이 준 맥락에서 한 줄로만 언급해도 된다.)

### 변경 파일 워크스루
| 경로 | 유형 | 한 줄 의도 |
|------|------|------------|
| `specs/.../spec.md` | 수정 | … |

### 필수 수정
- [파일:라인] 한 줄 요약 (무엇이 문제인지)
  - 문제 유형: 모호한 표현 | 시나리오 누락 | 용어 불일치 | 구조 오류 | 논리적 모순 | 팀 계약(CLAUDE.md) 위반
  - 상세 설명: 왜 문제가 되는지, 이 문서를 기반으로 구현할 때 어떤 혼란/오류가 발생할 수 있는지 서술
  - 관련 원칙:
    - 예: "스펙 문서는 구현자가 추가 질문 없이 구현 가능해야 한다", "모든 예외 상황은 명시적으로 기술한다" 등
  - 수정 제안:
    - before: 문제가 되는 현재 문구 인용
    - after: 구체적으로 수정된 문구 예시 제시

### 권장 수정
- [파일:라인] 한 줄 요약 (개선 포인트)
  - 문제 유형: 가독성 | 구조 개선 | 보완 권장 | 포맷 통일
  - 상세 설명: 현재도 이해는 가능하지만, 명확성/유지보수성 측면에서 개선이 필요한 이유
  - 수정 제안:
    - before/after 형태로 개선된 문구 제시

### 용어 일관성 분석
- 동일 개념에 대해 문서 내에서 다르게 사용된 용어 목록
  - 예: "사용자" vs "유저" → 하나로 통일 권장
  - 예: "요청" vs "리퀘스트" → 한글 또는 영문 중 하나로 통일
```

## 규칙

- **「요약」→「변경 파일 워크스루」→「필수 수정」→「권장 수정」→「용어 일관성 분석」** 순서를 지킨다. `### 변경 파일 워크스루`는 표 형식으로 항상 출력한다(변경이 없으면 “없음” 한 줄).
- `### 필수 수정`·`### 권장 수정`은 **반드시 존재**한다. 이슈가 없으면 해당 섹션에 **`- (해당 없음)`** 한 줄 이상을 넣어 비우지 않는다.
- diff에서 파일 경로와 라인 번호를 정확히 참조한다 (예: `specs/auth.md:42`). 통합 diff의 `+` 쪽 라인은 근사일 수 있으므로, 불확실하면 “파일 내 고유 문자열”을 `before`에 쓴다.
- 코드 품질 관점의 리뷰(함수 길이, 성능, 보안 취약점 등)는 하지 않는다.
- 변경 사항에 문제가 없으면 **필수/권장은 `(해당 없음)`** 으로 두고, **용어 일관성 분석**에서 잘된 점을 짧게 언급해도 된다.
- diff를 그대로 반복하지 않는다. 발견 사항에만 집중한다.
- 모호한 표현을 지적할 때는 반드시 구체적인 대안 문구를 함께 제시한다.
- **`CLAUDE.md`** 에 명시된 응답 필드명·권한·시드·예외 규약과 **충돌하는 스펙 문구**는 빠뜨리지 않고 **`### 필수 수정`** 또는 **`### 권장 수정`** 에 반영한다.
