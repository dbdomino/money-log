# Feature Specification: 지출유형별 목표금액과 월별 통계

**Feature Branch**: `006-backend-target-statistics`

**Created**: 2026-09-02

**Status**: Draft

**Input**: `프로젝트설계/기능명세상세-백엔드/phase5-목표-통계/` 의 API 6건(5.1~5.6)

## 대상 API

| 기능번호 | API 이름 | Method | URL |
|---|---|---|---|
| 5.1 | `ExpendTargetList` | GET | `/api/v1/expend-targets` |
| 5.2 | `ExpendTargetGet` | GET | `/api/v1/expend-targets/{year}/{month}/{expendGroupId}` |
| 5.3 | `ExpendTargetDefaultUpsert` | PATCH | `/api/v1/expend-targets/default/{expendGroupId}` |

전부 **로그인** 권한이다.

## 이 기능의 핵심 개념

**목표금액은 두 층이다.**

- **기본 목표금액** — 지출유형별 평상시 한 달 한도
- **월별 목표금액** — 특정 연·월에만 적용할 한도

둘은 **독립**이다. 기본을 바꿔도 이미 저장된 월별 값은 변하지 않고, 기본을 월별로 복사해 두지도 않는다. 통계가 쓰는 **적용 금액**은 `월별 값 ?? 기본 값`이다.

**월별 목표가 "없음"과 "0원"은 다른 상태다.** 없음은 기본값을 쓰겠다는 뜻이고, 0원은 그 달에 쓰지 않겠다는 의사 표시다.

**통계는 저장 시점의 스냅샷이다.** 저장본이 있으면 이후 지출을 고쳐도 그 저장본은 변하지 않는다.

## Clarifications

### Session 2026-09-02

- Q: 통계 저장(5.6)이 미래 월을 거절하는 기준은? → A: 현재 연월을 **초과**하는 달만 `3604`로 거절하고 이번 달은 저장할 수 있다
- Q: 지출·소득이 한 건도 없는 달을 저장하면? → A: 허용한다. 합계·비율이 전부 0인 스냅샷을 남긴다
- Q: 수단별 요약에 어떤 수단까지 행을 남기나? → A: 그 달 지출이 있는 수단은 상태와 무관하게 전부, 지출 0원 행은 저장 시점에 사용 중인 `EXPENSE` 수단만
- Q: 연·월을 받는 API의 연도 허용 범위는? → A: `2000 ~ 2100` 고정 범위이며 벗어나면 `3603`

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 지출유형별 목표를 정한다 (Priority: P1) 🎯 MVP

기본 목표를 정하고(5.3), 특정 달만 다르게 정하고(5.4), 목록·단건으로 확인한다(5.1·5.2).

**Why this priority**: 통계의 "목표 대비" 판정이 이 값에 의존한다. 목표 없이는 통계가 합계만 보여주는 표에 그친다.

**Independent Test**: 한 유형에 기본과 월별 목표를 각각 저장해 두 값이 독립적으로 읽히는지 확인한다. 통계 API 없이 완결된다.

**Acceptance Scenarios**:

1. **Given** 목표가 한 번도 저장된 적 없는 유형에, **When** 기본 목표를 저장하면, **Then** 새로 만들어진다(upsert)
2. **Given** 기본 목표가 이미 있을 때, **When** 다시 저장하면, **Then** 같은 행이 갱신되고 행이 늘지 않는다
3. **Given** 기본과 월별 목표가 모두 있을 때, **When** **기본만** 바꾸면, **Then** 월별 값은 **그대로다**
4. **Given** 월별 목표를 저장해도, **When** 기본 목표를 조회하면, **Then** **바뀌지 않았다**
5. **Given** 그 달에 월별 목표를 저장한 적이 없으면, **When** 조회하면, **Then** `monthlyTargetAmount`가 **`null`** 이고 `defaultTargetAmount`는 별도 필드로 온다
6. **Given** 월별 목표를 **0원**으로 저장하면, **When** 조회하면, **Then** `monthlyTargetAmount`가 `0`이다(`null`이 아니다)
7. **Given** 목표금액에 1억 초과를 주면, **When** 저장하면, **Then** 거부된다(0 ~ 1억)
8. **Given** `inUse=false`인 유형에, **When** 단건 조회·목표 변경을 하면, **Then** `3601`로 거부되고, 목록(5.1)은 그 유형을 **제외**하고 돌려준다
9. **Given** 삭제 표시된 유형에 목표가 있을 때, **When** 그 목표 행을 조회하면, **Then** 행과 참조가 **유지된다**

### User Story 2 - 이번 달 통계를 본다 (Priority: P1)

연·월로 통계를 조회한다(5.5). 저장본이 있으면 그것을, 없으면 지금 계산한 값을 돌려준다.

**Why this priority**: 사용자가 실제로 여는 화면이다. 저장 기능(US3) 없이도 계산 결과를 보여줄 수 있어 독립적이다.

**Independent Test**: 지출·소득·고정지출을 몇 건 만든 뒤 통계를 조회해 합계·비율·주별·유형별·수단별이 나오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 저장본이 없는 달을, **When** 조회하면, **Then** 지금 값으로 계산해 돌려주고 `source=CALCULATED`다
2. **Given** 저장본이 있는 달을, **When** (기본 조회로) 조회하면, **Then** **저장본**을 돌려주고 `source=SAVED`다
3. **Given** 저장본이 있는 달을, **When** `view=live`로 조회하면, **Then** 저장본을 무시하고 **지금** 값으로 다시 계산하며 `source=CALCULATED`다
4. **Given** `view=live`인데 저장본이 있으면, **When** 응답을 보면, **Then** `savedAt`에 마지막 저장 시각이 실려 "저장본 있음 / 지금 최신"을 구분할 수 있다
5. **Given** `view=live`로 조회해도, **When** 저장본을 확인하면, **Then** **DB 스냅샷은 바뀌지 않았다**
6. **Given** 그 달 1일이 월요일이 아니면, **When** 주별 지출을 보면, **Then** 첫 주는 **1일부터 첫 일요일까지**다
7. **Given** 지출이 0원인 지출유형이 있으면, **When** 유형별 요약을 보면, **Then** 그 유형은 **없다**
8. **Given** 지출이 0원인 수단이 있으면, **When** 수단별 요약을 보면, **Then** 그 수단은 **있다**(유형과 반대다)
9. **Given** 목표가 0원인 유형이면, **When** 사용률을 보면, **Then** `0`이다(나눗셈이 성립하지 않는다)
10. **Given** 월에 13을 주면, **When** 조회하면, **Then** `3603`으로 거부된다
11. **Given** 연도에 1999나 2101을 주면, **When** 조회하면, **Then** `3603`으로 거부된다(허용 범위는 2000~2100)

### User Story 3 - 지난달 통계를 확정해 남긴다 (Priority: P2)

그 달 통계를 스냅샷으로 저장한다(5.6).

**Why this priority**: 과거 월을 보존하는 값이 있지만, 조회(US2)가 저장본 없이도 동작하므로 뒤에 둔다.

**Independent Test**: 통계를 저장한 뒤 원본 지출을 고치고 다시 조회해 저장본이 변하지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 통계를 저장하면, **When** 저장 응답을 보면, **Then** `savedAt`과 `source=SAVED`가 실려 재조회 없이 화면을 갱신할 수 있고, 기본 조회로 다시 봐도 `source=SAVED`다
2. **Given** 통계를 저장한 뒤 그 달 지출을 고치면, **When** 기본 조회로 보면, **Then** **저장본은 변하지 않았다**
3. **Given** 같은 달을 **다시** 저장하면, **When** 통계 행을 세면, **Then** **1건**이고 `savedAt`이 갱신되어 있다
4. **Given** 재저장하면, **When** 상세(주별·유형별·수단별)를 보면, **Then** 이전 상세는 지워지고 새로 계산된 것으로 채워져 있다
5. **Given** 통계를 저장한 뒤 그 지출유형을 삭제 표시하면, **When** 통계를 조회하면, **Then** **유형별 요약이 그대로 남아 있고** 저장 당시 이름으로 읽힌다
6. **Given** 저장본이 있을 때, **When** 최신과 비교하려면, **Then** `view=live`로 조회해 나란히 본다

### Edge Cases

- 통계 상세가 가리키는 지출유형·수단이 나중에 **사라지면**? — 통계 상세에는 **참조 무결성 제약이 없다.** 저장 당시 이름으로 화면을 복원하며, 응답의 유형·수단 ID는 실재하지 않을 수 있다
- 통계를 저장한 뒤 목표금액을 바꾸면? — 저장본의 목표·사용률·상태는 **저장 당시 값** 그대로다
- `status` 판정 기준(90% 미만 UNDER / 90~110% OK / 110% 초과 OVER)이 나중에 바뀌면? — 이미 저장된 행은 **다시 계산하지 않는다**
- 사용률이 100%를 넘으면? — 넘을 수 있다. 목표 대비 1000%도 표현 가능해야 한다
- 통계 저장 대상 달에 데이터가 하나도 없으면? — **저장을 허용한다.** 합계·비율 여섯 값이 전부 0인 `tbl_statistics` 행 1건을 남긴다(FR-528). 거절하면 "이 달은 아무것도 쓰지 않았다"는 확정을 남길 방법이 없고, 화면이 그 상태를 저장본 없음(`source=CALCULATED`)과 구분하지 못한다
- 목표금액 목록(5.1)에 연·월이 왜 필수인가? — 기본만 보는 화면도 조회 연·월을 넘긴다. 모드 분기를 두지 않아 응답 형태가 하나로 유지된다

## Requirements *(mandatory)*

### Functional Requirements

- **FR-501**: 목표금액·통계는 회원 소유로만 만들어지고 **본인 것만** 조회·수정할 수 있어야 한다
- **FR-502**: 기본 목표금액은 회원·지출유형 조합당 **최대 1건**이어야 한다
- **FR-503**: 월별 목표금액은 회원·연·월·지출유형 조합당 **최대 1건**이어야 한다
- **FR-504**: 목표금액은 **0 ~ 100,000,000원**이어야 한다. 0은 유효한 값이다. 범위를 벗어나면 `3602`로 거절하며, 이 범위는 `tbl_expend_target_default`·`tbl_expend_target_monthly`의 CHECK 제약과 같은 값이다
- **FR-505**: 기본 목표와 월별 목표는 **독립**이어야 한다. 기본을 바꿔도 저장된 월별 값이 변하지 않고, 기본을 월별로 복사하지 않는다
- **FR-506**: 월별 목표가 **없는 것**과 **0원인 것**은 다른 상태로 구분해야 한다. 없으면 응답의 `monthlyTargetAmount`가 `null`이다
- **FR-507**: 적용 금액은 `월별 값 ?? 기본 값`이며, 목록·단건 응답은 두 값을 **별도 필드**로 내려 저장 여부를 드러내야 한다. 두 필드의 미설정 표현은 **의도적으로 다르다** — `monthlyTargetAmount`는 행이 없으면 `null`, `defaultTargetAmount`는 행이 없으면 `0`이다. 따라서 적용 금액은 항상 숫자이며 `null`이 되지 않는다
- **FR-508**: 목표금액은 **월 단위** 한도다. 일·주 단위가 아니다
- **FR-509**: 목표금액 목록은 **사용 중(`inUse=true`) 유형만** 돌려줘야 한다
- **FR-510**: 사용하지 않는 유형에 대한 단건 조회·목표 변경은 `3601`로 거절해야 한다
- **FR-511**: 지출유형이 삭제 표시돼도 그 유형을 참조하는 목표금액 행과 참조는 유지되어야 한다
- **FR-512**: 목표금액 저장은 upsert(PATCH)여야 한다. 최초 설정과 변경을 같은 경로로 처리한다
- **FR-513**: 통계 조회는 기본적으로 저장본이 있으면 저장본(`source=SAVED`), 없으면 즉석 계산(`source=CALCULATED`)을 돌려줘야 한다. 두 경로 모두 소득 합계(`incomeTotal`), 지출 합계(`expenseTotal` = 일반 + 할부 + 고정), 고정 대 일반 비율(`fixedAmount`·`regularAmount`·`fixedPercent`·`regularPercent`)을 함께 담는다. 비율은 `expenseTotal` 대비 백분율이고 소수 둘째 자리까지 두며(`numeric(5,2)`), `expenseTotal`이 0이면 두 비율 모두 `0`으로 둔다 — 이 여섯 값은 `tbl_statistics`에서 NOT NULL이라 비워 둘 수 없다
- **FR-514**: 통계 조회의 `view`는 **생략**·`saved`·`live` 셋만 허용하며 그 밖의 값은 `3603`으로 거절한다. 생략과 `saved`는 같은 동작(저장본 우선)이고, `view=live` 조회는 저장본을 **읽지도 쓰지도 않고** 즉석 계산만 돌려주며 `source`는 항상 `CALCULATED`여야 한다
- **FR-515**: `view=live`인데 저장본이 있으면 `savedAt`을 함께 실어 프론트가 두 상태를 구분할 수 있어야 한다
- **FR-516**: 통계 저장은 회원·연·월 조합당 **최대 1건**이어야 한다. 재저장은 행을 늘리지 않고 갱신하며 `savedAt`을 새로 쓴다
- **FR-517**: 재저장은 상세(주별·유형별·수단별)를 **지웠다 다시 넣어야** 한다
- **FR-518**: 저장된 통계는 **저장 시점 값을 보존**해야 한다. 이후 원본이 바뀌어도 변하지 않는다
- **FR-519**: 통계 상세의 지출유형·수단 참조에는 **FK를 두지 않는다.** 원본이 사라져도 기록이 남아야 하며, 화면 복원은 함께 저장한 **이름 스냅샷**이 맡는다
- **FR-520**: 주별 지출은 **월요일 시작**이며, 그 달 1일이 월요일이 아니면 첫 주는 1일부터 첫 일요일까지다. 마지막 주는 그 달 말일에서 끊는다. 통계를 저장할 때 주 시작일·종료일을 함께 저장하고, 저장본(`source=SAVED`)을 읽을 때는 저장된 경계를 그대로 쓴다 — 다시 계산하지 않는다. 저장본이 없거나 `view=live`인 즉석 계산 경로는 요청 시점에 경계를 계산하되 같은 규칙을 쓴다
- **FR-521**: 유형별 요약은 그 달 지출이 **0원인 유형을 저장하지 않는다.** 모집단은 그 달 지출이 1건 이상인 지출유형뿐이다
- **FR-521a**: 수단별 요약은 **0원인 수단도 저장한다.** 모집단은 두 집합의 합집합이다 — ① 그 달 지출이 1건 이상인 수단은 삭제 표시(`deleted=true`)·미사용(`in_use=false`)이어도 **전부** 포함한다(저장본은 그 달에 실제로 일어난 일을 보존해야 한다), ② 그 달 지출이 0원인 수단은 **저장 시점에 `in_use=true`이고 `deleted=false`인 `purpose=EXPENSE` 수단만** 포함한다. ②를 제한하지 않으면 오래전에 버린 카드의 0원 행이 매달 쌓여 요약이 계속 길어진다. `5.5-StatisticsMonthlyGet.md` 예시의 "옛 카드" 0원 행은 ②에 해당하는 사용 중 수단으로 읽는다
- **FR-522**: 사용률은 100%를 넘을 수 있어야 하며, 목표가 0이면 0으로 둔다. 소수 둘째 자리까지 두고 저장 상한은 `9999.99`이며(`tbl_statistics_expend_group.usage_rate`가 `numeric(6,2)`), 계산값이 이를 넘으면 `9999.99`로 잘라 저장한다
- **FR-523**: 목표 대비 상태는 `UNDER`·`OK`·`OVER` 셋뿐이다. 기준이 바뀌어도 이미 저장된 행은 다시 계산하지 않는다
- **FR-524**: 통계 저장은 연·월을 **Body**로 받는다(POST는 Path·Query를 쓰지 않는다)
- **FR-525**: 연 값은 **2000 이상 2100 이하**, 월 값은 **1 이상 12 이하**여야 하며, 어긋나거나 누락되면 `3603`으로 거절한다. 이 검증은 연·월을 받는 5.1·5.2·5.4·5.5·5.6 다섯 곳에 같은 규칙으로 적용한다. 연도 범위는 애플리케이션이 판정한다 — `tbl_statistics`의 `ck_statistics_month`은 월만 검사하므로 DB가 대신 막아주지 않는다. 현재 연도 기준 상대 범위를 쓰지 않는 것은 경계가 해마다 움직이면 테스트가 시간에 의존하기 때문이다
- **FR-526**: 목록 응답은 `data.list`(object 배열)로 통일한다. 목표금액 목록(5.1)은 `offset`·`limit`을 **필수** Query로 받고 `offset`·`limit`·`totalCount`를 응답에 실으며(`offset`은 0 이상이고 `limit`의 배수, `limit`은 1 이상, 위반은 `9001`), `expendGroupName` 부분 일치 검색을 **사용 중 유형 범위 안에서** 지원한다. `totalCount`도 사용 중 유형만 집계한다. 부가 필드 `year`·`month`는 `list`와 같은 레벨에 둔다. 통계 응답의 `weeklyExpenses[]`·`expendGroupSummaries[]`·`paymentMethodSummaries[]`는 목록 API가 아니므로 이 규칙의 적용 대상이 아니다
- **FR-527**: 통계 저장(5.6)은 저장 대상 연·월이 서버 기준 현재 연월을 **초과**하면 `3604`로 거절한다. 비교는 `연 × 12 + 월` 합성값으로 하며, 이번 달은 초과가 아니므로 저장할 수 있다. 진행 중인 달의 저장본은 이후 5.6을 다시 불러 덮어쓴다(FR-516·FR-517). `5.6-StatisticsMonthlySave.md`의 `3604` 설명 "(정책에 따라)"는 이 규칙으로 확정한다
- **FR-528**: 그 달에 지출·소득이 한 건도 없어도 통계를 저장할 수 있어야 한다. `tbl_statistics` 행 1건을 남기고 합계·비율 여섯 값은 모두 `0`으로 채운다. 주별 상세는 그 달의 주 수만큼 0원 행을 만들고, 유형별 상세는 빈 배열이며(FR-521의 "0원 유형은 저장하지 않는다"가 그대로 적용된다), 수단별 상세는 FR-521의 모집단 규칙을 따라 0원 행을 남긴다

### 이 기능이 쓰는 에러코드

`프로젝트설계/기능명세상세-백엔드/phase5-목표-통계/` 의 각 API 문서가 배정한 값이다. 목표금액·통계는 `36xx` 대역을 쓰고, 지출유형 자원 오류는 `003`이 정의한 `31xx`를 그대로 재사용한다.

| 코드 | 의미 | 사용 지점 |
|---|---|---|
| `1001` | 로그인 필요 | 6건 전부 |
| `3103` | 지출유형 없음 또는 타인 소유 | 5.2·5.3 |
| `3601` | 사용하지 않는(`inUse=false`) 지출유형에 대한 목표금액 단건 조회·변경 | 5.2·5.3·5.4 |
| `3602` | 목표금액이 0~100,000,000원 범위 밖 | 5.3·5.4 |
| `3603` | `year`·`month` 누락·범위 오류, 또는 `view` 값이 `saved`·`live` 밖 | 5.1·5.2·5.4·5.5·5.6 |
| `3604` | 미래 월 통계 저장 시도 | 5.6 |
| `9001` | `offset`·`limit` 누락·범위 오류 | 5.1 |

`3601`은 `003-backend-payment-expend-group`의 FR-212가 거절 조건만 만들고 정의를 이 기능에 넘긴 코드이므로 여기서 정의한다. 같은 "연·월 범위 오류"가 월별 고정지출 내역은 `3403`, 월별 가계부 목록은 `3501`, 목표금액·통계는 `3603`인 것은 자원이 달라서이며 의도된 차이다. `3404`·`3502`는 결번이므로 되살려 쓰지 않는다(`_공통.md § 결번`).

### Key Entities

- **기본 목표금액(`tbl_expend_target_default`)**: 지출유형별 평상시 월 한도. 회원·유형당 1건
- **월별 목표금액(`tbl_expend_target_monthly`)**: 특정 연·월의 한도. 회원·연·월·유형당 1건. 기본과 독립
- **월별 통계 스냅샷(`tbl_statistics`)**: 저장 시점의 계산 결과. 연·월, 저장 시각, 소득·지출 합계, 고정·일반 금액과 비율. 회원·연·월당 1건
- **통계 주별 지출(`tbl_statistics_weekly`)**: 주차·주 시작일·종료일·합계. 스냅샷에 딸린다
- **통계 지출유형별 요약(`tbl_statistics_expend_group`)**: 유형 대리키(**FK 없음**)·이름 스냅샷·합계·적용 목표·사용률·상태
- **통계 수단별 요약(`tbl_statistics_payment_method`)**: 수단 대리키(**FK 없음**)·이름 스냅샷·합계

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-501**: 6개 API가 모두 `{ resCode, data }` 형식으로 응답한다
- **SC-502**: 기본 목표를 바꾼 뒤 저장된 월별 목표를 조회하면 **값이 변하지 않는다**
- **SC-503**: 월별 목표를 저장하지 않은 달의 `monthlyTargetAmount`가 `null`이고, 0원으로 저장한 달은 `0`이다
- **SC-504**: 목표금액 1억 초과 저장 시도가 **100% 거부**된다
- **SC-505**: 같은 달 통계를 10번 저장해도 통계 행은 **1건**이고 `savedAt`이 매번 갱신된다
- **SC-506**: 통계를 저장한 뒤 그 달 지출을 고쳐도 기본 조회 결과가 **바뀌지 않는다**
- **SC-507**: `view=live`로 조회한 뒤 저장본을 확인하면 **변경되지 않았다**
- **SC-508**: 통계 저장 후 참조한 지출유형을 삭제 표시해도 유형별 요약이 **그대로 조회된다**
- **SC-509**: 통계 상세 2종에 지출유형·수단으로 나가는 FK가 **0건**이다
- **SC-510**: 연도 1999·2101과 월 0·13을 넣은 요청이 연·월을 받는 5개 API에서 **전부 `3603`** 으로 거부된다
- **SC-511**: 지출·소득이 없는 달을 저장한 뒤 조회하면 `source=SAVED`이고 합계·비율 여섯 값이 **모두 0**이다

## Assumptions

- 저장 구조는 `001-backend-db-schema`에서 만들어졌다. 유일 제약·CHECK·CASCADE와 통계 상세의 FK 부재가 이미 DB에 반영되어 있다
- 인증은 `002`, 수단·지출유형은 `003`, 지출·소득은 `004`, 고정지출·가계부는 `005`가 제공한다
- 통계 조회·저장은 월별 고정지출 내역의 **lazy 생성을 일으키지 않는다**. 생성을 일으키는 것은 `005`의 4.5·4.8·4.9뿐이므로, 한 번도 열지 않은 달의 통계는 고정지출 합계가 0으로 나온다. 그 달을 채우려면 화면이 4.8이나 4.9를 먼저 호출한다
- 통계 계산은 조회·저장 요청이 동기로 수행한다. 배치·스케줄러를 두지 않으며, 저장 API가 그 수동 트리거 역할을 한다
- 통계가 집계하는 지출은 일반·할부·고정지출이며 소득은 별도 합계로 둔다
- `status` 판정 기준(90%/110%)은 구현 시 조정될 수 있는 값이다. 저장된 행을 소급 재계산하지 않는 규칙이 그 조정을 안전하게 만든다
- 목표금액·통계 화면의 연·월은 프론트가 정해 넘긴다. 서버가 "이번 달"을 추론하지 않는다
