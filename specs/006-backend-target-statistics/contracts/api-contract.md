# API 계약: 지출유형별 목표금액과 월별 통계

**Feature**: `006-backend-target-statistics` | **Date**: 2026-09-02 | **Phase**: 1

각 API의 전체 필드 표는 `프로젝트설계/기능명세상세-백엔드/phase5-목표-통계/` 가 소유한다.
여기 적는 것은 **6건에 공통으로 걸리는 규칙**과 **설계 문서만 봐서는 갈리는 지점**이다.

- 목표금액 2층 구조 → [target-amount.md](./target-amount.md)
- 집계·저장본·`view` 분기 → [statistics-snapshot.md](./statistics-snapshot.md)

---

## 1. 인가와 소유자

**6건 전부 로그인 필요**다. `002`의 `SecurityFilterChain` 기본 규칙이 적용된다.

소유자는 **토큰의 `id_key`**로 정해진다. Path의 `{expendGroupId}`는 자원 식별자일 뿐이며,
그 유형이 본인 소유가 아니면 `3103`으로 거절한다 — `003`이 정의한 코드를 재사용한다.

---

## 2. 응답 규격 — 예외가 없다

**6건 전부** `{ resCode, data }`다. `005`와 같고 `003`·`004`와 다르다.

바이너리 응답이 없으므로 AOP 로깅 제외 규칙도 추가할 것이 없다.

---

## 3. 목록 응답 — 페이징이 있는 것은 5.1뿐

| API | 페이징 | 부가 필드 |
|---|:---:|---|
| 5.1 목표금액 목록 | **있다** | `year` · `month` · `offset` · `limit` · `totalCount` |
| 나머지 5건 | — | 목록 API가 아니다 |

**통계 응답의 배열 3종은 목록 API가 아니다.** `weeklyExpenses[]`·`expendGroupSummaries[]`·
`paymentMethodSummaries[]`는 한 통계 객체의 구성 요소이므로 `data.list` 규칙의 적용 대상이
아니다(`_공통.md § 적용 제외`).

5.1의 페이징 검증은 `002`의 관리자 목록(1.13)과 같다 — `offset`·`limit` 필수,
`limit <= 0` · `offset < 0` · `offset % limit != 0`이면 `9001`.

**`totalCount`는 사용 중 유형만 센다**(FR-509·526). 목록이 `in_use=false`를 제외하므로
전체 건수도 같은 기준이어야 한다.

`expendGroupName` 부분 일치 검색도 **사용 중 유형 범위 안에서** 동작한다.

---

## 4. HTTP 메서드

| API | 메서드 | 비고 |
|---|---|---|
| 5.1 · 5.2 · 5.5 | GET | 조회. **부작용 없다** — `005`와 다르다 |
| **5.3 · 5.4** | **PATCH** | **upsert**. 최초 설정과 변경을 같은 경로로(FR-512) |
| 5.6 | POST | 통계 저장 |

**5.3·5.4가 `PATCH`인 것**이 이 기능의 특징이다. 행이 없으면 만들고 있으면 갱신한다.
사용자에게 "최초 설정"과 "변경"은 같은 행위 — 목표금액 칸에 숫자를 넣는 것뿐이다.
API를 나누면 프론트가 "이미 있는가"를 먼저 조회해 분기해야 한다.

`PUT`은 쓰지 않는다(헌장 원칙 III).

**5.5는 GET이고 부작용이 없다.** `005`의 4.5·4.8과 다르다 —
006의 통계 조회는 월별 고정지출 내역의 lazy 생성을 **일으키지 않는다**.

## 5. 연·월 검증 (FR-525)

| 항목 | 허용 범위 | 위반 |
|---|---|---|
| 연 | **2000 ~ 2100** | `3603` |
| 월 | 1 ~ 12 | `3603` |

**연·월을 받는 다섯 곳에 같은 규칙으로 적용한다** — 5.1 · 5.2 · 5.4 · 5.5 · 5.6.

**연도는 애플리케이션이 판정한다.** `ck_statistics_month`는 월만 검사하므로(덤프 확인)
DB가 대신 막아주지 않는다. `year=0`이나 `year=999999`가 그대로 들어온다.

**현재 연도 기준 상대 범위를 쓰지 않는 것**은 경계가 해마다 움직이면 테스트가 시간에
의존하기 때문이다. 고정 상수라 경계 테스트가 안정적이다.

`3603`은 **`view` 값 오류에도 쓴다**(§6).

### 다른 기능과 코드가 다르다

같은 "연·월 범위 오류"의 코드가 자원마다 다르다.

| 자원 | 코드 |
|---|---|
| 월별 고정지출 내역 (`005` 4.5·4.6·4.9) | `3403` |
| 월별 가계부 목록 (`005` 4.8) | `3501` |
| **목표금액·통계 (006)** | **`3603`** |

`_공통.md`의 코드 블록 배정이 정한 **의도된 차이**다. 실수처럼 보이지만 자원별 대역 규칙의
결과다.

## 6. `view` 파라미터 (5.5 전용)

```text
생략 · view=saved   →  저장본이 있으면 저장본(source=SAVED), 없으면 즉석 계산(CALCULATED)
view=live           →  저장본을 읽지도 쓰지도 않고 즉석 계산. source 는 항상 CALCULATED
그 밖의 값           →  3603
```

**생략과 `saved`가 같은 동작이다.** `saved`가 명시적 값으로 존재한다는 사실을 놓치면
구현자가 `?view=saved`를 알 수 없는 값으로 보고 거절한다.

**Path(`year`·`month`)와 Query(`view`)를 함께 쓰는 것은 6건 중 5.5뿐이다.**
`view`가 자원 식별자가 아니라 **모드 스위치**라서 허용한 예외다.

`view=live`인데 저장본이 있으면 `savedAt`을 함께 싣는다(FR-515) —
프론트가 "저장본 있음 / 지금 최신"을 나란히 보여줄 수 있다.

## 7. 실패 코드 매핑 — 판정 순서가 결과를 바꾸는 곳

전체 7개는 [spec.md § 이 기능이 쓰는 에러코드](../spec.md)에 있다.

### 5.2 목표금액 단건 조회 — `3603` → `3103` → `3601`

```text
1. year·month 범위                          오류 → 3603
2. expendGroupId 로 지출유형 조회 (본인 소유?)  없음·타인 → 3103
3. in_use = false 인가                              → 3601
4. 기본·월별 목표를 각각 읽어 응답
   └ 월별이 없으면 null, 기본이 없으면 0
```

**2번과 3번의 순서가 중요하다.** 남의 유형 ID로 접근했는데 그게 마침 `in_use=false`라면
`3601`이 아니라 `3103`이어야 한다 — 존재 여부를 노출하지 않는다.

### 5.3 기본 목표 upsert — `3103` → `3601` → `3602`

```text
1. expendGroupId 로 지출유형 조회 (본인 소유?)  없음·타인 → 3103
2. in_use = false 인가                              → 3601
3. targetAmount 가 0 ~ 100,000,000 밖               → 3602
4. upsert (없으면 INSERT, 있으면 UPDATE)
   └ 유니크 위반은 흡수하거나 재시도한다
```

**5.4는 여기에 `year`·`month` 검증(`3603`)이 1번 앞에 붙는다.**
`5.4`의 실패 표에 `3103`이 없는데(덤프한 설계 명세 확인) 이는 표기 누락으로 보인다 —
Path에 `expendGroupId`가 있으므로 같은 검증이 필요하다. 5.3과 같게 처리한다.

### 5.6 통계 저장 — `3603` → `3604`

```text
1. year·month 범위                                오류 → 3603
2. 저장 대상이 현재 연월을 초과하는가 (연×12+월 비교) → 3604
   └ 이번 달은 초과가 아니므로 저장할 수 있다
3. 집계 계산 (5.5 의 즉석 계산과 같은 계산기)
4. 저장 — 통계 행 upsert + 상세 3종 삭제 후 재삽입
→ year · month · savedAt · source=SAVED · message
```

**2번의 경계가 "초과"다.** 이번 달은 진행 중이지만 실제 데이터가 있어 저장할 가치가 있고,
이후 5.6을 다시 불러 덮어쓴다.

**빈 달도 저장한다**(FR-528). 지출·소득이 한 건도 없어도 합계·비율 6값을 0으로 채운
행을 남긴다 — `tbl_statistics`의 여섯 컬럼이 NOT NULL이라 자리가 이미 있다.

## 8. 저장 응답 (5.6)

```json
{ "resCode": 200,
  "data": { "year": 2026, "month": 7, "savedAt": "...", "source": "SAVED", "message": "..." } }
```

**`savedAt`과 `source`를 함께 돌려주는 이유**(SC-511 계열): 저장 직후 재조회 없이 화면을
갱신할 수 있어야 한다. 저장 → 재조회의 왕복 두 번을 한 번으로 줄인다.

---

## 9. 이름 — 통계는 스냅샷, 목표금액은 현재 이름

| 대상 | 이름의 성격 |
|---|---|
| 목표금액 응답(5.1·5.2)의 `expendGroupName` | **현재 이름** — 원본에서 읽는다 |
| 통계 상세(5.5·5.6)의 `expendGroupName`·`paymentMethodName` | **저장 시점 스냅샷** |

목표금액은 **지금 유효한 설정**이라 현재 이름이 맞고(`005`의 고정지출과 같은 성격),
통계는 **과거 기록**이라 스냅샷이 맞다(`004`의 지출과 같은 성격).

`tbl_expend_target_*`에는 이름 컬럼이 없고, `tbl_statistics_*`에는 NOT NULL로 있다
(덤프 확인). 스키마가 이 구분을 이미 표현하고 있다.
