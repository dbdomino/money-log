# Implementation Plan: 프론트 목표금액·통계 화면

**Branch**: `develop` (기능 브랜치를 따로 두지 않는다) | **Date**: 2026-09-21 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/012-frontend-target-statistics/spec.md`

## Summary

007~011 이 세운 것 위에 **화면 2개**를 얹는다. 기본 목표금액 하나와 월별 통계 하나다.
백엔드 006 의 API 6건을 부른다. **모달이 없다** — 둘 다 풀페이지이고 입력이 표 안에서 일어난다.

**프론트의 마지막 기능이다.** 012 가 서면 화면 31건이 모두 선다.

009~011 과 성격이 이어지되 **넷이 새롭다.**

| 축 | 009~011 | 012 (목표·통계) |
|---|---|---|
| 모달 | 목록 위에 얹혔다 | **없다.** 입력이 표 안에 있다 |
| 서버가 주는 값 | 그대로 보인다 | **일부는 화면이 낸다** — 적용 금액이 응답에 없다 |
| 같은 응답의 두 목록 | 규칙이 같았다 | **반대다** — 유형별은 0원을 빼고 수단별은 남긴다 |
| 조회 | 한 가지 | **두 갈래** — 저장본과 즉석 계산 |

이 네 줄이 계획의 모양을 정한다.

**① "없음"과 "0원"이 다르다.** 월별 목표가 없으면 기본을 따르고, 0원으로 정했으면 **그 달엔
쓰지 않겠다**는 뜻이라 0 이 그대로 적용된다. 화면이 빈 칸과 0 을 같게 다루면 **이 의사 표시가
사라진다.** 이 기능에서 가장 놓치기 쉬운 지점이다.

**② 화면이 내는 값과 서버 값을 가른다.** 적용 금액(`월별 ?? 기본`)은 응답에 없어 화면이
낸다. 반대로 **사용률은 서버 값을 그대로** 쓴다 — 그쪽은 상한에서 자르는 규칙을 서버가 갖고
있어 화면이 계산하면 규칙이 두 곳에 생긴다.

**③ 같은 화면의 두 표가 반대 규칙을 쓴다.** 유형별은 0원 유형을 빼고, 수단별은 0원 수단을
남긴다. **화면이 통일하지 않는다** — 통일하면 한쪽이 계약과 어긋난다.

**④ 저장본은 불변이고 저장은 명시적 행위다.** 조회가 저장을 겸하지 않는다. 저장본과 최신이
다를 수 있으며 **갱신 방법은 다시 저장하는 것**이다.

기술 결정 16건은 [research.md](./research.md) 에 있다.

## Technical Context

**Language/Version**: Java 17

**Primary Dependencies**: Spring Boot 4.1.0 · Spring Web MVC · Thymeleaf ·
`common-mod`(에러코드 Enum 참조용). **이 기능은 의존성을 더하지 않는다.**

**차트 라이브러리를 넣지 않는다.** 스펙이 "차트는 표로 대체할 수 있다"로 정했고, 주별 지출은
**주차·기간·금액을 표로** 보이면 요구사항을 만족한다(research 9).

007~011 에서 받아 가는 것은 코드이지 의존이 아니다 — 백엔드 호출 통로, **페이징 환산기**,
로그인 세션, 진입 판정, 레이아웃, 폼 실패 착지 규약.

**Storage**: **없다.** 화면 모듈은 데이터베이스를 모른다. `sql/schema-moneylogdb.sql` 은
읽지도 바꾸지도 않는다. **세션에 더하는 상태도 없다** — 쪽 번호·연·월·조회 갈래가 주소에
실린다([data-model.md](./data-model.md)).

**Testing**: JUnit 5 · `spring-boot-starter-test` · `spring-boot-starter-webmvc-test`.
백엔드를 띄우지 않고 응답을 세워 화면을 검증한다.

**Target Platform**: JVM 서버. 화면 `:8080`, 백엔드 `:8081`.

**Project Type**: Spring Boot 멀티모듈 — 이 기능은 프론트 모듈 하나만 손댄다.

**Performance Goals**: 정하지 않는다. 다만 **성격은 기록한다.**

| 요청 | 백엔드 호출 |
|---|---|
| 6.1 기본 목표 목록 | **1회** — 목표 목록 |
| 6.2 통계 조회 | **2회** — 통계 + 목표 목록 |

**6.2 가 목표 목록을 함께 부르는 이유**는 통계 응답의 유형별 요약에 **월별·기본이 나뉘어
오지 않기 때문**이다. 표에서 그 달 목표를 고치려면 두 값을 따로 알아야 한다(research 5).

**저장 뒤 다시 조회하지 않는다**(FR-1121). 호출이 늘지 않는다.

**Constraints**:
- **007~011 의 공통 코드를 고치지 않는다.** 완료 판정에서 diff 로 확인한다.
- 브라우저는 **GET 과 POST 만** 쓴다. 백엔드가 요구하는 메서드로 옮기는 일은 화면 모듈이 한다.
- 화면 모듈은 **에러코드를 새로 정의하지 않는다.**
- **연·월 선택은 2000~2100 으로 제한한다**(FR-1107). 005 의 1900~9999 와 다르다.
- **"없음"과 "0"을 같게 다루지 않는다**(FR-1117·FR-1118).
- **적용 금액만 화면이 내고 사용률은 서버 값을 쓴다**(research 2).
- **유형별과 수단별의 0원 규칙을 통일하지 않는다**(FR-1110).
- **조회가 저장을 겸하지 않는다**(FR-1120).
- 폼 실패 착지는 **008 의 규약을 그대로** 쓴다.

**Scale/Scope**: 화면 2개 · FR 26건(FR-1101~1126) · SC 10건 · User Story 4개(P1 2 · P2 2) ·
부르는 API 6건 · 새 에러코드 0건 · DB 테이블 0개 · 새 의존 0건 · **모달 0개** ·
**007~011 을 고치는 파일 0개**.

**Structure Decision**: 화면 묶음별 패키지를 이어 가되 **패키지를 둘로 나눈다**(`target` ·
`statistics`).

009 는 자원 하나, 010 은 한 부모에 자원 둘, 011 은 한 부모에 저장 단위 둘이었다. 012 는
**부모가 없는 화면 둘**이다 — 모달이 없어 한쪽이 다른 쪽 위에 얹히지 않는다.

| 패키지 | 맡는 것 |
|---|---|
| `target` | 6.1 목록·검색·쪽 넘기기·**기본** 목표 저장 |
| `statistics` | 6.2 통계 조회·최신 계산 보기·통계 저장·**월별** 목표 저장 |

**목표 목록은 둘이 함께 쓴다.** 6.2 의 유형별 표에서 그 달 목표를 고치려면 **월별과 기본이
나뉜 값**이 필요한데 통계 응답은 합쳐진 목표 하나만 준다(research 5). 그래서
`TargetRow`·`TargetPageModel` 이 `target` 패키지에 있고 `statistics` 가 가져다 쓴다 —
009 의 수단 타입을 010 이 가져다 쓴 것과 같은 방향이다.

**월별 목표 저장이 `statistics` 에 있는 이유**는 그 입력이 통계 화면의 표 안에 있고, 저장 뒤
착지도 그 화면이기 때문이다. `target` 에 두면 **실패 착지가 남의 화면을 다시 그려야** 한다.

**템플릿 디렉터리를 주소에 맞춘다.** `/targets/default` → `targets/default.html`,
`/statistics` → `statistics/monthly.html`. 009 의 `payments/`, 010 의 `ledger/` 와 같은
규칙이며, 화면 문서 메타의 `target/default.html` 은 선행 개정에서 함께 고친다.

## Complexity Tracking

> Constitution Check 에 정당화가 필요한 위반이 있을 때만 채운다.

**위반이 없다.** 011 과 같이 **공통 코드를 하나도 고치지 않는다** — 필요한 것(페이징 환산기 ·
구조를 가진 실패 없음 · 파일 없음 · 모달 없음)이 전부 이미 서 있다.

아래 셋은 위반이 아니라 **앞 기능들과 달라지는 판단**이라 근거를 남긴다.

| 판단 | 왜 이렇게 했나 | 기각한 대안 |
|---|---|---|
| **적용 금액을 화면이 낸다** (010·011 은 서버 값을 그대로 썼다) | 응답에 없는 값이다. 서버가 기본과 월별 두 값만 주고 `월별 ?? 기본` 은 **화면이 낼 수밖에 없다** | **서버에 적용 금액을 더한다** — 012 의 전제가 백엔드 무변경이다. **월별이 없으면 기본을 복사해 보인다** — 「없음」과 「0」의 구분이 사라져 사용자의 의사 표시가 없어진다 |
| **사용률은 서버 값을 그대로 쓴다** (적용 금액과 반대) | 서버가 **상한(`9999.99`)에서 자르는 규칙**을 갖고 있다. 화면이 계산하면 그 규칙이 두 곳에 생기고, 상한에 걸린 값이 화면에서만 달라진다 | **화면이 `금액/목표*100` 으로 낸다** — 상한 규칙을 옮겨 와야 하고, 저장본에서는 **저장 당시 사용률**이어야 하는데 화면 계산은 지금 목표를 쓴다 |
| 패키지를 **둘로** 나눈다 (009~011 은 하나였다) | **부모가 없는 화면 둘**이다. 모달이 없어 한쪽이 다른 쪽 위에 얹히지 않고, 실패 착지도 각자의 화면이다 | **하나로 둔다** — 목표와 통계는 다루는 것이 다르고, 한 패키지에 두면 「저장」이 세 가지(기본 목표·월별 목표·통계)로 나란히 놓여 어느 것인지 읽어서 세야 한다 |
