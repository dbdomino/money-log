## 이 기능의 핵심 개념

**목록 하나 + 모달 셋**이 두 벌이다. 수단과 지출유형이 같은 모양이라 007 의 모달 셸·확인 다이얼로그를 그대로 쓴다. 이 스펙이 **그 패턴을 처음 실제 화면으로 세우는 곳**이라, 여기서 정한 모양을 010~012 가 따라간다.

**삭제가 진짜 삭제가 아니다.** 둘 다 **삭제 표시**이며 행은 남는다. 그래서 관리 목록에는 계속 보이고, 지출·소득 입력 화면의 "사용 중" 목록에서만 빠진다. 화면이 이 차이를 드러내지 않으면 사용자는 "지웠는데 왜 아직 보이나"로 읽는다.

**수단에는 용도가 있다.** 지출용·소득용 중 하나이며 **등록 시 필수**다. 그리고 **그 수단을 쓴 거래가 하나라도 있으면 바꿀 수 없다** — 바꾸면 과거 지출이 소득 수단을 가리키게 된다.

**지출유형은 아이콘을 갖는다.** 허용 형식 셋과 크기 한도가 있으며 서버가 **확장자가 아니라 파일 내용으로** 판정한다. 브라우저가 백엔드를 직접 부르지 않고 007 이 만든 중계를 거쳐 받는다.

**기본 지출유형은 손댈 수 없는 데가 있다.** 가입할 때 자동으로 생기며 **이름을 바꿀 수 없고 삭제할 수 없다.** 사용 여부는 바꿀 수 있다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 지출·소득 수단을 관리한다 (Priority: P1) 🎯 MVP

카드·계좌를 등록하고 목록에서 보고 고치고 지운다.

**Why this priority**: 수단이 없으면 지출도 소득도 등록할 수 없다. 010·011 이 이 화면에서 만든 수단을 고른다.

**Independent Test**: 수단을 만들고 목록에서 확인한 뒤 고치고 지우는 한 바퀴로 완결된다. 지출유형 없이 확인된다.

**Acceptance Scenarios**:

1. **Given** 수단 목록에서, **When** 등록 모달을 열어 이름·구분·용도·사용 여부를 채워 저장하면, **Then** 목록에 나타난다
2. **Given** 등록 모달에서, **When** 구분을 카드로 고르면, **Then** 유효기간 입력란이 보이고 계좌로 고르면 사라진다
3. **Given** 용도를 고르지 않고, **When** 저장하면, **Then** 저장되지 않고 그 칸을 채우라는 안내가 뜬다
4. **Given** 목록의 한 행에서, **When** 상세 모달을 열면, **Then** 값이 읽기 전용으로 보인다
5. **Given** 그 수단으로 등록한 지출이 있을 때, **When** 용도를 바꿔 저장하면, **Then** 사용 내역이 있어 바꿀 수 없다는 사유가 표시된다
6. **Given** 수단 하나를, **When** 확인 후 삭제하면, **Then** **과거 내역의 수단 이름은 유지된다**는 안내를 보고, 목록에는 삭제 표시로 남는다
7. **Given** 이미 삭제 표시된 수단을, **When** 다시 삭제하면, **Then** 이미 삭제된 수단이라는 사유가 표시된다

---

### User Story 2 - 지출유형을 관리한다 (Priority: P1)

지출유형을 만들고 아이콘을 붙이고 고치고 지운다.

**Why this priority**: 지출 등록에 유형이 **하나 필수**다. 010 이 이 화면에서 만든 유형을 고르고, 012 가 유형별 목표를 정한다.

**Independent Test**: 유형을 만들고 아이콘을 올려 목록에 이미지가 뜨는지 보고, 기본 유형이 보호되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 지출유형 목록에서, **When** 등록 모달을 열어 이름·사용 여부·아이콘을 채워 저장하면, **Then** 목록에 아이콘과 함께 나타난다
2. **Given** 아이콘을 고르면, **When** 파일을 선택하면, **Then** 저장 전에 미리보기가 보인다
3. **Given** 1MB 를 넘거나 허용되지 않는 형식의 파일로, **When** 저장하면, **Then** 거절되고 **허용 형식과 크기가 함께** 안내된다
4. **Given** 이미 쓰이는 이름으로, **When** 저장하면, **Then** 이미 쓰이는 이름이라는 사유가 표시되며 — **삭제 표시된 유형의 이름도 겹침으로 센다**는 것이 함께 안내된다
5. **Given** 가입 때 생긴 기본 유형을, **When** 이름을 바꾸려 하면, **Then** 화면이 그 칸을 **미리 잠가 두어** 바꿀 방법이 없다
6. **Given** 기본 유형을, **When** 삭제하려 하면, **Then** 삭제 버튼 자체가 없어 시도할 방법이 없다
7. **Given** 그 유형을 쓴 지출이 있을 때, **When** 삭제하면, **Then** 거절되고 **「사용 안 함으로 돌리라」는 대안**이 함께 뜬다
8. **Given** 아이콘이 없는 유형은, **When** 목록에 보이면, **Then** 이미지 자리가 깨지지 않고 대체 표시가 나온다

### User Story 3 - 목록에서 상태를 구분해 본다 (Priority: P2)

사용 중인 것과 사용하지 않는 것, 삭제 표시된 것을 한 목록에서 구분한다.

**Why this priority**: 삭제 표시 모델을 사용자가 이해하는 유일한 통로다. 다만 CRUD 가 먼저 서야 한다.

**Independent Test**: 사용 안 함으로 바꾸고 삭제도 해 본 뒤 목록에서 셋이 구분되는지 본다.

**Acceptance Scenarios**:

1. **Given** 사용 안 함으로 바꾼 수단이, **When** 관리 목록에 보이면, **Then** 사용 중이 아님이 표시된다
2. **Given** 삭제 표시된 수단이, **When** 관리 목록에 보이면, **Then** **목록에 남아 있고** 삭제됨이 표시된다
3. **Given** 사용 안 함과 삭제됨이, **When** 한 행에 함께 보이면, **Then** **서로 다른 열**에 표시되어 되돌릴 수 있는 것과 없는 것이 구분된다
4. **Given** 수단 목록과 지출유형 목록을, **When** 나란히 보면, **Then** 두 화면이 **같은 말**로 상태를 표시한다

**선택 목록은 이 스토리의 범위 밖이다.** 삭제·사용 안 함인 항목이 지출·소득 입력에서 고를 수 없게 되는 것은 **별도 API 가 하는 일**이며 010·011 이 그 화면을 만들 때 확인한다. 009 는 관리 목록만 만들고, 그 경계를 [contracts/list-modal.md](./contracts/list-modal.md) §2 에 남긴다 — 적지 않으면 010 을 맡은 사람이 이 목록을 그대로 재사용하고, 그러면 삭제한 항목이 지출 등록에서 다시 고를 수 있게 된다.

---

### Edge Cases

- **아이콘 파일을 바꾸지 않고 이름만 고치면?** 기존 아이콘이 그대로 남아야 한다. 파일 칸을 비운 것이 "아이콘을 지우라"는 뜻이 되면 안 된다.
- **확장자만 허용 형식으로 바꾼 파일이면?** 서버가 **파일 내용으로** 판정해 거절한다. 화면의 파일 선택 필터는 고르기를 돕는 장치일 뿐 검사가 아니다.
- **삭제 표시된 유형에 아이콘이 남아 있으면?** 행이 남으므로 아이콘도 계속 보인다.
- **남의 수단·유형을 가리키는 주소로 모달을 열면?** 없는 것과 같은 사유가 오며 **존재 여부가 드러나지 않는다.** 모달 없이 목록만 남긴다.
- **상세 모달 주소에 없는 대상을 넣으면?** 모달이 빈 채로 열리지 않고 실패 사유를 보인 뒤 목록만 남는다.

## Requirements *(mandatory)*

### Functional Requirements

**수단 (US1)**

- **FR-801**: 수단 등록은 이름·구분(카드 또는 계좌)·**용도(지출용 또는 소득용)**·사용 여부를 필수로 받아야 한다. 구분·용도·사용 여부는 **고를 수 있는 값만** 두고 자유 입력을 두지 않는다
- **FR-802**: 구분이 카드일 때만 유효기간 입력란을 보여야 하며, 계좌면 보내지 않아야 한다
- **FR-803**: 수단 수정에서 **용도는 그 수단을 쓴 거래가 없을 때만** 바뀌어야 한다. 거절당하면 「사용 내역이 있어 용도를 바꿀 수 없습니다」를 **용도 칸 가까이** 보이고, 사용자가 고른 값을 그대로 둔다
- **FR-804**: 수단 삭제는 확인 다이얼로그를 거치고 **"과거 내역의 수단 이름은 그대로 남는다"**를 함께 알려야 한다
- **FR-805**: 이미 삭제 표시된 수단을 다시 지우려 하면 그 사유를 알려야 한다. 오류 화면으로 보내지 않는다

**지출유형 (US2)**

- **FR-806**: 지출유형 등록은 이름·사용 여부를 필수로, 아이콘을 선택으로 받아야 한다
- **FR-807**: 아이콘 파일을 고르면 **저장 전에 미리보기**를 보여야 한다
- **FR-808**: 아이콘의 허용 형식과 크기 한도를 **입력 전에** 안내하고, 거절당하면 그 제약을 **다시** 알려야 한다
- **FR-809**: 아이콘 파일을 고르지 않은 수정은 **기존 아이콘을 유지**해야 한다
- **FR-810**: 이름 중복을 알릴 때 **삭제 표시된 유형의 이름도 겹침으로 센다**는 점을 함께 알려야 한다
- **FR-811**: 기본 지출유형은 **이름 입력란을 잠그고 삭제 버튼을 그리지 않아야** 한다. 주소로 직접 들어와 시도한 경우에는 서버가 준 사유를 보인다 — 화면이 막는 것과 서버가 막는 것은 서로를 대신하지 않는다
- **FR-812**: 사용 중인 유형의 삭제가 거절되면 **「사용 안 함으로 돌리라」는 대안**을 함께 제시해야 한다
- **FR-813**: 아이콘이 없는 유형은 이미지 자리가 깨지지 않도록 대체 표시를 보여야 한다
- **FR-814**: 아이콘은 **007 이 만든 화면 모듈의 중계**로 불러야 한다. 백엔드 주소를 이미지에 직접 걸지 않는다 — 인증이 붙지 않아 전부 실패한다

**목록·모달 공통 (US3)**

- **FR-815**: 관리 목록은 **삭제 표시된 것을 포함**해 보여야 하며, 사용 여부와 삭제 여부를 구분해 표시해야 한다
- **FR-816**: 등록·상세·수정은 목록 위 **모달**이며, 목록 주소에 어느 모달인지와 대상을 실어 **주소로도 곧바로 열 수 있어야** 한다
- **FR-817**: 상세 모달은 읽기 전용이며 거기서 수정 모달로 넘어갈 수 있어야 한다
- **FR-818**: 없는 대상이나 남의 대상으로 모달을 열면 **빈 모달을 띄우지 말고** 사유를 알린 뒤 목록만 남겨야 한다

### 실패를 다루는 방식

**화면 모듈은 새 실패 코드를 정의하지 않는다.** 백엔드가 준 코드를 그대로 받아 화면에 맞게 보여줄 뿐이다(007 FR-607).

- 폼에서 난 실패는 **그 모달을 연 채로** 부모 목록을 다시 그린다. 모달을 닫아 버리면 사용자가 채운 칸이 전부 사라진다.
- 어느 칸이 문제인지 아는 실패는 **그 칸 가까이**, 가릴 수 없는 실패는 **모달 폼 상단**에 붙인다.
- **삭제에서 난 실패는 목록의 안내로** 보인다. 삭제에는 폼이 없고 확인 다이얼로그만 있으며, 이미 원하는 상태이거나 대안이 있는 경우라 오류 화면으로 보낼 이유가 없다.
- **모달을 열기 전 조회가 실패하면** 모달 없이 목록만 보이고 사유를 띄운다. 낡은 북마크일 뿐이고 목록은 정상이다.
- 백엔드에 닿지 못한 경우는 반대로 007 의 오류 화면으로 간다. 사용자가 할 수 있는 일이 다르다.

어떤 코드가 어느 칸과 화면에 걸리는지는 [contracts/list-modal.md](./contracts/list-modal.md) §4 가 표로 정한다.

### Key Entities

- **지출·소득 수단**: 이름 · 구분(카드/계좌) · **용도**(지출용/소득용) · 사용 여부 · 삭제 여부 · 카드 유효기간. 삭제해도 행이 남는다
- **지출유형**: 이름 · 사용 여부 · 삭제 여부 · 기본 유형 여부 · 아이콘. 기본 유형은 이름 변경·삭제가 막힌다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-801**: 수단·지출유형 각각을 **모달 한 번**으로 만들고 목록에서 바로 확인한다
- **SC-802**: 삭제 표시한 항목이 **관리 목록에는 남고**, 사용 여부와 **다른 열**로 구분되어 보인다. 선택 목록에서 빠지는 것은 010·011 이 확인한다
- **SC-803**: 용도를 바꿀 수 없는 수단에서 사용자가 **왜 막혔는지** 화면에서 읽는다
- **SC-804**: 기본 지출유형에서 이름 변경·삭제를 시도할 방법이 화면에 없다
- **SC-805**: 아이콘이 있는 유형과 없는 유형이 목록에서 모두 깨지지 않게 보인다
- **SC-806**: 허용되지 않는 아이콘 파일을 올렸을 때 사용자가 **무엇이 허용되는지** 안다
- **SC-807**: 브라우저가 아이콘을 받을 때 백엔드 주소로 직접 요청하지 않는다
- **SC-808**: 화면 8개의 실패가 모두 **서버가 준 응답 코드와 안내 문구**로 사용자에게 전달된다

## Assumptions

- **007 이 이미 서 있다.** 모달 셸·확인 다이얼로그·아이콘 경로·API 클라이언트를 그대로 쓴다
- **백엔드 003 의 수단·지출유형 API 가 동작한다.** 009 는 관리 화면이 쓰는 11건을 부르고, **사용 중 목록 2건은 010·011 의 선택 목록이 부른다.** 백엔드 코드와 스키마는 바뀌지 않는다. 어느 화면이 무엇을 부르는지는 [contracts/](./contracts/) 가 정한다
- **화면기획 프로토타입을 그대로 옮긴다** — 두 목록이 이미 그려져 있고 폼의 칸 이름도 백엔드 계약에 맞춰져 있다. 다만 **상태 열과 삭제 버튼이 빠져 있어** 그대로 옮기면 지울 방법이 없는 목록이 된다
- **이 스펙이 목록+모달 패턴의 기준이 된다.** 010~012 가 같은 모양을 따른다
- **아이콘 파일명 형식에 화면이 의존하지 않는다.** 서버가 준 경로를 그대로 쓴다
