# Contract: 엑셀 일괄 등록 (3.5)

**Feature**: 010-frontend-ledger-expense-income | **관련 FR**: 924~928

| 항목 | 값 |
|---|---|
| 주소 | `/ledger/excel` |
| 껍데기 | 007 의 **로그인 후** 레이아웃 |
| 사이드바 활성 메뉴 | `excel` |
| 권한 | 로그인 |
| 부르는 API | `ExpenseIncomeExcelTemplateDownload` · `ExpenseIncomeExcelUpload` |

**같은 지출·소득을 다른 입구로 넣는 화면이다.** 한 건씩 넣는 길(3.1·3.3)이 있으면 없어도
되지만, 과거 기록을 옮길 때 쓴다.

```
받기:  브라우저 ──주소──> 화면 모듈 ──인증+조회──> 백엔드 ──파일──> 브라우저
올리기: 브라우저 ──파일──> 화면 모듈 ──파일──> 백엔드
```

**어느 방향으로도 브라우저가 백엔드를 직접 부르지 않는다.** 009 의 아이콘과 같은 규칙이다.

---

## 1. 양식 받기

| 단계 | 하는 일 |
|---|---|
| ① | 브라우저가 **화면 모듈 주소**의 링크를 누른다 |
| ② | 화면 모듈이 세션의 인증을 실어 백엔드에서 파일을 받는다 |
| ③ | 받은 바이트를 **파일 이름과 형식 그대로** 흘려보낸다 |

**백엔드 주소를 링크에 직접 걸지 않는다**(`FR-924`). 양식 받기에도 인증이 필요한데 브라우저의
링크는 인증을 붙이지 못한다 — 007 이 파일 응답을 받는 통로를 만들며 **"아이콘·엑셀 두 호출"**
이라고 적어 둔 그 자리다.

**받은 파일 이름을 그대로 넘긴다.** 화면이 이름을 지어내면 백엔드가 양식을 바꿀 때 파일
이름만 옛것으로 남는다.

**실패하면 오류 화면으로 간다.** 아이콘과 다른 점이다 — 아이콘은 화면 한 귀퉁이가 비는
것으로 끝나지만, 양식을 못 받으면 사용자가 이 화면에서 할 수 있는 일이 없다.

---

## 2. 올리기 전에 막는 것

| 검사 | 누가 | 무엇을 |
|---|---|---|
| 형식 | 브라우저 | 파일 선택 필터를 **`.xlsx` 하나로** 둔다 |
| 형식 | **서버** | 확장자가 아니라 내용으로 판정한다 |
| 행 수 | 브라우저 | **크기로 가늠해 경고**한다 |
| 행 수 | **서버** | 정확히 세어 300행 초과를 거절한다 |

**앞에서 막는 것이 검사를 대신하지 않는다.** 브라우저가 행 수를 정확히 세려면 파일을 파싱해야
하는데 그것은 화면이 할 일이 아니다. 009 의 아이콘에서 정한 것과 같은 규칙이다 — **파일 선택
필터는 고르기를 돕는 장치일 뿐 검사가 아니다.**

**경고는 막는 것이 아니라 알리는 것이다**(`FR-926` · `SC-908`). 가늠이 틀릴 수 있으므로 사용자가
그래도 올리겠다면 보낸다. 정확한 판정은 서버가 한다.

**프로토타입의 파일 필터가 `.xls` 를 함께 허용하고 있다.** 백엔드는 `.xlsx` 만 받으므로
고친다(`FR-925`).

---

## 3. 결과는 성공과 실패의 모양이 다르다

### 성공

| 보이는 것 |
|---|
| 등록된 전체 건수 · 지출 건수 · 소득 건수 |

**가계부로 가는 길을 함께 둔다.** 올린 것이 실제로 들어갔는지 확인할 자리가 있어야 한다.

### 행 오류

| 보이는 것 |
|---|
| **표** — 행 번호 · 열 · 사유 |

**표로 보인다**(`FR-927` · `SC-907`). 칸 하나짜리 폼이라 붙일 칸이 없고, 오류가 여럿이라 한
줄로 보일 수 없다.

**행 번호 순으로 보인다.** 사용자가 엑셀을 열어 위에서부터 고치기 때문이다.

**한 행이라도 틀리면 전체가 등록되지 않는다.** 백엔드가 그렇게 정했다 — 화면이 "몇 건은
들어갔다"고 말하지 않는다. 그 사실을 표 위에 적는다.

행 오류로 오는 코드는 **`3502`** 하나다. 이 코드만 응답 본문에 **구조를 가진 실패**를 함께
싣는다 — 행 번호·열·사유의 목록이다. 나머지는 코드와 문구 하나로 끝난다.

| 코드 | 뜻 | 보이는 것 |
|---|---|---|
| `3502` | 업로드 파일에 잘못된 행이 있음 | **결과 영역의 표.** 폼 상단이 아니다 |

### 그 밖의 실패

| 코드 | 뜻 | 보이는 것 |
|---|---|---|
| `3503` | `.xlsx` 가 아님 | 폼 상단에 사유와 **허용 형식** |
| `3504` | 300행 초과 | 폼 상단에 사유와 **한도** |
| `3505` | 빈 파일 | 폼 상단 |
| `9001` | 필수 누락 | 폼 상단 |

**거절 안내에 제약을 다시 적는다.** 009 의 아이콘과 같다 — 무엇이 허용되는지 모른 채 다른
파일을 시도하게 두지 않는다.

---

## 4. 중복 행에 경고하지 않는다

**그대로 등록되는 것이 계약이다**(`FR-928`). 화면이 임의로 막으면 같은 금액을 두 번 쓴
사용자가 기록하지 못한다.

같은 날 같은 금액을 두 번 쓰는 일은 흔하다 — 커피를 두 번 사는 것이 그렇다.

---

## 5. 실패한 응답에서 행 오류를 꺼내려면

**007 의 실패 예외에 봉투의 값을 통째로 실어야 한다**(research 1). 지금은 응답 코드와 문구
하나만 올라와 행 오류가 화면에 닿지 않는다.

**화면이 백엔드를 따로 부를 수도 없다** — 실패한 그 요청의 응답에만 들어 있는 값이다.

이것은 007 의 구멍이며 009 의 수정+파일 통로와 같은 성격이다. 근거는
[plan.md](../plan.md) 의 Complexity Tracking 에 있다.

| 행 오류 표 위에 **전체가 등록되지 않았다**가 적혀 있다 | §3 |
| `3503`·`3504` 안내에 허용 형식과 한도가 적혀 있다 | §3 |
| 중복 행에 별도 경고가 **없다** | FR-928 |
