# Contract: 지출·소득 모달 (3.1~3.4)

**Feature**: 010-frontend-ledger-expense-income | **관련 FR**: 908~917 · 922~923

| 화면 | 주소 | 표시 |
|---|---|---|
| 3.1 지출 등록 | `/ledger?m=expense-create` | 가계부 위 모달 |
| 3.2 지출 수정 | `/ledger?m=expense-edit&id={식별자}` | 가계부 위 모달 |
| 3.3 소득 등록 | `/ledger?m=income-create` | 가계부 위 모달 |
| 3.4 소득 수정 | `/ledger?m=income-edit&id={식별자}` | 가계부 위 모달 |

| 항목 | 값 |
|---|---|
| 부모 페이지 | 5.1 `/ledger` |
| 사이드바 활성 메뉴 | `ledger` (넷 모두) |
| 권한 | 로그인 |
| 부르는 API | `PaymentMethodListActive` · `ExpendGroupListActive` · `ExpenseCreate` · `ExpenseCreateInstallment` · `ExpenseGet` · `ExpenseUpdate` · `ExpenseDelete` · `ExpenseSettleInstallmentRemainder` · `IncomeCreate` · `IncomeGet` · `IncomeUpdate` · `IncomeDelete` |

목록 위에 모달이 얹히는 공통 모양은
[009 의 list-modal 규약](../../009-frontend-payment-expend-group/contracts/list-modal.md)을
그대로 따른다. 여기서는 **지출·소득에만 있는 것**을 적는다.

**넷 모두 목록 주소에 어느 모달인지와 대상을 실어 연다**(`FR-908`). 별도 주소를 갖지 않으며,
부모 목록이 함께 그려지고 그 위에 열린다.

**009 와 다른 점이 하나 있다.** 모달 값이 `create`·`edit` 둘이 아니라 **자원별로 넷**이다 —
한 부모에 두 자원이 얹히기 때문이다.

| 화면이 아는 모달 값 |
|---|
| `expense-create` · `expense-edit` · `income-create` · `income-edit` |

**상세 모달이 없다.** 009 와 달리 목록에 이미 값이 다 보여 따로 읽을 자리가 필요 없다.

---

## 1. 선택 목록은 관리 목록이 아니다

| 칸 | 채우는 곳 |
|---|---|
| 지출 모달의 수단 | 사용 중 수단 목록 — **지출용** |
| 소득 모달의 수단 | 사용 중 수단 목록 — **소득용** |
| 지출 모달의 지출유형 | 사용 중 지출유형 목록 |

009 의 관리 목록에는 **삭제 표시된 것과 사용 안 함이 함께** 들어 있다. 그것을 선택지로 쓰면
사용자가 지운 수단으로 지출을 등록하게 된다(`FR-909`). 009 가 계약에 못 박아 둔 경계다.

**용도를 섞지 않는다.** 지출에 소득 수단이 뜨면 고른 순간 백엔드가 용도 불일치로 거절하고,
사용자에게는 자기가 고른 것이 거절된 것으로 보인다.

**지출유형은 하나 필수다**(`FR-910`). 비우고 저장할 수 없다.

---

## 2. 지출 등록은 나가는 통로가 둘이다 (3.1)

| 칸 | 필수 | 일시불 | 할부 |
|---|:---:|:---:|:---:|
| 수단 | ✅ | ✅ | ✅ |
| 지출유형 | ✅ | ✅ | ✅ |
| 결제일 | ✅ | ✅ | — |
| 장소 | ✅ | ✅ | ✅ |
| 내용 | ✅ | ✅ | ✅ |
| **금액** | ✅ | **금액** | — |
| **월 납부액** | ✅ | — | **있다** |
| 개월 수 | ✅ | — | **있다** (2 이상) |
| 시작 연월 | ✅ | — | **있다** `YYYY-MM` |

**금액 칸의 이름이 다르다.** 일시불 폼 그대로 할부를 보내면 형식 오류다.

### 한 모달에 두 벌을 두고 토글로 접는다

**일시불과 할부를 토글로 고르고, 할부를 고르면 개월 수·월 납부액·시작 연월 칸이 나타난다**
(`FR-911`). 모달을 둘로 나누지 않는 이유는 사용자에게 **"지출 하나를 넣는 일"** 이기 때문이다.
나누면 등록 버튼이 둘이 되어 무엇을 고를지 먼저 판단해야 한다.

| 누가 | 무엇을 |
|---|---|
| 브라우저 | 토글에 따라 칸을 **접고 편다**. 입력 중의 편의다 |
| 화면 모듈 | 고른 값을 보고 **통로 자체를 가른다**. 보장이다 |

009 의 카드 유효기간과 같은 구조다. 스크립트가 막힌 환경에서 토글이 접히지 않아도 화면
모듈이 올바른 통로로 보낸다(`FR-912`).

---

## 3. 할부 수정은 두 칸이 잠긴다 (3.2)

| 칸 | 할부 건에서 |
|---|---|
| 개월 수 | **읽기 전용** |
| 시작 연월 | **읽기 전용** |
| 금액 · 결제일 · 수단 · 유형 · 장소 · 내용 | 고칠 수 있다 |

**화면이 미리 막는다**(`FR-913` · `SC-905`). 목록 응답이 할부인지 알려 주므로 고칠 수 없는
칸을 열어 두고 저장에서 실패시킬 이유가 없다. 009 의 기본 지출유형 이름과 같은 자리다.

**그래도 서버 실패를 함께 다룬다.** 주소를 직접 쳐서 올 수 있고, 화면이 막는 것과 서버가
막는 것은 서로를 대신하지 않는다.

**바꾸려면 지우고 다시 등록하라고 안내한다.** 그 길이 있다는 것을 적지 않으면 사용자는
막혔다고만 읽는다 — 009 의 「사용 안 함으로 돌리라」와 같은 성격의 대안 제시다.

**금액을 고치면 그 회차 하나만 바뀐다.** 할부 전체가 아니다.

---

## 4. 소득 모달에는 없는 칸이 둘이다 (3.3 · 3.4)

| 칸 | 필수 |
|---|:---:|
| 수단 | ✅ |
| 금액 | ✅ |
| 결제일 | ✅ |
| 내용 | ❌ |

**지출유형과 장소 칸이 없다**(`FR-914`). 백엔드가 그 칸을 받지 않는다 — 두면 사용자가 채운
값이 조용히 버려진다.

**할부 토글도 없다.** 소득에 할부라는 개념이 없다.

## 5. 삭제와 중도상환

### 삭제

| 항목 | 내용 |
|---|---|
| 부르는 곳 | 목록 행의 「삭제」. **고정지출 행에는 그리지 않는다** |
| 확인 | 007 의 공통 확인 다이얼로그 (`FR-915`) |
| 보내는 방법 | `POST`. 화면 모듈이 백엔드의 삭제 요청으로 옮긴다 |
| 본문에 담을 것 | ① 대상이 무엇인지(일자·금액·내용) ② **되돌릴 수 없다**는 것 ③ 합계에서도 빠진다는 것 |

### 중도상환

| 항목 | 내용 |
|---|---|
| 부르는 곳 | **할부 행에만** 있는 「중도상환」 (`FR-922`) |
| 확인 | 007 의 공통 확인 다이얼로그 (`FR-923`) |
| 보내는 방법 | `POST`. 본문 없이 보낸다 |
| 본문에 담을 것 | ① 어느 할부인지 ② **남은 회차가 한 번에 정리된다**는 것 ③ **되돌릴 수 없다**는 것 |

**수정 모달 안에 넣지 않는다**(research 7). 그 지출 한 건을 고치는 일이 아니라 여러 회차를
함께 바꾸는 일이라, 금액을 고치러 들어갔다가 할부 전체가 정리되는 사고가 난다.

**정리할 회차가 없으면** 오류 화면이 아니라 목록의 안내로 보인다. 이미 다 낸 할부이고
사용자가 할 일이 없다.

## 6. 실패가 붙는 칸

008·009 의 규약을 따른다 — 어느 칸인지 아는 실패는 그 칸 아래, 가릴 수 없는 실패는 모달 폼
상단, 모달 제출 실패는 **모달을 연 채로** 부모 목록을 다시 그린다.

| 코드 | 뜻 | 붙는 칸 | 화면 |
|---|---|---|---|
| `3003` | 수단 없음 · 타인 · 사용 안 함 · 삭제됨 · **용도 불일치** | **수단 칸** | 3.1~3.4 |
| `3103` | 지출유형 없음 · 타인 · 사용 안 함 · 삭제됨 | **지출유형 칸** | 3.1 · 3.2 |
| `3201` | 지출 값 오류 — 금액 0 이하 · 날짜 형식 · 장소 100자 · 내용 255자 초과 | **모달 폼 상단** | 3.1 · 3.2 |
| `3202` | 지출을 찾을 수 없음 | 목록 안내 (모달 없이) | 3.2 |
| `3203` | 할부 개월 수 · 시작 연월 변경 시도 | **개월 수 칸** | 3.2 |
| `3204` | 할부 개월 수 · 금액 오류 | **개월 수 칸** | 3.1 |
| `3207` | 정리할 남은 할부가 없음 | 목록 안내 | 5.1 |
| `3301` | 소득 값 오류 | 모달 폼 상단 | 3.3 · 3.4 |
| `3302` | 소득을 찾을 수 없음 | 목록 안내 (모달 없이) | 3.4 |
| `9001` | 필수 누락 · 형식 오류 | 모달 폼 상단 | 전부 |

**`3003` 이 수단 칸인 이유**는 그 코드가 가리키는 것이 언제나 수단 하나이기 때문이다. 없는
것인지 용도가 안 맞는 것인지는 가르지 않는다 — 백엔드가 존재를 감추려고 묶은 코드이고,
사용자가 할 일은 어느 쪽이든 **다른 수단을 고르는 것**이다.

**`3201` 이 상단인 이유**는 한 코드가 금액·날짜·장소·내용 네 칸을 함께 가리키기 때문이다.
어느 칸인지 코드만으로 가릴 수 없으므로 짐작하지 않는다.

**없는 대상은 모달을 열지 않는다**(`FR-916`). 빈 모달을 띄우지 말고 목록만 남긴다. 없는
것과 남의 것을 가르지 않는다.

## 7. 시험으로 고정할 것

| 항목 | 근거 |
|---|---|
| 선택 목록이 **사용 중 목록 API** 로 채워진다 | FR-909 |
| 지출 모달은 지출용, 소득 모달은 소득용 수단을 부른다 | FR-909 |
| 할부를 고르면 **다른 통로**로 나가고 금액 칸 이름이 다르다 | FR-912 · SC-904 |
| 토글이 막혀도 고른 값대로 통로가 갈린다 | research 5 |
| 할부 수정에서 개월 수·시작 연월이 **잠겨 있다** | FR-913 · SC-905 |
| 잠긴 이유와 **지우고 다시 등록하라는 대안**이 적혀 있다 | §3 |
| 소득 모달에 **지출유형·장소 칸이 없다** | FR-914 |
| 없는 대상으로 모달을 열면 **목록만** 남는다 | FR-916 |
| 삭제·중도상환이 **`POST`** 이고 확인 다이얼로그를 거친다 | FR-915 · FR-923 |
| 중도상환 확인 본문에 **되돌릴 수 없다**가 적혀 있다 | FR-923 |
| `3003` 이 수단 칸, `3103` 이 지출유형 칸에 붙는다 | §6 |
| 모달 제출 실패가 모달을 연 채로 돌아온다 | 009 list-modal §4 |
