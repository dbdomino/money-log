## Phase 2: Foundational (Blocking Prerequisites)

**Purpose**: 화면 6개가 공통으로 밟는 장치. **여기가 끝나기 전에는 어떤 스토리도 시작할 수 없다**

- [ ] T008 [P] `.../front/ledger/LedgerRow.java` — 화면이 보여 주는 가계부 행(종류·원본 식별자·결제일·금액·수단 이름·지출유형 이름·장소·내용·고정지출 이름·할부 그룹·회차). **종류를 말로 바꾸는 자리를 여기 둔다**. **비는 칸에 값을 지어내지 않는다**(data-model §1.1) — 소득에는 지출유형과 장소가 없고, 「없음」 같은 말을 채우면 "비어 있는 값"과 "없는 항목"이 구분되지 않는다. **행 종류로 열 수 있는 것을 가리는 판단**(수정·삭제·중도상환)도 여기 둔다
- [ ] T009 [P] `.../front/ledger/LedgerMonth.java` — 월 요약(지출 합계·소득 합계)과 목록을 담는다. **잔액은 두 값을 빼서 만들되 화면이 목록을 다시 더하지 않는다**(data-model §2) — 더해 맞추면 "필터를 걸었는데 이번 달 지출이 줄어드는" 화면이 되고 사용자는 자기가 쓴 돈이 줄었다고 읽는다
- [ ] T010 [P] `.../front/ledger/LedgerQuery.java` — 연·월과 필터를 **주소에서 읽고 다시 주소로 만든다**(data-model §4). 양방향인 이유는 목록·모달·연월 이동이 모두 그 값을 실어 나르기 때문이다. 이 단계에서는 **연·월만** 다룬다 — 필터 여섯은 US3 이 넓힌다. **주소에 연·월이 없으면 이번 달이고 서버 시각으로 정한다**(FR-901) — 브라우저 시각을 믿으면 시차가 있는 사용자가 다른 달을 본다
- [ ] T011 [P] `.../templates/fragments/ledger-badge.html` — 행 종류를 그리는 뱃지 조각. 지출·할부·소득·고정지출 넷이며 프로토타입이 쓰던 네 가지 모양을 그대로 쓴다. **조각으로 두는 이유**는 011·012 의 화면도 같은 종류를 보이기 때문이다 — 화면마다 만들면 같은 종류가 다른 색으로 보인다
- [ ] T012 `.../front/ledger/LedgerPageModel.java` — 목록·합계·필터·모달 값을 **모델에 담는 한 자리**. 컨트롤러 넷이 함께 쓴다(plan § Structure Decision). 실패 착지도 목록을 다시 그려야 하는데, 복사하면 **한쪽만 고친 차이가 화면에 남는다** — 지출 모달에서 실패했을 때와 소득 모달에서 실패했을 때 목록이 달라 보이는 식이다

**Checkpoint**: 구조를 가진 실패가 화면까지 오고, 행·요약·주소·뱃지를 네 컨트롤러가 같은 방식으로 쓸 수 있다

### Implementation for User Story 1

- [ ] T016 [US1] `.../front/ledger/LedgerController.java` 의 목록 — `GET /ledger` 가 `LedgerQuery` 로 연·월을 읽어 백엔드 월별 가계부를 부른다. **조회 구간을 싣지 않는다** — 한 달치를 전부 받고 합계가 함께 온다. 사이드바 활성 메뉴로 `ledger` 를 담는다. **응답이 비어 와도 빈 목록과 합계 0 으로 그린다** — 여기서 터지면 로그인 직후 착지가 오류 화면이 된다

- [ ] T018 [US1] T017 에 **상단 요약과 빈 달 안내**를 더한다 — 지출 합계·소득 합계·잔액 셋을 놓는다. 합계는 **백엔드가 준 값 그대로**이고 화면이 목록을 다시 더하지 않는다. 거래가 없으면 합계 0 과 함께 **빈 목록임을 알린다** — 목록만 비어 있으면 사용자는 불러오지 못한 것으로 읽는다
- [ ] T019 [US1] T017 에 **행별 관리 버튼**을 더한다 — 지출·소득은 수정·삭제, 할부는 거기에 중도상환, **고정지출은 아무것도 그리지 않고 고정지출 화면으로 가는 안내를 둔다**(FR-917). 여기서 지우면 그 달 내역만 사라질지 설정 전체가 사라질지 사용자가 알 수 없다 — **되돌릴 수 없는 동작의 범위가 불분명한 버튼**을 두지 않는다

## Dependencies & Execution Order

### Phase 의존

```
Phase 1 (Setup — 명세 선행 개정 · 스펙 품질 게이트)
   ↓  코드보다 반드시 먼저 (원칙 V)
Phase 2 (Foundational — 실패 예외 · 행 · 요약 · 주소 · 뱃지 · 모델 담기)
   ↓  여기가 끝나기 전에는 어떤 스토리도 시작할 수 없다
Phase 3 US1 (P1) 🎯 MVP ── 월별 가계부
   ↓  모달의 부모가 서야 열 곳이 생긴다
   ├─ Phase 4 US2 (P1) ── 지출·소득 모달
   ├─ Phase 5 US3 (P2) ── 필터
   └─ Phase 6 US4 (P3) ── 중도상환
   
Phase 7 US5 (P3) ── 엑셀        (US1 과 나란히 갈 수 있다)
   ↓
Phase 8 (Polish)
```

### 스토리 사이의 의존

| 스토리 | 다른 스토리에 의존하나 |
|---|---|
| US1 가계부 | 없다. Phase 2 만 있으면 완결된다 |
| US2 모달 넷 | **US1 이 필요하다.** 모달의 부모가 그 목록이고, 실패 착지도 목록을 다시 그린다 |
| US3 필터 | **US1 이 필요하다.** 좁힐 목록이 있어야 한다 |
| US4 중도상환 | **US1 이 필요하다.** 버튼이 목록 행에 붙는다 |
| US5 엑셀 | **없다.** 독립 페이지이며 Phase 2 의 실패 예외만 있으면 된다 |

**US5 만 US1 과 나란히 갈 수 있다.** 화면이 따로 있고 목록을 쓰지 않는다 — 사람이 나뉘면 한쪽이 가계부를, 다른 쪽이 엑셀을 맡을 수 있다.

**US2·US3·US4 는 US1 뒤에 오지만 서로는 독립이다.** 셋 다 목록 화면을 넓히지만 건드리는 자리가 다르다 — US2 는 모달, US3 은 도구줄, US4 는 행의 버튼 하나다.

## Implementation Strategy

### MVP 범위

**Phase 1 + Phase 2 + Phase 3(US1)** 이 최소 인도 단위다. 여기까지면 **로그인 뒤 착지가 처음으로 실제 화면이 된다** — 008 이 보내던 주소에 그동안 아무것도 없었다.

그 자리가 채워지는 것이 이 기능의 첫 산출물이다. 넣을 것이 아직 없어 목록이 비어 있더라도, 009 에서 만든 수단·지출유형과 011 이 만들 고정지출이 들어오면 그대로 보인다.

### 그다음

| 순서 | 스토리 | 왜 이 순서인가 |
|---|---|---|
| 2 | US2 지출·소득 모달 | 가계부에 넣을 것이 없으면 US1 이 빈 화면이다 |
| 3 | US3 필터 | 한 달 기록이 쌓이면 필요해진다 |
| 4 | US5 엑셀 | 한 건씩 넣는 길(US2)이 있으면 없어도 된다. 과거 기록을 옮길 때 쓴다 |
| 5 | US4 중도상환 | 쓰는 사람이 적고 할부 등록이 먼저 서야 한다 |

**US4 와 US5 는 둘 다 P3 이라 순서를 바꿔도 된다.** 위 순서는 "쓰는 사람이 얼마나 되는가"로 정했다 — 엑셀은 처음 옮겨 올 때 한 번 쓰지만 그 한 번이 크고, 중도상환은 할부를 쓰는 사람만 만난다.

### 병렬 인도

Phase 2 이후 사람이 둘이면 **한쪽이 US1→US2, 다른 쪽이 US5** 를 맡을 수 있다. 겹치는 파일이 없다.

셋이면 US1 이 끝난 뒤 **US2·US3·US4 로 갈린다.** 셋 다 목록 화면을 넓히지만 건드리는 자리가 달라 — 모달·도구줄·행 버튼 — 합칠 때 충돌이 적다.

## Notes

- **[P] 는 다른 파일이고 미완 작업에 기대지 않는다는 뜻이다.** 같은 파일을 넓혀 가는 작업에는 붙이지 않았다.
- **007 을 고치는 자리가 하나다**(T007). 근거는 plan.md 의 Complexity Tracking 에 있다. T052 가 그 밖의 007 파일이 바뀌지 않았는지 확인한다.
- **화면이 값을 고쳐 맞추지 않는다.** 합계는 필터와 무관하고 이름은 종류마다 규칙이 갈린다. 맞추려 들면 "필터를 걸었는데 지출이 줄어드는" 화면과 "과거 기록이 사후에 바뀌는" 화면이 된다.
- **엑셀을 화면이 파싱하지 않는다.** 행 수는 가늠해 경고하고 판정은 서버가 한다 — 파싱하면 저장 규칙이 두 곳에 생긴다.
- **고정지출 행은 읽기만 한다.** 만들고 고치는 것은 011 이다.
- **에러코드를 새로 정의하지 않는다.** 백엔드가 준 코드를 그대로 옮긴다.
- 화면이 부르는 API 15건의 주소와 칸은 `프로젝트설계/기능명세상세-백엔드/` 의 phase2·phase3·phase4 가 갖고 있다. 010 은 그것을 소비만 한다.
