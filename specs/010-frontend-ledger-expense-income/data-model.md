# Data Model: 프론트 가계부·지출·소득 화면

**Feature**: 010-frontend-ledger-expense-income | **Date**: 2026-09-14 | **Plan**: [plan.md](./plan.md)

**DB 저장 단위가 없다.** 화면 모듈은 데이터베이스를 모르고, 거래는 백엔드가 돌려주는 값을
그때그때 받아 그린다. `sql/schema-moneylogdb.sql` 은 읽지도 바꾸지도 않는다.

**세션에 더하는 상태가 없다.** 009 와 같다 — 화면 여섯이 전부 한 요청 안에서 끝난다. 연·월과
필터는 주소에 실린다.

| 갈래 | 사는 곳 | 수명 |
|---|---|---|
| 로그인 세션 | 서버 세션 | 007 이 정의한 그대로. 010 은 읽지도 쓰지도 않는다 |
| 가계부 화면의 상태 | 주소 | 그 요청 동안만 |
| 폼과 화면 값 | 요청 하나 | 그 요청 동안만 |

## 1. 가계부 행 — 한 목록에 네 종류

**저장은 세 곳에 나뉘어 있고 가계부라는 저장 단위는 없다.** 조회 시점에 합쳐서 온다.

| 값 | 타입 | 화면에서 |
|---|---|---|
| 행 식별자 | string | 목록 안에서 행을 가리킨다. 화면에 보이지 않는다 |
| 종류 | string | 지출 · 할부 · 소득 · 고정지출. **뱃지로 먼저 보인다** |
| 원본 식별자 | number | 수정·삭제 모달 주소에 싣는다. 고정지출은 연·월과 함께여야 한 행이 특정된다 |
| 결제일 | string | `YYYY-MM-DD` |
| 금액 | number | 원 단위 정수 |
| 수단 이름 | string | **고정지출만 현재 이름**, 나머지는 등록 당시 스냅샷 |
| 지출유형 이름 | string 또는 없음 | 위와 같은 규칙. **소득에는 없다** |
| 장소 | string 또는 없음 | **소득·고정지출에는 없다** |
| 내용 | string 또는 없음 | 네 종류 모두 갖는다 |
| 고정지출 이름 | string 또는 없음 | **고정지출에만** 있다 |
| 할부 그룹 | number 또는 없음 | **할부에만** 있다. 중도상환이 이 값을 쓴다 |
| 할부 회차 · 총 개월 | number 또는 없음 | **할부에만** 있다. 「3/12」처럼 보인다 |

### 1.1 비는 칸은 비워 둔다

**응답에 없는 것이 정상이다.** 화면이 「없음」 같은 말을 채우면 사용자는 "비어 있는 값"과
"없는 항목"을 구분하지 못한다.

| 종류 | 지출유형 | 장소 | 할부 회차 | 고정지출 이름 |
|---|:---:|:---:|:---:|:---:|
| 지출 | 있다 | 있다 | — | — |
| 할부 | 있다 | 있다 | **있다** | — |
| 소득 | **없다** | **없다** | — | — |
| 고정지출 | 있다 | **없다** | — | **있다** |

**뱃지가 먼저 오는 이유가 이 표다.** 종류를 알아야 그 행에 왜 빈 칸이 있는지 읽힌다.

### 1.2 행이 열 수 있는 것

| 종류 | 수정 | 삭제 | 중도상환 |
|---|:---:|:---:|:---:|
| 지출 | ✅ | ✅ | ❌ |
| 할부 | ✅ (개월·시작월 잠김) | ✅ | **✅** |
| 소득 | ✅ | ✅ | ❌ |
| 고정지출 | **❌** | **❌** | ❌ |

**고정지출 행은 읽기만 한다**(research 8). 만들고 고치는 것은 011 이며, 이 화면에서 지우면
그 달 내역만 사라질지 설정 전체가 사라질지 사용자가 알 수 없다.

## 2. 월 요약

| 값 | 타입 | 설명 |
|---|---|---|
| 지출 합계 | number | **그 달 전체.** 일반·할부·고정지출을 모두 더한 값이다 |
| 소득 합계 | number | 그 달 전체 |
| 잔액 | number | 화면이 두 값을 빼서 만든다. 응답에는 없다 |

**필터와 무관하다.** 화면이 목록을 다시 더해 맞추지 않는다 — 맞추면 "필터를 걸었는데 이번
달 지출이 줄어드는" 화면이 되고, 사용자는 자기가 쓴 돈이 줄었다고 읽는다.

**잔액도 같은 기준의 두 값을 빼는 것**이라 그 성질이 유지된다.

**거래가 없는 달은 합계가 0 이다.** 빈 목록임을 함께 알린다 — 목록만 비어 있으면 사용자는
불러오지 못한 것으로 읽는다.

## 3. 폼 — 사용자가 채우는 것

| 폼 | 화면 | 칸 |
|---|---|---|
| 지출 등록 | 3.1 | 수단 · 지출유형 · 금액 · 결제일 · 장소 · 내용 · **할부 토글** (+ 개월 수 · 월 납부액 · 시작 연월) |
| 지출 수정 | 3.2 | 위와 같되 **할부면 개월 수·시작 연월이 잠긴다** |
| 소득 등록 | 3.3 | 수단 · 금액 · 결제일 · 내용 |
| 소득 수정 | 3.4 | 위와 같다 |
| 엑셀 업로드 | 3.5 | 파일 하나 |

**소득 폼에는 지출유형과 장소가 없다**(`FR-914`). 백엔드가 그 칸을 받지 않는다 — 두면 사용자가
채운 값이 조용히 버려진다.

### 3.1 지출 등록은 나가는 통로가 둘이다

| 사용자가 고른 것 | 금액 칸 | 함께 나가는 것 |
|---|---|---|
| 일시불 | 금액 | — |
| 할부 | **월 납부액** | 개월 수 · 시작 연월 |

**한 폼에 두 벌의 칸을 두고 토글로 접는다.** 모달을 둘로 나누면 등록 버튼이 둘이 되어
사용자가 무엇을 고를지 먼저 판단해야 한다.

**접는 것은 브라우저, 통로를 가르는 것은 서버다**(research 5). 009 의 카드 유효기간과 같은
구조다.

### 3.2 선택 목록은 관리 목록이 아니다

| 칸 | 채우는 곳 |
|---|---|
| 지출 모달의 수단 | 사용 중 수단 목록 (**지출용**) |
| 소득 모달의 수단 | 사용 중 수단 목록 (**소득용**) |
| 지출 모달의 지출유형 | 사용 중 지출유형 목록 |

009 의 관리 목록에는 **삭제 표시된 것과 사용 안 함이 함께** 들어 있다. 그것을 선택지로 쓰면
사용자가 지운 수단으로 지출을 등록하게 된다(`FR-909`).

**용도를 섞지 않는다.** 지출에 소득 수단이 뜨면 고른 순간 백엔드가 용도 불일치로 거절한다.

## 4. 화면의 상태 — 주소에 들고 다닌다

**세션에 두지 않는다.** 두면 뒤로 가기와 새 탭에서 다른 목록이 뜬다.

| 값 | 기본 | 설명 |
|---|---|---|
| 연 · 월 | **이번 달** | 주소에 없으면 서버 시각으로 정한다. 브라우저 시각을 믿으면 시차가 있는 사용자가 다른 달을 본다 |
| 수단 | 없음 | 그 수단의 행만 남긴다 |
| 지출유형 | 없음 | 그 유형의 행만 남긴다 |
| 시작일 · 종료일 | 없음 | 그 달 안에서 결제일을 더 좁힌다 |
| 검색어 | 없음 | **내용과 장소** 두 칸을 본다 |
| 종류 | 없음(전부) | **여러 개를 함께** 고를 수 있다 |
| 정렬 기준 · 방향 | 결제일 · 내림차순 | |
| 열 모달 | 없음 | 등록·수정 넷 중 하나 |
| 대상 식별자 | 없음 | 수정 모달에만 쓴다 |

**연·월을 바꿔도 필터가 유지된다**(`FR-921`). 주소 방식에서 저절로 따라온다 — 연·월만 바꾼
주소를 만들면 나머지가 그대로 실린다.

**필터 결과가 0건이어도 필터를 풀지 않는다.** 사용자가 건 조건이다. 빈 목록임을 알리기만 한다.

## 5. 엑셀 업로드 결과

성공과 실패의 **모양이 다르다.**

| 결과 | 담기는 것 |
|---|---|
| 성공 | 등록된 전체 건수 · 지출 건수 · 소득 건수 |
| 실패 (행 오류) | **행 번호 · 열 · 사유**의 목록 |
| 실패 (그 밖) | 응답 코드와 문구 하나 |

**행 오류는 표로 보인다.** 칸 하나짜리 폼이라 붙일 칸이 없고, 오류가 여럿이라 한 줄로 보일
수 없다(research 15).

**한 행이라도 틀리면 전체가 등록되지 않는다.** 백엔드가 그렇게 정했다 — 화면이 "몇 건은
들어갔다"고 말하지 않는다.

**중복 행에 경고하지 않는다**(`FR-928`). 그대로 등록되는 것이 계약이며, 화면이 임의로 막으면
같은 금액을 두 번 쓴 사용자가 기록하지 못한다.

## 6. 상태 변화 — 할부

되돌릴 수 없는 전이가 하나 있어 여기만 흐름을 적는다.

```
할부 등록 (개월 수 · 시작 연월 · 월 납부액)
   │
   ├─ 회차가 달마다 목록에 나타난다
   │
   ├─ 회차 하나를 수정 ─→ 그 회차의 금액·날짜만 바뀐다
   │                      개월 수와 시작 연월은 잠겨 있다
   │
   ├─ 중도상환 ─→ 남은 회차가 한 번에 정리된다. 되돌릴 수 없다
   │               정리할 회차가 없으면 그 사유를 알린다
   │
   └─ 삭제 ─→ 그 회차가 사라진다
```

**개월 수와 시작 연월을 바꾸려면 지우고 다시 등록한다.** 그 길이 있다는 것을 화면이 적는다 —
적지 않으면 사용자는 막혔다고만 읽는다(research 6).

**중도상환은 수정 모달 안에 넣지 않는다.** 그 지출 한 건을 고치는 일이 아니라 여러 회차를
함께 바꾸는 일이라, 금액을 고치러 들어갔다가 할부 전체가 정리되는 사고가 난다.
