# Implementation Plan: 프론트 가계부·지출·소득 화면

**Branch**: `develop` (기능 브랜치를 따로 두지 않는다) | **Date**: 2026-09-14 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/010-frontend-ledger-expense-income/spec.md`

## Summary

007~009 가 세운 것 위에 **화면 6개**를 얹는다. 월별 가계부 하나와 그 위의 모달 넷, 그리고
독립 페이지인 엑셀 일괄 등록이다. 백엔드 003·004·005 의 API 15건을 부른다.

**로그인 뒤 착지가 처음으로 실제 화면이 되는 기능이다.** 008 이 로그인 성공 시 보내는 곳이
`/ledger` 였고 010 까지 서야 그 자리가 채워진다.

009 와 성격이 이어지되 넷이 새롭다.

| 축 | 009 (수단·지출유형) | 010 (가계부·지출·소득) |
|---|---|---|
| 목록 | 한 자원, 한 종류 | **한 목록에 네 종류** — 비는 칸과 이름 규칙이 종류마다 다르다 |
| 모달 | 자원 하나에 셋(등록·상세·수정) | **자원 둘에 넷**(지출·소득 × 등록·수정). 상세가 없다 |
| 필터 | 없다 | **여섯** — 수단·유형·날짜 범위·검색어·종류·정렬 |
| 파일 | 올리기만 (아이콘) | **받고 올린다.** 실패가 **구조**로 온다 |

이 네 줄이 계획의 모양을 정한다.

**① 종류가 먼저다.** 한 행에 왜 빈 칸이 있는지는 그 행의 종류가 설명한다. 뱃지를 먼저 보이고
비는 칸은 **비워 둔다** — 「없음」 같은 말을 채우면 "비어 있는 값"과 "없는 항목"이 구분되지
않는다.

**② 화면이 값을 고쳐 맞추지 않는다.** 합계는 필터와 무관하고, 이름은 종류마다 규칙이 갈린다.
둘 다 **백엔드가 준 대로 보이는 것이 맞다** — 맞추려 들면 "필터를 걸었는데 지출이 줄어드는"
화면과 "과거 기록이 사후에 바뀌는" 화면이 된다.

**③ 한 폼에서 통로가 갈린다.** 지출 등록은 일시불과 할부가 서로 다른 API 이고 금액 칸 이름도
다르다. 사용자에게는 "지출 하나를 넣는 일"이라 모달을 나누지 않고, **접는 것은 브라우저 ·
가르는 것은 서버**로 둔다.

**④ 007 의 구멍 하나를 고친다.** 엑셀 행 오류가 응답 본문에 **구조로** 오는데 007 의 실패
예외는 코드와 문구 하나만 들고 올라간다. 009 의 수정+파일 통로에 이어 두 번째다.

기술 결정 15건은 [research.md](./research.md) 에 있다.

## Technical Context

**Language/Version**: Java 17

**Primary Dependencies**: Spring Boot 4.1.0 · Spring Web MVC · Thymeleaf · Bean Validation ·
`common-mod`(에러코드 Enum 참조용). **이 기능은 의존성을 더하지 않는다.** 파일을 받고 올리는
일은 007 의 통로와 Spring Web MVC 가 이미 다룬다 — **엑셀을 파싱하지 않는다.**

007~009 에서 받아 가는 것은 코드이지 의존이 아니다 — 백엔드 호출 통로, 파일 응답 통로,
로그인 세션, 진입 판정, 레이아웃 둘, 모달 껍데기, 확인 다이얼로그, 모달 딥링크 판정, 폼 실패
착지 규약, 상태 뱃지 조각, 모달 여는 조각.

**Storage**: **없다.** 화면 모듈은 데이터베이스를 모른다. `sql/schema-moneylogdb.sql` 은
읽지도 바꾸지도 않는다. **세션에 더하는 상태도 없다** — 연·월과 필터는 주소에 실린다
([data-model.md](./data-model.md)).

**Testing**: JUnit 5 · `spring-boot-starter-test` · `spring-boot-starter-webmvc-test` ·
`MockMultipartFile`. 백엔드를 띄우지 않고 응답을 세워 화면을 검증한다. 파일을 받는 쪽은
007 의 파일 응답 타입을 세워 확인한다.

**Target Platform**: JVM 서버. 화면 `:8080`, 백엔드 `:8081`.

**Project Type**: Spring Boot 멀티모듈 — 이 기능은 프론트 모듈 하나만 손댄다.

**Performance Goals**: 정하지 않는다. 다만 **성격은 기록한다** — 가계부 목록은 한 달치를
전부 받고 합계가 함께 온다(쪽 넘기기 없음).

선택 목록은 **한 화면에 한 번만** 받아 도구줄의 필터와 모달 넷이 함께 쓴다. 수단을 용도별로
둘 다 받는 이유는 **도구줄의 수단 필터가 둘을 합쳐 쓰기 때문**이다 — 목록에 네 종류가 섞여
있어 한쪽만 놓으면 소득 행을 수단으로 거를 방법이 없다.

| 요청 | 백엔드 호출 |
|---|---|
| 목록만 (모달 없음) | **4회** — 목록 + 수단(지출용) + 수단(소득용) + 지출유형 |
| 수정 모달을 연 요청 | **5회** — 위 넷 + 대상 조회 |

도구줄과 모달이 **각자 부르면 같은 목록을 한 화면에서 두 번 받는다.** 모달을 연 채 목록을
그리는 것이 이 화면의 기본 동작이라 그 중복이 늘 일어난다.

**Constraints**:
- **007 의 공통 코드를 고치지 않는다.** 예외는 **실패 예외 한 자리**이며 그것은 007 의
  구멍이다(research 1). 그 밖의 파일은 손대지 않고 완료 판정에서 diff 로 확인한다.
- 브라우저는 **GET 과 POST 만** 쓴다. 백엔드가 요구하는 메서드로 옮기는 일은 화면 모듈이 한다.
- 화면 모듈은 **에러코드를 새로 정의하지 않는다.**
- **합계를 화면이 다시 계산하지 않는다**(FR-904 · SC-903).
- **이름을 다시 조회해 덮어쓰지 않는다**(FR-905 · SC-906).
- 선택 목록은 **사용 중 목록 API** 로만 채운다(FR-909).
- **엑셀을 화면이 파싱하지 않는다.** 행 수는 가늠해 경고하고 판정은 서버가 한다.
- 폼 실패 착지는 **008·009 의 규약을 그대로** 쓴다.

**Scale/Scope**: 화면 6개 · FR 28건(FR-901~928) · SC 9건 · User Story 5개(P1 2 · P2 1 · P3 2) ·
부르는 API 15건 · 새 에러코드 0건 · DB 테이블 0개 · 새 의존 0건 ·
**007 을 고치는 파일 2개**(실패 예외와 그것을 던지는 자리).

넷으로 나눈다.**

얹히고** 엑셀이 독립 페이지다. 한 컨트롤러에 담으면 지출과 소득의 등록·수정·삭제가 한 파일에
여덟 개 처리로 쌓인다.

| 컨트롤러 | 맡는 것 |

| `ExpenseController` | 지출 등록 · 수정 · 삭제 · 중도상환 |
| `IncomeController` | 소득 등록 · 수정 · 삭제 |
| `LedgerExcelController` | 양식 받기 · 업로드 |

**나누어도 실패 착지는 목록으로 모인다.** 세 컨트롤러가 각자 실패 선언을 두되 **같은 뷰
이름**을 돌려주고, 목록을 다시 그리는 일은 한 곳에 모아 셋이 함께 쓴다 — 복사하면 한쪽만
고친 차이가 화면에 남는다.

`LedgerQuery` 를 따로 두는 이유는 **연·월과 필터 여섯을 주소에서 읽고 다시 주소로 만드는
일이 양방향이기 때문**이다. 목록·모달·쪽 이동이 모두 그 값을 실어 나른다.
