# 아이콘 저장·조회 계약

**Feature**: `003-backend-payment-expend-group` | **Date**: 2026-09-02 | **Phase**: 1

아이콘은 이 프로젝트에서 **DB 밖에 실체가 있는 유일한 자원**이고,
2.10은 **`{ resCode, data }` 래퍼를 쓰지 않는 유일한 API**다. 두 특이점의 계약을 정한다.

---

## 1. 파일명

```text
{id_key}_{expendGroupId}.{확장자}
```

| 조각 | 출처 | 예 |
|---|---|---|
| `{id_key}` | `tbl_user`의 대리키 | `1` |
| `{expendGroupId}` | `tbl_user_expend_group.idx` | `10` |
| `{확장자}` | **업로드 파일의 실제 형식** | `png` · `jpg` · `gif` |

예: `1_10.png`

**유형 이름과 로그인 아이디를 넣지 않는다**(FR-224). 파일명이 조회 URL 경로
(`/api/v1/expend-groups/icons/{filename}`)에 그대로 실리기 때문이다.

| 넣으면 생기는 문제 | |
|---|---|
| 유형 이름 | `/`·`..`로 경로를 벗어난다. 공백·유니코드는 인코딩이 어긋난다. 이름을 바꾸면 파일명이 낡는다 |
| 로그인 아이디 | 자식 데이터에 `user_id`를 복사하는 것이 된다(헌장 DB 저장 구조 규칙 위반). URL에 아이디가 노출된다 |

ID 기반이라 **이름을 바꿔도 파일명이 그대로 유효하다** — FR-214("파일명은 이름 변경을
따라가지 않는다")를 규칙이 아니라 구조로 보장한다.

## 2. 업로드 (2.7 등록 · 2.11 수정)

전용 업로드 API를 두지 않는다(FR-218). 등록·수정 요청의 `multipart/form-data` 파트로 받는다.

| 항목 | 값 |
|---|---|
| Content-Type | `multipart/form-data` |
| 파트 이름 | `iconFile` |
| 필수 | 아니다 (2.7·2.11 둘 다 선택) |
| 2.11에서 omit하면 | 기존 아이콘 유지 (PATCH omit 규칙) |

### 검증 순서

```text
1. 크기 검사 (1MB 초과 → 3102)
   └ 디코딩 전에 한다. 큰 파일을 먼저 디코딩하면 메모리를 그만큼 쓴다
2. 내용으로 형식 판정 (png·jpg·gif 아니면 → 3102)
   └ ImageIO.read() 로 실제 디코딩을 시도한다. 확장자를 믿지 않는다
3. 판정된 형식에서 확장자를 정한다
```

**확장자를 믿지 않는 이유**(FR-219): 2.10이 저장된 파일의 확장자를 보고 `Content-Type`을
정한다. 확장자만 `png`로 바꾼 파일이 통과하면 `image/png`라고 말하면서 실제로는 다른 바이트를
내보내게 된다.

서블릿 계층에도 `spring.servlet.multipart.max-file-size`를 걸어 1차로 막는다.
애플리케이션 검사만 두면 1MB 초과 파일이 일단 전부 업로드된 뒤에 거절된다.

**서버는 리사이즈하지 않는다.** 30×30은 화면 표시 규격이지 저장 규격이 아니다(FR-219).

### 저장 순서 (등록 2.7)

파일명에 `expendGroupId`가 들어가므로 **행이 먼저** 있어야 한다.

```text
① 행 INSERT (PK 획득)
② 커밋
③ 파일 저장 → IconStorage.save(idKey, expendGroupId, ext, bytes)
④ icon_filename UPDATE
```

**②를 ③보다 앞에 두는 것이 이 계약의 핵심 결정이다.** 파일 시스템은 트랜잭션에 참여하지 않는다.

| 순서 | 중간 실패 시 남는 것 | 회수 |
|---|---|---|
| 파일 먼저 → DB 롤백 | 주인 없는 파일. 파일명의 PK가 재사용되지 않아 영영 남는다 | **불가능** |
| DB 먼저 → 파일 실패 | `icon_filename`이 `null`인 행 | **정상 상태다.** 아이콘 없는 유형은 원래 허용된다 |

후자는 사용자가 아이콘을 다시 올리면 해결된다. 전자는 아무도 모르게 디스크가 찬다.

수정(2.11)은 행이 이미 있으므로 ③④만 한다. **기존 파일은 덮어쓴다** — 파일명이 ID 기반이라
같은 유형이면 같은 이름이 나온다. 확장자가 바뀌면(png → jpg) 옛 파일이 남는데,
그건 `icon_filename`이 새 이름을 가리키므로 참조되지 않는 고아 파일이 된다.
지울지는 정하지 않았다 → [남은 판단](#남은-판단) 참고.

## 3. 조회 (2.10) — 래퍼를 쓰지 않는 유일한 API

```text
GET /api/v1/expend-groups/icons/{filename}
Authorization: Bearer <accessToken>      ← 다른 API와 똑같이 요구한다 (FR-216)
```

### 세 갈래 응답

이 API는 상황에 따라 **응답 형태 자체가 다르다.** 프로젝트에서 유일하다.

| 상황 | HTTP | 본문 |
|---|---|---|
| 성공 | 200 | **이미지 바이너리**. `Content-Type: image/png`·`image/jpeg`·`image/gif` |
| 파일 없음 | 200 | `{ "resCode": 3104, "data": { "message": "..." } }` — **래퍼를 쓴다** |
| 인증 실패 | **401** | **본문 없음.** 래퍼도 없다 |

세 줄이 함께 있어야 의미가 완결된다. **성공만 바이너리이고, 비즈니스 실패는 래퍼이며,
인증 실패는 래퍼 없는 401이다.**

인증 실패가 래퍼를 쓰지 않는 이유는 US4 시나리오 4가 정했다 — "이 API만
`{ resCode, data }` 예외라 4자리 코드를 실을 본문이 없다". 프론트는 이 API를 `<img src>`로
직접 붙이지 않고 fetch+blob으로 받으므로(스펙 Assumptions) 401을 상태 코드로 판정할 수 있다.

### 구현상 주의

| # | 주의 |
|---|---|
| 1 | **`GlobalExceptionHandler`가 이 경로를 가로채면 안 된다.** 성공 응답이 JSON이 아니므로 공통 처리가 `Content-Type`을 덮어쓰면 깨진다. 파일 없음(`3104`)만 래퍼로 나가야 한다 |
| 2 | `002`의 `RestAuthEntryPoint`가 인증 실패를 `{ resCode: 1001 }`로 바꾸는데, **이 경로만 예외**로 빈 401을 내보내야 한다 |
| 3 | `Content-Type`은 **저장된 확장자**에서 정한다. §2의 내용 기반 판정이 확장자를 정확히 만들어 두었으므로 이 시점에는 확장자를 믿어도 된다 |
| 4 | 경로 정규화를 반드시 한다. `filename`이 Path Variable이라 `..`이 들어올 수 있다. `IconStorage`가 저장 루트 밖을 벗어나지 않는지 확인한 뒤 읽는다 |
| 5 | 응답 본문을 AOP 로깅에서 제외한다 → [api-contract.md §7](./api-contract.md) |

4번은 FR-224가 **입력**(파일명 생성)을 막은 것과 별개다. 파일명은 서버가 만들지만
조회 요청의 `filename`은 **클라이언트가 보내는 값**이라 신뢰할 수 없다.

### 삭제된 유형의 아이콘

**파일은 남는다**(FR-215). 삭제 표시가 행을 보존하므로 파일을 지우면 "행은 있는데 파일이
없는" 상태가 되어 2.10이 `3104`를 낸다. US4 시나리오 7이 이를 검증한다.

## 4. `iconUrl` — 응답에 실리는 값

DB에는 파일명만 있고, 조회 경로는 **응답을 만들 때 붙인다**(FR-213).

| `icon_filename` | 응답 `iconUrl` |
|---|---|
| `1_10.png` | `/api/v1/expend-groups/icons/1_10.png` |
| `null` | **`null`** — 필드를 생략하지 않는다 |

두 번째 줄이 SC-209다. Jackson이 `null` 필드를 빼지 않도록 확인한다. 프론트가
`'iconUrl' in obj`로 분기하면 생략과 `null`이 다른 결과를 낸다.

경로를 DB에 저장하지 않는 이유는 Base URL이 바뀌면 전 행을 고쳐야 하기 때문이다.

조립은 `ExpendGroupMapper`가 한다 — 응답을 만드는 지점이 거기다. Service가 HTTP 경로
문자열을 알게 하지 않는다.

## 5. `IconStorage`의 연산

파일 시스템을 만지는 **유일한 지점**이다. Service는 `Files.*`를 직접 부르지 않는다.

| 연산 | 하는 일 |
|---|---|
| `save(idKey, expendGroupId, ext, bytes) → filename` | 파일명을 만들고 저장. 같은 이름이면 덮어쓴다 |
| `read(filename) → bytes` | 경로 정규화 후 읽는다. 없으면 빈 결과 |
| `exists(filename)` | 위와 같음 |
| `copyFromSeed(seedName, idKey, expendGroupId) → filename` | 시드 원본을 회원별 복사본으로 |

마지막 것은 `002`의 가입 흐름(FR-106)이 쓴다. 002가 먼저 구현되므로 003은 **재사용하고
새로 만들지 않는다.** 두 곳에서 각자 파일명을 조립하면 규칙이 갈린다.

### 설정

```yaml
icon:
  storage:
    dir: ${ICON_STORAGE_DIR}        # 기본값 없음 — 없으면 기동에서 막는다
    max-file-size: 1MB
```

**기본값을 두지 않는다.** 기본값이 있으면 설정을 빠뜨린 채 기동해 임시 디렉터리 같은 곳에
파일이 쌓이고, 재기동하면 사라지는 사고가 조용히 난다. 기동에서 막으면 배포 시점에 드러난다.

클래스패스 안(`resources/`)에 쓸 수 없다 — 배포 시 jar 내부가 되어 쓰기가 불가능하다.
시드 원본은 읽기 전용으로 클래스패스에 있고, 회원별 복사본은 이 디렉터리에 쌓인다.

## 남은 판단

구현 단계에서 정하면 되는 것이고, 어느 쪽을 골라도 스펙의 FR·SC를 어기지 않는다.

| 항목 | 선택지 |
|---|---|
| 확장자가 바뀐 재업로드(png → jpg)의 옛 파일 | ① 그대로 둔다(고아 파일 1개) ② 옛 `icon_filename`을 보고 지운다 |
| `IconStorage`의 디렉터리 분할 | ① 평면 ② `id_key` 앞자리로 하위 디렉터리 |

둘 다 회원당 유형 수가 제한적이라(FR-217의 규모 가정) 당장 문제되지 않는다.
파일 수가 늘어 문제가 되면 그때 정한다.
