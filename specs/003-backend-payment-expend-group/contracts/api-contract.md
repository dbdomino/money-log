# API 계약: 지출·소득 수단과 지출유형 관리

**Feature**: `003-backend-payment-expend-group` | **Date**: 2026-09-02 | **Phase**: 1

각 API의 전체 필드 표는 `프로젝트설계/기능명세상세-백엔드/phase2-수단-지출유형/` 이 소유한다.
여기 적는 것은 **13건에 공통으로 걸리는 규칙**과 **설계 문서만 봐서는 갈리는 지점**이다.
아이콘(2.7·2.10·2.11)의 상세는 [icon-storage.md](./icon-storage.md)에 따로 있다.

---

## 1. 인가

**13건 전부 로그인 필요**다. `002`의 `SecurityFilterChain` 기본 규칙(`authenticated`)이
그대로 적용되므로 003이 인가 설정을 추가할 것은 없다.

소유자는 **Access Token이 지시하는 `id_key`**로 정해지며 요청 Body·Path가 지정할 수 없다(FR-201).
Path의 `{paymentMethodId}`·`{expendGroupId}`는 **자원 식별자일 뿐 소유자 지정이 아니다** —
조회한 행의 `id_key`가 토큰의 `id_key`와 다르면 거절한다.

| 자원 | 없음·타인 소유 |
|---|---|
| 수단 | `3003` |
| 지출유형 | `3103` |

**"없음"과 "타인 소유"를 같은 코드로 묶는다**(FR-201). 코드를 나누면 존재하지 않는 ID와
남의 ID를 구분할 수 있게 되어 자원의 존재 여부가 새어 나간다.

## 2. 응답 규격

**12건**은 `{ resCode, data }`. **2.10만 예외**다.

| 구분 | HTTP | `resCode` | `data` |
|---|---|---|---|
| 성공 | 200 | `200` | API별 객체 |
| 비즈니스·검증 실패 | **200** | 4자리 코드 | `{ "message": "..." }` |
| 서버 오류 | 500 | `9000` | `{ "message": "..." }` |

`002`가 만든 `GlobalExceptionHandler`를 그대로 쓴다. 003이 예외 처리를 새로 만들지 않는다.

### 목록 응답 (2.2·2.6·2.8·2.13)

```json
{ "resCode": 200, "data": { "list": [ {...} ] } }
```

**`data`에 `list` 하나만 담는다.** `offset`·`limit`·`totalCount`를 **싣지 않는다**(FR-217).

`002`의 관리자 회원 목록(1.13)은 페이징 3필드를 싣는데, 이 차이는 **의도된 것**이다.
회원 목록은 전체 회원을 보는 관리자 화면이라 수가 늘지만, 수단·지출유형은 본인 보유분이라
제한적이다. 두 형태를 통일하려고 여기에 `totalCount`를 넣으면 페이징 없는 목록에
"전체 건수"라는 무의미한 필드가 붙는다.

## 3. 필터 조건 (FR-207) — 목록 4건의 차이

| API | 조건 | 삭제분 |
|---|---|---|
| 2.2 수단 관리 목록 | `id_key` | **포함** (`deleted` 필드로 구분) |
| 2.6 수단 사용 중 목록 | `id_key` + `purpose` 일치 + `in_use=true` + `deleted=false` | 제외 |
| 2.8 지출유형 관리 목록 | `id_key` | **포함** (`deleted` 필드로 구분) |
| 2.13 지출유형 사용 중 목록 | `id_key` + `in_use=true` + `deleted=false` | 제외 |

**2.13에 `purpose` 조건이 없다.** 지출유형에는 용도 구분이 없다. 인덱스
`ix_user_expend_group_active (id_key, in_use, deleted)`에도 `purpose`가 없어 이 사실이
DB에 드러나 있다.

**2.6의 `purpose`는 Path Variable이다** — `/api/v1/payment-methods/active/{purpose}`.
Query가 아니다. 허용 값(`EXPENSE`·`INCOME`) 밖이면 `3001`.

### `deleted` 필드를 싣는 곳

| API | `deleted` | 근거 |
|---|---|---|
| 2.2 · 2.3 (수단 목록·상세) | **싣는다** | 설계 명세가 원래 갖고 있다 |
| 2.8 · 2.9 (유형 목록·상세) | **싣는다** | FR-223 — 이번에 추가한 것 |
| 2.6 · 2.13 (사용 중 목록) | 싣지 않는다 | `deleted=false`만 돌려주므로 무의미하다 |

## 4. PATCH omit 규칙 (2.4·2.11)

전송한 필드만 갱신하고 omit한 필드는 유지한다. `PUT`은 쓰지 않는다.

**omit이 판정 자체를 건너뛰게 하는 경우가 둘 있다.**

| API | 필드 | omit하면 |
|---|---|---|
| 2.4 | `purpose` | 기존 값 유지 + **참조 0건 검사도 하지 않는다** (스펙 Edge Case) |
| 2.11 | `name` | 기존 값 유지 + **기본 유형 이름 변경 검사(`3105`)도 하지 않는다** |
| 2.11 | `iconFile` | 기존 아이콘 유지 (FR-218) |

2.11의 두 번째 줄이 특히 중요하다. FR-220이 "기본 지출유형은 이름을 바꿀 수 없으나
**사용 여부·아이콘 변경은 허용한다**"고 정했으므로, 기본 유형에 `inUse`만 보낸 요청은
성공해야 한다. **"필드가 왔는가"를 먼저 보고 그다음에 기본 유형 여부를 본다.**
순서를 뒤집으면 기본 유형은 아무것도 못 바꾸게 되고 SC-208 후반이 깨진다.

`null`을 보낸 것과 omit한 것의 구분은 `002`가 정한 방식을 그대로 따른다.

## 5. 실패 코드 매핑

전체 15개는 [spec.md § 이 기능이 쓰는 에러코드](../spec.md)에 있다.
여기서는 **판정 순서가 결과를 바꾸는 3곳**만 못박는다.

### 2.4 수단 수정 — `3003` → `3001`/`3002` → `3005`

```text
1. 대상 수단 조회 (본인 소유?)        없음·타인 → 3003
2. 보낸 필드의 값 검증
   ├ type·purpose 가 허용 값 밖       → 3001
   └ cardExpiry 가 YYYY-MM 아님       → 3002
3. purpose 를 실제로 보냈는가?
   └ 보냈고 값이 바뀐다면 참조 검사
       tbl_expense · tbl_income · tbl_fixed_expense · tbl_fixed_expense_monthly
       └ 1건이라도 있으면            → 3005
4. UPDATE
```

3번의 **참조 검사 대상이 4개**다(FR-205). 하나라도 빠뜨리면 "소득 수단으로 낸 지출"이
만들어져 월별 집계와 통계 수단별 요약이 어긋난다.

### 2.12 지출유형 삭제 — `3103` → `3108` → `3107` → `3106`

```text
1. 대상 유형 조회 (본인 소유?)         없음·타인 → 3103
2. 이미 deleted=true 인가              → 3108
3. default_group=true 인가             → 3107
4. 그 유형을 쓴 지출이 있는가           → 3106
   (tbl_expense 만 본다 — 고정지출·목표금액·통계는 참조를 유지한다, FR-211)
5. deleted=true 로 UPDATE
```

**4번이 `tbl_expense` 하나만 보는 것이 2.4와의 차이다.** 수단의 `purpose` 변경은 4개 테이블을
보지만, 지출유형 삭제는 지출 1종만 본다. FR-211이 "삭제 표시돼도 목표금액·통계의 참조는
유지되어야 한다"고 정했기 때문이다 — 참조가 있어도 삭제 표시는 된다.

순서를 바꾸면 코드가 달라진다. 이미 삭제된 기본 유형을 다시 삭제하면 **`3108`**이지
`3107`이 아니다.

### 2.11 지출유형 수정 — `3103` → `3101`/`3105` → `3102`

```text
1. 대상 유형 조회                      없음·타인 → 3103
2. name 을 보냈는가?
   ├ 예 + default_group=true          → 3105
   └ 예 + 같은 회원에 그 이름이 이미 있음 → 3101 (삭제 표시된 행 포함)
3. iconFile 을 보냈는가?
   └ 예 + 형식·크기 위반               → 3102
4. UPDATE
```

2번의 `3101` 판정은 **삭제 표시된 행도 센다**(FR-209). 유니크 제약
`ux_user_expend_group_name (id_key, name)`에 부분 조건이 없어 DB도 같은 기준이다.

## 6. 등록 시 소유자·감사 컬럼

| 컬럼 | 값 |
|---|---|
| `id_key` | **토큰의 `id_key`**. 요청 Body가 지정할 수 없다 |
| `created_by` · `updated_by` | 같은 값 (`002`의 `AuditorAware`가 공급) |
| `deleted` | `false` |
| `in_use` | 요청값. 2.1은 기본 `true`, 2.7은 필수 |
| `default_group` | **`false` 고정** — 2.7로는 기본 유형을 만들 수 없다 |

`default_group`을 요청으로 받지 않는 것이 중요하다. 받으면 사용자가 임의로 기본 유형을
만들어 `3107`(삭제 불가) 보호를 스스로에게 걸 수 있다. 기본 10종은 `002`의 가입 흐름만 만든다.

## 7. 로깅

`002`가 만든 AOP 로깅을 그대로 쓴다. 003이 추가로 정할 것은 하나다.

**2.10의 응답 본문은 로그에 찍지 않는다.** 이미지 바이너리라 로그 파일이 깨지고 용량이 커진다.
AOP가 반환값을 직렬화해 남기므로, `byte[]`·`Resource`·`ResponseEntity<Resource>` 반환은
크기만 남기고 내용을 생략하는 규칙이 필요하다.

2.7·2.11의 **요청**도 같다 — `MultipartFile` 파라미터는 파일명·크기만 남긴다.

마스킹 대상은 003에 새로 추가할 것이 없다(비밀번호·토큰을 다루지 않는다).
