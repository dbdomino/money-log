# Quickstart: 지출·소득 수단과 지출유형 관리

**Feature**: `003-backend-payment-expend-group` | **Date**: 2026-09-02 | **Phase**: 1

이 기능이 실제로 동작하는지 확인하는 **검증 가이드**다. 구현 코드는 담지 않는다.

## 0. 착수 전

### 선행 기능

**`002`가 먼저 서야 한다.** 13건 전부 로그인이 필요하고, 응답 규격·에러 처리·AOP 로깅·
`AuditorAware`를 전부 002가 만든다. 002 없이 003만 구현하면 인증 없이 도는 API가 되고
감사 컬럼(NOT NULL)에 넣을 값이 없다.

`IconStorage.copyFromSeed()`도 002의 가입 흐름(FR-106)이 먼저 쓴다. 003은 재사용한다.

### 명세 선행 개정 (원칙 V)

개정 5건 중 **4건은 커밋 `84ad88c`에서 완료**됐다. 남은 것은 하나다.

| # | 파일 | 고칠 내용 |
|---|---|---|
| 5 | `2.7-ExpendGroupCreate.md` · `2.11-ExpendGroupUpdate.md` | `iconFile` 파트 설명의 "아이콘 이미지 (png, jpg, gif 등)" → **"`png`·`jpg`·`gif` 세 형식, 1MB 이하. 형식은 파일 내용으로 판정한다"** |

"등"으로 열어 두면 헌장 원칙 V의 "설명 칸은 그 칸만 보고 의미가 읽혀야 한다"에 걸린다.
FR-219가 규격을 확정했으므로 반영만 하면 된다.

확인:

```bash
grep -rn 'png, jpg, gif 등' 프로젝트설계/기능명세상세-백엔드/phase2-수단-지출유형/
# → 0건이어야 한다
```

## 1. 전제

| 항목 | 값 |
|---|---|
| PostgreSQL 18 | `localhost:5432` · DB `moneylogdb` · 스키마 `moneylog` |
| 스키마 | 15개 테이블. **이 기능은 스키마를 바꾸지 않는다** |
| 백엔드 | `:8081` · `/api/v1` |
| `ICON_STORAGE_DIR` | 쓰기 가능한 디렉터리. **기본값이 없어 없으면 기동에서 막힌다** |
| 로그인 계정 | 002의 가입(1.2)으로 만든다. 기본 지출유형 10종이 함께 생긴다 |

스키마·인덱스 확인:

```bash
psql -h localhost -U moneyloguser -d moneylogdb -c \
  "select indexname from pg_indexes where schemaname='moneylog'
     and indexname in ('ix_user_payment_method_active','ix_user_expend_group_active');"
# → 2건

psql -h localhost -U moneyloguser -d moneylogdb -c \
  "select conname, pg_get_constraintdef(oid) from pg_constraint
     where conname = 'ux_user_expend_group_name';"
# → UNIQUE (id_key, name)  — WHERE 절이 없어야 한다 (FR-209 의 근거)
```

**주의 — `ddl-auto`가 `create`다.** 기동할 때마다 전 테이블이 drop 후 재생성된다.
검증 중 만든 수단·유형은 재기동하면 사라지는데, **디스크의 아이콘 파일은 남는다.**
DB와 파일이 어긋난 상태가 되므로 재기동 후에는 `ICON_STORAGE_DIR`도 비우고 시작한다.

## 3. 검증 시나리오

spec.md의 User Story·SC와 1:1로 대응한다. 통합 테스트의 `@DisplayName`을 `#N`으로 맞춘다.

### US1 — 수단 관리 (P1, MVP)

| # | 시나리오 | 기대 | 대응 |
|---|---|---|---|
| 1 | `type=CARD`·`purpose=EXPENSE`로 등록 | 본인 소유로 저장, `deleted=false` | US1-1 |
| 2 | `type=ACCOUNT`로 등록 | `cardExpiry`가 `null` | US1-2 |
| 3 | `type`에 허용 값 밖 | `3001` | US1-3 |
| 4 | `purpose`에 허용 값 밖 | `3001` | US1-4 |
| 5 | `cardExpiry`가 `YYYY-MM`이 아님 | `3002` | FR-221 |
| 6 | 삭제 후 관리 목록(2.2) | **그 수단이 여전히 보인다**, `deleted=true` | US1-5·SC-204 |
| 7 | 삭제 후 사용 중 목록(2.6) | 그 수단은 빠진다 | US1-6 |
| 8 | 이미 삭제된 수단을 다시 삭제 | `3004` | Edge Case |
| 9 | 남의 수단 ID로 상세 조회 | `3003` | US1-7·SC-207 |
| 10 | 삭제 표시된 수단을 수정 | **성공한다** (이름 정리 등) | Edge Case |

10번이 "삭제 표시는 읽기 전용이 아니다"를 확인하는 자리다.

### US2 — 사용 중 목록 (P2)

| # | 시나리오 | 기대 | 대응 |
|---|---|---|---|
| 11 | 지출용·소득용·미사용·삭제된 수단 4건 → `purpose=EXPENSE`로 사용 중 목록 | **정확히 1건** | US2-1·SC-202 |
| 12 | `inUse=false`인 유형 → 사용 중 유형 목록(2.13) | 그 유형은 빠진다 | US2-2 |
| 13 | `purpose`에 허용되지 않은 값으로 2.6 | `3001` | US2-3 |
| 14 | 목록 4건(2.2·2.6·2.8·2.13)의 응답 | `data`에 **`list`만** 있고 `totalCount`가 없다 | FR-217 |

11번이 네 조건이 전부 걸리는지 확인하는 핵심 시나리오다.
14번은 `002`의 관리자 목록과 형태가 다른 것이 의도임을 확인한다.

### US3 — 지출유형 관리 (P2)

| # | 시나리오 | 기대 | 대응 |
|---|---|---|---|
| 15 | 같은 회원이 같은 이름으로 두 번 등록 | `3101` | US3-1·SC-203 |
| 16 | 다른 회원이 같은 이름으로 각자 등록 | 둘 다 성공 | US3-2·SC-203 |
| 17 | 삭제 표시 후 **같은 이름**으로 재등록 | `3101` (삭제된 이름도 점유) | US3-3 |
| 18 | 그 유형을 쓴 지출이 있을 때 삭제 | `3106` | US3-4 |
| 19 | 기본 유형(`defaultGroup=true`) 삭제 | `3107` | US3-5 |
| 20 | 이미 삭제된 유형을 다시 삭제 | `3108` | US3-6·SC-210 |
| 21 | 기본 유형의 **이름** 변경 | `3105` | SC-208 |
| 22 | 기본 유형의 **사용 여부·아이콘** 변경 | **성공한다** | SC-208·FR-220 |
| 23 | 삭제 표시 후 그 유형을 참조하던 목표금액 조회 | 행과 참조가 **유지된다** | US3-7·FR-211 |
| 24 | 2.8 관리 목록 | 삭제분 포함, 각 행에 `deleted` | FR-223·SC-204 |

**21·22가 한 쌍이다.** 판정 순서를 뒤집으면 기본 유형이 아무것도 못 바꾸게 되어 22가 깨진다.
17번은 유니크 제약에 `WHERE` 조건이 없다는 사실을 실제로 검증한다.
20번은 순서 검증이기도 하다 — 이미 삭제된 **기본** 유형을 다시 삭제하면 `3108`이지 `3107`이 아니다.

### US4 — 아이콘 (P3)

| # | 시나리오 | 기대 | 대응 |
|---|---|---|---|
| 25 | 아이콘 있는 유형의 목록·상세 | `iconUrl`이 경로 문자열 | US4-1 |
| 26 | **아이콘 없는** 유형의 목록·상세 | `iconUrl` 필드가 **존재하고 값이 `null`** | US4-2·SC-209 |
| 27 | `png`·`jpg`·`gif`가 아닌 파일 업로드 | `3102` | US4-3·SC-211 |
| 28 | **확장자만 `.png`로 바꾼** 텍스트 파일 업로드 | `3102` (내용으로 판정한다) | FR-219 |
| 29 | 1MB 초과 파일 업로드 | `3102` | SC-211 |
| 30 | `iconUrl`을 **Bearer 없이** 호출 | **래퍼 없는 HTTP 401** | US4-4 |
| 31 | 아이콘 조회 성공 | `{ resCode, data }`가 **아니라** 이미지 바이너리 | US4-5·SC-201 |
| 32 | 없는 파일명으로 조회 | `3104` (**래퍼를 쓴다**) | US4-6 |
| 33 | 유형 삭제 표시 후 그 아이콘 조회 | **파일이 남아 있다** | US4-7·FR-215 |
| 34 | 유형 이름 변경 후 아이콘 조회 | 파일명이 이름을 담지 않아 **그대로 유효** | US4-8 |
| 35 | 저장된 파일명 전수 검사 | 전부 `{id_key}_{expendGroupId}.{확장자}` 형태 | SC-212 |
| 36 | `filename`에 `..`을 넣어 조회 | 저장 루트 밖을 읽지 않는다 | icon-storage §3 |
| 37 | 2.11에서 `iconFile`을 omit | 기존 아이콘 유지 | FR-218 |

**28번이 FR-219의 핵심이다.** 확장자만 검사하면 통과한다.
**30·31·32가 함께 세 갈래 응답을 검증한다** — 성공은 바이너리, 비즈니스 실패는 래퍼,
인증 실패는 래퍼 없는 401. 이 셋 중 하나라도 어긋나면 2.10의 계약이 깨진 것이다.
36번은 스펙에 없지만 `filename`이 클라이언트가 보내는 값이라 반드시 확인한다.

| # | 시나리오 | 기대 | 대응 |

40번이 omit 규칙과 참조 검사의 관계를 확인한다.

| 항목 | 확인 수단 |

| 명세 선행 개정 | `grep -rn 'png, jpg, gif 등' 프로젝트설계/.../phase2-*/` → 0건 |
| API 13건 동작 | 시나리오 1~42 |
| SC-201~212 (12건) | 위 표의 "대응" 열에 전부 나온다 |
| 2.10의 세 갈래 응답 | 시나리오 30·31·32 |
| 경로 탈출 방어 | 시나리오 36 |
| 스키마 무변경 | `git diff sql/schema-moneylogdb.sql` → 변경 없음 |
| `:data-mod:test` | 77건 통과 |
| `:app-mod:money-backend-app:test` | 002 테스트 + 003 신규 통과 |
| 헌장 게이트 6개 | [plan.md § Constitution Check](./plan.md#constitution-check) |

**스키마 무변경 확인이 원칙 VI의 이 기능판이다.** 덤프가 바뀌었다면 의도치 않게 Entity를
건드린 것이므로 원인을 찾는다.

디스크 정리도 확인한다 — 검증이 끝난 뒤 `ICON_STORAGE_DIR`에 남은 파일이
전부 시나리오에서 만든 것인지 본다. 주인 없는 파일이 있으면 저장 순서(커밋 → 파일)가
지켜지지 않은 것이다([icon-storage.md §2](./contracts/icon-storage.md)).
