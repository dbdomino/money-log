# Research: 지출·소득 수단과 지출유형 관리

**Feature**: `003-backend-payment-expend-group` | **Date**: 2026-09-02 | **Phase**: 0

Technical Context의 미결 항목과, 기존 코드·DB를 읽어야 답이 나오는 항목을 정리한다.
형식은 **결정 / 근거 / 기각한 대안**이다.

조사 기준점은 `sql/schema-moneylogdb.sql`(실제 컬럼·제약),
`프로젝트설계/기능명세상세-백엔드/phase2-수단-지출유형/`, 헌장, 그리고 `002`의 계획이다.

## 1. 아이콘 파일 I/O를 어디에 둘 것인가

**결정**: `money-backend-app`에 `storage` 패키지를 만들고 `IconStorage` 하나가 파일 시스템을
전담한다. Service는 `IconStorage`만 부르고 `Files.*`를 직접 쓰지 않는다.

**근거**: 두 가지다.

1. **경로 조립이 한 곳이어야 안전하다.** 파일명이 조회 URL 경로
   (`/api/v1/expend-groups/icons/{filename}`)에 그대로 실린다. 저장 경로를 여러 곳에서 조립하면
   그중 하나가 `..`을 거르지 않는 순간 경로 탈출이 된다. FR-224가 파일명에서 유형 이름을 뺀 것도
   같은 이유인데, 그건 **입력**을 막은 것이고 저장·조회 시점의 **경로 정규화**는 별개 방어다.
2. **레이어 규칙(원칙 II).** Service는 유스케이스를 조립하는 자리다. 파일 스트림을 직접
   다루기 시작하면 트랜잭션 경계와 I/O 실패 처리가 섞인다.

`IconStorage`가 갖는 연산은 넷뿐이다 — `save(idKey, expendGroupId, ext, bytes) → filename`,
`read(filename) → bytes`, `exists(filename)`, `copyFromSeed(...)`.
마지막 것은 `002`의 가입 흐름(FR-106)이 쓰므로 002 구현 시 함께 만들어질 수 있다.
그 경우 003은 재사용하고 새로 만들지 않는다.

**기각한 대안**:
- **Service가 직접 `Files.write`** — 위 1번. 저장 경로 규칙이 `ExpendGroupService`와
  가입 흐름(`002`) 두 곳으로 갈린다.
- **DB에 BLOB으로 저장** — 001이 이미 "파일명만 저장한다"로 확정했고(FR-213),
  `icon_filename varchar(255)` 컬럼이 그 결정의 산물이다.

## 2. 파일 쓰기와 트랜잭션의 순서

**결정**: **DB 커밋이 끝난 뒤 파일을 쓴다.** 등록(2.7)은 ① 행 저장(PK 획득) → ② 커밋 →
③ 파일 저장 → ④ `icon_filename` UPDATE 순서다.

**근거**: 파일 시스템은 트랜잭션에 참여하지 않는다. 파일을 먼저 쓰고 DB가 롤백되면
**주인 없는 파일**이 디스크에 남고, 그 파일명은 `{id_key}_{expendGroupId}.png`라
나중에 같은 PK가 재사용될 일이 없으므로 영영 회수되지 않는다.

반대 순서(DB 먼저)의 실패 모드는 "행은 있는데 `icon_filename`이 `null`"이다. 이건
**정상 상태와 구분되지 않는다** — 아이콘 없는 유형은 원래 허용되고(`icon_filename` nullable),
응답의 `iconUrl`이 `null`로 나가면 그만이다(FR-209·SC-209). 사용자는 아이콘을 다시 올리면 된다.

즉 **한쪽 실패 모드는 회수 불가능한 쓰레기를 남기고, 다른 쪽은 정상 상태로 흡수된다.**
후자를 고른다.

파일명에 `expendGroupId`가 들어가므로 **행을 먼저 저장해 PK를 받아야** 한다는 제약도 같은
방향을 가리킨다.

**기각한 대안**:
- **파일 먼저, DB 나중** — 위 이유.
- **`TransactionSynchronization`의 `afterCommit`에 파일 쓰기를 건다** — 순서는 보장되지만
  `afterCommit`에서 실패하면 예외를 호출자에게 돌려줄 방법이 마땅치 않다. 응답은 이미 성공으로
  결정된 뒤다. 명시적 4단계가 실패를 다루기 쉽다.

## 3. 이미지 형식 판정 — 확장자가 아니라 내용으로

**결정**: JDK의 `javax.imageio.ImageIO.read()`로 실제 디코딩을 시도해 판정한다.
새 라이브러리를 넣지 않는다. 확장자는 판정 결과에서 **역으로** 정한다.

**근거**: FR-219가 "형식 판정은 확장자가 아니라 파일 내용으로 한다 — 확장자만 바꾼 파일이
통과하면 2.10이 잘못된 `Content-Type`을 돌려준다"고 못박았다. 2.10은 저장된 파일의 확장자를
보고 `Content-Type`을 정하므로, 확장자를 신뢰하면 `image/png`라고 말하면서 실제로는 다른
바이트를 내보내게 된다.

`ImageIO.read()`는 png·jpg·gif를 표준 플러그인으로 읽으며, **읽히지 않으면 `null`을 돌려주거나
예외를 던진다.** 이 셋만 허용하므로 "읽히면 통과, 아니면 `3102`"가 그대로 판정 규칙이 된다.
`ImageIO.getImageReaders()`로 실제 포맷 이름(`png`/`jpeg`/`gif`)을 얻어 확장자를 정한다.

`Files.probeContentType`은 **쓰지 않는다.** OS의 파일명·매직넘버 데이터베이스에 의존해
플랫폼마다 결과가 다르고, 이 프로젝트는 Windows와 Linux를 모두 대상으로 한다.

**크기 검사(1MB)는 디코딩 전에** 한다. 큰 파일을 먼저 디코딩하면 메모리를 그만큼 쓴다.
Spring의 `spring.servlet.multipart.max-file-size`도 함께 걸어 서블릿 계층에서 1차로 막는다.

**기각한 대안**:
- **Apache Tika** — 정확하지만 이 목적에 라이브러리 하나가 통째로 들어온다. 허용 형식이
  세 개뿐이라 과하다.
- **매직넘버를 직접 비교** — png(`89 50 4E 47`)·gif(`47 49 46`)·jpg(`FF D8 FF`)를 손으로 검사한다.
  가능하지만 "헤더는 png인데 뒤가 깨진 파일"이 통과한다. `ImageIO`는 실제로 디코딩하므로
  그것까지 걸러낸다.
- **확장자만 검사** — FR-219가 명시적으로 금지했다.

## 4. 아이콘 저장 위치와 설정

**결정**: 저장 디렉터리를 `application.yml`의 `icon.storage.dir`로 외부화하고
`IconStorageProperties`로 바인딩한다. 기본값은 두지 않고 **없으면 기동에서 막는다**.

**근거**: 클래스패스 안(`resources/`)에 쓸 수 없다 — 배포 시 jar 내부가 되어 쓰기가 불가능하다.
시드 원본(`resources/seed/expend-group-icons/`)은 **읽기 전용**이고, 회원별 복사본은
디스크의 별도 디렉터리에 쌓인다. 이 둘을 섞으면 배포마다 사용자 데이터가 사라진다.

기본값을 두지 않는 이유는, 기본값이 있으면 설정을 빠뜨린 채 기동해서 임시 디렉터리 같은
엉뚱한 곳에 파일이 쌓이고 **재기동 시 사라지는** 사고가 조용히 난다. 기동에서 막으면
배포 시점에 드러난다.

**기각한 대안**: 오브젝트 스토리지(S3 등) — 스펙 Assumptions가 "아이콘은 서버 로컬 디스크에
저장한다. 오브젝트 스토리지 전환은 범위 밖이다"로 정했다. `IconStorage` 인터페이스 하나로
가둬 두었으므로 전환이 필요해지면 구현만 바꾼다.

## 5. `iconUrl` 조립 위치

**결정**: Mapper(`ExpendGroupMapper`)가 `icon_filename` → `iconUrl` 변환을 담당한다.
`icon_filename`이 `null`이면 `iconUrl`도 `null`이며 **필드를 생략하지 않는다**.

**근거**: FR-213이 "조회 경로는 응답을 만들 때 붙인다. 경로를 저장하면 Base URL 변경 시
전 행을 고쳐야 한다"고 정했다. 응답을 만드는 지점이 Mapper이므로 거기가 자연스럽다.

`null`일 때 필드를 생략하지 않는 것은 SC-209가 "`iconUrl` 필드가 **항상 존재하고 값이 `null`**"을
요구하기 때문이다. Jackson이 `null` 필드를 빼지 않도록 해당 DTO에 `@JsonInclude(ALWAYS)`를
명시하거나 전역 설정이 `NON_NULL`이 아님을 확인한다. 프론트가 `'iconUrl' in obj`로 분기하면
생략과 `null`이 다른 결과를 낸다.

**기각한 대안**: Service에서 조립 — 가능하지만 Service가 HTTP 경로 문자열을 알게 된다.
경로는 표현 계층의 관심사다.

## 6. 참조 0건·사용 이력 검사 (`3005`·`3106`)

**결정**: Repository에 `existsBy...` 계열 메서드를 두고 **`count`가 아니라 `exists`**로 판정한다.
검사 대상 테이블은 `3005`가 4개(`tbl_expense`·`tbl_income`·`tbl_fixed_expense`·
`tbl_fixed_expense_monthly`), `3106`이 1개(`tbl_expense`)다.

**근거**: FR-205가 "그 수단을 참조하는 지출·소득·고정지출(관리·월별)이 **0건일 때만** 허용"이라
넷을 전부 봐야 한다. 필요한 답은 "있나/없나"뿐이므로 `exists`가 맞다 — `count`는 전부 세고
`exists`는 첫 행에서 멈춘다.

**FR-210의 `3106`은 지출만 본다.** 설계 명세 `2.12`의 실패 표가 "지출 사용 이력 있음"으로
지출만 적었고, 고정지출·목표금액·통계는 삭제 표시된 유형을 참조한 채로 **남아 있어야 한다**
(FR-211). 즉 지출유형은 참조가 있어도 삭제 표시가 되며, 막는 것은 지출 1종뿐이다.
수단(`3005`)과 지출유형(`3106`)의 검사 범위가 다른 것은 의도된 차이다.

**이 검사들은 애플리케이션이 한다.** 삭제가 UPDATE라 FK RESTRICT가 발동하지 않고,
`purpose` 변경은 애초에 FK와 무관하다(스펙 Assumptions).

**기각한 대안**: DB 트리거 — 판정 로직이 DB로 흩어져 스키마 덤프만 봐서는 규칙을 알 수 없다.
001이 "제약은 선언적인 것만 DB에 둔다"는 방향으로 정리한 것과 어긋난다.

## 7. 지출유형 이름 유일성 (`3101`)

**결정**: 애플리케이션 선검사 + **유니크 위반 처리**를 둘 다 둔다.
유일 판정은 `deleted` 여부를 조건에 넣지 않는다.

**근거**: DB에 `ux_user_expend_group_name UNIQUE (id_key, name)`이 있고 **부분 조건이 없다**
(덤프에서 확인). 즉 삭제 표시된 행의 이름도 계속 점유한다 — FR-209가 "삭제 표시된 행도
포함해 유일성을 판정한다"고 적은 것과 DB가 일치한다.

선검사만 두면 동시 등록 창이 열린다. 두 요청이 같은 순간 "없음"을 보고 둘 다 INSERT하면
하나가 유니크 위반으로 실패하는데, 그걸 `9000`으로 흘리면 사용자에게는 원인 불명 오류가 된다.
위반을 잡아 `3101`로 바꾼다.

**기각한 대안**: 유니크 위반만 처리하고 선검사를 없앤다 — 코드는 줄지만 정상 경로에서도
예외를 던져 흐름을 만든다. 예외는 예외적인 상황에 쓴다.

## 8. 기본 지출유형 보호 (`3105`·`3107`)

**결정**: `default_group = true`인 행에 대해 **이름 변경은 `3105`로 거절**하고
**삭제는 `3107`로 거절**한다. 사용 여부·아이콘 변경은 허용한다.

**근거**: FR-220이 "기본 지출유형은 이름을 바꿀 수 없으며 시도하면 `3105`.
사용 여부·아이콘 변경은 허용한다"로 정했다. 근거는 이름이 화면·통계에서 일관되게 읽혀야
한다는 것이다(`1.2-MemberSignup.md`가 10종을 "등"으로 열지 않고 확정한 것과 같은 이유).

**판정 순서가 중요하다.** 2.11(수정)은 `name`을 실제로 보냈을 때만 `3105`를 낸다.
`name`을 omit하고 `inUse`만 보낸 요청은 통과해야 한다(FR-220 후반). PATCH omit 규칙과
맞물리므로, "필드가 왔는가"를 먼저 판정하고 그다음에 기본 유형 여부를 본다.

**기각한 대안**: 기본 유형을 아예 수정 불가로 막는다 — FR-220이 사용 여부·아이콘 변경을
명시적으로 허용했다. 안 쓰는 기본 유형을 목록에서 숨길 방법이 없어진다.

## 9. 사용 중 목록의 필터 조건 (2.6·2.13)

**결정**: 2.6은 **세 조건**(`purpose` 일치 · `in_use=true` · `deleted=false`),
2.13은 **두 조건**(`in_use=true` · `deleted=false`)이다. 지출유형에는 용도 구분이 없다.

**근거**: FR-207이 그대로 정했다. 인덱스도 그 형태로 이미 있다 —
`ix_user_payment_method_active (id_key, purpose, in_use, deleted)`와
`ix_user_expend_group_active (id_key, in_use, deleted)`. 001이 이 조회를 예상하고 만든 것이라
컬럼 순서가 조건과 일치한다.

**2.6의 `purpose`는 Path Variable이다**(`/payment-methods/active/{purpose}`, 설계 명세에서 확인).
Query가 아니다. 허용 값 밖이면 `3001`로 거절한다(FR-207과 US2 시나리오 3).

`ix_user_expend_group_active`에 `purpose`가 없는 것이 "지출유형에는 용도가 없다"는 사실을
DB 차원에서 확인해 준다.

**기각한 대안**: 관리 목록 하나에 필터 파라미터를 붙여 두 API를 합친다 — 설계 명세가
2.2/2.6, 2.8/2.13으로 나눠 놓았고, 조회 축이 다르다(관리 화면 vs 입력 화면).
합치면 프론트가 매번 필터를 정확히 걸어야 하고, 빠뜨리면 삭제된 유형이 입력 화면에 뜬다.
