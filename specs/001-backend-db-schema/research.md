# Research: 001-backend-db-schema

**재작성**: 2026-08-31 — spec 전면 재작성 + clarification 4건 반영. 이전 판(`tbl_be_*` 접두사, 회원 자연키 PK, 지출유형 물리 삭제)은 폐기되었다.

## 1. 물리 테이블 명명

**Decision (2026-09-02 개정)**: 테이블 이름은 **`tbl_<자원명>`** 이 기본이고, `tbl_user_` 접두사는 **꼭 필요한 곳에만** 쓴다. 필요한 곳은 두 가지다 — ① 레거시 `money-app` 이름과 정면 충돌하는 3개, ② FR-009가 이름을 확정한 2개.

이전 판은 15개 전부에 `tbl_user_`를 붙였다. 실제로 충돌하는 것은 3개뿐인데 전면 적용해서, `tbl_user_statistics_payment_method`가 "통계의 수단별 요약"이 아니라 "회원 통계 수단 방법"처럼 읽혔다. 이름이 자원을 설명하지 못하면 접두사가 값을 못 한다.

| # | 논리 단위 | 물리 테이블 | 레거시(비겹침 확인) |
|---|-----------|-------------|---------------------|
| 1 | 회원 | `tbl_user` | `tbl_member` |
| 2 | 회원 세션 | `tbl_user_session` | (없음) |
| 3 | 로그인 이력 | `tbl_user_login_history` | `tbl_login_history` |
| 4 | 지출·소득 수단 | `tbl_user_payment_method` | `tbl_payment_Method` → PG 소문자 `tbl_payment_method` |
| 5 | 지출유형 | `tbl_user_expend_group` | `tbl_expend_group` |
| 6 | 월별 지출 내역 | `tbl_expense` | `tbl_expend` |
| 7 | 월별 수입 내역 | `tbl_income` | (없음) |
| 8 | 고정지출 관리 | `tbl_fixed_expense` | `tbl_expend_fix` |
| 9 | 월별 고정지출 내역 | `tbl_fixed_expense_monthly` | (없음) |
| 10 | 기본 목표금액 | `tbl_expend_target_default` | `tbl_Ammount` → `tbl_ammount` |

| 15 | 통계 수단별 요약 | `tbl_statistics_payment_method` | (없음) |

**접두사를 유지하는 5개와 그 사유**

| 테이블 | 사유 |
|--------|------|
| `tbl_user` | 회원 테이블 자체. FR-009 확정 |
| `tbl_user_session` | FR-009 확정. "회원 세션"으로 자연스럽게 읽힌다 |
| `tbl_user_login_history` | 레거시 `tbl_login_history`와 충돌 |
| `tbl_user_payment_method` | 레거시 `tbl_payment_Method`(PG 소문자 접힘 → `tbl_payment_method`)와 충돌 |
| `tbl_user_expend_group` | 레거시 `tbl_expend_group`과 충돌 |

**Rationale**: FR-009는 `tbl_user`·`tbl_user_session`만 확정하고 나머지를 "레거시와 겹치지 않는 신규 명명"으로 남겼다. 겹치지 않기만 하면 되므로, 겹치지 않는 이름에까지 접두사를 붙일 근거가 없다. 접두사 뒤 부분이 명세의 API 자원 이름(`expense`, `income`, `fixed-expense`, `expend-target`, `statistics`)과 1:1로 맞는다는 이점은 접두사를 떼면 오히려 더 곧게 드러난다.

**충돌이 실재하는 이유** — `money-app`은 루트 `build.gradle`에서 `data-mod`를 의존하고, 자기 `application.yml`의 `spring.profiles.active: postgresql`로 data-mod의 datasource 설정을 쓴다. 그리고 레거시 Entity 12개(`tbl_member`·`tbl_expend`·`tbl_expend_group`·`tbl_payment_Method` 등)를 `ddl-auto`와 함께 갖고 있다. 즉 `money-app`을 띄우면 **같은 `moneylog` 스키마에 레거시 테이블이 생긴다.** 가정이 아니라 현재 구성이다.

PostgreSQL은 따옴표 없는 식별자를 소문자로 접으므로 대소문자 차이는 충돌 회피 근거가 되지 않는다.

가장 긴 이름은 `tbl_statistics_payment_method`(29자)로 PostgreSQL 식별자 한계(63자) 안이다.

**제약·인덱스 이름도 함께 맞춘다** — 테이블 이름이 바뀌면 `ix_<테이블>_<컬럼들>`·`ux_<테이블>_<컬럼들>`·`fk_<테이블>_<대상>` 규칙에 따라 그 테이블의 제약 이름에서도 `user_`가 빠진다(예: `ix_user_expense_date` → `ix_expense_date`). 접두사를 유지하는 5개 테이블의 제약 이름은 그대로다.

**Alternatives considered**:
- `tbl_be_*` — `be`가 무엇인지 이름만 보고 알 수 없고, `tbl_user` 확정과 어긋난다
- **15개 전면 `tbl_user_` 접두사**(이전 판) — 충돌하지 않는 이름까지 길어지고, 이름이 자원을 설명하지 못한다. 실제로 이 이유로 폐기했다
- 접두사 없이 자원 이름만 15개 전부 — 레거시와 3건 정면 충돌
- 레거시를 별도 스키마(`moneylog_legacy`)로 분리하고 15개 전부 접두사 제거 — 충돌 자체가 사라져 가장 깨끗하지만, `money-app`의 서비스·컨트롤러 다수가 레거시 Entity를 쓰고 있어 이 기능의 범위를 넘는다. `money-app`이 "DB 직접 접근 없음"(CLAUDE.md)에 도달하면 그때 다시 본다

## 2. 기본키와 회원 참조

**Decision**: `tbl_user`의 PK는 `id_key BIGINT GENERATED BY DEFAULT AS IDENTITY`, 로그인 아이디는 별도 컬럼 `user_id VARCHAR(20) UNIQUE`. 나머지 14개 테이블의 PK는 `idx BIGINT IDENTITY`이고, 회원 소유 항목은 `id_key BIGINT NOT NULL REFERENCES tbl_user(id_key)`다.

**Rationale**: FR-008이 규칙을 그대로 정했다. 대리키 참조의 실익은 (a) 로그인 아이디 문자열이 자식 테이블·인덱스에 반복 저장되지 않고, (b) 아이디 표기 변경 요구가 생겨도 자식 데이터가 영향받지 않으며, (c) 조인·인덱스가 8바이트 정수로 균일해지는 것이다.

API가 주고받는 `memberId`는 `user_id` 값이므로, 인증 필터가 토큰의 `sub`(=`user_id`)를 `id_key`로 한 번 환산해 `SecurityContext`에 함께 싣는 것을 전제한다. 이 환산은 인증 기능(Phase 1)의 몫이고 본 기능 범위 밖이다.

**Alternatives considered**:
- 로그인 아이디 자연키 PK(이전 판) — clarification으로 폐기
- UUID PK — 길이·인덱스 비용만 늘고 이점 없음
- 자식에 `id_key`와 `user_id`를 함께 보관 — FR-008이 명시적으로 금지(같은 정보 이중 저장)

## 3. 공통 감사 컬럼

**Decision**: 15개 테이블 전부에 `created_at TIMESTAMPTZ NOT NULL`, `updated_at TIMESTAMPTZ NOT NULL`, `created_by BIGINT`, `updated_by BIGINT`를 둔다. `created_by`/`updated_by`는 그 행을 만들거나 고친 회원의 `id_key`다.

`tbl_user`의 `created_by`만 **NULL을 허용**한다 — 회원가입은 자기 자신을 만드는 행위라 INSERT 시점에 `id_key`가 없다. NULL = 본인 가입, 값 있음 = 그 `id_key`를 가진 관리자가 추가(`AdminMemberCreate`). 나머지 14개는 NOT NULL이다.

`created_by`/`updated_by`에는 **FK 제약을 걸지 않는다**. 감사 기록은 대상 회원이 남아 있든 아니든 보존되어야 하고, `tbl_user` 자신이 자기 컬럼으로 자신을 참조하는 순환을 피하기 위해서다.

**Rationale**: FR-004. 소유자(`id_key`)와 별개로 "누가 손댔는가"를 남긴다 — 관리자가 다른 회원을 수정하는 경로(`AdminMemberUpdate`, `AdminMemberDeactivate`)에서 둘이 갈린다.

**구현 방식**: JPA `@MappedSuperclass` + `@EntityListeners(AuditingEntityListener.class)` 공통 상위 클래스 하나로 4개 컬럼을 상속시킨다. `created_by`/`updated_by`는 `AuditorAware<Long>` 구현이 `SecurityContext`의 `id_key`를 공급한다. 레거시 `CuDate`는 재사용하지 않는다(모듈·컬럼 규칙이 다름).

**Alternatives considered**:
- 시각 2개만(이전 판) — clarification B로 폐기
- DB 트리거로 채우기 — 애플리케이션이 아는 "누가"를 DB가 알 수 없음
- 별도 감사 이력 테이블 — 이 기능이 요구하지 않는 범위 확대

## 4. 삭제 정책과 FK

**Decision**: 기준 데이터는 삭제 표시(soft delete), 기록 데이터는 물리 삭제. 이 구분 덕분에 **참조 무결성 제약을 넓게 걸 수 있다.**

| 관계 | DB 동작 | 근거 |
|------|---------|------|
| 모든 자식 → `tbl_user(id_key)` | `RESTRICT` | 회원 물리 삭제 없음(FR-014, 정지는 플래그) |
| 지출·소득 → 수단 | `RESTRICT` | 수단은 삭제 표시만(FR-031) |
| 지출 → 지출유형 | `RESTRICT` | 지출유형도 삭제 표시만(FR-037) |
| 고정지출 관리 → 수단·지출유형 | `RESTRICT` | 위와 같음 |
| 월별 고정지출 내역 → 수단·지출유형 | `RESTRICT` | 위와 같음 |
| 목표금액(기본·월별) → 지출유형 | `RESTRICT` | FR-038 — 삭제 표시와 무관하게 참조 유지 |
| 월별 고정지출 내역 → 고정지출 관리 | **`CASCADE`** | FR-059 — 관리 행 삭제 시 지난 달 포함 전부 삭제 |
| 통계 상세 3종 → 통계 스냅샷 | **`CASCADE`** | 스냅샷이 사라지면 상세가 남을 이유 없음 |
| 통계 상세 → 지출유형·수단 | **FK 없음** | FR-078a — 끊긴 참조 허용 |
| 모든 테이블의 `created_by`/`updated_by` | FK 없음 | §3 참조 |

**이전 판과의 차이**: 이전 판은 지출유형이 **물리 삭제**되는 전제였고, 그래서 고정지출·목표금액·통계의 `expend_group_id`에 FK를 걸 수 없어 "논리 참조"로 남겼다. 지출유형이 삭제 표시로 바뀌면서 이 회피책이 통째로 불필요해졌고, 통계 상세만 예외로 남는다.

**지출유형 삭제 차단 조건**은 DB가 아니라 애플리케이션이 판정한다 — `ExpendGroupDelete`(2.12)의 `3106`(지출 사용 이력 있음)·`3107`(기본 유형)이다. 삭제가 UPDATE라서 FK RESTRICT가 대신 막아줄 수 없기 때문이다. 이 검사는 Phase 2 구현의 몫이고, 본 기능은 검사에 필요한 컬럼(`deleted`, `default_group`)과 인덱스만 제공한다.

## 5. 업무 유일 제약

**Decision**: PK는 전부 대리키이므로, 명세의 "최대 1건" 조건은 모두 **UNIQUE 제약**으로 따로 건다.

| 테이블 | UNIQUE | 근거 |
|--------|--------|------|
| `tbl_user` | `(user_id)` / `(email) WHERE email IS NOT NULL` | FR-010 / FR-012 |
| `tbl_user_session` | `(session_id)` / `(id_key) WHERE revoked = false` | FR-015 / FR-017 |
| `tbl_user_expend_group` | `(id_key, name)` | FR-035 |
| `tbl_fixed_expense_monthly` | `(fixed_expense_idx, year, month)` | FR-053 |
| `tbl_expend_target_default` | `(id_key, expend_group_idx)` | FR-070 |
| `tbl_expend_target_monthly` | `(id_key, year, month, expend_group_idx)` | FR-071 |
| `tbl_statistics` | `(id_key, year, month)` | FR-074 |
| `tbl_statistics_weekly` | `(statistics_idx, week_index)` | FR-077 |
| `tbl_statistics_expend_group` | `(statistics_idx, expend_group_idx)` | FR-077 |
| `tbl_statistics_payment_method` | `(statistics_idx, payment_method_idx)` | FR-077 |

**이메일 부분 유니크**: `UNIQUE (email) WHERE email IS NOT NULL`. 빈 이메일은 여러 명 허용, 값이 있으면 전역 유일(FR-012·Edge Cases).

**활성 세션 부분 유니크**: `UNIQUE (id_key) WHERE revoked = false`. DB가 "활성 세션 최대 1건"을 강제하면 동시 로그인 레이스에서도 안전하다(FR-017).

**지출유형 이름 유일성 범위**: 삭제 표시된 행을 **포함**해 유일하다(부분 유니크를 쓰지 않는다). FR-035가 조건 없이 "같은 회원 안에서 유일"이라고 적었고, 아이콘 파일명이 `{회원id}_{유형이름}.{확장자}`(2.7 비고)라 이름을 재사용하면 삭제된 유형의 아이콘 파일을 덮어쓰게 된다. 삭제된 이름을 다시 쓰고 싶다는 요구가 나오면 그때 아이콘 파일명 규칙과 함께 다시 본다.

**부분 유니크 인덱스와 Hibernate**: Hibernate `ddl-auto: update`는 `WHERE` 절이 붙은 부분 인덱스를 만들지 못한다. 부분 유니크 3건(이메일, 활성 세션, 그리고 필요 시)은 **보조 DDL 스크립트**로 따로 적용한다(§8).

## 6. 연·월·날짜·금액 타입

**Decision**:

| 항목 | 타입 | 적용 |
|------|------|------|
| 연 | `INT` | 고정지출 시작·종료, 월별 내역·목표·통계 키 |
| 월 | `INT` + `CHECK (month BETWEEN 1 AND 12)` | 위와 같음 |
| 결제일·주 시작·종료일 | `DATE` | `payment_date`, `week_start`, `week_end` |
| 매달 결제일 | `INT` + `CHECK (BETWEEN 1 AND 31)` | `tbl_fixed_expense.payment_day_of_month` |
| 금액 | `BIGINT` | 원 단위 정수(FR-005) |
| 비율·사용률 | `NUMERIC(5,2)` | 0.00~100.00 (FR-005 예외) |
| 시각 | `TIMESTAMPTZ` | 감사 컬럼, 토큰 만료, 저장 시각 |
| 카드 유효기간 | `CHAR(7)` | `YYYY-MM` 표시용 문자열(FR-030) |

**연·월을 INT 2개로 나누는 이유**: FR-051이 "연과 월을 각각 비교·정렬할 수 있는 형태"를 요구한다. 고정지출 적용 기간 판정은 `year * 12 + month` 합성값 비교로 하면 월 경계 계산이 단순해진다 — 월별 내역 lazy 생성(FR-054)과 수동 재작성(FR-060)이 같은 식을 쓴다.

**카드 유효기간만 문자열인 이유**: 값이 "2028-12"라는 표기 그 자체이고 범위 비교·정렬 요구가 없다. API도 `YYYY-MM` 문자열로 주고받는다.

**Alternatives considered**:
- 연월을 `CHAR(7) YYYY-MM`으로 — API와 같은 모양이지만 범위 비교와 `CHECK` 작성이 번거롭다
- 금액을 `NUMERIC` — 원 단위 정수라 소수 자리가 불필요하고 연산이 느리다
- 시각을 `TIMESTAMP`(무시간대) — 토큰 만료 비교에서 시간대 사고가 나기 쉽다

## 7. 스냅샷 vs 현재 이름

**Decision**: 세 갈래로 갈린다.

| 저장 단위 | 이름 처리 | 근거 |
|-----------|-----------|------|
| 지출·소득 | 등록 당시 이름을 **컬럼에 보존**(`payment_method_name`, `expend_group_name`) | FR-041 |
| 고정지출 관리·월별 고정지출 내역 | **보존하지 않음.** 조회 시 원본의 현재 이름 | FR-050·FR-053, 4.5·4.8 문서 |
| 통계 유형별·수단별 요약 | 저장 당시 이름을 **컬럼에 보존** + 대리키도 값으로 보관(FK 없음) | FR-078·FR-078a |

**왜 고정지출만 다른가**: 고정지출 내역은 "설정에서 파생된 값"이라 그 달 행이 관리 설정을 계속 따라간다는 성격을 유지해야 한다. 이름을 스냅샷으로 굳히면 수동 재작성(FR-060) 후 같은 달의 이름이 갱신 여부에 따라 갈린다.

**지출 수정 시 이름 갱신**: FR-042 — 참조가 바뀌면 보존 이름도 새 참조의 현재 이름으로 다시 쓴다. 이름만 바뀐 경우에는 과거 건을 건드리지 않는다.

## 8. 스키마 반영 수단

**Decision (2026-09-02 개정)**: **스키마 객체를 전부 Hibernate가 만든다.** 앱 기동 한 번으로 끝나며 뒤이어 실행할 보조 DDL 스크립트가 없다. `sql/04_constraints.sql`은 삭제했다.

| 수단 | 만드는 것 |
|------|-----------|
| `hibernate.hbm2ddl.create_namespaces: true` | 스키마 `moneylog` |
| Entity 애너테이션 (JPA 3.2 `@Table`) | 테이블·컬럼·PK·FK·일반 인덱스·조건 없는 UNIQUE·**CHECK 20건**·**테이블 주석 15건** |
| `AdditionalMappingContributor` (`MoneylogSchemaContributor`) | **부분 유니크 2건**·**시퀀스 `seq_installment_group`** |

**이전 판이 틀렸던 지점**: "Hibernate가 CHECK을 만들지 못한다"는 전제가 사실이 아니었다. Hibernate에는 `@Check(name, constraints)`가 있었고, Hibernate 7에서는 그것이 deprecated되고 **JPA 3.2 표준** `@Table(check = @CheckConstraint(name, constraint))`로 대체됐다 — 둘 다 **제약 이름을 지정할 수 있다.** 이름 통제가 스크립트를 둔 유일한 이유였으므로 근거가 사라졌다. 주석도 `@Table(comment = ...)`로 표준화되어 있다.

애너테이션으로 <b>정말</b> 표현할 수 없는 것은 둘뿐이다:

- **부분 유니크 인덱스** — `@Table(uniqueConstraints)`·`@Index`에 `WHERE` 절을 붙일 자리가 없다. JPA에도 Hibernate 애너테이션에도 부분 인덱스 개념이 없다
- **독립 시퀀스** — `@SequenceGenerator`는 어떤 Entity의 식별자 생성기로 쓰일 때만 DDL에 나온다. `seq_installment_group`은 N개 행이 공유하는 값이라 어느 PK의 생성기도 아니다(§9)

이 둘은 Hibernate의 `AdditionalMappingContributor` SPI(`META-INF/services`로 등록)가 보조 데이터베이스 객체로 낸다. **스크립트가 아니라 Hibernate의 스키마 관리 안에서** 실행되므로 별도 단계가 생기지 않는다. SQL은 `CREATE ... IF NOT EXISTS`로 멱등하게 두고, 스키마는 `${schema}` 자리표시자로 적는다 — 기여 시점에는 기본 네임스페이스가 확정되지 않아 이름을 직접 읽으면 빈 문자열이 되고, SQL이 스키마 없이 나가 접속의 `search_path`를 타고 엉뚱한 스키마에 만들어진다(실측 확인).

**Rationale**: 반영 단계가 둘에서 하나로 준다. 종전에는 앱을 띄운 뒤 스크립트를 잊지 않고 실행해야 했고, 잊으면 CHECK·부분 유니크가 없는 채로 조용히 동작했다 — 제약 위반이 잡히지 않는 상태라 발견이 늦다. 이제 기동만으로 완결된다. Flyway 도입은 여전히 이 기능의 범위 밖이다.

**동등성 검증**: 빈 스키마에 Hibernate만으로 만든 결과와 종전 방식으로 만든 스키마를 대조해 제약 72건·인덱스 35건·전 컬럼의 정의 차이가 **0건**임을 확인했다(주석 15건만 추가).

**`ddl-auto`**: 개발 단계라 `create`를 쓴다. `update`는 **이미 있는 테이블에 주석을 붙이지 않는다** — `comment on table`이 `create table`과 함께만 나가기 때문이다. 데이터를 남겨야 하는 시점이 오면 `update`로 되돌리고 주석 변경분은 스키마 재생성으로 반영한다.

반영 후 `pg_dump`로 `sql/schema-moneylogdb.sql`을 재생성한다(헌장 VI·FR-007). 이때 시드 데이터는 없다 — 기본 지출유형 10종은 마스터가 아니라 **회원마다 생기는 데이터**라 덤프에 넣지 않는다.

**Alternatives considered**:
- Flyway·Liquibase 전면 도입 — 범위 초과. 나중에 운영 배포가 생기면 별도 기능으로
- `ddl-auto: validate` + 전량 수동 DDL — 안전하지만 Entity 15개를 손 DDL과 이중 유지
- 부분 유니크를 애플리케이션 검사로 대체 — 동시성 레이스(중복 로그인·이메일)를 막지 못함

## 9. 할부 그룹 식별자

**Decision**: `installment_group_id BIGINT` — 전용 시퀀스 `seq_installment_group`에서 발급하고, 같은 할부의 N개 지출 행이 공유한다. 그룹 전용 테이블은 만들지 않는다.

**Rationale**: FR-043·FR-044. 할부 등록은 시퀀스에서 값 하나를 받아 N행에 같이 넣는 한 트랜잭션이다. 중도상환(FR-045)은 `WHERE installment_group_id = ? AND payment_date > CURRENT_DATE` 삭제 한 번으로 끝난다 — 이 조건을 위해 `(installment_group_id, payment_date)` 인덱스를 둔다.

**Alternatives considered**:
- 첫 회차 지출의 `idx`를 그룹 id로 — 첫 회차가 중도상환·삭제로 사라질 수 있어 그룹 식별이 깨진다
- UUID — 문자열 비교·용량만 늘고 이점 없음
- 할부 그룹 테이블 신설 — spec이 "저장 단위를 만들지 않는 것"에 명시

## 10. 조회 인덱스

**Decision**: FR-006이 요구하는 조회 조건을 인덱스로 뒷받침한다.

| 테이블 | 인덱스 | 쓰이는 곳 |
|--------|--------|-----------|
| `tbl_expense` | `(id_key, payment_date)` | 4.8 월별 가계부, 5.5 통계 |
| `tbl_expense` | `(installment_group_id, payment_date)` | 3.6 중도상환 |
| `tbl_income` | `(id_key, payment_date)` | 4.8, 5.5 |
| `tbl_fixed_expense` | `(id_key, start_year, start_month, end_year, end_month)` | 4.5·4.9 적용 기간 판정 |
| `tbl_fixed_expense_monthly` | `(id_key, year, month)` | 4.5·4.8·4.9 |
| `tbl_user_payment_method` | `(id_key, purpose, in_use, deleted)` | 2.6 사용 중 수단 |
| `tbl_user_expend_group` | `(id_key, in_use, deleted)` | 2.13 사용 중 유형 |
| `tbl_user_login_history` | `(id_key, login_at)` | 이력 조회 |

**장소·내용 부분 일치(`keyword`)**: 별도 인덱스를 두지 않는다. 월 범위로 먼저 좁힌 뒤 `LIKE '%...%'`를 걸므로 대상 행이 수십~수백 건이고, 개인 가계부 규모에서 trigram 인덱스는 과설계다. 규모가 커지면 `pg_trgm` GIN을 별도로 검토한다.

**회원 아이디·닉네임 검색(1.13)**: `tbl_user`는 전체 회원 수가 작아 순차 스캔으로 충분하다. `user_id`는 UNIQUE 인덱스가 이미 있다.

## 11. 기본 지출유형·아이콘

**Decision**: 회원가입·관리자 회원 추가 시 10종을 INSERT하고, 템플릿 PNG를 `{user_id}_{유형이름}.png`로 복사한 뒤 `icon_filename`에 그 파일명을 저장한다.

템플릿 위치·상태: `app-mod/money-backend-app/src/main/resources/seed/expend-group-icons/` — 10개 파일(교육·교통·기타·문화·쇼핑·식비·의료·장보기·주거·통신) **이미 커밋되어 있다.**

DB에는 **파일명만** 저장한다. `iconUrl`(`/api/v1/expend-groups/icons/{filename}`)은 응답 조립 시 파일명 앞에 고정 경로를 붙여 만든다 — 경로 문자열을 저장하면 Base URL이 바뀔 때 전 행을 고쳐야 한다(FR-036).

파일명을 컬럼에 담아 두므로 유형 이름을 나중에 바꿔도 기존 아이콘을 계속 찾을 수 있다(Edge Case). 즉 파일명은 **생성 시점에 한 번 정해지고 이름 변경을 따라가지 않는다.**

**시드 데이터 아님**: 10종은 회원마다 생기는 데이터라 `schema-moneylogdb.sql` 덤프에 넣지 않는다(FR-007 — 덤프는 코드·마스터 성격만).

INSERT·파일 복사 로직 자체는 회원가입 구현(Phase 1 API)의 몫이다. 본 기능은 컬럼·제약·템플릿 파일까지 준비한다.

## 12. 보존 정책

**Decision**: 폐기된 세션 행과 로그인 이력을 무기한 보존한다. 정리 배치·건수 상한·파티셔닝을 두지 않는다.

**Rationale**: FR-019a. 사용자 수가 많지 않아 누적량이 문제되지 않는다는 판단이다. 활성 세션 판정은 행 수와 무관하게 부분 유니크 인덱스(`WHERE revoked = false`)가 처리하므로, 폐기 행이 쌓여도 로그인 경로는 느려지지 않는다.
