**Created**: 2026-08-05

**Status**: Draft

## 개요

`프로젝트설계/2.1. 기능명세 - 백엔드.md`와 그 하위 상세 문서(`기능명세상세-백엔드/`)는 56개 백엔드 API를 정의하지만, 이 API들이 읽고 쓸 **데이터 저장 구조가 아직 없다**. 현재 `sql/schema-moneylogdb.sql` 덤프에는 `moneylog` 스키마만 있고 테이블이 한 개도 없다.

이 기능은 **56개 API가 요구하는 모든 데이터를 저장·조회할 수 있는 테이블 구조를 확정하는 것**이다. API 구현(Phase 1~5)은 이 구조가 확정된 뒤에 시작한다.

**범위에 포함**: 저장해야 하는 데이터 항목, 각 항목의 필수 여부·값 범위·유일성, 데이터 간 관계, 삭제·보존 정책, 가입 시 자동 생성되는 기본 데이터.

**범위에서 제외**: API Controller·Service 구현, 화면, 인증 필터 로직. 이 기능은 저장 구조만 확정한다.

## Clarifications

### Session 2026-08-07

- Q: 지출유형 삭제 시 어떤 참조가 삭제를 막나요? → A: 지출 내역만 막음(현재 FR-027). 고정지출·목표금액·통계는 삭제를 막지 않음
- Q: 할부 중도상환 시 “남은 회차”는 무엇인가요? → A: 결제일이 오늘 초과(> today)인 회차만 제거. 오늘 결제일 건은 유지
- Q: 수단의 용도(purpose)는 등록 후 바꿀 수 있나요? → A: 해당 수단을 참조하는 지출·소득이 한 건도 없을 때만 용도 변경 허용
- Q: 고정지출 설정도 수단·유형 이름을 스냅샷으로 저장하나요? → A: 설정에는 참조만 저장. 조회·전개 시 원본 이름으로 표시
- Q: 가입 시 기본 지출유형 10종의 아이콘은 어떻게 하나요? → A: 10종 모두 기본 아이콘 파일(30×30px)을 두고 각 행에 파일 식별 정보를 채움. 템플릿 아이콘도 제공

### Session 2026-08-29

- Q: 고정지출을 지출 내역에 섞어 저장하나요? → A: **아니다.** 고정지출 관리(설정), 월별 고정지출 내역, 월별 수입/지출 내역을 **서로 다른 저장 단위로 분리**한다. 월별 조회 시 고정지출과 일반 수입·지출을 나눠서 읽을 수 있어야 한다
- Q: 월별 수입/지출 내역은 한 저장 단위인가요? → A: 지출과 소득은 지금처럼 **각각 별도 저장 단위**로 둔다(지출에만 할부·지출유형이 있어 구조가 다름). 분리 목적은 고정지출과의 분리로 이미 충족된다
- Q: 월별 고정지출 내역 행은 언제 만들어지나요? → A: **그 달을 처음 조회할 때 생성**한다(lazy). 미리 전체 기간을 만들지 않고, 배치도 쓰지 않는다
- Q: 기존 "고정지출 월별 예외"는 어떻게 되나요? → A: **없앤다.** 월별 고정지출 내역이 대체한다. 그 달 값을 바꾸려면 예외 행을 따로 두지 않고 그 달의 내역 행을 직접 고친다

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 회원·인증 데이터를 저장할 수 있다 (Priority: P1)

회원가입·로그인·토큰 갱신·로그아웃·회원 정보 수정·관리자 회원 관리(기능번호 1.1~1.16)가 필요한 데이터를 모두 저장하고 다시 읽을 수 있다. 회원 한 명당 활성 세션이 하나만 존재하는 규칙을 저장 구조 차원에서 지킬 수 있다.

**Why this priority**: Phase 1은 다른 모든 Phase의 선행 조건이다. 회원 식별자가 확정되지 않으면 이후 모든 데이터가 소유자를 가리킬 수 없다. 이 스토리만 완성해도 "가입 → 로그인 → 내 정보 조회"라는 최소 동작 가능한 제품이 성립한다.

**Independent Test**: 회원 1건과 그 회원의 세션 1건을 저장한 뒤, 아이디로 회원을 찾고 세션 식별자로 세션을 찾을 수 있는지 확인한다. 같은 회원에 활성 세션을 두 개 만들려 하면 이전 세션이 폐기 상태로 남는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 저장 구조가 준비된 상태, **When** 아이디·비밀번호 해시·닉네임·권한·활성 여부를 갖춘 회원 1건을 저장하면, **Then** 저장이 성공하고 아이디로 그 회원을 다시 읽을 수 있다.
2. **Given** 이미 같은 아이디의 회원이 있는 상태, **When** 동일한 아이디로 회원을 또 저장하려 하면, **Then** 저장이 거부된다.
3. **Given** 이미 같은 이메일의 회원이 있는 상태, **When** 동일한 이메일로 회원을 또 저장하려 하면, **Then** 저장이 거부된다. 이메일이 비어 있는 회원은 여러 명 존재할 수 있다.
4. **Given** 회원 1건이 저장된 상태, **When** 그 회원의 세션(Access·Refresh 해시, 각 만료 시각, 폐기 여부, 생성 시각)을 저장하면, **Then** 세션 식별자로 세션을 읽을 수 있고 회원과 연결된다.
5. **Given** 활성 세션이 있는 회원이 다시 로그인한 상태, **When** 기존 세션을 폐기 처리하면, **Then** 그 세션의 Access·Refresh 해시가 비워지고 폐기 여부가 참으로 남으며, 회원의 활성 세션은 새로 만든 1건뿐이다.
6. **Given** 회원가입이 일어난 상태, **When** 기본 지출유형 자동 등록이 수행되면, **Then** 그 회원 소유의 기본 지출유형 **10건**(식비·교통·주거·통신·쇼핑·장보기·의료·교육·문화·기타)이 생성되고 각 행은 "시스템 기본 유형"으로 표시되며, **각 행에 30×30 기본 아이콘 파일 식별 정보가 채워진다**.

### User Story 2 - 지출·소득 수단과 지출유형을 저장할 수 있다 (Priority: P2)

수단 CRUD와 지출유형 CRUD(기능번호 2.1~2.13)가 필요한 데이터를 저장한다. 수단은 삭제해도 과거 내역이 참조할 수 있도록 흔적을 남기고, 지출유형은 아이콘 파일을 다시 찾을 수 있는 정보를 갖는다.

**Why this priority**: 지출·소득 1건은 반드시 수단 1개와(지출은) 지출유형 1개를 가리킨다. Phase 3 이후 데이터를 만들려면 이 두 축이 먼저 있어야 한다.

**Independent Test**: 한 회원의 수단·지출유형을 등록·수정·삭제한 뒤, "사용 중이고 삭제되지 않은 것만" 골라내는 조회와 "삭제된 것까지 전부" 조회가 서로 다른 결과를 내는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 회원 1명이 있는 상태, **When** 이름·종류(카드/계좌)·용도(지출 또는 소득)·사용 여부를 갖춘 수단을 저장하면, **Then** 저장이 성공하고 그 회원의 수단으로 조회된다. 한 수단은 지출용 또는 소득용 중 하나만 갖는다.
2. **Given** 카드 종류의 수단을 저장할 때, **When** 카드 유효기간을 `YYYY-MM` 형태로 함께 저장하면, **Then** 그 값이 보존된다. 계좌 종류일 때 유효기간은 비어 있을 수 있다.
3. **Given** 지출 내역이 이미 참조하고 있는 수단, **When** 그 수단을 삭제하면, **Then** 행이 물리적으로 사라지지 않고 삭제 표시만 남으며 과거 내역에 남은 수단 이름이 그대로 읽힌다.
4. **Given** 한 회원이 "식비" 지출유형을 가진 상태, **When** 같은 회원이 이름이 "식비"인 지출유형을 또 만들려 하면, **Then** 저장이 거부된다. 다른 회원은 같은 이름을 쓸 수 있다.
5. **Given** 아이콘 파일이 업로드된 지출유형, **When** 유형을 다시 읽으면, **Then** 아이콘 파일을 특정할 수 있는 정보가 함께 읽히고, 아이콘이 없는 유형은 그 값이 비어 있다.
6. **Given** 지출 내역이 한 번이라도 사용한 지출유형, **When** 그 유형을 삭제하려 하면, **Then** 삭제가 거부된다.

### User Story 3 - 지출·소득과 할부 내역을 저장할 수 있다 (Priority: P3)

지출·소득 CRUD, 할부 일괄 등록·중도상환, 엑셀 일괄 등록(기능번호 3.1~3.12)이 필요한 데이터를 저장한다. 할부는 등록 시점에 개월 수만큼의 건이 만들어지고, 같은 할부 계획끼리 묶여서 식별된다.

**Why this priority**: 가계부의 핵심 데이터다. 다만 수단·유형(P2)이 없으면 저장할 수 없으므로 그 다음 순위다.

**Independent Test**: 일시불 지출 1건, 12개월 할부 1건(12행), 소득 1건을 저장한 뒤, 할부 12행이 같은 그룹 식별자를 공유하고 1~12번째 순번을 갖는지, 남은 회차만 골라 제거할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 수단·지출유형이 있는 회원, **When** 수단·금액·결제일·장소·내용·지출유형을 갖춘 지출 1건을 저장하면, **Then** 저장이 성공하고 등록 시점의 수단 이름·지출유형 이름이 그 지출 건에 함께 남는다.
2. **Given** 지출 1건이 저장된 뒤 수단 이름이 바뀐 상태, **When** 그 지출을 다시 읽으면, **Then** 지출에 남은 수단 이름은 등록 당시 값 그대로다.
3. **Given** 월 납부액·12개월·시작 연월을 갖춘 할부 등록, **When** 저장이 수행되면, **Then** 12개 건이 만들어지고 모두 같은 할부 그룹 식별자를 공유하며 1~12의 순번과 총 개월 수 12를 각각 갖는다.
4. **Given** 12개월 할부 중 결제일이 오늘인 회차와 그 이전·이후 회차가 있는 상태, **When** 중도상환을 처리하면, **Then** 결제일이 오늘보다 뒤인 건만 사라지고 오늘·과거 결제일 건은 그대로 남는다.
5. **Given** 소득 저장 요청, **When** 수단·금액·결제일만 주고 내용을 비운 채 저장하면, **Then** 저장이 성공하고 내용은 비어 있는 상태로 읽힌다.
6. **Given** 같은 날짜·금액·수단의 지출 2건, **When** 둘 다 저장하면, **Then** 둘 다 저장된다(중복 허용).

### User Story 4 - 고정지출 관리와 월별 고정지출 내역을 분리해 저장할 수 있다 (Priority: P4)

고정지출 관리 CRUD(4.1~4.4, 4.7), 월별 고정지출 내역 조회·단건 수정·수동 재작성(4.5·4.6·4.9), 그리고 월별 가계부 목록(4.8)이 필요한 데이터를 저장한다. **고정지출 관리**(달마다 반복되는 설정)와 **월별 고정지출 내역**(실제 그 달에 잡히는 한 건)을 서로 다른 저장 단위로 두고, **월별 수입·지출 내역**과도 섞지 않는다. 월별 고정지출 내역은 그 달을 처음 조회할 때 설정에서 만들어 저장한다.

**Why this priority**: 월별 가계부 목록에 고정지출이 포함되므로 목록 조회 완성 전에 필요하다. 지출·소득(P3)만으로도 목록의 일부는 성립하므로 그 다음 순위다.

**Independent Test**: 고정지출 1건을 시작·종료 연월과 함께 저장하고, 그 기간 중 두 달을 각각 조회해 월별 고정지출 내역이 두 건 생겼는지 확인한다. 한 달의 금액만 고친 뒤 두 달을 다시 읽어 값이 다르게 나오고, 같은 달을 또 조회해도 내역이 늘지 않는지 확인한다. 같은 달의 일반 지출·소득 내역과 고정지출 내역을 **따로** 셀 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 수단·지출유형이 있는 회원, **When** 이름·수단·기본 금액·매달 결제일·내용·지출유형·시작 연월·종료 연월을 갖춘 고정지출을 저장하면, **Then** 고정지출 관리 저장이 성공하고 이 시점에는 월별 내역이 하나도 만들어지지 않는다.
2. **Given** 적용 기간이 2026-01~2026-12인 고정지출 1건, **When** 2026-03 가계부를 처음 조회하면, **Then** 그 달의 고정지출 내역 1건이 설정값(금액·결제일·내용·수단·지출유형)으로 만들어져 저장된다.
3. **Given** 2026-03 내역이 이미 만들어진 상태, **When** 같은 달을 다시 조회하면, **Then** 내역이 중복 생성되지 않고 기존 1건이 그대로 읽힌다.
4. **Given** 2026-03 고정지출 내역 1건, **When** 그 달의 금액만 다르게 저장하면, **Then** 2026-03은 바뀐 값이 읽히고 2026-04는 설정 기본값으로 만들어진다.
5. **Given** 월별 고정지출 내역이 3건 만들어진 고정지출, **When** 고정지출 관리 행을 삭제하면, **Then** 월별 내역 3건도 함께 사라진다.
6. **Given** 같은 달에 일반 지출 2건·소득 1건·고정지출 내역 2건이 있는 상태, **When** 그 달을 조회하면, **Then** 고정지출 내역과 일반 수입·지출 내역을 **각각 따로** 읽을 수 있다.
7. **Given** 적용 기간이 2026-01~2026-12인 고정지출, **When** 2025-12 가계부를 조회하면, **Then** 그 달에는 고정지출 내역이 만들어지지 않는다.

### User Story 5 - 목표금액과 월별 통계 스냅샷을 저장할 수 있다 (Priority: P5)

지출유형별 기본 목표금액·월별 목표금액(기능번호 5.1~5.4)과, 저장 시점 계산 결과를 그대로 보존하는 월별 통계 스냅샷(5.5~5.6)이 필요한 데이터를 저장한다.

**Why this priority**: 통계는 앞선 모든 데이터를 집계한 결과이므로 마지막이다. 없어도 가계부 본체는 동작한다.

**Independent Test**: 한 지출유형에 기본 목표금액을 저장하고, 특정 연·월에만 다른 목표금액을 저장한 뒤, 두 값이 각각 독립적으로 읽히는지 확인한다. 통계를 저장한 뒤 원본 지출을 바꿔도 저장된 통계 값이 변하지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 사용 중인 지출유형, **When** 기본 목표금액을 저장하면, **Then** 연·월과 무관하게 그 유형의 기본값으로 읽힌다.
2. **Given** 기본 목표금액이 저장된 지출유형, **When** 특정 연·월의 목표금액만 저장하면, **Then** 기본값은 바뀌지 않고 그 연·월에만 다른 값이 읽힌다.
3. **Given** 같은 회원·연·월·지출유형의 월별 목표금액이 이미 있는 상태, **When** 같은 조합으로 다시 저장하면, **Then** 행이 중복되지 않고 값만 갱신된다.
4. **Given** 어떤 달의 통계를 저장한 상태, **When** 그 달의 지출을 이후에 수정하고 저장된 통계를 다시 읽으면, **Then** 저장 당시의 합계·목표·비율 값이 그대로 읽힌다.
5. **Given** 어떤 달의 통계가 이미 저장된 상태, **When** 같은 달의 통계를 다시 저장하면, **Then** 스냅샷이 1건으로 유지되며 값과 저장 시각이 갱신된다.
6. **Given** 통계 스냅샷 1건, **When** 그것을 읽으면, **Then** 주별 지출·유형별 요약·수단별 요약·고정 대 일반 비율·소득 합계를 모두 되살릴 수 있고, 유형별 요약에 남은 유형 이름은 저장 당시 이름이다.

---

### Edge Cases

- 회원이 이메일을 입력하지 않은 경우: 이메일 중복 제약이 "비어 있는 값" 여러 건을 막지 않아야 한다.
- 수단이 삭제 표시된 뒤 그 수단을 참조하는 새 지출을 만들려는 경우: 저장 구조는 참조를 물리적으로 막지 않되, 과거 참조는 계속 유효해야 한다.
- 수단 용도를 바꾸려는데 그 수단을 참조하는 지출 또는 소득이 이미 있는 경우: 용도 변경이 거부되어야 한다. 참조가 하나도 없을 때만 변경할 수 있다.
- 지출유형 이름이 변경된 뒤 과거 지출 건을 조회하는 경우: 과거 건의 유형 이름은 변경 전 이름으로 남는다.
- 지출 내역이 없고 고정지출·목표만 있는 지출유형을 삭제하는 경우: 삭제가 허용된다. 고정지출·목표가 가리키던 유형 참조는 저장 구조가 삭제를 막지 않는다(애플리케이션 검증은 별도).
- 아이콘 파일명이 회원 아이디와 유형 이름으로 만들어지는데 유형 이름을 바꾼 경우: 기존 아이콘 파일을 계속 찾을 수 있어야 한다(파일명을 이름에서 매번 다시 계산하면 찾을 수 없게 된다).
- 할부 12개월 중 일부 저장이 실패한 경우: 12건이 부분 저장된 상태로 남지 않아야 한다.
- 할부 그룹의 모든 회차가 삭제된 경우: 그룹 식별자만 남아 아무 건도 없는 상태를 조회할 수 있어야 한다(오류가 아니라 "남은 회차 없음").
- 중도상환 시 결제일이 오늘인 할부 건이 있는 경우: 그 건은 제거 대상이 아니다(`paymentDate` > 오늘만 제거).
- 고정지출의 매달 결제일이 31일이고 해당 월이 30일까지인 경우: 관리 테이블에는 31로 저장되고, 월별 고정지출 내역을 만들 때 그 달의 마지막 날로 보정한다.
- 고정지출 적용 기간 밖의 연·월을 조회하거나 그 연·월에 수동 재작성을 실행하는 경우: 그 고정지출의 내역은 만들어지지 않는다.
- 같은 연·월을 두 요청이 **동시에** 처음 조회하는 경우: 월별 고정지출 내역이 중복으로 만들어지지 않아야 한다.
- 어떤 달의 고정지출 내역을 직접 수정한 뒤 고정지출 관리의 금액을 바꾸는 경우: 직접 수정한 달의 값은 **바뀌지 않는다**.
- 직접 수정한 달에 수동 재작성을 실행하는 경우: 기본값(보존)으로 실행하면 그 행은 그대로 남고, 덮어쓰기를 선택하면 관리 테이블 값으로 되돌아간다.
- 고정지출 적용 기간을 줄인 뒤 이미 만들어진 달에 수동 재작성을 실행하는 경우: 그 연·월이 더는 기간에 포함되지 않으면 내역이 사라진다.
- 고정지출이 참조하는 수단·유형 이름이 바뀐 뒤 가계부를 조회하는 경우: 월별 고정지출 내역 조회 결과에 보이는 이름은 **변경 후 현재 이름**이다(관리·내역 어느 쪽에도 이름 스냅샷 없음).
- 같은 달에 일반 지출과 고정지출이 함께 있는 경우: 두 내역은 서로 다른 저장 단위에 있으므로 한쪽만 골라 조회하거나 지우는 것이 가능해야 한다.
- 월별 목표금액이 없는 달을 조회하는 경우: 값이 "없음"으로 구분되어야 하며, 기본값 `0`이 저장된 것과 혼동되지 않아야 한다.
- 통계 저장 시 지출이 0원인 지출유형: 유형별 요약에서 제외된다. 반면 0원인 수단은 수단별 요약에 포함된다.
- 회원이 삭제(정지)된 경우: 정지는 활성 여부 표시이며 회원 행과 그 회원의 가계부 데이터는 남는다.

## Requirements *(mandatory)*

### Functional Requirements — 공통·전역

- **FR-001**: 저장 구조는 `프로젝트설계/2.1. 기능명세 - 백엔드.md`와 `기능명세상세-백엔드/` 하위 문서에 정의된 56개 API가 요구하는 모든 요청 저장 항목과 응답 반환 항목을 **저장하거나 저장된 값에서 파생**할 수 있어야 한다.
- **FR-002**: 회원별 데이터(수단, 지출유형, 지출, 소득, 고정지출, 목표금액, 통계)는 **모두 소유 회원을 식별할 수 있어야** 한다. 소유자가 다른 데이터가 서로 섞이지 않아야 한다.
- **FR-003**: 모든 데이터 항목에 대해 **필수 여부(빈 값 허용 여부)** 가 명시되어야 하며, 명세에서 필수인 항목은 빈 값으로 저장될 수 없어야 한다.
- **FR-004**: 각 저장 항목은 **생성 시각과 최종 수정 시각**을 남긴다. 세션은 명세가 정한 생성 시각·최종 접근 시각을 별도로 갖는다.
- **FR-005**: 금액은 **원 단위 정수**로 저장하며 소수점 오차가 생기는 방식으로 저장하지 않는다.
- **FR-006**: 목록·조회 API가 조건으로 사용하는 항목(연·월, 결제일 범위, 수단, 지출유형, 장소·내용 부분 일치, 회원 아이디·닉네임 검색)은 **그 조건으로 찾을 수 있는 형태**로 저장되어야 한다.
- **FR-007**: 구조가 확정·반영되면 `sql/schema-moneylogdb.sql` 덤프를 **재생성해 같은 커밋에 포함**한다. 덤프에는 코드·마스터 성격의 기본 데이터만 포함하고 회원·거래 실데이터는 포함하지 않는다.
- **FR-008**: 신규 저장 구조의 물리 테이블 이름은 **`tbl_` 접두사**를 붙인다. 레거시 `money-app` 엔티티가 쓰는 테이블 이름(`tbl_member`, `tbl_expend`, `tbl_expend_group`, `tbl_payment_Method`, `tbl_card`, `tbl_expend_fix`, `tbl_Ammount`, `tbl_login_history`, `tbl_system_stat`, 통계 관련 등)과 **이름이 겹치지 않아야** 한다. 레거시 테이블은 그대로 두고, 백엔드 신규 API용 테이블은 **별도 이름**으로 공존한다.

### Functional Requirements — 회원·인증 (Phase 1)

- **FR-010**: 회원은 **로그인 아이디**를 가지며 전체에서 유일하다. 아이디는 4~20자, 영문·숫자·`_`만 허용한다. 아이디는 변경 API가 없으므로 변경되지 않는 값으로 취급한다.
- **FR-011**: 비밀번호는 **단방향 해시 문자열만** 저장한다(약 60자). 평문 비밀번호는 어떤 항목에도 저장하지 않는다.
- **FR-012**: 회원은 **닉네임**(2~20자, 필수), **이메일**(비어 있을 수 있음, 값이 있으면 전체에서 유일), **전화번호**(비어 있을 수 있음, 숫자만), **자기소개**(비어 있을 수 있음)를 갖는다.
- **FR-013**: 회원은 **권한**을 갖고 값은 `1`(관리자) 또는 `3`(일반)만 허용한다. 가입 시 기본값은 `3`이다.
- **FR-014**: 회원은 **활성 여부**를 갖는다. 생성 시 활성이고, 관리자 정지 시 비활성으로 바뀐다. 비활성화는 회원 행이나 그 회원의 가계부 데이터를 삭제하지 않는다.
- **FR-015**: 세션은 **세션 식별자**(전역 유일, 토큰에 담기는 값), 소유 회원, **Access 토큰 해시**, **Refresh 토큰 해시**, **Access 만료 시각**, **Refresh 만료 시각**, **폐기 여부**, **생성 시각**, **최종 접근 시각**을 갖는다. 두 토큰 해시와 최종 접근 시각은 비어 있을 수 있다.
- **FR-016**: 세션 폐기는 **두 토큰 해시를 비우고 폐기 여부를 참으로 바꾸는 것**이며 세션 행을 삭제하지 않는다. 폐기 이력이 남아야 "다른 곳에서 로그인됨"과 "세션 없음"을 구분할 수 있다.
- **FR-017**: 한 회원에게 **폐기되지 않은 세션은 동시에 1건만** 존재한다.
- **FR-018**: 로그인 이력을 남긴다. 최소 항목은 대상 회원, 로그인 시각, 접속 IP다.
- **FR-019**: 회원가입·관리자 회원 추가 시 **그 회원 소유의 기본 지출유형 10건**이 함께 생성된다. 생성되는 행은 "시스템 기본 유형"으로 표시되고 사용 중 상태로 시작한다. 확정 목록(순서 고정): **식비, 교통, 주거, 통신, 쇼핑, 장보기, 의료, 교육, 문화, 기타**. **10종 모두 기본 아이콘 파일**을 두고 각 행의 아이콘 파일 식별 정보를 채운다. 아이콘은 **30×30 픽셀**이며, 가입 시 템플릿에서 `{회원id}_{유형이름}.png` 형식으로 복사·저장한다.

### Functional Requirements — 수단·지출유형 (Phase 2)

- **FR-020**: 수단은 소유 회원, **이름**(필수), **종류**(`CARD` 또는 `ACCOUNT`), **용도**(`EXPENSE` 또는 `INCOME`, 필수), **사용 여부**, **카드 유효기간**(`YYYY-MM`, 비어 있을 수 있음), **삭제 표시**를 갖는다.
- **FR-021**: 수단 삭제는 **삭제 표시만 바꾸고 행을 지우지 않는다**. 과거 지출·소득 내역이 그 수단의 이름을 계속 읽을 수 있어야 한다.
- **FR-022**: "사용 중인 수단 목록"은 **사용 여부가 참이고 삭제되지 않은** 것만 골라낼 수 있어야 한다.
- **FR-023**: 수단 **1건은 지출용(`EXPENSE`) 또는 소득용(`INCOME`) 중 한쪽만** 갖는다. 용도는 저장 항목으로 두고, "사용 중인 수단 목록"은 이 값으로 걸러낸다. 한 수단을 지출·소득에 동시에 쓰지 않는다. **등록 후 용도 변경은 그 수단을 참조하는 지출·소득이 한 건도 없을 때만** 허용한다. (상세 명세 `PaymentMethodCreate`/`Update`에 `purpose` 반영이 필요하며, 이 기능의 후속·병행으로 `프로젝트설계/기능명세상세-백엔드/` 문서를 개정한다.)
- **FR-024**: 지출유형은 소유 회원, **이름**(필수), **사용 여부**, **시스템 기본 유형 여부**, **아이콘 파일 식별 정보**(비어 있을 수 있음)를 갖는다.
- **FR-025**: 지출유형 이름은 **같은 회원 안에서 유일**하다. 회원이 다르면 같은 이름이 존재할 수 있다.
- **FR-026**: 아이콘은 **파일 저장소에 두고 데이터베이스에는 그 파일을 찾을 수 있는 정보만** 남긴다. 아이콘이 없으면 그 값은 비어 있다.
- **FR-027**: 지출유형은 **지출 내역이 한 번도 참조하지 않았고 시스템 기본 유형이 아닐 때만** 삭제된다. 삭제 시 행은 사라지고 아이콘 파일은 남는다. **고정지출 설정·목표금액(기본·월별)·통계 스냅샷**이 같은 유형을 가리켜도 삭제를 막지 않는다(지출 외 참조는 저장 구조상 삭제 차단 조건이 아님).

### Functional Requirements — 지출·소득 (Phase 3)

- **FR-030**: 지출은 소유 회원, **수단 참조**, **등록 당시 수단 이름**, **금액**(0보다 큰 정수), **결제일**(날짜), **장소**(필수), **내용**(필수), **지출유형 참조**, **등록 당시 지출유형 이름**을 갖는다.
- **FR-031**: 수단 이름·지출유형 이름은 **지출 건 자체에 보존**된다. 이후 원본 이름이 바뀌거나 원본이 삭제되어도 과거 건의 이름은 등록 당시 값을 유지한다.
- **FR-032**: 지출 수정으로 수단 또는 지출유형 참조가 바뀌면 **보존된 이름도 새 참조의 현재 이름으로 갱신**된다.
- **FR-033**: 지출은 추가로 **할부 그룹 식별자**, **할부 회차 번호**(1부터), **총 할부 개월 수**를 가질 수 있다. 세 값이 모두 비어 있으면 일시불이다.
- **FR-034**: 할부 등록은 개월 수만큼의 지출 건을 만들고, 그 건들은 **같은 할부 그룹 식별자를 공유**한다. 그룹 식별자는 서버가 만든다. 일부가 실패하면 전체가 저장되지 않는다.
- **FR-035**: 할부 중도상환은 **결제일이 오늘보다 뒤인(`paymentDate` > 오늘) 회차 건들을 제거**하는 것이며, 별도의 상환 상태 항목을 두지 않는다. **결제일이 오늘인 건과 오늘 이전인 건은 그대로 남긴다**.
- **FR-036**: 소득은 소유 회원, **수단 참조**, **등록 당시 수단 이름**, **금액**(0보다 큰 정수), **결제일**, **내용**(비어 있을 수 있음)을 갖는다. 소득에는 장소·지출유형·할부 항목이 없다.
- **FR-037**: 지출·소득 삭제는 **행을 실제로 지운다**(삭제 표시 방식이 아니다).
- **FR-038**: 같은 회원·같은 날짜·같은 금액·같은 수단의 건이 여러 개 존재할 수 있다. 업무 항목 조합에 중복 금지 제약을 걸지 않는다.
- **FR-039**: 엑셀 일괄 등록은 **지출·소득 행만** 만든다. 업로드 이력·배치 식별자·오류 로그를 저장하지 않는다.

### Functional Requirements — 고정지출 (Phase 4)

- **FR-040**: **고정지출 관리** 저장 단위는 소유 회원, **이름**(중복 허용), **수단 참조**, **기본 금액**, **매달 결제일**(1~31), **내용**, **지출유형 참조**, **시작 연월**, **종료 연월**을 갖는다. **수단 이름·지출유형 이름은 이 행에 스냅샷으로 두지 않는다.** 목록·상세·가계부 조회 시 원본 수단·유형의 현재 이름을 읽는다.
- **FR-041**: 연월은 **연과 월을 각각 비교·정렬할 수 있는 형태**로 저장한다. 종료 연월은 시작 연월보다 뒤여야 한다.
- **FR-042**: 고정지출 관리와 **월별 고정지출 내역**은 **서로 다른 저장 단위**다. 월별 고정지출 내역은 **월별 지출 내역(FR-030 계열)과도 같은 저장 단위에 두지 않는다.** 월별 가계부는 고정지출 내역과 일반 수입·지출 내역을 **각각 따로 조회할 수 있어야** 한다.
- **FR-043**: 월별 고정지출 내역은 **고정지출 1건 + 연 + 월 조합에 대해 최대 1건**만 존재한다. 소유 회원, 그 달의 **금액**, **결제일**, **내용**, **수단 참조**, **지출유형 참조**, 그리고 **그 달 값이 직접 수정되었는지 여부**를 갖는다. 수단·유형 이름 스냅샷은 두지 않는다.
- **FR-044**: 월별 고정지출 내역은 **그 연·월을 처음 조회할 때** 고정지출 관리 값을 복사해 만들어 저장한다. 등록 시점에 적용 기간 전체를 미리 만들지 않으며, 배치로 만들지도 않는다. 같은 연·월을 다시 조회해도 **행이 늘어나지 않는다**(동시 요청 포함). 결제일은 저장 시점에 **그 달에 실제로 존재하는 날짜로 확정**된다(매달 결제일이 그 달의 마지막 날보다 크면 마지막 날로 보정).
- **FR-045**: 월별 고정지출 내역이 만들어지는 연·월은 **고정지출 적용 기간(시작~종료 연월) 안**으로 한정된다. 기간 밖 연·월에는 내역이 만들어지지 않는다.
- **FR-046**: 그 달만 값을 바꾸는 월별 수정은 **그 달의 고정지출 내역 행을 직접 고쳐** 이뤄진다. 바꿀 수 있는 항목은 **금액, 결제일, 내용, 수단**이며, 바꾼 행은 **직접 수정됨**으로 표시된다. 별도의 "예외" 저장 단위는 두지 않는다.
- **FR-047**: 고정지출 관리 값을 바꾸면 **직접 수정되지 않았고 아직 오지 않은 달**의 내역만 새 설정값을 따라간다. **직접 수정된 달**과 **이미 지난 달·이번 달**의 내역은 그대로 남는다.
- **FR-048**: 고정지출 관리 행을 삭제하면 그 고정지출의 **월별 고정지출 내역도 모두 함께 사라진다**. 이미 지난 달의 내역도 함께 사라진다.
- **FR-049**: 특정 연·월의 고정지출 내역을 **고정지출 관리 내용 기준으로 다시 맞추는 조작**(수동 재작성)을 지원한다. 이 조작은 그 연·월에 대해 다음을 한 번에 처리한다.
  - **추가**: 적용 기간에 걸리는데 내역이 없는 고정지출(신규 등록분 포함) → 새 내역을 만든다.
  - **갱신**: 이미 있는 내역 중 **직접 수정되지 않은** 행 → 관리 테이블의 현재 값으로 덮어쓴다.
  - **삭제**: 관리 테이블에서 사라졌거나 적용 기간이 그 연·월을 더는 포함하지 않는 내역 → 없앤다.
  - **보존 선택**: **직접 수정된** 행을 덮어쓸지 남길지는 조작 시 선택할 수 있어야 한다. 기본은 **남긴다**.

  FR-047의 자동 반영이 "미래 달, 직접 수정되지 않은 행"으로 제한되는 것과 달리, 이 조작은 **지정한 연·월 하나**를 대상으로 하며 **지난 달에도 쓸 수 있다**.

### Functional Requirements — 목표금액·통계 (Phase 5)

- **FR-050**: 기본 목표금액은 **회원 + 지출유형 조합에 최대 1건**이며 금액 하나를 갖는다. 값 범위는 0 이상 1억 이하다.
- **FR-051**: 월별 목표금액은 **회원 + 연 + 월 + 지출유형 조합에 최대 1건**이며 금액 하나를 갖는다. 값 범위는 0 이상 1억 이하다.
- **FR-052**: 기본 목표금액과 월별 목표금액은 **서로 독립적으로 저장·변경**된다. 기본값을 바꿔도 이미 저장된 월별 값은 바뀌지 않으며, 기본값을 월별 항목에 복사해 저장하지 않는다.
- **FR-053**: "월별 목표금액이 저장되지 않은 상태"와 "월별 목표금액이 0으로 저장된 상태"는 **서로 구분**되어야 한다.
- **FR-054**: 월별 통계 스냅샷은 **회원 + 연 + 월 조합에 최대 1건**이며, 다시 저장하면 행이 늘지 않고 값과 **저장 시각**이 갱신된다.
- **FR-055**: 스냅샷은 저장 당시 계산 결과를 그대로 보존해야 하며, 이후 원본 지출·소득·목표금액이 바뀌어도 값이 변하지 않아야 한다.
- **FR-056**: 스냅샷은 다음을 모두 되살릴 수 있어야 한다.
  - 월 소득 합계, 월 지출 합계
  - 고정 지출 금액·일반 지출 금액과 각각의 비율
  - **주별 지출**: 주 순번, 주 시작일, 주 종료일, 그 주 지출 합계
  - **지출유형별 요약**: 지출유형 참조, 저장 당시 유형 이름, 지출 합계, 적용된 목표금액, 사용률, 상태 구분
  - **수단별 요약**: 수단 참조, 저장 당시 수단 이름, 지출 합계
- **FR-057**: 지출유형별 요약과 수단별 요약은 **회원 + 연 + 월 안에서 각 지출유형·수단마다 최대 1건**이다. 주별 지출은 회원 + 연 + 월 안에서 주 순번마다 최대 1건이다.
- **FR-058**: 통계에 저장되는 이름(유형 이름·수단 이름)은 **저장 시점 값**이며 이후 원본 이름 변경에 영향받지 않는다.
- **FR-059**: 저장본 존재 여부로 "저장된 통계"와 "즉석 계산 통계"를 구분한다. 즉석 계산 결과는 저장하지 않는다.

### Key Entities

명세가 요구하는 저장 단위는 다음 15종이다. 이름은 논리적 명칭이며 물리 명칭은 설계 단계에서 확정한다.

| # | 저장 단위 | 무엇을 담는가 | 주요 관계 |
|---|---|---|---|
| 1 | 회원 | 로그인 아이디, 비밀번호 해시, 닉네임, 이메일, 전화번호, 자기소개, 권한, 활성 여부 | 아래 대부분 저장 단위의 소유자 |
| 2 | 회원 세션 | 세션 식별자, 두 토큰 해시와 각 만료 시각, 폐기 여부, 생성·최종 접근 시각 | 회원 1 : N 세션(폐기되지 않은 것은 1건) |
| 3 | 로그인 이력 | 로그인 시각, 접속 IP | 회원 1 : N 이력 |
| 4 | 지출·소득 수단 | 이름, 종류(카드/계좌), 용도(지출 또는 소득 중 하나), 사용 여부, 카드 유효기간, 삭제 표시 | 회원 1 : N 수단. 지출·소득·고정지출이 참조 |
| 5 | 지출유형 | 이름, 사용 여부, 시스템 기본 유형 여부, 아이콘 파일 식별 정보 | 회원 1 : N 유형. 지출·고정지출·목표금액·통계가 참조 |
| 6 | 월별 지출 내역 | 수단 참조와 당시 이름, 금액, 결제일, 장소, 내용, 지출유형 참조와 당시 이름, 할부 그룹·회차·총 개월 | 회원 1 : N 지출. 같은 할부 그룹끼리 묶임. **고정지출은 담지 않음** |
| 7 | 월별 수입 내역 | 수단 참조와 당시 이름, 금액, 결제일, 내용 | 회원 1 : N 소득 |
| 8 | 고정지출 관리 | 이름, 수단 참조, 기본 금액, 매달 결제일, 내용, 지출유형 참조, 시작·종료 연월(이름 스냅샷 없음) | 회원 1 : N 관리 행. 조회 시 원본 이름 사용 |
| 9 | 월별 고정지출 내역 | 연, 월, 그 달의 금액·결제일·내용·수단 참조·지출유형 참조, 직접 수정 여부 | 관리 1 : N 내역(연·월마다 1건). 그 달 최초 조회 시 생성. 관리 행 삭제 시 함께 삭제 |
| 10 | 기본 목표금액 | 지출유형별 기본 목표 금액 | 회원+지출유형 조합에 1건 |
| 11 | 월별 목표금액 | 연, 월, 지출유형별 목표 금액 | 회원+연+월+지출유형 조합에 1건 |
| 12 | 월별 통계 스냅샷 | 연, 월, 저장 시각, 소득 합계, 지출 합계, 고정·일반 금액과 비율 | 회원+연+월 조합에 1건. 아래 3종의 머리 행 |
| 13 | 통계 주별 지출 | 주 순번, 주 시작일·종료일, 그 주 지출 합계 | 스냅샷 1 : N 주 |
| 14 | 통계 지출유형별 요약 | 지출유형 참조와 당시 이름, 지출 합계, 적용 목표금액, 사용률, 상태 구분 | 스냅샷 1 : N 유형(0원 유형 제외) |
| 15 | 통계 수단별 요약 | 수단 참조와 당시 이름, 지출 합계 | 스냅샷 1 : N 수단(0원 수단 포함) |

**저장 단위를 만들지 않는 것**

- **월별 가계부 목록**: 월별 지출·수입 내역(#6·#7)과 월별 고정지출 내역(#9)을 조회 시점에 함께 보여주는 결과이며 별도 저장 단위를 두지 않는다. 세 저장 단위는 **각각 따로도 조회할 수 있다**.
- **할부 그룹**: 지출 건들이 공유하는 식별자로 표현하며 그룹 자체를 위한 저장 단위를 두지 않는다.
- **엑셀 업로드 이력**: 저장하지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 명세의 56개 API 가운데 데이터 읽기·쓰기가 필요한 모든 API에 대해, 요청으로 받는 저장 항목과 응답으로 돌려주는 항목이 **하나도 빠짐없이** 저장되거나 저장된 값에서 파생 가능하다(항목 대조표 100% 충족).
- **SC-002**: 위 15종 저장 단위와 각 항목의 필수 여부·값 범위·유일성 조건이 문서로 확정되어, 구현자가 추가 질문 없이 저장 구조를 만들 수 있다.
- **SC-003**: Phase 1~5 각 Phase의 완료 기준(명세 「Phase 요약」의 완료 기준 열)에 적힌 흐름을 수행할 때, **저장 구조 변경 없이** 끝까지 진행된다.
- **SC-004**: 구조 반영 후 재생성한 `sql/schema-moneylogdb.sql`에 15종 저장 단위가 모두 나타나고, 회원·거래 실데이터는 한 건도 포함되지 않는다.
- **SC-005**: 원본 이름이 바뀌거나 삭제된 뒤에도 과거 지출·소득 내역과 저장된 통계에 남은 이름은 **등록·저장 당시 값 그대로** 읽힌다(이름 변경 시나리오 검증 100% 통과).
- **SC-006**: 한 회원의 데이터를 다른 회원 자격으로 읽으려는 시도가 저장 구조상 소유자 조건으로 걸러지며, 소유자 없는 데이터가 만들어질 수 없다.
- **SC-007**: 같은 달의 통계를 반복 저장해도 스냅샷 관련 저장 단위의 행 수가 늘지 않는다(중복 저장 시 행 수 증가 0건).

## Assumptions

- **저장 대상 DB**: PostgreSQL 18의 `moneylog` 스키마를 쓴다(프로젝트 헌장 「기술 스택 및 제약」). 현재 이 스키마에는 테이블이 없어 기존 데이터 이관 문제가 없다고 본다.
- **물리 테이블 이름**: 신규 테이블은 `tbl_` 접두사를 쓰며, 레거시 `money-app` 테이블 이름과 겹치지 않는다. 레거시는 유지하고 신규 API용 테이블은 별도 이름으로 공존한다. 구체적 물리 명칭은 `/speckit-plan`에서 확정한다.
- **회원 식별**: 회원의 로그인 아이디는 변경 API가 없으므로 변하지 않는 값으로 취급하고, 다른 저장 단위가 회원을 가리키는 기준으로 쓸 수 있다고 가정한다.
- **수단 용도**: 수단 1건은 `EXPENSE` 또는 `INCOME` 중 하나만 갖는다. `PaymentMethodCreate` 등 상세 명세에 `purpose` 반영은 이 기능의 병행·후속 문서 개정으로 처리한다.
- **기본 지출유형**: 가입·관리자 회원 추가 시 식비·교통·주거·통신·쇼핑·장보기·의료·교육·문화·기타 10종을 회원별로 생성한다. 각 유형에 **30×30px** 기본 아이콘 템플릿을 복사해 파일 식별 정보를 채운다. 템플릿 위치: `app-mod/money-backend-app/src/main/resources/seed/expend-group-icons/`.
- **고정지출 이름 표시**: 고정지출 관리·월별 고정지출 내역 어느 쪽에도 수단·유형 이름 스냅샷을 두지 않고, 조회 시 원본 현재 이름을 쓴다. 지출·소득 내역이 이름 스냅샷을 갖는 것과 의도적으로 다르다(고정지출은 "설정에서 파생된 값"이라는 성격을 유지).
- **고정지출 API 개정(병행 과제)**: 저장 구조 3분할에 맞춰 상세 명세(4.x)에 다음 두 API를 추가해야 한다 — ① **월별 고정지출 내역 수동 재작성**(연·월 지정, 직접 수정 행 보존 여부 옵션, FR-049), ② **월별 고정지출 내역 단건 수정**(내역 1건의 금액·결제일·내용·수단 변경, FR-046). 기존 "월별 예외 저장" API(4.5~4.7 계열)는 ②로 대체된다. 이 기능은 두 API가 필요로 하는 **저장 구조만** 확정하고 API 구현은 하지 않는다.
- **고정지출 종료 연월**: 상세 명세 4.1은 종료 연월을 필수로 정의하고, 화면 시제품은 "선택"으로 표기해 서로 다르다. 이 기능은 **명세를 기준으로 필수**로 본다(기간이 열린 고정지출은 이번 범위 밖).
- **할부 결제일**: 할부 각 회차의 결제일은 시작 연월부터 매달 같은 날로 정해지며, 구체적인 날짜 규칙은 명세 3.5의 "매월 1일(또는 정책일)"을 따른다.
- **통계 상태 구분 기준**: 사용률 90% 미만·90~110%·110% 초과의 세 구간을 상태 구분값으로 저장한다. 명세는 이 값을 "구현 시 조정 가능"으로 두었으므로, 기준이 바뀌어도 이미 저장된 스냅샷의 값은 다시 계산하지 않는다.
- **금액 상한**: 목표금액만 명세에 상한(1억)이 있다. 지출·소득·고정지출 금액에는 명세상 상한이 없어 이 기능에서도 상한을 두지 않는다.
- **아이콘 파일**: 아이콘 이미지는 파일 저장소에 두고 데이터베이스에 이미지 자체를 넣지 않는다.
- **로그인 이력**: 명세 1.3은 이력 기록을 "할 수 있다"로 두었으나, 레거시에 동일 목적 구조가 있고 감사 목적이 뚜렷하므로 이 기능 범위에 포함한다.
- **삭제 정책 차이**: 수단은 삭제 표시(보존), 지출유형·지출·소득·고정지출은 실제 삭제다. 이는 과거 내역이 수단 이름을 계속 참조해야 한다는 명세 요구에서 나온 의도된 차이로 본다.
- **선행 의존**: 이 기능은 `프로젝트설계/2.1. 기능명세 - 백엔드.md`와 `기능명세상세-백엔드/` 하위 문서가 확정된 상태를 전제한다. 두 문서가 서로 어긋나면 구조를 임의로 정하지 않고 명세를 먼저 개정한다(프로젝트 헌장 원칙 V).
