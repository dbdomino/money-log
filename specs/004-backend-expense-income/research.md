# Research: 지출·소득 등록과 할부·엑셀 일괄 등록

**Feature**: `004-backend-expense-income` | **Date**: 2026-09-02 | **Phase**: 0

형식은 **결정 / 근거 / 기각한 대안**이다. 기준점은 `sql/schema-moneylogdb.sql`,
`프로젝트설계/기능명세상세-백엔드/phase3-지출-소득/`, 헌장, 그리고 `002`·`003`의 계획이다.

## 1. 엑셀 라이브러리

**결정**: `org.apache.poi:poi-ooxml`. `money-backend-app`에만 넣는다. 버전은 명시한다
(Spring Boot BOM이 관리하지 않는다).

**근거**: `.xlsx`를 **읽고 쓰는 것 둘 다** 필요하다(3.11 생성 · 3.12 파싱).
게다가 3.11은 단순 표가 아니라 **데이터 유효성 목록(드롭다운)**을 넣어야 한다(FR-317).
POI의 `XSSFDataValidation`이 이걸 지원한다. 경량 라이브러리 대부분은 읽기 전용이거나
유효성 검사 같은 서식 기능이 없다.

`poi-ooxml`은 `.xlsx`(OOXML)만 다룬다. `.xls`(구형 바이너리)는 `poi`가 필요한데
FR-319가 `.xlsx`만 허용하므로 넣지 않는다 — 의존성이 줄고, 실수로 `.xls`가 파싱되는 일도 없다.

**`common-mod`가 아니라 `money-backend-app`에 넣는다.** `common-mod`는 프론트 `money-app`도
의존하는 최하위 모듈이라, 여기에 POI가 들어가면 프론트 빌드가 엑셀 라이브러리를 끌고 간다.
`002`의 Spring Security 배치와 같은 기준이다.

**기각한 대안**:
- **fastexcel / easyexcel** — 대용량에 유리하지만 우리 상한은 300행이다. 데이터 유효성 목록
  지원이 POI만큼 확실하지 않다.
- **CSV로 대체** — 드롭다운을 넣을 수 없어 FR-317이 성립하지 않는다.

## 2. 이름 스냅샷의 갱신 조건

**결정**: 스냅샷은 **참조 컬럼이 실제로 바뀔 때만** 새 참조의 현재 이름으로 다시 읽는다.
원본 이름 변경은 과거 행을 건드리지 않는다.

**근거**: FR-304가 그대로 정했고, `tbl_expense`에 `payment_method_idx`와
`payment_method_name`이 **둘 다** 있는 이유가 이것이다(덤프에서 확인).

경계가 셋 있다.

| 상황 | 스냅샷 |
|---|---|
| 등록(3.1·3.7·3.12) | 그 시점 원본 이름을 읽어 저장 |
| 수정에서 `paymentMethodId`를 **바꿈** | 새 수단의 **현재** 이름으로 갱신 |
| 수정에서 `paymentMethodId`를 omit하거나 같은 값 | **건드리지 않는다** |
| 원본(`003`)에서 이름만 바꿈 | 과거 행은 그대로 (`003`의 FR-208·SC-205) |

세 번째가 놓치기 쉽다. "수정 요청이 왔으니 스냅샷도 최신화한다"고 구현하면
같은 수단을 유지한 채 금액만 고쳤을 때 이름이 조용히 바뀐다. **참조가 바뀌었는가**를
명시적으로 비교해야 한다.

이 판정을 `ReferenceResolver` 한 곳에 모은다. 필요한 경로가 다섯이라
(3.1·3.3·3.7·3.9·3.12) 각자 구현하면 한 곳만 어긋나도 과거 데이터가 오염된다.

**기각한 대안**:
- **스냅샷 없이 조회 시 JOIN으로 현재 이름을 읽는다** — 001이 스냅샷 컬럼을 만든 결정을
  뒤집는 것이고, 과거 지출이 이름 변경을 따라가 버린다.
- **수정 때마다 무조건 갱신** — 위 세 번째 경계가 깨진다.

## 3. 참조 검증의 비대칭 (FR-325 vs FR-326)

**결정**: **새로 거는 참조**만 사용 중(`in_use=true`·`deleted=false`)을 요구한다.
이미 저장된 행은 참조가 나중에 죽어도 조회·수정·삭제가 전부 정상 동작한다.

**근거**: 두 FR이 짝을 이룬다. FR-325는 "등록·수정이 참조하는 수단·유형은 사용 중이어야
한다", FR-326은 "이미 저장된 지출·소득은 참조가 나중에 죽어도 정상 동작해야 한다"이다.

이 비대칭이 없으면 003의 삭제 표시가 004를 망가뜨린다. 수단을 삭제 표시하는 순간
그 수단으로 적은 과거 지출 전부가 조회 불가가 된다. 003이 물리 삭제 대신 삭제 표시를
고른 이유 자체가 "과거 기록을 보존한다"인데 그 목적이 무너진다.

구현상 함정은 **수정 경로**다. 금액만 고치는 수정에서도 참조 검증을 돌리면
죽은 수단을 쓰던 과거 지출을 못 고치게 된다. **참조를 실제로 바꿀 때만** 검증한다 —
§2의 스냅샷 갱신 조건과 같은 판정이다. 그래서 둘을 `ReferenceResolver` 한 곳에 둔다.

**기각한 대안**: 저장 시점에 검증하고 조회는 무조건 허용 — 수정 경로가 여전히 갈린다.

## 4. 할부 그룹 식별자

**결정**: `seq_installment_group` 시퀀스에서 **그룹당 한 번** 뽑아 N개 행이 공유한다.
Entity의 `@GeneratedValue`로 쓰지 않는다.

**근거**: FR-312가 "행마다 새로 발급되면 안 된다"고 못박았다. `installment_group_id`는
`tbl_expense`의 PK가 아니라 **일반 컬럼**이라(덤프 확인) JPA의 식별자 생성기로 쓸 수 없다.

001의 커밋 메시지가 이 시퀀스를 `AdditionalMappingContributor`로 따로 만든 이유를 적어 두었다 —
"`@SequenceGenerator`는 어느 Entity의 식별자 생성기로 쓰일 때만 DDL에 나오는데
`seq_installment_group`은 N개 행이 공유하는 값이라 어느 PK의 생성기도 아니다".

따라서 서비스가 **명시적으로** 다음 값을 조회한다. Repository에
`SELECT nextval('moneylog.seq_installment_group')` 네이티브 쿼리를 두는 것이 가장 단순하다.

**기각한 대안**:
- **`UUID`나 타임스탬프로 그룹 식별자를 만든다** — 컬럼이 `bigint`다(덤프 확인). 타입이 안 맞는다.
- **`MAX(installment_group_id) + 1`** — 동시 등록에서 충돌한다. 시퀀스가 있는 이유다.

## 5. 할부 3개 컬럼의 불변식

**결정**: `installment_group_id`·`installment_index`·`installment_total`이
**셋 다 비거나 셋 다 채워지도록** 애플리케이션이 한 곳에서 강제한다.

**근거**: DB의 CHECK은 각 컬럼의 **범위만** 본다(덤프에서 확인) —
`ck_expense_installment_index`(NULL 또는 1 이상), `ck_expense_installment_total`(NULL 또는 2 이상).
**세 컬럼의 동시성을 보는 제약이 없다.** 즉 `installment_index`만 채운 행을 DB가 받아들인다.

그런 행이 생기면 "일시불인가 할부인가"를 판정할 수 없다. 조회·집계·중도상환이 전부
이 판정에 의존하므로 한 번 오염되면 조용히 틀린 답이 나온다.

강제 지점은 Entity가 아니라 **서비스의 저장 경로**다. 진입점이 셋뿐이라
(3.1 일시불 · 3.5 할부 · 3.12 엑셀) 그 셋만 지키면 된다.

**DB에 CHECK을 추가하지 않는 이유**는 스키마 변경이 되기 때문이다. 이 기능은 스키마
무변경이 전제이고(원칙 VI), 애플리케이션에서 막을 수 있는 것을 위해 001의 결정을
번복하지 않는다. 필요해지면 별도 작업으로 다룬다.

**기각한 대안**: Entity의 `@PrePersist`에서 검사 — 동작하지만 실패가 `PersistenceException`으로
올라와 `3201` 같은 업무 코드로 바꾸기 어렵다. 서비스에서 미리 판정하는 편이 응답 코드를 통제한다.

## 6. 할부 회차의 결제일

**결정**: 회차 n의 `payment_date`는 `startYearMonth`에 **n-1개월을 더한 달의 1일**이다.

**근거**: 요청이 `startYearMonth`(`YYYY-MM`)만 받고 **일(day)을 받지 않는다**(설계 명세 3.5).
카드별 결제일을 쓰려면 `tbl_user_payment_method`에 결제일 컬럼이 있어야 하는데 **없다**
(덤프 확인 — `card_expiry`뿐이다). 즉 "정책일"을 살리려면 스키마 변경이 따라온다.

매월 1일로 고정하면 **말일 보정이 필요 없다.** 31일 시작 할부가 2월에 며칠이 되는가 하는
문제가 애초에 생기지 않는다. clarify에서 이 방향을 확정했다.

`3.5-ExpenseCreateInstallment.md` 비고의 "(또는 정책일)"을 삭제하는 개정이 함께 필요하다(FR-324).

**기각한 대안**: 수단에 결제일 컬럼 추가 / 요청에 `paymentDay` 추가 — 둘 다 clarify에서
기각했다. 전자는 001 스키마·덤프 개정이 따라오고, 후자는 사용자가 매번 입력해야 한다.

## 7. 중도상환의 날짜 경계

**결정**: 서버 기준 오늘을 `today`라 할 때 **`payment_date > today`인 회차만** 물리 삭제한다.
`payment_date <= today`는 남긴다.

**근거**: 경계를 `>=`로 잡으면 **오늘 결제된 회차까지 사라져 이번 달 합계가 소급해 줄어든다.**
사용자가 이미 본 숫자가 바뀌는 것이라 신뢰를 잃는다.

"미결제"를 기준으로 삼지 않는 이유는 `tbl_expense`에 **결제 완료 여부 컬럼이 없기 때문**이다
(덤프 확인). 날짜 말고는 판정할 근거가 없다.

`ix_expense_installment (installment_group_id, payment_date)` 인덱스가 이 조회의
컬럼 순서와 정확히 일치한다 — 001이 이 연산을 예상하고 만든 것이다.

**대상이 0건이면 `3207`**로 거절한다(설계 명세 3.6). 멱등 성공으로 흘리지 않는다 —
"방금 정리했다"와 "이미 정리되어 있었다"를 화면이 구분해야 한다.

**기각한 대안**: `>=` 경계 / 결제 완료 컬럼 추가 — 전자는 위 이유, 후자는 스키마 변경이다.

## 8. 엑셀 업로드의 트랜잭션과 오류 보고

**결정**: **전체 롤백**이다. 한 행이라도 실패하면 아무것도 저장하지 않고,
`3502`와 함께 `data.errors[]`에 `row`·`column`·`message`를 담아 돌려준다.

**근거**: FR-320이 정했다. 부분 성공을 허용하면 사용자가 "몇 번째 행까지 들어갔는지" 모르는
상태에서 파일을 고쳐 다시 올리게 되고, 그러면 앞부분이 중복 등록된다.
**004는 중복을 허용하므로**(FR-309, 업무 유일 제약 없음) DB가 그 중복을 막아주지 않는다.
전체 롤백이 유일하게 안전한 선택이다.

**검증을 저장보다 먼저 전부 끝낸다.** 저장하다가 실패해서 롤백하는 것이 아니라,
읽기 → 전 행 검증 → (오류 있으면 즉시 반환) → 저장 순서다. 이유는 오류를 **전부** 모아
한 번에 알려주기 위해서다. 저장 중 첫 실패에서 멈추면 사용자가 파일을 여러 번 왕복하게 된다.

파일 단위 거절(`3503` `.xlsx` 아님 · `3504` 300행 초과 · `3505` 빈 파일)은
**행 검증에 들어가기 전에** 판정한다(FR-319). 코드를 나눠 둔 이유는 프론트가
"파일을 다시 고르라"와 "표의 이 행을 고치라"를 다르게 안내해야 하기 때문이다.

**기각한 대안**:
- **부분 성공 + 실패 행 목록 반환** — 위 중복 문제.
- **첫 오류에서 중단** — 사용자가 파일을 여러 번 고쳐 올려야 한다.

## 9. 엑셀 컬럼 정의를 어디에 둘 것인가

**결정**: `ExcelColumn`(enum 또는 상수 목록) 하나를 **양식 생성과 업로드 파싱이 공유**한다.

**근거**: FR-318이 "양식 다운로드와 업로드의 컬럼 정의가 일치해야 한다"고 요구한다.
두 곳에 각자 적으면 반드시 갈린다 — 컬럼을 하나 추가하면서 한쪽만 고치는 일이 생긴다.

공유하면 일치가 **구조로 보장된다.** 컬럼 순서·헤더 문자열·필수 여부가 한 곳에서 나온다.

POI 타입(`Workbook`·`Row`·`Cell`)은 `excel` 패키지 밖으로 내보내지 않는다. Service는
`ExcelRowReader`가 만든 평범한 DTO 목록을 받는다. 라이브러리를 바꿔야 할 때 손댈 곳이
한 패키지로 묶인다.

**기각한 대안**: 양식은 리소스의 고정 `.xlsx` 파일, 업로드만 코드로 파싱 — FR-317이
"본인의 사용 중 수단·지출유형이 데이터 유효성 목록으로 포함"을 요구한다.
**양식은 회원마다 내용이 다르다.** 고정 파일로는 불가능하다.

## 10. 물리 삭제와 003의 삭제 표시

**결정**: 지출·소득 삭제는 **물리 삭제**(`DELETE`)다. 삭제 표시 컬럼을 두지 않는다.

**근거**: FR-308과 헌장의 DB 저장 구조 규칙("수단·지출유형은 삭제 표시(행 보존),
지출·소득·고정지출은 물리 삭제")이 일치한다. `tbl_expense`·`tbl_income`에 `deleted` 컬럼이
**없다**(덤프 확인) — 001이 이 결정을 스키마로 못박았다.

이유는 성격이 다르기 때문이다. 수단·유형은 **과거 기록이 참조하는 대상**이라 지우면
참조가 끊긴다. 지출·소득은 **기록 자체**라, 사용자가 지웠다는 것은 "이 지출은 없었던 일로
한다"는 뜻이다. 남겨 두면 합계가 틀린다.

003과 004에서 삭제의 의미가 반대라는 점을 구현자가 혼동하기 쉬우므로
[data-model.md](./data-model.md)에 대비표를 두었다.

**기각한 대안**: 004도 삭제 표시로 통일 — 모든 조회에 `deleted=false` 조건이 붙고,
빠뜨리면 지운 지출이 합계에 남는다. 001이 이미 반대로 결정했다.
