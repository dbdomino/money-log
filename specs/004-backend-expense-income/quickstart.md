# Quickstart: 지출·소득 등록과 할부·엑셀 일괄 등록

**Feature**: `004-backend-expense-income` | **Date**: 2026-09-02 | **Phase**: 1

이 기능이 실제로 동작하는지 확인하는 **검증 가이드**다. 구현 코드는 담지 않는다.

## 0. 착수 전

### 선행 기능

**`002`와 `003`이 먼저 서야 한다.**

| 선행 | 004가 쓰는 것 |
|---|---|
| `002` | 인증 필터 · 응답 규격 · `GlobalExceptionHandler` · AOP 로깅 · `AuditorAware` |
| `003` | `tbl_user_payment_method` · `tbl_user_expend_group` 행. 참조 검증과 이름 스냅샷의 원본 |

003 없이 004만 구현하면 참조할 수단·유형이 없어 지출을 한 건도 등록할 수 없다.
검증용 수단·유형을 DB에 직접 넣어 부분 확인은 가능하지만, `in_use`·`deleted` 상태별
동작(FR-325·326)은 003의 API가 있어야 제대로 본다.

## 1. 전제

| 항목 | 값 |
|---|---|
| PostgreSQL 18 | `localhost:5432` · DB `moneylogdb` · 스키마 `moneylog` |
| 스키마 | 15개 테이블. **이 기능은 스키마를 바꾸지 않는다** |
| 백엔드 | `:8081` · `/api/v1` |
| 로그인 계정 | `002`의 가입(1.2). 기본 지출유형 10종이 함께 생긴다 |
| 수단 | `003`의 2.1로 지출용·소득용을 각각 만든다 |

시퀀스·인덱스 확인:

```bash
psql -h localhost -U moneyloguser -d moneylogdb -c \
  "select sequence_name from information_schema.sequences
     where sequence_schema='moneylog' and sequence_name='seq_installment_group';"
# → 1건 (FR-312 의 근거)

psql -h localhost -U moneyloguser -d moneylogdb -c \
  "select indexname from pg_indexes where schemaname='moneylog'
     and indexname in ('ix_expense_date','ix_expense_installment','ix_income_date');"
# → 3건

psql -h localhost -U moneyloguser -d moneylogdb -c \
  "select column_name from information_schema.columns
     where table_schema='moneylog' and table_name='tbl_expense' and column_name='deleted';"
# → 0건이어야 한다. 지출은 물리 삭제다 (FR-308)
```

마지막 확인이 003과의 차이를 드러낸다.

## 3. 검증 시나리오

spec.md의 User Story·SC와 대응한다.

### US1 — 일시불 지출 (P1, MVP)

| # | 시나리오 | 기대 | 대응 |
|---|---|---|---|
| 1 | 사용 중 수단·유형으로 등록 | **이름 2개가 스냅샷으로** 함께 저장 | US1-1·SC-301 |
| 2 | 등록 후 **수단 이름을 바꾸고** 그 지출 조회 | `paymentMethodName`이 **등록 당시 이름 그대로** | US1-2·SC-305 |
| 3 | 등록 후 그 수단을 **삭제 표시**하고 조회 | **정상적으로 읽힌다**. 이름도 남아 있다 | US1-3·FR-326 |
| 4 | 금액 0 이하 | `3201` | US1-4 |
| 5 | 장소 101자 · 내용 256자 | `3201` (`9000`이 아니다) | FR-305 |
| 6 | 수정에서 `paymentMethodId`를 **바꿈** | 스냅샷이 **새 수단의 현재 이름으로 갱신** | US1-5 |
| 7 | 수정에서 `paymentMethodId`를 **omit**하고 금액만 변경 | 스냅샷이 **바뀌지 않는다** | FR-304 |
| 8 | 수정에서 `paymentMethodId`에 **같은 값**을 보냄 | 스냅샷이 **바뀌지 않는다** | FR-304 |
| 9 | **삭제 표시된 수단**을 쓰던 지출의 금액만 수정 | **성공한다** | FR-326 |
| 10 | 남의 지출 ID로 조회·수정·삭제 | `3202` | US1-6·SC-307 |
| 11 | 삭제 후 재조회 | 없다 (**물리 삭제**) | US1-7·SC-306 |
| 12 | 같은 날짜·금액·수단으로 두 건 등록 | **둘 다 성공** | US1-8·SC-303 |
| 13 | 사용 안 함·삭제 표시된 수단으로 **새 지출** 등록 | `3003` | SC-310·FR-325 |
| 14 | 사용 안 함·삭제 표시된 유형으로 **새 지출** 등록 | `3103` | FR-325 |

**6·7·8이 한 묶음**이다. 스냅샷 갱신 조건(FR-304)의 세 갈래를 전부 덮는다.
7·8을 빠뜨리면 "수정 요청이 왔으니 최신화한다"는 잘못된 구현이 통과한다.

**9·13이 비대칭(FR-325 ↔ FR-326)의 핵심**이다. 새 참조는 막고 기존 행은 통과시킨다.

5번은 DB 오류가 `9000`으로 새는지 확인한다.

**29번이 이 기능에서 가장 중요한 경계 시나리오다.** 오늘 회차가 남는지 확인한다 —
경계를 `>=`로 잡으면 이번 달 합계가 소급해 줄어든다. 오늘 날짜의 회차를 반드시 만들어 둔다.

33번은 API로 확인할 수 없으므로 DB를 직접 조회한다:

```sql
select count(*) from moneylog.tbl_expense
 where (installment_group_id is null) <> (installment_index is null)
    or (installment_group_id is null) <> (installment_total is null);
-- → 0
```

### US4 — 엑셀 (P3)

| # | 시나리오 | 기대 | 대응 |
|---|---|---|---|
| 34 | 양식 다운로드 후 파일 열기 | 본인 **사용 중** 수단·지출유형이 드롭다운으로 | US4-1·FR-317 |
| 35 | 양식 다운로드 성공 | `{ resCode, data }`가 **아니라** 파일. `Content-Disposition: attachment` | US4-2·SC-301 |
| 36 | 양식 다운로드를 **Bearer 없이** | **래퍼를 쓴다** (`1001`) — 003의 2.10과 다르다 | FR-322 |
| 37 | 사용 안 함·삭제 표시된 수단 | 드롭다운에 **없다** | FR-317 |
| 38 | 올바른 파일 업로드 | 각 행이 지출·소득으로 저장. 별도 "가계부" 행 없음 | US4-3 |
| 39 | 업로드 성공 응답 | **래퍼를 쓴다.** 파일을 돌려주지 않는다 | FR-322 |
| 40 | 중간 한 행에 오류 | `3502` + **전체 롤백** + `errors[]`에 `row`·`column`·`message` | US4-4·FR-320 |
| 41 | 오류가 **여러 행**에 있음 | `errors[]`에 **전부** 담긴다 (첫 오류에서 멈추지 않는다) | FR-320 |
| 42 | 301행 파일 | `3504` | US4-5 |
| 43 | `.xlsx`가 아닌 파일 | `3503` | US4-6 |
| 44 | 헤더만 있고 데이터 0행 | `3505` | FR-319 |
| 45 | 같은 내용의 행이 두 번 | **둘 다 저장** (중복 허용) | US4-7·FR-309 |
| 46 | 파일의 수단 이름이 DB에 없음 | 그 행을 오류로 보고 전체 롤백 | Edge Case |
| 47 | 업로드가 만든 행의 이름 스냅샷 | 3.1·3.7과 **같은 규칙**으로 채워져 있다 | Edge Case |
| 48 | 업로드가 만든 지출 행의 할부 3컬럼 | **전부 NULL** | excel-contract §4 |
| 49 | 소득 행에 지출유형·장소가 채워져 있음 | 오류 → `3502` | FR-306 |

**35·36이 한 쌍이다.** 성공은 파일, 인증 실패는 **래퍼**다.
`003`의 아이콘(2.10)은 인증 실패도 래퍼를 쓰지 않으므로 헷갈리기 쉽다.

**41번이 "오류를 전부 모은다"를 확인한다.** 첫 오류에서 멈추면 사용자가 파일을 여러 번
왕복하게 된다.

42·43·44는 **행 검증에 들어가기 전에** 판정되는지 본다 — 300행 초과 파일에 행 오류가
섞여 있어도 `3502`가 아니라 `3504`가 나와야 한다.
