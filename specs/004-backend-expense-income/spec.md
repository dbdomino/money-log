## User Scenarios & Testing *(mandatory)*

### User Story 1 - 일시불 지출을 기록한다 (Priority: P1) 🎯 MVP

지출을 등록(3.1)하고, 상세를 보고(3.2), 고치고(3.3), 지운다(3.4).

**Why this priority**: 가계부의 핵심 행위다. 이것 하나만 있어도 "쓴 돈을 적는다"는 가치가 성립한다.

**Independent Test**: 수단·유형을 하나씩 만들어 두고 지출을 등록·조회·수정·삭제한다. 할부·소득·엑셀 없이 완결된다.

**Acceptance Scenarios**:

1. **Given** 사용 중인 지출 수단과 유형이 있을 때, **When** 지출을 등록하면, **Then** 등록 당시 **수단 이름과 유형 이름이 스냅샷으로** 함께 저장된다
2. **Given** 지출을 등록한 뒤 수단 이름을 바꾸면, **When** 그 지출을 조회하면, **Then** `paymentMethodName`은 **등록 당시 이름 그대로**다
3. **Given** 지출을 등록한 뒤 그 수단을 삭제 표시하면, **When** 그 지출을 조회하면, **Then** 정상적으로 읽히고 이름도 남아 있다
4. **Given** 금액을 0 이하로 주면, **When** 등록하면, **Then** 거부된다
5. **Given** 지출 수정에서 `paymentMethodId`를 바꾸면, **When** 저장하면, **Then** `paymentMethodName` 스냅샷이 **새 수단의 현재 이름으로 갱신**된다
6. **Given** 남의 지출 ID로, **When** 조회·수정·삭제하면, **Then** 거부된다
7. **Given** 지출을 삭제하면, **When** 다시 조회하면, **Then** 없다(**물리 삭제**이며 삭제 표시가 아니다)
8. **Given** 같은 날짜·금액·수단으로 두 건을 등록하면, **When** 저장하면, **Then** **둘 다 성공한다**(중복 허용)

### User Story 2 - 소득을 기록한다 (Priority: P2)

소득을 등록(3.7)하고, 조회·수정·삭제한다(3.8~3.10).

**Why this priority**: 지출만 있으면 월별 수지를 낼 수 없다. 다만 구조가 지출보다 단순하고 지출에 의존하지 않아 독립적으로 붙일 수 있다.

**Independent Test**: 소득용 수단으로 소득을 등록·조회·수정·삭제한다. 지출 API 없이 완결된다.

**Acceptance Scenarios**:

1. **Given** `purpose=INCOME`인 수단으로, **When** 소득을 등록하면, **Then** 수단 이름 스냅샷과 함께 저장된다
2. **Given** `내용`을 비우고, **When** 소득을 등록하면, **Then** 성공한다(내용은 선택 항목이다)
3. **Given** 소득 등록 Body에 `place`·`expendGroupId`·할부 필드를 실어 보내면, **When** 저장되면, **Then** 그 필드들은 무시되고 `tbl_income`에 대응 컬럼이 없어 저장되지 않으며, 응답 Income에도 나타나지 않는다(지출과 구조가 다르다)
4. **Given** 소득 수단을 바꾸면, **When** 저장하면, **Then** 이름 스냅샷이 갱신된다

### User Story 3 - 할부를 등록하고 중도상환한다 (Priority: P2)

12개월 할부를 한 번에 등록(3.5)하고, 남은 회차를 정리한다(3.6).

**Why this priority**: 카드 가계부에서 빠질 수 없는 요구다. 일시불(US1)이 선 뒤에만 의미가 있어 P2다.

**Independent Test**: 12개월 할부를 등록해 12행이 같은 그룹 식별자와 1~12 순번으로 생기는지, 중도상환이 미래 회차만 지우는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 12개월 할부를 등록하면, **When** 저장되면, **Then** **12개 행**이 생기고 같은 `installmentGroupId`를 공유하며 순번이 1~12다
2. **Given** 할부 12행 중 1건이라도 저장에 실패하면, **When** 트랜잭션이 끝나면, **Then** **전부 롤백**되어 한 행도 남지 않는다
3. **Given** 할부 등록이 성공하면, **When** 응답을 보면, **Then** 생성 건수(`createdCount`)만 오고 지출 목록은 실려 있지 않다
4. **Given** 할부 회차 하나를, **When** 상세 조회하면, **Then** 일시불과 **같은 API**(3.2)로 읽힌다
5. **Given** 할부 회차 하나를 수정하면, **When** 저장하면, **Then** **그 달 1건만** 바뀐다
6. **Given** 할부 개월 수나 시작 연월을 바꾸려 하면, **When** 수정하면, **Then** 거부된다(삭제 후 재등록해야 한다)
7. **Given** 과거 2회차·오늘 1회차·미래 9회차인 할부에서, **When** 중도상환하면, **Then** **미래 9건만 사라지고** 과거·오늘 회차는 남는다
8. **Given** 할부 그룹이 두 개 있을 때, **When** 하나를 중도상환하면, **Then** 다른 그룹은 영향받지 않는다
9. **Given** 미래 회차가 이미 0건인 할부 그룹(마지막 회차까지 지났거나 이미 중도상환한 그룹)을, **When** 다시 중도상환하면, **Then** `3207`로 거부되고 남은 회차는 한 건도 삭제되지 않는다
10. **Given** 남의 `installmentGroupId`로, **When** 중도상환하면, **Then** `3206`으로 거부된다

### User Story 4 - 엑셀로 한 번에 올린다 (Priority: P3)

양식을 내려받아(3.11) 채운 뒤 일괄 등록한다(3.12).

**Why this priority**: 편의 기능이다. 없어도 한 건씩 등록하면 되지만, 과거 내역을 옮겨 담을 때 값이 크다.

**Independent Test**: 양식을 받아 몇 행을 채우고 업로드해 지출·소득으로 저장되는지, 잘못된 행 하나가 전체를 롤백시키는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 양식을 내려받으면, **When** 파일을 열면, **Then** 본인의 **활성 수단·지출유형**이 드롭다운으로 들어 있다
2. **Given** 양식 다운로드가 성공하면, **When** 응답을 보면, **Then** `{ resCode, data }` **래퍼가 아니라** 파일이다
3. **Given** 올바른 파일을 올리면, **When** 저장되면, **Then** 각 행이 **지출 또는 소득으로** 저장되고 별도의 "가계부" 행은 만들어지지 않는다
4. **Given** 중간 한 행에 오류가 있으면, **When** 업로드하면, **Then** **전체가 롤백**되고 `row`·`column`·`message`로 위치를 알려준다
5. **Given** 301행짜리 파일을 올리면, **When** 업로드하면, **Then** 거부된다(최대 300행)
6. **Given** `.xlsx`가 아닌 파일을 올리면, **When** 업로드하면, **Then** 거부된다
7. **Given** 같은 내용의 행이 두 번 있으면, **When** 업로드하면, **Then** **둘 다 저장된다**(중복 허용)

### Edge Cases

- 할부 회차의 결제일은 어떻게 정하는가? — 요청은 `startYearMonth`(`YYYY-MM`)만 받고 일(day)을 받지 않으므로, 3.5 설계 명세대로 **시작 연월부터 매월 1일**을 `paymentDate`로 쓴다. 회차 n의 결제일은 `startYearMonth`에 n-1개월을 더한 달의 1일이며 말일 보정이 필요 없다. [NEEDS CLARIFICATION: 3.5 비고의 "매월 1일 (또는 정책일)"에서 "정책일"이 카드 결제일 같은 다른 기준일을 열어 둔 표현인지, 삭제하고 1일로 확정할지 결정이 필요하다]
- 중도상환의 기준 시각은? — 서버 기준 오늘 날짜를 `today`라 할 때 **`payment_date > today`인 회차만** 제거하고 `payment_date <= today`인 회차는 남긴다. 경계를 `>=`로 잘못 잡으면 오늘 결제된 회차까지 사라져 이번 달 금액이 소급해 줄어든다. [NEEDS CLARIFICATION: 3.6 비고가 "오늘 이후(또는 미결제)"로 적혀 오늘 포함 여부와 "미결제" 기준이 확정되지 않았다. 이 스펙의 `payment_date > today`로 3.6을 개정할지 확인이 필요하다]
- 할부 3개 컬럼 중 일부만 채워진 행은? — 만들어지지 않아야 하는 상태다. `installment_group_id`·`installment_index`·`installment_total`은 **셋 다 비거나(일시불) 셋 다 채워져야(할부)** 한다. DB의 CHECK은 각 컬럼의 범위만 보고 세 컬럼의 동시성은 검사하지 않으므로, 애플리케이션이 한 곳에서 판정·강제한다
- 사용하지 않는(`in_use=false`) 수단·유형으로 **새 지출**을 등록하려 하면? — 3.1 설계 명세대로 수단은 `3003`, 지출유형은 `3103`으로 거절한다. 삭제 표시된(`deleted=true`) 수단·유형은 [NEEDS CLARIFICATION: 3.1 실패 표가 "없음·비활성"까지만 적어 삭제 표시분을 같은 코드로 묶을지 별도 코드를 배정할지 명세에 없다]
- 엑셀 업로드 중 수단·유형 이름이 파일에는 있는데 DB에 없으면? — 그 행을 오류로 보고 전체 롤백한다
- 엑셀 업로드가 만드는 행에도 이름 스냅샷이 필요한가? — 필요하다. 규칙은 `ExpenseCreate`·`IncomeCreate`와 동일하다

## Requirements *(mandatory)*

### Functional Requirements

- **FR-301**: 지출·소득은 회원 소유로만 만들어지고 조회·수정·삭제도 **본인 것만** 가능해야 한다
- **FR-302**: 지출 등록 시 **수단 이름과 지출유형 이름을 등록 당시 값으로 스냅샷 저장**해야 한다. 원본 이름이 나중에 바뀌어도 과거 건은 그때 이름으로 남는다
- **FR-303**: 소득 등록 시 **수단 이름을 스냅샷 저장**해야 한다
- **FR-304**: 이름 스냅샷은 **참조 자체가 바뀔 때만** 새 참조의 현재 이름으로 갱신해야 한다
- **FR-305**: 지출·소득 금액은 0보다 커야 하며, 저장 타입이 `BIGINT`(원 단위 정수)이므로 소수점·문자·범위 초과 값은 지출 `3201`·소득 `3301`로 거절해야 한다. 장소는 100자, 내용은 255자를 넘을 수 없으며(DB `tbl_expense.place varchar(100)`·`content varchar(255)`) 초과 시 같은 코드로 거절한다. 이 검증은 단건 등록·수정과 엑셀 업로드에 동일하게 적용한다
- **FR-306**: 소득에는 장소·지출유형·할부 항목이 없어야 한다. 지출과 구조가 다르므로 별도 자원으로 다룬다
- **FR-307**: 소득의 내용은 비어 있을 수 있다. 지출의 내용·장소는 필수다
- **FR-308**: 지출·소득 삭제는 **물리 삭제**여야 한다. 삭제 표시로 남기지 않는다
- **FR-309**: 같은 날짜·금액·수단의 지출을 여러 건 등록할 수 있어야 한다. 업무 유일 제약을 두지 않는다
- **FR-310**: 할부 등록은 개월 수만큼의 행을 **한 트랜잭션에** 만들고 같은 할부 그룹 식별자를 공유해야 한다. 일부 실패 시 전체 롤백한다
- **FR-311**: 할부 회차는 1부터 시작하고 총 개월 수는 2 이상이어야 한다. 1개월 할부는 일시불이므로 허용하지 않는다
- **FR-312**: 할부 그룹 식별자는 전용 시퀀스가 발급해야 한다. 행마다 새로 발급되면 안 된다
- **FR-313**: 할부 건의 수정·삭제는 **해당 월 1건만** 대상으로 해야 한다
- **FR-314**: 할부의 **개월 수와 시작 연월은 수정할 수 없어야** 한다. 바꾸려면 삭제 후 재등록한다
- **FR-315**: 중도상환은 결제일이 오늘보다 **뒤인** 회차만 물리 삭제해야 한다. 오늘·과거 회차는 남긴다
- **FR-316**: 중도상환은 자원 1건 삭제가 아니라 그룹의 상태·일정 처리이므로 `PATCH`로 표현한다
- **FR-317**: 엑셀 양식에는 본인의 **활성 수단·지출유형**이 데이터 유효성 목록으로 포함되어야 한다
- **FR-318**: 엑셀 양식 다운로드와 업로드의 컬럼 정의가 일치해야 한다
- **FR-319**: 엑셀 업로드는 `.xlsx`만 허용하고(아니면 `3503`), 헤더를 제외한 데이터 행이 **최대 300행**이어야 하며(초과 시 `3504`), 데이터 행이 **0건인 파일은 거절**해야 한다(`3505`). 이 세 조건은 행 단위 검증에 들어가기 전에 파일 단위로 먼저 판정한다
- **FR-320**: 엑셀 업로드는 검증 실패 시 **전체 롤백**하고 `row`·`column`·`message`로 위치를 안내해야 한다
- **FR-321**: 엑셀 업로드는 지출·소득 행만 만들며 업로드 이력을 저장하지 않는다
- **FR-322**: 엑셀 양식 다운로드(3.11)**만** `{ resCode, data }` 래퍼를 쓰지 않는 예외이며, `.xlsx` 바이너리를 `Content-Disposition: attachment`로 직접 돌려준다. 엑셀 업로드(3.12)는 파일을 돌려주지 않고 성공·실패 모두 래퍼를 쓴다. 3.11도 인증 실패처럼 래퍼로 답할 수 있는 상황에서는 래퍼를 쓴다
- **FR-323**: **고정지출 행은 이 기능이 만들지 않는다.** 고정지출은 별도 저장 단위이며 `005-backend-ledger-fixed-expense`가 다룬다

### 이 기능이 쓰는 에러코드

`프로젝트설계/기능명세상세-백엔드/phase3-지출-소득/` 의 각 API 문서가 배정한 값이다. 지출·할부는 `32xx`, 소득은 `33xx`, 엑셀 일괄은 `35xx` 대역을 쓴다.

| 코드 | 의미 | 사용 지점 |
|---|---|---|
| `1001` | 로그인 필요 | 12건 전부 |
| `3003` | 수단 없음·비활성 | 3.1·3.7 |

### Key Entities

- **월별 지출 내역(`tbl_expense`)**: 일시불과 할부를 함께 담는다. 수단·유형 참조와 **이름 스냅샷 2개**, 금액·결제일·장소·내용, 할부 3개 항목(그룹 식별자·회차·총 개월)
- **월별 수입 내역(`tbl_income`)**: 수단 참조와 이름 스냅샷, 금액·입금일(DB `payment_date`, 응답 필드 `paymentDate`)·내용(비어 있을 수 있다). 장소·지출유형·할부가 없다
- **할부 그룹**: 한 할부의 N개 행이 공유하는 식별자. 전용 시퀀스가 발급한다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-301**: 12개 API가 모두 `{ resCode, data }` 형식으로 응답한다. 단 엑셀 양식 다운로드(3.11)는 파일을 돌려주는 명시된 예외다
- **SC-302**: 12개월 할부를 등록하면 지출 행이 **정확히 12건** 생기고 순번이 1~12로 빠짐없다
- **SC-303**: 할부 등록 중 실패를 주입하면 남는 행이 **0건**이다
- **SC-304**: 과거·오늘·미래 회차가 섞인 할부를 중도상환하면 **미래 회차만** 사라지고 오늘 회차는 남는다
- **SC-305**: 수단·유형 이름을 바꾼 뒤 과거 지출을 조회하면 스냅샷 이름이 **바뀌지 않는다**
- **SC-306**: 오류 행이 하나 포함된 엑셀을 올리면 저장된 행이 **0건**이고 응답이 그 행 번호를 가리킨다
- **SC-307**: 남의 지출·소득 ID로 조회·수정·삭제를 시도하면 **100% 거부**된다

## Assumptions

- 저장 구조는 `001-backend-db-schema`에서 만들어졌다. 할부 시퀀스·CHECK·인덱스가 이미 DB에 있다
- 인증은 `002-backend-member-auth`, 수단·지출유형은 `003-backend-payment-expend-group`이 제공한다
- 소득 수단은 `purpose=INCOME`인 수단이어야 한다. 이 판정은 애플리케이션이 한다 — DB CHECK으로는 다른 테이블 값을 볼 수 없다
- 엑셀 처리 라이브러리 선택은 구현 단계에서 정한다
- 월별 목록 조회는 이 기능이 아니라 `005-backend-ledger-fixed-expense`의 `LedgerMonthlyList`가 담당한다
- 엑셀 업로드는 동기 처리다. 비동기 잡·진행률 표시는 범위 밖이다
