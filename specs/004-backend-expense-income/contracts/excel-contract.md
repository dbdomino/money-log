# 엑셀 양식·업로드 계약

**Feature**: `004-backend-expense-income` | **Date**: 2026-09-02 | **Phase**: 1

3.11(양식 다운로드)과 3.12(일괄 업로드)의 계약이다. 두 API는 **컬럼 정의를 공유**해야
하므로(FR-318) 한 문서에 둔다.

---

## 1. 컬럼 정의 — 양식과 업로드가 공유한다

설계 명세 `3.11`의 양식 시트 구조가 그대로 업로드 파싱 규칙이 된다.

| 열 | 헤더 | 필수 | 값 | 대응 컬럼 |
|---|---|:---:|---|---|
| A | 구분 | ✅ | `EXPENSE` \| `INCOME` | 어느 테이블에 넣을지 결정 |
| B | 결제일 | ✅ | `YYYY-MM-DD` | `payment_date` |
| C | 금액 | ✅ | 원 단위 정수, 0 초과 | `amount` |
| D | 수단 | ✅ | **드롭다운** — 본인 사용 중 수단 이름 | `payment_method_idx` + `payment_method_name` |
| E | 지출유형 | 지출만 | **드롭다운** — 본인 사용 중 지출유형 이름 | `expend_group_idx` + `expend_group_name` |
| F | 장소 | 지출만 | 100자 이하 | `place` |
| G | 내용 | 지출만 ✅ / 소득은 선택 | 255자 이하 | `content` |

**필수 여부가 A열 값에 따라 달라진다.** `EXPENSE`면 E·F·G가 전부 필수이고,
`INCOME`이면 E·F는 **비어 있어야 하며** G는 선택이다(FR-306·307).
소득 행에 E·F가 채워져 있으면 오류로 본다 — `tbl_income`에 그 컬럼이 없다.

**할부 컬럼이 없다.** 엑셀 업로드는 일시불 지출과 소득만 만든다. 할부는 3.5 전용이다.
따라서 업로드가 만드는 모든 지출 행은 할부 3컬럼이 **전부 NULL**이다
([api-contract.md §8](./api-contract.md)).

### 구현 — `ExcelColumn` 하나를 공유한다

양식 생성(`ExcelTemplateWriter`)과 업로드 파싱(`ExcelRowReader`)이 같은 정의를 읽는다.
두 곳에 각자 적으면 컬럼을 추가할 때 한쪽만 고치는 일이 생기고, FR-318이 깨진다.
공유하면 **일치가 구조로 보장된다**.

POI 타입(`Workbook`·`Row`·`Cell`)은 `excel` 패키지 밖으로 내보내지 않는다.
Service는 평범한 DTO 목록을 받는다.

## 2. 3.11 양식 다운로드 — 래퍼를 쓰지 않는 예외

```text
GET /api/v1/expense-incomes/excel/template
Authorization: Bearer <accessToken>
```

### 두 갈래 응답

| 상황 | HTTP | 본문 |
|---|---|---|
| 성공 | 200 | **`.xlsx` 바이너리**<br>`Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`<br>`Content-Disposition: attachment; filename="expense_income_template.xlsx"` |
| 인증 실패 · 생성 오류 | 200 / 500 | **래퍼를 쓴다** — `1001` · `9000` |

**`003`의 아이콘 조회(2.10)와 다르다.** 2.10은 인증 실패도 래퍼 없는 401이지만,
3.11은 **인증 실패에 래퍼를 쓴다**(FR-322 — "인증 실패처럼 래퍼로 답할 수 있는 상황에서는
래퍼를 쓴다").

이유는 사용 흐름이 다르기 때문이다. 2.10은 `<img>`/fetch로 받는 이미지라 상태 코드만으로
판정하지만, 3.11은 사용자가 **다운로드 버튼을 누르는** 흐름이라 실패 사유를 화면에 띄워야 한다.

### 회원마다 내용이 다르다

FR-317 — 본인의 **사용 중** 수단·지출유형(`in_use=true`이고 `deleted=false`)이
D·E열의 데이터 유효성 목록(드롭다운)으로 들어간다.

이것 때문에 양식을 정적 파일로 미리 만들어 둘 수 없다. 요청마다 회원의 목록을 읽어
POI로 생성한다.

**드롭다운 목록의 필터는 `003`의 2.6·2.13과 같은 조건**이다 —
수단은 `purpose` 구분 없이 사용 중 전부(양식 A열이 지출·소득을 모두 담으므로),
지출유형은 사용 중 전부.

## 3. 3.12 업로드 — 래퍼를 쓴다

```text
POST /api/v1/expense-incomes/excel/upload
Content-Type: multipart/form-data
```

**3.12는 예외가 아니다.** 파일을 돌려주지 않고 성공·실패 모두 `{ resCode, data }`를 쓴다.

| 상황 | `resCode` | `data` |
|---|---|---|
| 성공 | `200` | `importedCount` · `expenseCount` · `incomeCount` · `message` |
| 행별 검증 오류 | `3502` | `errors[]` — `row` · `column` · `message` |
| `.xlsx`가 아님 | `3503` | `message` |
| 300행 초과 | `3504` | `message` |
| 빈 파일 | `3505` | `message` |

`3502`는 `_공통.md`의 결번 표에서 **철회**된 코드다(커밋 `84ad88c`). 결번 사유가
"배정 이력 없음"이었는데 3.12가 실제로 쓰고 있어 기재가 사실과 달랐다.

### 검증 순서 — 파일 단위가 먼저다

```text
[1단계] 파일 단위 — 행을 읽기 전에 판정한다 (FR-319)
   ├ 확장자·형식이 .xlsx 가 아님        → 3503
   ├ 헤더 제외 데이터 행 > 300          → 3504
   └ 헤더 제외 데이터 행 == 0           → 3505

[2단계] 행 단위 — 전 행을 읽고 전부 검증한다
   ├ A열 구분이 EXPENSE·INCOME 밖
   ├ 필수 열이 비어 있음 (A열 값에 따라 다름)
   ├ 금액이 0 이하·소수점·문자·범위 초과
   ├ 결제일 형식 오류
   ├ 길이 초과 (장소 100 · 내용 255)
   ├ 수단·유형 이름이 DB에 없거나 사용 중이 아님
   └ 소득 행에 지출유형·장소가 채워져 있음
   → 오류가 하나라도 있으면 errors[] 를 모아 3502. 아무것도 저장하지 않는다

[3단계] 저장 — 2단계를 전부 통과했을 때만
   └ 한 트랜잭션. 이름 스냅샷은 3.1·3.7과 동일 규칙
```

**2단계에서 오류를 전부 모은다.** 첫 오류에서 멈추면 사용자가 파일을 여러 번 왕복하며
고치게 된다. 300행 상한이 있으므로 전 행을 검증해도 비용이 크지 않다.

**검증을 저장보다 앞에 완전히 끝낸다.** 저장하다가 실패해서 롤백하는 것이 아니다.
그래야 `errors[]`에 전체 목록을 담을 수 있다.

### 왜 전체 롤백인가 (FR-320)

부분 성공을 허용하면 사용자가 "몇 번째 행까지 들어갔는지" 모르는 채로 파일을 고쳐 다시
올리게 되고, 앞부분이 **중복 등록**된다. 004는 업무 유일 제약을 두지 않으므로(FR-309)
DB가 그 중복을 막아주지 않는다. 전체 롤백이 유일하게 안전한 선택이다.

### 파일 단위와 행 단위의 코드를 나눈 이유

프론트가 안내 문구를 다르게 내야 한다.

| 코드 | 화면이 해야 할 말 |
|---|---|
| `3503`·`3504`·`3505` | "**파일을 다시 고르세요**" — 표를 고쳐도 소용없다 |
| `3502` | "**표의 N행 M열을 고치세요**" — 위치를 짚어 준다 |

한 코드로 묶으면 프론트가 `errors[]`의 유무로 분기해야 하고, 그건 계약이 아니라 추측이다.

## 4. 업로드가 만드는 행의 규칙

**3.1·3.7과 완전히 같다.** 엑셀이라고 예외를 두지 않는다.

| 항목 | 규칙 |
|---|---|
| 이름 스냅샷 | 그 시점 원본 이름을 읽어 저장 (FR-302·303, Edge Case에서 확인) |
| 참조 검증 | 사용 중(`in_use=true`·`deleted=false`)만 (FR-325) |
| 할부 3컬럼 | **전부 NULL** — 양식에 할부가 없다 |
| 소유자 | 토큰의 `id_key` |
| 감사 컬럼 | `002`의 `AuditorAware`가 공급 |
| 중복 | **허용한다** — 같은 내용의 행이 두 번 있으면 둘 다 저장 (FR-309) |

마지막 줄이 US4 시나리오 7이다. 엑셀에 같은 행이 두 번 있어도 거절하지 않는다 —
실제로 같은 날 같은 금액을 두 번 쓸 수 있다.

**수단·유형은 이름으로 찾는다.** 양식이 드롭다운으로 이름을 넣게 하므로 파일에는 ID가 없다.
이름 → 행 조회에서 못 찾으면 그 행을 오류로 본다(Edge Case). 지출유형 이름은 회원 안에서
유일하므로(`003` FR-209) 이름으로 특정된다. 수단 이름에는 유일 제약이 없다 →
[남은 판단](#남은-판단) 참고.

## 5. 파일 크기 제한

| 계층 | 설정 |
|---|---|
| 서블릿 | `spring.servlet.multipart.max-file-size` |
| 애플리케이션 | 300행 판정(FR-319) |

서블릿 제한을 함께 걸어야 거대한 파일이 일단 전부 업로드된 뒤에 거절되는 일을 막는다.
`003`의 아이콘(1MB)과 다른 값이 필요하면 `max-file-size`를 엑셀 기준으로 잡고
아이콘은 애플리케이션에서 1MB로 더 좁힌다.

300행짜리 `.xlsx`는 수십 KB 수준이라 여유 있게 잡아도 된다.

## 남은 판단

구현 단계에서 정하면 되고, 어느 쪽이든 FR·SC를 어기지 않는다.

| 항목 | 상황 | 선택지 |
|---|---|---|
| 수단 이름 중복 | `003`은 수단 이름에 유일 제약을 두지 않는다. 같은 이름의 수단이 둘이면 업로드가 어느 쪽을 고를지 갈린다 | ① 첫 매치 ② 오류로 보고 `3502` |
| 양식의 시트 이름·설명 행 | 명세에 없다 | ① 헤더만 ② 사용법 안내 행 추가 (읽을 때 건너뛰어야 한다) |

첫 번째가 실제로 걸릴 수 있는 지점이다. `003`의 `tbl_user_payment_method`에는
`ux_user_expend_group_name` 같은 이름 유일 제약이 **없다**(덤프 확인).
"국민카드"를 두 개 만들 수 있다. ②(오류)가 안전하지만 사용자에게는 불친절하므로,
구현 시 `003`에 수단 이름 유일 제약을 넣을지와 함께 판단한다.
