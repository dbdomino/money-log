# API 계약: 지출·소득 등록과 할부

**Feature**: `004-backend-expense-income` | **Date**: 2026-09-02 | **Phase**: 1

각 API의 전체 필드 표는 `프로젝트설계/기능명세상세-백엔드/phase3-지출-소득/` 이 소유한다.
여기 적는 것은 **12건에 공통으로 걸리는 규칙**과 **설계 문서만 봐서는 갈리는 지점**이다.
엑셀(3.11·3.12)의 상세는 [excel-contract.md](./excel-contract.md)에 따로 있다.

---

## 1. 인가와 소유자

**12건 전부 로그인 필요**다. `002`의 `SecurityFilterChain` 기본 규칙이 적용된다.

소유자는 **토큰의 `id_key`**로 정해진다. Path의 `{expenseId}`·`{incomeId}`·
`{installmentGroupId}`는 자원 식별자일 뿐이며, 조회한 행의 `id_key`가 토큰과 다르면 거절한다.

| 자원 | 없음·타인 소유 |
|---|---|
| 지출 | `3202` |
| 소득 | `3302` |
| 할부 그룹 | `3206` |

003과 같은 원칙이다 — "없음"과 "타인 소유"를 같은 코드로 묶어 존재 여부를 노출하지 않는다.

---

## 2. 응답 규격

**11건**은 `{ resCode, data }`. **3.11만 예외**다(성공 시 `.xlsx` 바이너리).
**3.12는 예외가 아니다** — 파일을 돌려주지 않고 성공·실패 모두 래퍼를 쓴다.

`002`의 `GlobalExceptionHandler`를 그대로 쓴다.

### 목록 응답

**이 기능에는 목록 API가 없다.** 3.1~3.10은 전부 단건이고, 월별 목록은 `005`의
가계부 목록(4.8)이 담당한다. 따라서 `data.list` 규칙이 적용되는 API가 004에 없다.

예외처럼 보이는 것이 둘 있는데 목록이 아니다.

| API | `data` | 왜 목록이 아닌가 |
|---|---|---|
| 3.5 할부 등록 | `createdCount`만 | 생성 건수다. 지출 목록을 싣지 않는다 |
| 3.12 엑셀 업로드 | `importedCount`·`expenseCount`·`incomeCount`·`message` | 결과 요약이다 |

## 3. HTTP 메서드

| API | 메서드 | 비고 |
|---|---|---|
| 3.1·3.5·3.7·3.12 | POST | 생성 |
| 3.2·3.8·3.11 | GET | 조회 |
| 3.3·3.9 | PATCH | 수정 (omit=유지) |
| 3.4·3.10 | DELETE | **물리 삭제** |
| **3.6 중도상환** | **PATCH** | 자원 1건 삭제가 아니라 **그룹의 일정 처리**다(FR-316) |

3.6이 `DELETE`가 아닌 이유가 중요하다. URL은
`/api/v1/expenses/installments/{installmentGroupId}/remainder`인데, 삭제되는 것은
`installmentGroupId`가 가리키는 자원이 아니라 **그 그룹의 미래 회차 일부**다.
`DELETE`로 표현하면 "그룹을 지운다"로 읽혀 과거 회차까지 사라지는 것으로 오해된다.

`PUT`은 쓰지 않는다.

## 4. 이름 스냅샷 — 전 경로 공통 규칙

**이 기능에서 가장 틀리기 쉬운 규칙이다.** 등록·수정 경로 다섯 곳이 똑같이 지켜야 한다.

```text
등록 (3.1 · 3.5 · 3.7 · 3.12)
    → 참조가 사용 중인지 검증
    → 그 시점 원본 이름을 읽어 스냅샷 컬럼에 저장

수정 (3.3 · 3.9)
    → 참조 필드를 보냈는가?
        ├ 아니오(omit)          → 참조·스냅샷 둘 다 건드리지 않는다. 검증도 하지 않는다
        ├ 예, 값이 기존과 같음   → 건드리지 않는다
        └ 예, 값이 다름          → 새 참조가 사용 중인지 검증
                                  → 새 참조의 현재 이름으로 스냅샷 갱신
```

**"수정 요청이 왔으니 스냅샷도 최신화한다"고 구현하면 안 된다.** 같은 수단을 유지한 채
금액만 고쳤을 때 이름이 조용히 바뀌고, `003`의 SC-205("이름을 바꾼 뒤 과거 지출을 조회하면
스냅샷이 바뀌지 않는다")가 깨진다.

세 번째 갈래의 **"값이 기존과 같음"** 도 갱신하지 않는다. 같은 참조를 다시 보낸 것뿐이라
바뀐 것이 없다.

이 판정을 `ReferenceResolver` 한 곳에 모은다. 다섯 경로가 각자 구현하면 한 곳만 어긋나도
과거 데이터가 오염된다.

## 5. 참조 검증의 비대칭

| 경로 | 참조가 `in_use=false`·`deleted=true`이면 |
|---|---|
| **새로** 참조를 건다 | 거절 — 수단 `3003`, 지출유형 `3103` (FR-325) |
| 이미 저장된 행을 조회·수정·삭제 | **정상 동작** (FR-326) |

죽은 수단을 쓰던 과거 지출의 **금액만 고치는 수정도 성공해야 한다.**
§4의 omit 갈래가 이걸 보장한다 — 참조를 안 보냈으므로 검증 자체를 하지 않는다.

## 6. 실패 코드 매핑 — 판정 순서가 결과를 바꾸는 곳

전체 18개는 [spec.md § 이 기능이 쓰는 에러코드](../spec.md)에 있다.

### 3.3 지출 수정 — `3202` → `3203` → `3003`/`3103` → `3201`

```text
1. 대상 지출 조회 (본인 소유?)              없음·타인 → 3202
2. 할부 개월 수·시작 연월을 바꾸려 하는가?    → 3203
   (할부 건이든 아니든, 이 필드를 보냈으면 거절)
3. 참조 필드를 보냈고 값이 달라졌는가?
   └ 새 수단·유형이 사용 중이 아님          → 3003 / 3103
4. 값 검증 (금액·날짜·길이)                 → 3201
5. UPDATE (+ 참조가 바뀌었으면 스냅샷 갱신)
```

2번이 먼저인 이유: 할부 구조를 바꾸려는 요청은 다른 필드가 아무리 정상이어도 거절이다.
"바꾸려면 삭제 후 재등록한다"(FR-314).

### 3.5 할부 등록 — `3204` → `3003`/`3103` → `3205`

```text
1. 개월 수·금액 검증                        → 3204
   ├ months < 2          (1개월 할부는 일시불이다, FR-311)
   └ amount <= 0
2. 참조 검증 (사용 중인가)                   → 3003 / 3103
3. seq_installment_group.nextval → groupId
4. N개 행을 한 트랜잭션에 INSERT
   └ 도중 실패 → 전체 롤백 → 3205
→ { createdCount: N }
```

**4번이 전체 롤백**이다(FR-310). 부분 생성되면 재등록 시 앞부분이 중복된다 —
004는 업무 유일 제약을 두지 않으므로(FR-309) DB가 막아주지 않는다.

### 3.6 중도상환 — `3206` → `3207`

```text
1. installmentGroupId 로 그룹 조회 (본인 소유?)   없음·타인 → 3206
2. payment_date > today 인 회차를 센다
   └ 0건                                        → 3207
3. 그 회차들만 물리 삭제. payment_date <= today 는 남긴다
```

**2번의 경계가 `>`다.** `>=`로 잡으면 오늘 결제된 회차까지 사라져 이번 달 합계가
소급해 줄어든다.

**3207을 멱등 성공으로 흘리지 않는다.** "방금 정리했다"와 "이미 정리되어 있었다"를
화면이 구분해야 한다.

### 3.1 지출 등록 — `3003`/`3103` → `3201` → `9001`

```text
1. 필수 필드 누락                            → 9001
2. 참조 검증 (수단·유형이 사용 중인가)         → 3003 / 3103
3. 값 검증                                   → 3201
   ├ amount <= 0, 소수점·문자, BIGINT 범위 초과
   ├ place 100자 초과, content 255자 초과
   └ 날짜 형식
4. 스냅샷 획득 + INSERT (할부 3컬럼은 전부 NULL)
```

3번의 **길이 검사**를 빠뜨리면 DB 오류가 `9000`(서버 오류)으로 새어 나간다.
사용자 입력 문제인데 서버 장애처럼 보인다.

## 7. 소득이 지출과 다른 점 (3.7~3.10)

| 항목 | 지출 | 소득 |
|---|---|---|
| 지출유형 | 필수 | **없다** |
| 장소 `place` | 필수 | **없다** |
| 할부 | 있다 | **없다** |
| `content` | 필수 | **비어 있을 수 있다** |
| 값 오류 코드 | `3201` | `3301` |
| 없음·타인 소유 | `3202` | `3302` |

**컬럼이 아예 없는 것**이지 비워 두는 것이 아니다(FR-306).
소득 등록 Body에 `place`·`expendGroupId`·할부 필드를 실어 보내면 **무시**되고
`tbl_income`에 대응 컬럼이 없어 저장되지 않으며 응답에도 나타나지 않는다.

## 8. 할부 3컬럼 불변식 — 저장 진입점 3곳

```text
일시불:  세 컬럼 전부 NULL
할부:    세 컬럼 전부 채움 (group_id 공유, index 1..N, total N>=2)
```

**DB가 막지 않는다.** CHECK 2건이 각 컬럼의 범위만 보고 세 컬럼의 동시성은 검사하지 않는다.
저장 진입점 셋이 지킨다.

| 진입점 | 무엇을 넣나 |
|---|---|
| 3.1 지출 등록 | 세 컬럼 전부 NULL |
| 3.5 할부 등록 | 세 컬럼 전부 채움 |
| 3.12 엑셀 업로드 | **세 컬럼 전부 NULL** — 양식에 할부 컬럼이 없다 |

부분 채움 행이 생기면 "일시불인가 할부인가"를 판정할 수 없고, 조회·집계·중도상환이 전부
그 판정에 의존하므로 조용히 틀린 답이 나온다.

## 9. 로깅

`002`의 AOP 로깅을 쓴다. 004가 추가로 정할 것은 둘이다.

| 대상 | 규칙 |
|---|---|
| 3.11 응답 본문 | **찍지 않는다.** `.xlsx` 바이너리다. 크기만 남긴다 |
| 3.12 요청의 `MultipartFile` | 파일명·크기만 남긴다 |

`003`이 아이콘에 대해 정한 것과 같은 규칙이다 — `byte[]`·`Resource`·`MultipartFile`은
내용을 생략한다.

마스킹 대상은 004에 새로 추가할 것이 없다(비밀번호·토큰을 다루지 않는다).
