# Research: 프론트 회원·인증 화면

**Feature**: 008-frontend-member-auth | **Date**: 2026-09-11 | **Plan**: [plan.md](./plan.md)

007 이 통로와 껍데기를 세웠으므로 008 이 새로 정할 것은 **화면이 사용자와 주고받는 방식**뿐이다.
아래 14건이 그 판단이며, 결정하지 않고 구현에 들어가면 화면 9개가 제각각 달라지는 항목들이다.

---

## 1. 폼이 실패하면 같은 폼으로 되돌린다

**Decision**: 폼을 가진 컨트롤러마다 **컨트롤러 지역 `@ExceptionHandler(BackendApiException)`** 를 두고
같은 뷰 이름을 돌려준다. 사용자가 넣었던 값은 **템플릿이 요청 파라미터에서 되읽어** 채운다.

**Rationale**: 007 의 `FrontExceptionHandler` 는 실패를 오류 화면으로 보낸다. 그것이 목록·상세에는
맞지만 폼에는 틀리다 — 가입 폼에서 아이디가 중복이라는 이유로 오류 화면으로 튕기면 **사용자가
입력한 일곱 칸이 전부 사라진다.** 스펙의 Acceptance(US1-3)가 "입력이 남아 있다"를 요구한다.

컨트롤러 안의 `@ExceptionHandler` 는 `@ControllerAdvice` 보다 먼저 잡으므로 007 을 고치지 않고
화면별로 착지만 바꿀 수 있다. 그리고 이것은 `try-catch` 로 응답을 손수 만드는 것이 아니라
**선언으로 착지를 지정하는 것**이라 헌장 III 의 금지(“컨트롤러에서 try-catch 로 응답을 제각각
만들지 않는다”)에 걸리지 않는다.

값을 요청 파라미터에서 되읽는 이유는 **예외 처리로 넘어갈 때 모델이 새로 만들어지기 때문**이다.
제출한 폼 객체는 그 자리에 없지만 요청 파라미터는 그대로 살아 있다. 모델을 옮겨 심는 장치를
만드는 것보다 짧고, 어느 화면에서도 같은 방식으로 동작한다.

**비밀번호 칸은 되채우지 않는다.** 응답 HTML 에 평문 비밀번호가 실리면 SC-708 이 깨진다.

**Alternatives considered**:

- **전역 핸들러가 폼인지 목록인지 가려 착지를 고른다** — 가리는 기준이 없다. 요청 경로로 나누면
  화면이 늘 때마다 007 의 공통 코드를 고쳐야 하고, 그것은 008~012 가 007 을 계속 건드린다는 뜻이다.
- **실패를 예외가 아니라 반환값으로 받는다** — 007 이 예외로 만든 이유가 "확인을 빠뜨린 코드도
  컴파일되기 때문"이다. 그 결정을 008 에서 뒤집으면 화면 31개가 다시 확인을 빠뜨릴 수 있게 된다.
- **실패를 flash 에 담아 GET 으로 되돌린다** — 새로고침에는 강하지만 왕복이 한 번 더 늘고,
  입력값 전부를 flash 에 실어야 해서 비밀번호가 세션에 잠시 머문다.

## 2. 1.4 가 확인한 아이디·닉네임을 1.5 로 넘기는 방법

**Decision**: **서버 세션의 짧은 표식**으로 넘긴다. 1.4 가 확인에 성공하면 아이디·닉네임을 세션에
담고 1.5 로 보낸다. 1.5 는 그 값을 읽어 화면에 숨은 값으로 싣고, **재설정에 성공하는 순간 지운다.**
표식을 읽고 쓰는 자리는 한 클래스로 묶는다(007 의 `LoginSession` 과 같은 규율).

**Rationale**: 1.5 의 저장 API 가 아이디·닉네임을 다시 요구하는데, 사용자에게 두 번 묻지 않는 것이
FR-712 다. 주소에 실으면 아이디가 주소창·방문 기록·Referer 에 남는다. flash 로 넘기면 한 번의
redirect 만 살아남아 **사용자가 1.5 에서 새로고침하면 처음으로 되돌아간다** — 비밀번호를 고르는
중에 일어나기 쉬운 일이다.

세션은 로그인하지 않은 사용자에게도 이미 만들어진다(flash 자체가 세션에 산다). 표식을 성공 직후
지우므로 남는 시간은 재설정 한 번 동안이다.

**Alternatives considered**:

- **주소 질의 문자열** — 아이디가 눈에 보이는 곳에 남는다.
- **flash attribute** — 새로고침에 약하다. 위 이유.
- **화면의 숨은 값만으로 들고 다닌다** — 1.5 에 직접 들어온 사용자와 1.4 를 거친 사용자를 서버가
  구분할 수 없어 FR-714 를 지킬 수 없다. 값 자체는 백엔드가 다시 대조하므로 조작해도 남의 비밀번호를
  바꿀 수는 없지만, **"어디서 왔는가"를 서버가 모르는 상태**가 된다.

## 3. 1.5 는 완료 문구를 보인 뒤 로그인으로 보낸다

**Decision**: 저장에 성공하면 **같은 화면을 완료 상태로 다시 그리고**, 그 화면이 잠시 뒤 로그인
화면으로 옮겨 가게 한다. 완료 전용 주소를 만들지 않는다.

**Rationale**: FR-713 이 "같은 화면에 완료 문구"를 요구한다. 완료 전용 주소를 두면 화면이 하나 늘고,
그 주소에 직접 들어온 사용자에게는 아무 맥락도 없는 완료 문구가 보인다.

프로토타입(`auth-reset-password.html`)도 완료 블록과 「로그인으로」 버튼을 같은 화면에 두고 있다.
**버튼을 함께 두는 것이 중요하다** — 자동 이동만 두면 그 이동이 막힌 환경에서 사용자가 갇힌다.

**Alternatives considered**:

- **곧바로 로그인으로 보낸다** — 비밀번호가 바뀌었는지 사용자가 확인할 자리가 없다.
- **완료 전용 주소** — FR-713 이 명시적으로 배제한다.

---

## 4. 이미 로그인한 사용자가 로그인·가입 화면에 오면

**Decision**: **1.1·1.2 의 조회 처리에서** 세션을 보고 월별 가계부로 보낸다. 007 의 비로그인 허용
목록은 건드리지 않는다.

**Rationale**: 그 목록은 "로그인 없이 **열 수 있는가**"를 정하는 것이고(FR-618), 여기서 필요한 것은
"로그인했으면 **열 필요가 없다**"는 다른 판단이다(FR-709). 진입 판정에 섞으면 공통 기반이 화면별
사정을 알게 된다.

1.3~1.5(찾기·재설정)는 보내지 않는다. 로그인한 사용자가 비밀번호를 잊은 지인을 돕는 등
**들어올 이유가 있는 화면**이고, 스펙도 1.1·1.2 만 지목한다.

---

## 5. 회원 검색은 아이디와 닉네임 **두 칸**이다

**Decision**: 검색 입력을 아이디 칸과 닉네임 칸으로 나눈다. 둘 다 선택이며, 함께 넣으면 **둘 다
맞는 회원**만 나온다는 것을 화면에 적는다.

**Rationale**: 백엔드 목록 API 가 두 값을 받아 **AND 로 묶는다**(`data-mod`
`UserRepository.search` 가 `like ... and like ...`). 프로토타입처럼 칸 하나에 받아 두 값에 똑같이
실으면 "아이디에도 있고 닉네임에도 있는" 회원만 걸려서, 사용자가 기대한 "아이디 **또는** 닉네임"과
정반대로 동작한다. 그리고 그 오작동은 **결과가 비는 형태**로 나타나 원인을 짐작하기 어렵다.

한 칸으로 두려면 백엔드가 OR 검색을 제공해야 하는데, 008 의 전제는 "백엔드 코드는 바뀌지 않는다"다.

**Alternatives considered**:

- **한 칸 + 대상 선택(아이디/닉네임)** — 동작은 맞지만 조작이 두 단계가 되고, 두 조건을 함께 좁히는
  일을 못 한다.
- **한 칸을 아이디에만 싣는다** — 닉네임으로 찾을 방법이 사라진다. FR-718 이 둘 다 요구한다.

---

## 6. 검색어가 바뀌면 첫 쪽으로 되돌아간다

**Decision**: 검색 폼은 **쪽 번호를 싣지 않는다.** 쪽 번호는 목록 아래의 쪽 이동 링크만 싣는다.

**Rationale**: FR-719 를 "바뀌었는지 서버가 비교한다"로 풀면 이전 검색어를 어딘가에 들고 있어야
한다. 검색 폼이 쪽 번호를 아예 보내지 않으면 새 검색은 언제나 쪽 번호가 없는 요청이 되고,
기본값 0 이 첫 쪽이다. 비교도 저장도 필요 없다.

007 의 `Paging` 이 같은 이유로 개수가 바뀔 때 첫 쪽으로 되돌린다 — 그쪽은 시작점이 개수의 배수가
아니게 되는 문제였고, 이쪽은 결과가 줄어 빈 쪽이 뜨는 문제다.

## 7. 본인 정보에서 빈 칸의 뜻

**Decision**: 두 가지로 나눈다.

| 칸 | 비워 두면 |
|---|---|
| 새 비밀번호 | **바꾸지 않는다** (요청에 싣지 않는다) |
| 이메일 · 폰 · 소개 | **비운다** (요청에 빈 값으로 싣는다) |

**Rationale**: 백엔드 수정 API 는 보내지 않은 항목은 유지하고, 값을 비우려면 빈 값을 명시해야 한다.
화면이 이 둘을 구분해 보내야 한다.

비밀번호 칸은 **현재 값이 채워져 있지 않다.** 비어 있는 것이 기본 상태이므로 "비웠다"가 아니라
"건드리지 않았다"로 읽는 것이 맞고, FR-716 이 그렇게 못 박는다.

나머지 세 칸은 **현재 값이 채워진 채로 뜬다.** 사용자가 지웠다면 지우려는 뜻이다. 이것을 "유지"로
읽으면 사용자는 이메일을 지우고 저장했는데 그대로 남아 있는 화면을 보게 된다.

**이 규칙을 화면 문서에 적는다**(원칙 V). 표만 보고는 두 칸의 성격이 다르다는 것을 알 수 없다.

## 8. 브라우저는 GET 과 POST 만 쓴다

**Decision**: 화면의 폼은 전부 `POST` 로 화면 모듈에 보낸다. 화면 모듈이 그것을 백엔드 규칙
(`POST` 생성 · `PATCH` 수정)으로 옮긴다.

**Rationale**: HTML 폼은 `PATCH` 를 보낼 수 없다. 자바스크립트로 보내게 만들 수는 있지만 007 이
"화면 스크립트는 API 를 부르지 않는다"로 정했고, 그러면 토큰을 브라우저가 알아야 한다.

헌장 III 의 메서드 규칙은 **API 응답 규격에 대한 것**이라 화면 모듈이 백엔드를 부르는 구간에
적용된다. 브라우저와 화면 모듈 사이는 화면 주소이지 API 가 아니다 — 007 이 로그아웃을
`POST /auth/logout` 으로 둔 것과 같은 자리다.

**되돌릴 수 없는 동작은 링크로 두지 않는다.** 회원 정지를 `GET` 링크로 두면 브라우저가 미리
불러오는 것만으로 계정이 정지된다.

---

## 9. 수정 모달은 열기 전에 서버가 값을 가져온다

**Decision**: `?m=edit&id={아이디}` 로 들어오면 **목록을 그리기 전에** 그 회원을 조회해 모델에
싣는다. 007 의 모달 판정이 아는 값일 때만 조회한다.

**Rationale**: 007 이 "서버가 판정하고 스크립트가 연다"로 정한 이유가 바로 이것이다. 모달을 여는
일만 브라우저가 하면 열린 모달이 빈 채로 뜨고, 값을 채우려면 브라우저가 다시 요청해야 한다.

모르는 식별자면 조회가 `2001` 로 실패한다. 이때는 오류 화면이 아니라 **모달 없이 목록만** 보이고
안내를 띄운다 — 북마크가 낡았을 뿐이고 목록은 정상이다.

---

## 10. 폰의 하이픈은 서버가 걷어낸다

**Decision**: 화면 모듈이 전송 직전에 숫자만 남긴다. 브라우저 스크립트에 맡기지 않는다.

**Rationale**: FR-703 과 SC-704 는 "어떤 형식으로 입력해도 저장값은 숫자만"을 요구한다. 브라우저에서만
걷어내면 스크립트가 막힌 환경에서 하이픈이 그대로 나가고, 백엔드는 형식 오류로 거절한다.

입력 중의 편의(숫자 자판 띄우기)는 브라우저가 맡되, **보장은 서버가 한다.** 두 곳에서 하는 것이
아니라 보장하는 자리를 한 곳으로 정하는 것이다.

## 11. 정지를 되돌리는 API 가 없다

**Finding**: 프로토타입(`member-admin-list.html`)에는 정지된 회원 행에 「해제」 버튼이 있다. 그런데
백엔드 002 에는 **정지 해제 API 가 없다.** 008 의 전제는 백엔드를 바꾸지 않는 것이다.

**Decision**: 「해제」 버튼을 **만들지 않는다.** 화면 문서에 "정지는 화면에서 되돌릴 수 없다"를 적고,
정지 확인 다이얼로그 본문에도 그 사실을 싣는다.

**Rationale**: 누를 수 없는 버튼을 두면 관리자는 언제든 되돌릴 수 있다고 믿고 정지를 누른다.
되돌릴 수 없다는 사실은 **누르기 전에** 보여야 한다.

해제가 필요하다는 판단이 서면 백엔드 명세부터 고치는 것이 순서다(원칙 V).

---

## 12. 목록에 가입일이 없다

**Finding**: 프로토타입의 회원 목록에 「가입일」 열이 있지만 백엔드 목록 응답에는 그 값이 없다.

**Decision**: 열을 **빼고** 화면 문서의 표에 그 사실을 적는다. 남은 열은 아이디·닉네임·이메일·
권한·상태·관리 여섯이다.

**Rationale**: 응답에 없는 값을 열로 두면 구현자가 다른 API 를 찾아 헤매거나 빈 칸을 그린다.
빈 칸은 "가입일을 모르는 회원"으로 읽혀 데이터가 잘못된 것처럼 보인다.

---

## 13. 비밀번호는 화면에도 로그에도 남기지 않는다

**Decision**: 세 가지를 건다.

- 비밀번호 칸은 **어떤 경우에도 값을 채워 보내지 않는다.** 실패로 폼을 다시 그릴 때도 비운다.
- 폼 객체를 로그에 통째로 찍지 않는다. 007 의 호출 로그가 본문을 남기지 않는 것과 같은 이유다.
- 실패 안내는 백엔드가 준 문구를 그대로 쓴다. 화면이 "비밀번호 `abc` 는 규칙에 맞지 않습니다"처럼
  입력값을 되비추는 문구를 만들지 않는다.

**Rationale**: SC-708 이 "브라우저가 받은 응답 어디에도 비밀번호·토큰 원문이 없다"를 요구한다.
되채우기를 한 번만 허용해도 비밀번호가 HTML 에 실리고, 그 HTML 은 브라우저 캐시와 방문 기록에 남는다.

---

## 14. 007 의 세션 만료 안내가 로그인 화면에 닿는지 확인한다

**Finding**: 007 은 세션이 끝났을 때 안내 문구를 실어 로그인 화면으로 보낸다. 그런데 **로그인 화면이
007 시점에 없어서 그 경로를 끝까지 확인한 시험이 없다.** 008 이 그 화면을 만드는 첫 기능이다.

**Decision**: 1.1 로그인 화면이 그 문구를 받아 보여 주는 것을 **시험으로 고정한다.** 007 의 전달
방식이 실제로 동작하지 않으면 그 자리에서 드러나며, 그때는 007 의 전달 방식을 고친다(화면 쪽을
맞추지 않는다 — 문구를 넘기는 쪽이 007 의 책임이다).

**Rationale**: 다른 곳에서 로그인해 밀려난 사용자는 로그인 화면에서 **왜 밀려났는지** 알아야 한다.
그 문구가 없으면 "가만히 있었는데 로그아웃됐다"로만 보이고, 사용자는 계정이 털렸다고 의심한다.
