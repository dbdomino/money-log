# Contract: 폼 실패를 화면에 되돌리는 규약

**Feature**: 008-frontend-member-auth | **관련 FR**: 701~724 전반 · SC-707 · SC-708

화면 9개 중 8개가 폼을 가지고 있다. 그 폼들이 실패를 **같은 방식으로** 보여야 사용자가 무엇이
잘못됐는지 한 번 배우면 다음 화면에서도 안다.

## 1. 착지는 폼이다

007 의 공통 실패 처리는 오류 화면으로 보낸다. 목록·상세에는 맞지만 폼에는 틀리다 — 아이디가
중복이라는 이유로 오류 화면으로 튕기면 **사용자가 채운 일곱 칸이 전부 사라진다.**

| 실패 종류 | 착지 |
|---|---|
| 백엔드가 준 업무·검증 실패 (`1003`·`2002`·`2004` 등) | **그 폼 화면을 다시 그린다** |
| 백엔드에 닿지 못함 | 007 의 오류 화면 |
| 로그인 상태가 끝남 (`1001` 재발급 실패 · `1006`) | 007 이 로그인 화면으로 보낸다 |

가운데 둘은 007 이 이미 처리한다. 008 이 더하는 것은 **첫 줄 하나**다.

## 2. 되돌리는 방법

폼을 가진 컨트롤러마다 **그 컨트롤러 안에** 실패 처리를 선언하고 자기 뷰 이름을 돌려준다.
컨트롤러 안의 선언이 공통 선언보다 먼저 잡히므로 007 을 고치지 않는다.

```
POST 처리 → 백엔드 호출 → 실패 예외
                              │
                              └─ 이 컨트롤러의 실패 선언이 받는다
                                   · 응답 코드와 백엔드 문구를 모델에 담는다
                                   · 같은 뷰 이름을 돌려준다 (redirect 하지 않는다)
```

**`try-catch` 로 응답을 손수 만드는 것이 아니다.** 착지를 선언으로 지정하는 것이며, 응답 형태를
바꾸지도 코드를 바꾸지도 않는다(헌장 III).

**redirect 하지 않는 이유**는 입력값이 요청에 실려 있기 때문이다. redirect 하면 그 요청이 끝나고
값이 사라진다.

## 3. 값을 되채우는 방법

**템플릿이 요청 파라미터에서 되읽는다.** 실패 처리로 넘어갈 때 모델은 새로 만들어져 제출한 폼
객체가 없지만, 요청 파라미터는 그대로 살아 있다.

| 칸 | 다시 그릴 때 |
|---|---|
| 아이디 · 닉네임 · 이메일 · 폰 · 소개 · 권한 | 사용자가 넣은 값을 그대로 채운다 |
| 비밀번호 · 비밀번호 확인 · 새 비밀번호 | **언제나 비운다** |

**비밀번호를 되채우지 않는 것이 규약이다.** 한 번만 허용해도 평문이 HTML 에 실리고, 그 HTML 은
브라우저 캐시와 방문 기록에 남는다(SC-708). 사용자가 비밀번호를 다시 입력하는 불편보다 낫다.

## 4. 보여 주는 것

| 모델에 담는 것 | 화면에서 |
|---|---|
| 응답 코드 | 폼 상단 안내에 함께 적는다. 문의할 때 단서가 된다 |
| 백엔드 문구 | 그대로 보여 준다. 화면이 문구를 새로 만들지 않는다 |

**입력값을 되비추는 문구를 만들지 않는다.** "비밀번호 `abc123` 은 규칙에 맞지 않습니다" 같은 문구는
화면과 로그 양쪽에 사용자의 입력을 남긴다.

### 칸 가까이 붙이는 실패

FR-717 이 이메일 중복과 비밀번호 규칙 위반을 "해당 칸 가까이" 요구한다. 코드로 칸을 가른다.

| 코드 | 붙는 칸 | 화면 |
|---|---|---|
| `2002` 아이디 중복 | 아이디 | 1.2 · 1.9 |
| `2003` 이메일 중복 | 이메일 | 1.2 · 1.7 · 1.9 · 1.10 |
| `2004` 비밀번호 규칙 위반 | 비밀번호 | 1.2 · 1.5 · 1.7 · 1.9 · 1.10 |
| `2005` 비밀번호 확인 불일치 | 비밀번호 확인 | 1.2 · 1.5 |
| 그 밖의 코드 | **폼 상단** | 전부 |

**어느 칸인지 모르면 상단이다.** 엉뚱한 칸에 붙이면 사용자가 맞는 칸을 고치고 또 틀린다.

## 5. 로그인 실패만 다르게 다룬다

`1003` 은 **아이디와 비밀번호 중 무엇이 틀렸는지 드러내지 않는다**(FR-706 · SC-702).

- 안내를 **아이디 칸에도 비밀번호 칸에도 붙이지 않는다.** 폼 상단에만 둔다.
- 백엔드 문구를 그대로 쓴다. 백엔드가 두 경우를 한 코드로 묶은 이유를 화면이 풀지 않는다.
- 아이디 칸의 값은 되채운다. 그것만으로는 존재 여부가 드러나지 않는다 — 사용자가 방금 친 값이다.

`1004`(비활성 계정)는 반대로 **상태를 분명히 알린다**(FR-707). 이 코드는 아이디가 맞다는 사실을
드러내지만, 정지된 사용자가 이유를 모른 채 비밀번호만 계속 시도하는 쪽이 더 나쁘다고 002 가 이미
판단했다.

## 6. 모달 안의 실패

1.9·1.10 은 목록 위 모달이다. **부모 목록으로 튕기지 않고 모달을 연 채로** 폼 상단에 보인다.

다시 그릴 때 007 의 모달 판정에 같은 값을 실어 모달이 열린 상태로 뜨게 한다. 실패한 요청이
모달 제출이라는 것을 컨트롤러가 알고 있으므로 판정에 다시 물을 필요가 없다.

## 7. 시험으로 고정할 것

| 항목 | 근거 |
|---|---|
| 가입 실패 응답에 아이디·닉네임·이메일이 남아 있다 | US1-3 |
| 가입 실패 응답에 비밀번호 평문이 **없다** | SC-708 |
| 로그인 실패 안내가 아이디 칸에 붙지 않는다 | FR-706 · SC-702 |
| 이메일 중복이 이메일 칸 가까이 붙는다 | FR-717 |
| 모달 제출 실패가 모달이 열린 목록 화면으로 돌아온다 | §6 |
| 백엔드 불통은 폼이 아니라 오류 화면으로 간다 | 007 FR-606 |
## 8. 이 기능이 다루는 실패 코드

**화면 모듈은 새 코드를 정의하지 않는다.** 백엔드가 준 코드를 그대로 옮겨 화면에 맞게 보여줄
뿐이다. 코드가 어느 칸에 붙는지는 §4 가, 화면별로 무엇이 보이는지는 각 화면 계약이 정한다.

| 코드 | 뜻 | 어느 화면 | 붙는 자리 |
|---|---|---|---|
| `1003` | 아이디 또는 비밀번호가 틀림 | 1.1 | **폼 상단에만** (§5) |
| `1004` | 비활성 계정 | 1.1 · 1.4 · 1.5 | 폼 상단 |
| `2001` | 회원을 찾을 수 없음 | 1.3 · 1.4 · 1.5 · 1.10 | 폼 상단 또는 목록 안내 |
| `2002` | 아이디 중복 | 1.2 · 1.9 | 아이디 칸 |
| `2003` | 이메일 중복 | 1.2 · 1.7 · 1.9 · 1.10 | 이메일 칸 |
| `2004` | 비밀번호 규칙 위반 | 1.2 · 1.5 · 1.7 · 1.9 · 1.10 | 비밀번호 칸 |
| `2005` | 비밀번호 확인 불일치 | 1.2 · 1.5 | 비밀번호 확인 칸 |
| `9001` | 필수 누락 · 형식 오류 · 권한 값 오류 · 페이징 규칙 위반 | 전부 | 폼 상단 |

`9001` 이 여러 뜻을 한 코드에 담고 있어 **어느 칸인지 가릴 수 없다.** 그래서 언제나 상단이다 —
짐작해 아무 칸에나 붙이면 사용자가 맞는 칸을 고치고 또 틀린다.

---

## 9. 이 기능이 부르는 백엔드 API

화면 9개가 백엔드 002 의 API **12건**을 부른다.

| 묶음 | API |
|---|---|
| 비로그인 화면 (1.1~1.5) | `MemberSignup` · `MemberLogin` · `MemberFindId` · `MemberFindPassword` · `MemberResetPassword` |
| 본인 정보 (1.7) | `MemberGetMe` · `MemberUpdateMe` |
| 관리자 (1.8~1.10) | `AdminMemberList` · `AdminMemberCreate` · `AdminMemberGet` · `AdminMemberUpdate` · `AdminMemberDeactivate` |

**토큰 검증·재발급·비활성화 3건은 008 이 부르지 않는다.** 007 의 세션 계층이 부른다 — 로그아웃
버튼은 008 이 만들지만 호출은 007 이 하며, 토큰 비활성화와 세션 버리기의 순서를 한 곳에서
지켜야 하기 때문이다.

앞의 다섯은 **인증 없이** 부른다. 만료된 토큰을 실어 보내면 로그인조차 만료로 거절된다.
