# 월별 내역 생명주기 계약: lazy 생성 · 설정 반영 · 재작성

**Feature**: `005-backend-ledger-fixed-expense` | **Date**: 2026-09-02 | **Phase**: 1

이 기능의 개념적 핵심이다. **설정과 그 달의 값이 분리되어 있고, 그 달의 값은 조회할 때
만들어진다.** 그래서 "언제 만들어지는가 / 설정을 고치면 어디까지 따라가는가 /
어긋난 것을 어떻게 되맞추는가" 셋이 규칙이 된다.

---

## 1. 생성 — 누가 일으키나

**셋뿐이다.**

| API | 생성 대상 |
|---|---|
| 4.5 월별 내역 목록 | 그 연·월에 기간이 걸리는 **전체** |
| 4.8 월별 가계부 목록 | 위와 같다 |
| 4.9 재작성 | 위와 같다 (명시적 호출) |

**`006`의 통계 조회는 생성을 일으키지 않는다.** 따라서 한 번도 열지 않은 달의 통계는
고정지출 합계가 0으로 나온다. 이 사실은 `005`·`006` 양쪽 Assumptions에 적혀 있다 —
006 구현자가 반대로 가정하면 GET이 다른 테이블에 쓰는 부작용이 하나 더 생긴다.

### 생성 조건

```text
그 연·월(ym)에 대해, 회원의 각 고정지출 설정마다:

    적용 기간에 포함되는가?
        (start_ym <= ym <= end_ym,  ym = 연 × 12 + 월)
        ├ 아니오  → 만들지 않는다 (FR-408)
        └ 예
             이미 그 연·월 행이 있는가?
             ├ 예    → 아무것도 하지 않는다
             └ 아니오 → 설정에서 복사해 만든다
```

복사되는 값:

| 월별 내역 컬럼 | 설정에서 |
|---|---|
| `amount` | `amount` |
| `payment_date` | `payment_day_of_month`를 **그 달에 맞게 말일 보정** |
| `content` | `content` |
| `payment_method_idx` | `payment_method_idx` |
| `expend_group_idx` | `expend_group_idx` |
| `modified` | **`false`** |

**이름은 복사하지 않는다.** 컬럼 자체가 없다.

### 말일 보정 (FR-409)

```text
payment_day_of_month = 31,  대상이 2026-02  →  payment_date = 2026-02-28
payment_day_of_month = 31,  대상이 2028-02  →  payment_date = 2028-02-29  (윤년)
payment_day_of_month = 25,  대상이 2026-02  →  payment_date = 2026-02-25
```

**만들 때 한 번만 보정해 저장한다.** 조회 때 다시 계산하지 않는다.
계산 지점이 둘이면(4.5와 4.8) 한쪽만 윤년 처리를 빠뜨렸을 때 같은 달의 결제일이
두 화면에서 다르게 보인다. 저장해 두면 출처가 하나다.

### 필터와 생성의 순서 (FR-406)

**생성을 먼저 전부 끝낸 뒤 필터로 결과를 좁힌다.**

4.5는 `paymentMethodId`·`expendGroupId` 선택 필터를 지원하는데,
**필터가 걸려 있어도 그 연·월의 대상 전체가 생성된다.**

순서를 뒤집으면 위험하다. `paymentMethodId=5`로 필터를 걸고 그 달을 처음 열면
수단 5의 고정지출만 생성되고, 나중에 필터 없이 같은 달을 열면 나머지가 그때 생긴다.
그러면 **같은 달의 내역이 "언제 어떤 필터로 처음 열었는가"에 따라 달라진다.**

4.8은 필터가 있어도 그 달 전체를 만들어야 하므로(FR-418), 4.5가 부분 생성을 하면
두 API가 만드는 결과가 갈린다.

## 2. 동시 생성 경합

**`INSERT ... ON CONFLICT DO NOTHING`으로 처리하고, 삽입 후 다시 조회한다.**

```text
요청 A ─┐
        ├─ 둘 다 "그 연·월 행 없음" 을 본다
요청 B ─┘
        │
        ├─ A: INSERT ... ON CONFLICT DO NOTHING  → 1행 삽입
        └─ B: INSERT ... ON CONFLICT DO NOTHING  → 0행 (충돌 무시, 예외 없음)
        │
        └─ 둘 다 직후 SELECT → 같은 1건을 본다
```

**근거**: SC-403이 "동시에 두 요청이 처음 열어도 행은 1건이고 **어느 쪽도 오류로 끝나지
않는다**"를 요구한다. 뒷부분이 핵심이다.

DB 유니크 제약 `ux_fixed_expense_monthly (fixed_expense_idx, year, month)`가 최종 방어선이다.
애플리케이션의 "있으면 건너뛴다" 검사만으로는 두 트랜잭션이 같은 순간 "없음"을 보는 창을
닫지 못한다.

**`002`의 로그인 세션 경합과 다르게 처리한다.** 거기서는 재시도를 골랐는데,
재로그인이 "기존 폐기 → 새로 삽입"이라 단순 무시로 끝나지 않기 때문이다.
여기서는 **먼저 만든 쪽의 행을 그대로 쓰면 되므로** 무시가 맞다.

## 3. 설정 수정(4.4)의 자동 반영 범위

```text
서버 기준 현재 연월을 now 라 할 때  (ym = 연 × 12 + 월)

    ym <  now   지난 달              →  갱신하지 않는다
    ym == now   이번 달              →  갱신하지 않는다
    ym >  now   미래 달
                ├ modified = false   →  갱신한다
                └ modified = true    →  갱신하지 않는다
```

갱신되는 값은 §1의 복사 항목과 같다. **`modified`는 건드리지 않는다** —
설정 수정이 값을 덮어써도 그 행은 여전히 "직접 수정된 적 없는" 행이다.

### 이번 달을 포함하지 않는 이유

포함하면 월세를 올렸을 때 **이번 달 가계부 금액이 소급해 바뀐다.**
사용자가 이미 본 숫자가 변한다.

`004`의 중도상환 경계(`payment_date > today`)와 같은 성격의 결정이다.
"이미 일어난 일과 진행 중인 것은 건드리지 않는다."

지난 달·이번 달을 새 설정값으로 맞추고 싶으면 **4.9를 명시적으로 부른다.**
**자동과 수동의 경계가 여기다.**

### 자동 반영이 하지 않는 것

**삭제하지 않는다.** 적용 기간을 줄여서(종료를 2027-02 → 2026-12로) 기간 밖이 된
월별 내역이 있어도 자동 반영은 값 갱신만 한다. 정리는 4.9의 ④가 맡는다.

## 4. 재작성(4.9) — 네 처리

**한 트랜잭션**에서 지정한 **한 연·월**에 대해 넷을 수행한다(FR-413·414).

```text
그 연·월(ym) 에 대해, 회원의 각 고정지출 설정마다:

  기간에 포함?   행 존재?   modified   →  처리              건수
  ─────────────────────────────────────────────────────────────────
     예           아니오       —        →  ① 생성           createdCount
     예            예        false      →  ② 관리 값으로 갱신 updatedCount
     예            예        true       →  ③ 보존            keptCount
     예            예        true       →  ②' overwriteModified=true 면
                                            갱신 + modified=false     updatedCount
     아니오        예         —         →  ④ 삭제            deletedCount
     아니오       아니오      —         →  아무것도 안 한다   —
```

### ④가 필요한 이유

설정의 적용 기간을 줄이면 이미 만들어진 행이 기간 밖이 된다.
자동 반영(§3)은 값 갱신만 하고 삭제하지 않으므로, 이 정리를 재작성이 맡는다.

### `overwriteModified`

기본값은 `false`(③ 보존). `true`면 직접 수정분이 **관리 값으로 되돌아가고
`modified` 표시가 내려간다**(SC-406).

`modified=true`를 `false`로 되돌리는 **유일한 경로**다. 4.6은 항상 `true`로 세운다.

사용자 확인은 화면에서 받는 것을 전제한다 — 되돌리면 직접 고친 값이 사라진다.

### 결과 목록을 함께 돌려준다 (FR-415)

건수 넷과 **재작성 결과 목록**을 함께 싣는다. 호출 후 재조회가 필요 없어야
화면이 한 번의 왕복으로 끝난다.

부가 필드: `year` · `month` · `createdCount` · `updatedCount` · `keptCount` · `deletedCount`
(`list`와 같은 레벨).

## 5. `연 × 12 + 월` 합성 비교 — 한 곳에 가둔다

이 비교가 **네 곳**에 나온다.

| 위치 | 무엇을 비교하나 |
|---|---|
| FR-404 (4.1 검증) | `end_ym >= start_ym` |
| FR-408 (생성 대상) | `start_ym <= ym <= end_ym` |
| FR-412 (자동 반영) | `ym > now_ym` |
| FR-413 (재작성 대상) | 위와 같은 기간 판정 |

각자 계산하면 한 곳만 틀려도 **해를 넘기는 구간에서 조용히 어긋난다**
(2026-12 vs 2027-01을 연·월 따로 비교하면 12 > 1이라 뒤집힌다).

DB CHECK도 같은 식을 쓴다 —
`ck_fixed_expense_period CHECK ((end_year * 12 + end_month) >= (start_year * 12 + start_month))`.
001이 이미 스키마에 못박았으므로 애플리케이션도 같은 식이어야 한다.

`YearMonthValue` 값 객체 하나로 가둔다. **`java.time.YearMonth`를 쓰지 않는 것**은
저장 형태가 `year`·`month` INT 두 개이기 때문이다(헌장 DB 저장 구조 규칙).
매핑 계층에서 변환은 하되, 비교 규칙은 DB CHECK과 같은 식으로 둔다.

## 6. 삭제 (4.7)

```text
관리 행 DELETE
    └ ON DELETE CASCADE  →  그 고정지출의 월별 내역 전부 (지난 달 포함)
```

**물리 삭제다**(FR-416). 삭제 표시로 남기지 않으며 `deleted` 컬럼도 없다.

**막는 조건이 없다.** `003`의 지출유형 삭제(사용 이력이 있으면 `3106`)와 다르다 —
고정지출을 참조하는 것은 자기 월별 내역뿐이고, 그건 함께 지우는 것이 맞다.
"고정지출을 지웠다"는 것은 그 항목 자체를 없앤다는 뜻이다.

CASCADE는 FK `fk_fixed_monthly_fixed_expense`에만 걸려 있다(덤프 확인).
회원·수단·지출유형 FK 3개에는 없다.

## 7. `3405` — 아직 만들어지지 않은 달

4.6(단건 수정)이 그 연·월 행을 찾지 못하면 `3405`로 거절한다(FR-411).

**lazy 생성 모델의 대가다.** 열어 본 적 없는 달은 수정할 수 없다.
사용자는 먼저 4.5로 그 달을 열거나 4.9로 재작성해야 한다.

4.6이 없는 행을 **직접 만들지 않는 이유**: 수정 요청의 값과 설정의 값 중 무엇을 기준으로
만들지 정해야 하는데, 그 규칙이 명세에 없다. 생성은 §1의 세 경로로 한정하는 편이
"내역은 언제나 설정에서 복사돼 시작한다"는 모델을 유지한다.
