# API 계약: 고정지출 관리와 월별 가계부 목록

**Feature**: `005-backend-ledger-fixed-expense` | **Date**: 2026-09-02 | **Phase**: 1

각 API의 전체 필드 표는 `프로젝트설계/기능명세상세-백엔드/phase4-가계부/` 가 소유한다.
여기 적는 것은 **9건에 공통으로 걸리는 규칙**과 **설계 문서만 봐서는 갈리는 지점**이다.

- lazy 생성·설정 반영·재작성 → [monthly-lifecycle.md](./monthly-lifecycle.md)
- 4.8 통합 목록의 조립 → [ledger-list.md](./ledger-list.md)

---

## 1. 인가와 소유자

**9건 전부 로그인 필요**다. `002`의 `SecurityFilterChain` 기본 규칙이 적용된다.

소유자는 **토큰의 `id_key`**로 정해진다. Path의 `{fixedExpenseId}`는 자원 식별자일 뿐이며,
조회한 행의 `id_key`가 토큰과 다르면 `3402`로 거절한다.

**"없음"과 "타인 소유"를 같은 코드로 묶는다** — 003·004와 같은 원칙이다.

---

## 2. 응답 규격 — 예외가 없다

**9건 전부** `{ resCode, data }`다.

`003`(아이콘 조회)·`004`(엑셀 양식)에는 래퍼를 쓰지 않는 API가 하나씩 있었지만
**005에는 없다.** 바이너리 응답이 없으므로 AOP 로깅 제외 규칙도 추가할 것이 없다.

| 구분 | HTTP | `resCode` |
|---|---|---|
| 성공 | 200 | `200` |
| 비즈니스·검증 실패 | 200 | 4자리 코드 |
| 서버 오류 | 500 | `9000` |

---

## 3. 목록 응답 — 페이징이 있는 것은 4.2뿐

```json
{ "resCode": 200, "data": { "list": [ ... ], "<부가 필드>": ... } }
```

| API | 페이징 | 부가 필드 (`list`와 같은 레벨) |
|---|:---:|---|
| 4.2 고정지출 설정 목록 | **있다** | `offset` · `limit` · `totalCount` |
| 4.5 월별 내역 목록 | 없다 | `year` · `month` · `total`(그 달 고정지출 합계) |
| 4.8 월별 가계부 목록 | 없다 | `year` · `month` · `expenseTotal`(일반+할부+고정) · `incomeTotal` |
| 4.9 재작성 결과 | 없다 | `year` · `month` · `createdCount` · `updatedCount` · `keptCount` · `deletedCount` |

**부가 필드는 `list` 안이 아니라 같은 레벨이다**(FR-423). `data.list`와 `data.total`이
형제다.

**4.8에 페이징이 없는 것은 `_공통.md`가 확정했다** — "페이징 ❌(합계 필드 병행)".
한 달치를 전부 돌려주고 합계를 함께 싣는다.

4.2의 페이징 검증은 `002`의 관리자 목록(1.13)과 같다 — `offset`·`limit` 필수,
`limit <= 0` · `offset < 0` · `offset % limit != 0`이면 `9001`.

---

## 4. HTTP 메서드

| API | 메서드 | 비고 |
|---|---|---|
| 4.1 | POST | 설정 등록. **관리 행 1건만** 만든다(FR-402) |
| 4.2·4.3·4.5·4.8 | GET | 조회. **4.5·4.8은 부작용이 있다** — lazy 생성 |
| 4.4·4.6 | PATCH | 수정 (omit=유지) |
| 4.7 | DELETE | **물리 삭제**. CASCADE로 월별 내역까지 |
| **4.9** | **POST** | 재작성. **연·월을 Body로 받는다**(FR-421) |

**4.9가 Path·Query를 안 쓰는 이유**(FR-421): POST의 입력은 Body에 둔다는 규칙이다.
같은 연·월을 4.5·4.6은 Path로 받는데 4.9만 Body인 것이 어색해 보이지만,
4.9는 `overwriteModified` 같은 옵션을 함께 받으므로 Body가 자연스럽다.

`PUT`은 쓰지 않는다.

---

## 5. 연·월 검증 — 코드가 자원마다 다르다

| API | 연·월 오류 코드 |
|---|---|
| 4.5 · 4.6 · 4.9 | `3403` |
| 4.8 | **`3501`** |

**같은 "연·월 범위 오류"인데 코드가 다르다.** 자원이 달라서이며 `_공통.md`의 코드 블록
배정이 정한 **의도된 차이**다(고정지출 `34xx` / 가계부 목록 `35xx`).

`006`의 통계는 또 다른 `3603`을 쓴다. 세 코드가 같은 뜻인 것이 실수처럼 보이지만
자원별 대역 규칙의 결과다.

**`3404`는 결번이다.** 폐기된 구 `FixedExpenseMonthlyOverrideUpsert`의 코드이므로
이 기능에서 되살려 쓰지 않는다(`_공통.md § 결번`).

## 6. 실패 코드 매핑 — 판정 순서가 결과를 바꾸는 곳

전체 9개는 [spec.md § 이 기능이 쓰는 에러코드](../spec.md)에 있다.

### 4.1 설정 등록 — `3003`/`3103` → `3401`

```text
1. 참조 검증
   ├ 수단이 없거나 타인 소유            → 3003
   ├ 지출유형이 없거나 타인 소유         → 3103
   └ 수단의 purpose 가 EXPENSE 가 아님   → 3401
2. 값 검증                              → 3401
   ├ payment_day_of_month 가 1~31 밖
   ├ amount <= 0
   ├ start_month·end_month 가 1~12 밖
   └ (end_year*12+end_month) < (start_year*12+start_month)
3. 관리 행 1건만 INSERT
   └ 적용 기간 전체의 월별 내역을 만들지 않는다 (FR-402)
```

3번이 이 API의 특징이다. 등록은 **행 1건**이고, 월별 내역은 그 달을 열 때 생긴다.

### 4.6 월별 내역 단건 수정 — `3402` → `3403` → `3405` → `3401`

```text
1. fixedExpenseId 로 설정 조회 (본인 소유?)   없음·타인 → 3402
2. Path 의 year·month 범위                   오류    → 3403
3. 그 연·월의 월별 내역이 있는가              없음    → 3405
   (아직 한 번도 조회되지 않은 달이다. 먼저 4.5 를 부르거나 4.9 로 재작성한다)
4. 값 검증                                            → 3401
   ├ 바꿀 필드를 하나도 보내지 않음
   ├ amount <= 0
   ├ paymentDate 가 Path 의 year·month 와 다른 달
   └ paymentMethodId 가 본인 소유의 purpose=EXPENSE 수단이 아님
5. UPDATE + modified = true
```

**3번이 이 API의 핵심 제약이다.** lazy 생성 모델의 대가로, 열어 본 적 없는 달은
수정할 수 없다. `3405`가 그 신호다.

**4번의 "바꿀 필드를 하나도 보내지 않음"**을 빠뜨리기 쉽다. PATCH omit 규칙상
빈 Body는 "아무것도 안 바꾼다"로 읽히지만, 설계 명세가 이를 `3401`로 거절한다 —
의미 없는 요청이 성공으로 흘러 `modified=true`만 세우는 것을 막는다.

**이름·지출유형은 이 경로로 바꾸지 않는다**(FR-410). 바꿀 수 있는 것은
금액·결제일·내용·수단 넷뿐이다.

### 4.4 설정 수정 — `3402` → `3401` → 자동 반영

```text
1. 대상 설정 조회 (본인 소유?)     없음·타인 → 3402
2. 값 검증 (보낸 필드만)           오류     → 3401
3. 설정 UPDATE
4. 자동 반영 — 미래 달이면서 modified=false 인 월별 내역만 갱신
   (FR-412. 자세한 규칙은 monthly-lifecycle.md)
```

4번이 이 API의 부작용이다. 응답에는 나타나지 않지만 다른 행이 바뀐다.

### 4.7 설정 삭제 — `3402` → CASCADE

```text
1. 대상 설정 조회 (본인 소유?)     없음·타인 → 3402
2. 관리 행 DELETE
   └ ON DELETE CASCADE 로 그 고정지출의 월별 내역 전부 삭제 (지난 달 포함)
```

**막는 조건이 없다.** `003`의 지출유형 삭제와 다르다 — 거기는 사용 이력이 있으면
`3106`으로 막았지만, 고정지출은 참조하는 것이 자기 월별 내역뿐이라 함께 지운다.

## 7. PATCH omit 규칙 (4.4·4.6)

전송한 필드만 갱신하고 omit한 필드는 유지한다.

| API | 특이점 |
|---|---|
| 4.4 | 적용 기간을 **줄이면** 기간 밖이 된 월별 내역이 남는다. 자동 반영은 값 갱신만 하고 **삭제하지 않는다** — 정리는 4.9의 ④가 맡는다 |
| 4.6 | **전부 omit하면 `3401`**. 빈 요청이 `modified=true`만 세우는 것을 막는다 |

4.4의 특이점이 4.9(재작성)가 필요한 이유 중 하나다.

## 8. 이름 — 저장하지 않는다

설정 응답(4.1·4.2·4.3·4.4)과 월별 내역 응답(4.5·4.6)의
`paymentMethodName`·`expendGroupName`은 **조회 시점에 원본에서 읽은 현재 이름**이다(FR-405).

`tbl_fixed_expense`·`tbl_fixed_expense_monthly` 어디에도 이름 컬럼이 없다(덤프 확인).
수단 이름을 바꾸면 **기존 설정의 응답도 새 이름으로 바뀐다** — 지금 유효한 설정이지
과거 기록이 아니기 때문이다.

`004`의 지출·소득과 정반대이고, 4.8이 두 규칙을 한 응답에 섞는다 →
[ledger-list.md](./ledger-list.md).

**개정 필요**: `4.1`·`4.3`이 두 이름을 "스냅샷"으로 적고 있다. 그대로 두면 구현자가
001 스키마에 이름 컬럼을 추가하려 든다.
