# 월별 가계부 목록 계약 (4.8)

**Feature**: `005-backend-ledger-fixed-expense` | **Date**: 2026-09-02 | **Phase**: 1

`GET /api/v1/ledger/monthly` — 일반 지출·할부·소득·고정지출을 **한 응답 목록**으로 합친다.

저장 단위가 아니라 **조회 시점에 조립되는 형태**라, 정렬·식별자·이름 규칙을 새로 정해야 한다.
사용자가 실제로 여는 화면이므로 이 기능에서 가장 눈에 띄는 API다.

---

## 1. 네 출처

| `type` | 출처 테이블 | 판별 조건 |
|---|---|---|
| `EXPENSE` | `tbl_expense` | 할부 3컬럼이 **전부 NULL** |
| `INSTALLMENT` | `tbl_expense` | 할부 3컬럼이 **전부 채워짐** |
| `INCOME` | `tbl_income` | — |
| `FIXED` | `tbl_fixed_expense_monthly` | 그 연·월 |

`EXPENSE`와 `INSTALLMENT`가 **같은 테이블**에서 나온다. `004`가 할부 3컬럼의 불변식
(셋 다 비거나 셋 다 채움)을 지켜야 이 판정이 성립한다. 부분 채움 행이 있으면
어느 쪽으로도 분류되지 않거나 잘못 분류된다.

---

## 2. 조립 순서 — lazy 생성이 먼저다

```text
1. year·month 검증                          오류 → 3501  (3403 이 아니다)
2. 그 연·월의 고정지출 월별 내역을 생성       (FR-418, monthly-lifecycle §1 과 동일 규칙)
   └ 필터가 걸려 있어도 그 달 대상 전체를 만든다
3. 네 출처를 각각 조회
4. 공통 형태(LedgerItem)로 변환
   └ FIXED 는 수단·지출유형을 조인해 현재 이름을 읽는다
5. 합치고 필터 적용
6. 정렬
7. 합계 계산 (expenseTotal · incomeTotal)
```

**2번이 이 API의 부작용이다.** GET이 쓰기를 한다 — 이 기능의 lazy 생성 모델 때문이며,
[plan.md의 Complexity Tracking](../plan.md#complexity-tracking)에 근거를 남겼다.

**2번이 3번보다 앞이어야 한다.** 순서가 뒤집히면 방금 만든 내역이 목록에서 빠진다.

### SQL `UNION`을 쓰지 않는다

네 출처의 컬럼 구성이 다르다.

| 출처 | 지출유형 | 장소 | 할부 | 이름의 성격 |
|---|:---:|:---:|:---:|---|
| `tbl_expense` | 있다 | 있다 | 있다 | 스냅샷 |
| `tbl_income` | **없다** | **없다** | 없다 | 스냅샷 |
| `tbl_fixed_expense_monthly` | 있다 | **없다** | 없다 | **현재 이름(조인 필요)** |

`UNION`으로 맞추려면 없는 컬럼을 `NULL`로 채워야 하는데, 그러면 "값이 없다"와
"컬럼이 아예 없다"가 SQL에서 구분되지 않는다. 게다가 `FIXED`의 이름은 조인해서 읽어야 하고,
2번의 lazy 생성은 SELECT 한 방으로 표현할 수 없다.

페이징이 없어(FR-422) 메모리 조립이 성립한다. 한 회원의 한 달 거래 건수가 상한이다.

## 3. `ledgerItemId` — 행 식별자

```text
EXPENSE · INSTALLMENT →  expense:{expenseId}
INCOME                →  income:{incomeId}
FIXED                 →  fixed:{fixedExpenseId}:{year}:{month}
```

원본 PK는 **`sourceId`로 따로** 싣는다.

**왜 접두사가 필요한가**: 네 출처의 PK가 서로 다른 테이블에서 나온다.
`expense.idx = 5`와 `income.idx = 5`가 숫자만으로는 구분되지 않는다.

**왜 `FIXED`만 세 조각인가**: `sourceId`(= `fixedExpenseId`)만으로는 월별 내역 1행이
특정되지 않는다. 같은 고정지출이 여러 달에 걸쳐 행을 갖기 때문이다.
유니크 제약 `ux_fixed_expense_monthly (fixed_expense_idx, year, month)`와 같은 조합이다.

**`tbl_fixed_expense_monthly.idx`를 쓰지 않는 이유**: 1행을 특정하긴 하지만
프론트가 그 값으로 4.6(수정)을 부를 수 없다. 4.6의 Path가
`/monthly/{year}/{month}/{fixedExpenseId}`라 세 값이 필요하다.
`ledgerItemId`를 쪼개면 그대로 4.6을 부를 수 있다.

## 4. 이름 — 한 응답에 두 규칙이 섞인다

**이 목록에서 가장 헷갈리는 지점이다**(FR-419·425).

| `type` | `paymentMethodName` · `expendGroupName` |
|---|---|
| `EXPENSE` · `INSTALLMENT` · `INCOME` | **등록 당시 스냅샷** (`004`가 저장한 값) |
| `FIXED` | **현재 이름** (조회 시점에 원본에서 읽는다) |

수단 이름을 "국민카드" → "국민체크"로 바꿨다면, 같은 목록 안에서
지난달 지출 행은 "국민카드", 고정지출 행은 "국민체크"로 나온다.

**의도된 동작이다.** 지출은 과거 기록이고 고정지출은 지금 유효한 설정이다.
고정지출 계열은 어디서도 이름을 저장하지 않으므로(`tbl_fixed_expense`·
`tbl_fixed_expense_monthly`에 이름 컬럼이 없다) 구조적으로 현재 이름일 수밖에 없다.

**행 종류로 구분한다.** 프론트가 이름의 성격을 알아야 하면 `type`을 보면 된다.

## 5. 필터와 정렬 (FR-420)

전부 Query Parameter다.

| 이름 | 필수 | 값 |
|---|:---:|---|
| `year` · `month` | ✅ | 조회 연·월. 오류는 `3501` |
| `type` | ❌ | `EXPENSE` \| `INCOME` \| `FIXED` \| `INSTALLMENT`. **콤마로 복수 지정**. 생략하면 전부 |
| `paymentMethodId` | ❌ | 수단 필터 |
| `expendGroupId` | ❌ | 지출유형 필터 (지출·고정·할부 행) |
| `dateFrom` | ❌ | `YYYY-MM-DD`. 결제일 **이상**(포함) |
| `dateTo` | ❌ | `YYYY-MM-DD`. 결제일 **이하**(포함) |
| `keyword` | ❌ | 장소·내용 **부분 일치** |
| `sort` | ❌ | `paymentDate` \| `amount`. 기본 **`paymentDate`** |
| `order` | ❌ | `asc` \| `desc`. 기본 **`desc`** |

### 놓치기 쉬운 것

| # | 주의 |
|---|---|
| 1 | **`type`은 콤마 복수 지정**이다. `type=EXPENSE,INSTALLMENT`가 유효하다 |
| 2 | `dateFrom`·`dateTo`는 `year`·`month`로 잡은 달 **안에서** 더 좁히는 용도다. 달을 넘나들지 않는다 |
| 3 | `expendGroupId` 필터는 **소득 행에 적용되지 않는다** — 소득에는 지출유형이 없다. 이 필터가 걸리면 `INCOME` 행은 전부 빠진다 |
| 4 | `keyword`는 장소·내용을 본다. **소득에는 장소가 없으므로** 내용만 본다 |
| 5 | 필터는 **lazy 생성 이후**에 적용한다(§2). 필터가 생성 대상을 좁히면 안 된다 |
| 6 | 정렬 기본값이 `paymentDate desc`다. 명시하지 않으면 최근 것이 위다 |

3·4가 "출처마다 컬럼이 다르다"는 사실에서 나오는 결과다. 필터를 SQL 한 방으로 밀지 않고
조립 후 적용하는 편이 이 차이를 다루기 쉽다.

## 6. 응답 형태

```json
{
  "resCode": 200,
  "data": {
    "year": 2026,
    "month": 7,
    "expenseTotal": 650000,
    "incomeTotal": 3500000,
    "list": [ { "ledgerItemId": "...", "type": "...", ... } ]
  }
}
```

**부가 필드는 `list`와 같은 레벨**이다(FR-423).

| 필드 | 값 |
|---|---|
| `expenseTotal` | 그 달 지출 합계 — **일반 + 할부 + 고정** |
| `incomeTotal` | 그 달 소득 합계 |

**`expenseTotal`에 고정지출이 포함된다.** 세 종류를 합친 값이고, `type` 필터가 걸려 있으면
**필터된 결과의 합계**인지 전체 합계인지가 갈리는 지점이다 →
[남은 판단](#남은-판단).

**페이징 필드가 없다**(FR-422). `offset`·`limit`·`totalCount` 어느 것도 싣지 않는다.
`_공통.md`의 목록 응답 규칙 적용 대상 표가 4.8을 "페이징 ❌(합계 필드 병행)"으로 확정했다.

## 7. 연·월 오류가 `3501`인 것

4.5·4.6·4.9는 `3403`인데 **4.8만 `3501`**이다.

같은 뜻인데 코드가 다른 이유는 `_공통.md`의 코드 블록 배정 때문이다 —
고정지출은 `34xx`, 월별 가계부 목록은 `35xx`다. **의도된 차이**이며
`006`의 통계는 또 다른 `3603`을 쓴다.

실수처럼 보이지만 자원별 대역 규칙의 결과다. 구현 시 4.8만 다른 코드를 쓴다는 점을
놓치기 쉽다.

## 남은 판단

구현 단계에서 정하면 되고, 어느 쪽이든 FR·SC를 어기지 않는다.

| 항목 | 상황 | 선택지 |
|---|---|---|
| `type` 필터가 걸렸을 때의 합계 | `type=INCOME`으로 조회하면 `expenseTotal`은? | ① 필터된 결과 기준(= 0) ② 필터 무관 전체 기준 |
| `keyword`의 대소문자 | 부분 일치의 대소문자 구분 | ① 구분 ② 무시(`ILIKE`) |

첫 번째가 실제로 갈리는 지점이다. 설계 명세 `4.8`이 합계 필드의 기준을 적어 두지 않았다.
**②(전체 기준)가 자연스럽다** — 합계는 "그 달의 지출·소득 총액"이라는 화면 상단 요약이고,
필터는 목록을 좁히는 도구다. 다만 필터를 건 사용자가 "보이는 것의 합"을 기대할 수도 있으므로
구현 전에 화면 기획과 맞춘다.
