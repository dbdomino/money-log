# Implementation Plan: 프론트 고정지출 화면

**Branch**: `develop` (기능 브랜치를 따로 두지 않는다) | **Date**: 2026-09-20 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/011-frontend-fixed-expense/spec.md`

## Summary

007~010 이 세운 것 위에 **화면 5개**를 얹는다. 고정지출 설정 목록 하나와 그 위의 모달 넷
(등록·상세·수정·월별 내역)이다. 백엔드 003·005 의 API 10건을 부른다.

010 이 **읽기만 하던** 가계부의 고정지출 행을 **만들고 고치는 곳**이 여기다.

009·010 과 성격이 이어지되 **넷이 새롭다.**

| 축 | 009·010 | 011 (고정지출) |
|---|---|---|
| 저장 단위 | 하나 | **둘** — 설정과 그 달 내역이 다른 것이다 |
| 수정의 파급 | 그 건만 | **미래 달로 번진다.** 어디까지인지 사용자가 알아야 한다 |
| 목록 | 쪽 넘기기 없음 | **있다.** 007 의 환산기를 쓰는 두 번째 화면이다 |
| 이름 규칙 | 등록 당시 스냅샷 | **조회 시점 현재 이름** — 010 과 정반대다 |

이 네 줄이 계획의 모양을 정한다.

**① 설정과 내역은 다른 저장 단위다.** 4.2~4.5 는 "매달 이만큼 나간다"는 **기준값**이고
4.6 은 **그 달에 실제로 잡힌 값**이다. 화면이 둘을 같은 것으로 보이면 사용자는 "왜 고쳤는데
지난달이 안 바뀌나"를 버그로 읽는다.

**② 수정의 파급 범위를 저장 전에 알린다.** 기준값을 바꾸면 **미래 달이면서 직접 고치지 않은
내역**만 따라온다. 이것은 응답에 드러나지 않는 부작용이라 **화면이 말하지 않으면 알 길이
없다.** 이 기능에서 가장 오해하기 쉬운 지점이며 US2 를 통째로 여기 할애했다.

**③ 되돌릴 수 없는 것이 둘이다.** 삭제는 **지난 달 내역까지** 함께 지우고, 「직접 수정분도
되돌리기」는 사용자가 손으로 고친 값을 날린다. 둘 다 **확인 전에 범위를 적는다.**

**④ 적용 기간은 정수 네 칸이다.** 010 의 할부가 문자열 `YYYY-MM` 한 칸이었던 것과 다르다 —
한쪽 규칙을 다른 쪽에 옮기면 등록이 형식 오류로 막힌다.

기술 결정 14건은 [research.md](./research.md) 에 있다.

## Technical Context

**Language/Version**: Java 17

**Primary Dependencies**: Spring Boot 4.1.0 · Spring Web MVC · Thymeleaf ·
`common-mod`(에러코드 Enum 참조용). **이 기능은 의존성을 더하지 않는다.**

007~010 에서 받아 가는 것은 코드이지 의존이 아니다 — 백엔드 호출 통로, **페이징 환산기**,
로그인 세션, 진입 판정, 레이아웃 둘, 모달 껍데기, 확인 다이얼로그, 모달 딥링크 판정, 폼 실패
착지 규약, 모달 여는 조각.

**Storage**: **없다.** 화면 모듈은 데이터베이스를 모른다. `sql/schema-moneylogdb.sql` 은
읽지도 바꾸지도 않는다. **세션에 더하는 상태도 없다** — 쪽 번호와 연·월은 주소에 실린다
([data-model.md](./data-model.md)).

**Testing**: JUnit 5 · `spring-boot-starter-test` · `spring-boot-starter-webmvc-test`.
백엔드를 띄우지 않고 응답을 세워 화면을 검증한다.

**Target Platform**: JVM 서버. 화면 `:8080`, 백엔드 `:8081`.

**Project Type**: Spring Boot 멀티모듈 — 이 기능은 프론트 모듈 하나만 손댄다.

**Performance Goals**: 정하지 않는다. 다만 **성격은 기록한다.**

선택 목록은 **한 화면에 한 번만** 받아 모달 넷이 함께 쓴다 — 010 이 그렇게 정리했고 같은
이유다(모달을 연 채 목록을 그리는 것이 기본 동작이라 각자 부르면 중복이 늘 일어난다).

| 요청 | 백엔드 호출 |
|---|---|
| 목록만 (모달 없음) | **3회** — 설정 목록 + 수단(지출용) + 지출유형 |
| 상세·수정 모달을 연 요청 | **4회** — 위 셋 + 대상 조회 |
| 월별 내역 모달을 연 요청 | **4회** — 위 셋 + 그 달 내역 |

**월별 내역 조회는 쓰기를 겸한다.** 그 달 행이 없으면 서버가 만든다 — 조회처럼 보이지만
부작용이 있는 유일한 호출이다(research 6).

**Constraints**:
- **007~010 의 공통 코드를 고치지 않는다.** 010 이 고친 실패 예외까지 포함해 그대로 쓴다.
  완료 판정에서 diff 로 확인한다.
- 브라우저는 **GET 과 POST 만** 쓴다. 백엔드가 요구하는 메서드로 옮기는 일은 화면 모듈이 한다.
- 화면 모듈은 **에러코드를 새로 정의하지 않는다.**
- **적용 기간은 정수 네 칸으로 보낸다**(FR-1002). 문자열 `YYYY-MM` 이 아니다.
- **이름을 저장하지 않는다**(FR-1007). 받은 현재 이름을 그대로 보인다.
- 선택 목록은 **사용 중 목록 API** 로만 채운다(FR-1003).
- **합계를 화면이 다시 계산하지 않는다**(FR-1015). 010 에서 정한 것과 같다.
- 「직접 수정분도 되돌리기」는 **기본 꺼짐**이며 켜면 확인을 한 겹 더 받는다(FR-1020·1021).
- 폼 실패 착지는 **008·009 의 규약을 그대로** 쓴다.

**Scale/Scope**: 화면 5개 · FR 21건(FR-1001~1021) · SC 8건 · User Story 4개(P1 2 · P2 2) ·
부르는 API 10건 · 새 에러코드 0건 · DB 테이블 0개 · 새 의존 0건 ·
**007~010 을 고치는 파일 0개**.

**Structure Decision**: 화면 묶음별 패키지를 이어 가되(`fixedexpense`), **컨트롤러를 둘로
나눈다.**

009 는 자원 하나에 한 컨트롤러, 010 은 한 부모에 자원 둘이라 넷이었다. 011 은 **한 부모에
저장 단위 둘**이 얹힌다 — 설정과 그 달 내역이다.

| 컨트롤러 | 맡는 것 |
|---|---|
| `FixedExpenseController` | 목록 · 쪽 넘기기 · **모달 판정과 선행 조회** · 설정의 등록·수정·삭제 |
| `FixedExpenseMonthlyController` | 그 달 내역 조회 · 단건 수정 · **반영** |

**나누는 이유가 010 과 다르다.** 010 은 자원이 둘이라 나눴고, 여기는 **다루는 저장 단위가
다르고 수정의 뜻도 다르기** 때문이다 — 설정 수정은 미래 달로 번지고 내역 수정은 그 달에서
끝난다. 한 파일에 두면 **두 개의 "수정"이 나란히 놓여** 읽는 사람이 매번 어느 쪽인지 세야
한다.

**나누어도 실패 착지는 목록으로 모인다.** 둘이 같은 뷰 이름을 돌려주고, 목록을 다시 그리는
일은 `FixedExpensePageModel` 한 곳에 모아 함께 쓴다 — 010 에서 복사가 만드는 차이를 확인했다.

**템플릿은 하나다.** 모달 넷이 전부 그 목록 위에 얹히므로 010 의 `ledger/list.html` 과 같은
모양이다.

`MonthlyQuery` 를 따로 두는 이유는 **연·월을 주소에서 읽고 다시 주소로 만드는 일이
양방향이기 때문**이다 — 모달 안의 연·월 이동과 단건 수정 착지가 모두 그 값을 실어 나른다.
010 의 `LedgerQuery` 와 같은 자리이며 **여기는 필터가 없어 훨씬 작다.**

## Complexity Tracking

> Constitution Check 에 정당화가 필요한 위반이 있을 때만 채운다.

**위반이 없다.** 010 이 007 의 실패 예외를 고쳐야 했던 것과 달리, 011 은 **공통 코드를
하나도 고치지 않는다** — 필요한 것(페이징 환산기·파일 없음·구조를 가진 실패 없음)이 전부
이미 서 있다.

아래 둘은 위반이 아니라 **010 과 달라지는 판단**이라 근거를 남긴다.

| 판단 | 왜 이렇게 했나 | 기각한 대안 |
|---|---|---|
| 컨트롤러를 **둘로** 나눈다 | 한 부모에 **저장 단위 둘**이 얹히고 각각의 "수정"이 다른 뜻을 갖는다 — 설정 수정은 미래 달로 번지고 내역 수정은 그 달에서 끝난다 | **하나로 둔다** — 두 개의 "수정"이 한 파일에 나란히 놓여 어느 쪽인지 읽어서 세야 한다. **넷으로 나눈다**(010 처럼) — 등록·수정·삭제가 같은 저장 단위라 나눌 경계가 없다 |
| 월별 내역을 **모달**로 둔다 (독립 페이지가 아니라) | 확정 계약이 `?m=monthly` 로 정했고, 설정을 보다가 "그 달은 어떻게 잡혔나"를 확인하는 흐름이라 **부모가 설정 목록인 것이 맞다** | **독립 페이지로 뺀다** — 주소가 하나 늘고 사이드바 메뉴도 늘어나는데, 사용자가 설정과 내역을 **오가며** 보는 화면이라 왕복이 길어진다. 010 의 엑셀과 다른 점이다(그쪽은 목록을 쓰지 않았다) |
