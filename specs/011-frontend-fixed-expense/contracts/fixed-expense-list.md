# Contract: 고정지출 설정 목록과 모달 셋 (4.2~4.5)

**Feature**: 011-frontend-fixed-expense | **관련 FR**: 1001~1010

| 화면 | 주소 | 표시 |
|---|---|---|
| 4.2 고정지출 설정 목록 | `/fixed-expenses` | 페이지 |
| 4.3 고정지출 등록 | `/fixed-expenses?m=create` | 가계부 위 모달 |
| 4.4 고정지출 상세 | `/fixed-expenses?m=detail&id={식별자}` | 모달 |
| 4.5 고정지출 수정 | `/fixed-expenses?m=edit&id={식별자}` | 모달 |

| 항목 | 값 |
|---|---|
| 껍데기 | 007 의 **로그인 후** 레이아웃 |
| 사이드바 활성 메뉴 | `fixed-list` (넷 모두) |
| 권한 | 로그인 |
| 부르는 API | `FixedExpenseList` · `FixedExpenseGet` · `FixedExpenseCreate` · `FixedExpenseUpdate` · `FixedExpenseDelete` · `PaymentMethodListActive` · `ExpendGroupListActive` |

목록 위에 모달이 얹히는 공통 모양은
[009 의 list-modal 규약](../../009-frontend-payment-expend-group/contracts/list-modal.md)을
그대로 따른다. 여기서는 **고정지출에만 있는 것**을 적는다.

**010 이 읽기만 하던 것을 만들고 고치는 곳이다.** 가계부 목록의 고정지출 행에는 수정·삭제가
없고 대신 이 화면으로 오는 길이 있다.

---

## 1. 목록

### 열

| 열 | 값 |
|---|---|
| 이름 | 고정지출 이름 |
| 수단 | 수단 이름. **조회 시점 현재 이름** |
| 유형 | 지출유형 이름. 위와 같은 규칙 |
| 기본 금액 | 원 단위. 오른쪽 정렬. **「그 달 금액」이 아니다** |
| 결제일 | 「매달 N일」 |
| **적용 기간** | 「2026-01 ~ 2026-12」 |
| 관리 | 상세 · 수정 · 삭제 |

**「기본 금액」으로 적는다.** 그냥 「금액」이라고 하면 4.6 의 그 달 금액과 같은 것으로 읽힌다.

### 프로토타입과 세 곳이 다르다

| 프로토타입 | 이 화면 | 왜 |
|---|---|---|
| 도구줄에 **상태 필터**(전체·진행·완료·중도상환) | **없다** | 백엔드에 상태 개념 자체가 없다. 목록은 `offset`·`limit` 만 받는다 — 그대로 두면 **아무것도 걸러지지 않는 필터**가 남는다 |
| 열에 **주기·다음 결제일·상태** | **적용 기간** 열 | 백엔드가 주지 않는 값이다. 「진행 중」이 뜻하려던 것은 적용 기간이 지금을 포함하는가이며, **시작·종료를 보이면 사용자가 읽는다** |
| 관리 열에 상세·수정·**월별** | 상세·수정·**삭제** | 삭제가 없으면 **지울 방법이 없는 목록**이다. 월별은 그 달 **전체**를 보는 화면이라 행에 두면 "이 고정지출의 월별"로 읽힌다 |

**「월별 내역」은 화면 상단의 버튼 하나**로 둔다. **버튼의 위치가 곧 범위의 선언**이다.

**화면이 「진행 중」을 계산해 보이지 않는다.** 계산 규칙이 화면에 숨고, 백엔드가 나중에
상태를 도입하면 두 규칙이 갈린다.

### 쪽 넘기기가 있다

**009·010 과 다르다.** 백엔드가 `offset`·`limit` 을 **필수로** 받으며 시작점이 개수의 배수가
아니면 목록이 통째로 실패한다.

007 의 **페이징 환산기**를 쓴다 — 008 의 관리자 회원 목록에 이어 두 번째다. 환산기는 쪽
번호에서만 시작점을 만들므로 어긋난 값이 생길 경로가 없다.

**사용자가 시작점을 직접 넣는 칸을 두지 않는다.**

### 이름은 현재 값이다

**010 과 정반대다.** 고정지출에는 이름 컬럼이 없어 조회 시점에 수단·지출유형 행에서 읽는다 —
수단 이름을 바꾸면 이 목록도 새 이름으로 보인다.

**화면이 저장된 값으로 덮어쓰지 않는다**(`FR-1007`). 할 일은 010 과 같다: **받은 값 그대로.**

## 2. 등록·수정 폼 (4.3 · 4.5)

| 칸 | 필수 | 설명 |
|---|:---:|---|
| 이름 | ✅ | |
| 수단 | ✅ | **사용 중 수단 목록(지출용)** 으로 채운다 |
| 지출유형 | ✅ | **사용 중 지출유형 목록**으로 채운다 |
| 기본 금액 | ✅ | 원 단위 양의 정수 |
| 매달 결제일 | ✅ | **1~31** |
| 내용 | ✅ | |
| 적용 시작 연 | ✅ | **정수** |
| 적용 시작 월 | ✅ | **정수 1~12** |
| 적용 종료 연 | ✅ | 정수 |
| 적용 종료 월 | ✅ | 정수 1~12 |

**등록은 열 칸 전부 필수다**(`FR-1001`).

### 적용 기간은 정수 네 칸이다

| 기능 | 형식 |
|---|---|
| 010 할부 등록 | 문자열 한 칸 `"2026-01"` |
| **011 고정지출** | **정수 네 칸** `2026`·`1`·`2026`·`12` |

**한쪽 규칙을 다른 쪽에 옮기면 등록이 형식 오류로 막힌다**(`FR-1002` · `SC-1007`). 폼 타입이
네 칸을 그대로 들고 있게 해 옮기다 틀릴 자리를 없앤다.

**화면이 쪼개거나 합치지 않는다.** 입력 칸도 넷이고 보내는 값도 넷이다.

### 선택 목록은 관리 목록이 아니다

009 의 관리 목록에는 **삭제 표시된 것과 사용 안 함이 함께** 들어 있다. 그것을 선택지로 쓰면
사용자가 **지운 수단으로 고정지출을 만들게** 된다(`FR-1003`).

**수단은 지출용을 가리킨다.** 소득용을 고르면 저장에서 거절된다.

## 3. 수정은 미래 달로 번진다 (4.5)

**응답에 드러나지 않는 부작용이다.** 기본값을 고치면 백엔드가 **미래 달이면서 사용자가 직접
고치지 않은 월별 내역**을 함께 갱신한다.

| 달 | 따라오나 |
|---|:---:|
| 미래 달 · 직접 고치지 않음 | **✅ 바뀐다** |
| 미래 달 · **직접 고침** | ❌ 그대로 |
| 이번 달 · 지난 달 | ❌ 그대로 |

### 저장 전에 알린다

수정 모달에 **셋을 적는다**(`FR-1009` · `FR-1010`).

| 담을 것 | 왜 |
|---|---|
| **미래 달에만 반영된다** | 이 기능에서 **가장 오해하기 쉬운 지점**이다. 안내가 없으면 지난달이 안 바뀐 것을 버그로 신고한다 |
| **직접 고친 달은 그대로다** | 「수정됨」으로 지켜 둔 값이 보존된다는 뜻이며, 4.6 의 반영과 이어지는 개념이다 |
| **지난 달을 맞추려면 4.6 의 반영을 쓴다** | 제약만 적고 길을 적지 않으면 사용자는 막혔다고만 읽는다 |

**저장 뒤가 아니라 저장 전이다.** 뒤에 알리면 "그럴 줄 알았으면 안 고쳤다"가 되고 되돌릴
방법도 마땅치 않다(`SC-1002`).

**길을 모달 안에 둔다.** 안내를 읽은 그 자리에서 4.6 으로 갈 수 있어야 한다(`SC-1003`).

**화면이 "몇 건이 바뀝니다"를 계산하지 않는다.** 그 숫자를 내려면 월별 내역을 전부 뒤져야
하고, 판정 규칙이 화면과 백엔드 두 곳에 생긴다 — **규칙을 말로 적는다.**

## 4. 삭제는 월별 내역까지 지운다

| 항목 | 내용 |
|---|---|
| 부르는 곳 | 목록 행의 「삭제」 |
| 확인 | 007 의 공통 확인 다이얼로그 (`FR-1008`) |
| 보내는 방법 | `POST`. 화면 모듈이 백엔드의 삭제 요청으로 옮긴다 |
| 본문에 담을 것 | ① 어느 고정지출인지 ② **월별 내역이 지난 달 것까지 함께 사라진다** ③ **되돌릴 수 없다** |

**009 의 수단·지출유형과 다르다.** 그쪽은 **삭제 표시**라 행이 남고 과거 내역의 이름도
살아 있었다. 고정지출은 **물리 삭제**이고 **월별 내역이 따라 사라진다.**

**②를 적지 않으면** 사용자는 "설정만 지우는 것"으로 읽고, 지난 기록이 날아간 뒤에야
안다(`SC-1006`).

**되돌릴 수 없는 동작이라 링크로 두지 않는다.**

## 5. 실패가 붙는 칸

008·009 의 규약을 따른다 — 어느 칸인지 아는 실패는 그 칸 아래, 가릴 수 없는 실패는 모달 폼
상단, 모달 제출 실패는 **모달을 연 채로** 부모 목록을 다시 그린다.

| 코드 | 뜻 | 붙는 칸 | 화면 |
|---|---|---|---|
| `3003` | 수단 없음 · 타인 · 사용 안 함 · 삭제됨 | **수단 칸** | 4.3 · 4.5 |
| `3103` | 지출유형 없음 · 타인 · 사용 안 함 · 삭제됨 | **지출유형 칸** | 4.3 · 4.5 |
| `3401` | 결제일 1~31 밖 · 금액 0 이하 · 기간 오류 · **수단 용도 불일치** | **모달 폼 상단** | 4.3 · 4.5 |
| `3402` | 고정지출을 찾을 수 없음 | 목록 안내 (모달 없이) | 4.4 · 4.5 |
| `9001` | 필수 누락 · 페이징 규칙 위반 | 모달 폼 상단 / 목록 안내 | 4.2 · 4.3 |

### `3401` 이 상단인 이유

**한 코드가 두 가지를 겸한다** — 값 오류(결제일·금액·기간)와 **수단 용도 불일치**다.

코드만으로는 어느 칸인지 가릴 수 없고, 짐작해 결제일 칸에 붙이면 **수단을 잘못 고른
사용자가 결제일을 고치고 또 틀린다.**

**서버 문구를 그대로 보인다.** 용도 불일치일 때 그 문구가 「지출용 수단을 고르라」를
말해 준다(`FR-1005`) — 화면이 "수단이 없다"로 바꿔 적지 않는다. **수단은 실재하고 목록에도
보인다.**

### 없는 대상은 모달을 열지 않는다

빈 모달을 띄우지 말고 목록만 남긴다. **없는 것과 남의 것을 가르지 않는다** — 009·010 과 같다.

## 6. 시험으로 고정할 것

| 항목 | 근거 |
|---|---|
| 적용 기간이 **정수 네 칸**으로 실린다 | FR-1002 · SC-1007 |
| 문자열 `YYYY-MM` 이 실리지 않는다 | FR-1002 |
| 선택 목록이 **사용 중 목록 API** 로 채워지고 수단은 **지출용**이다 | FR-1003 |
| 결제일 칸이 1~31 로 제한된다 | FR-1004 |
| `3003` 이 수단 칸, `3103` 이 지출유형 칸에 붙는다 | §5 |
| **`3401` 이 폼 상단**이고 서버 문구가 그대로 보인다 | FR-1005 · §5 |
| 수정 모달에 **미래 달에만 반영된다**가 저장 전에 보인다 | FR-1009 · SC-1002 |
| 같은 안내에 **4.6 으로 가는 길**이 있다 | FR-1010 · SC-1003 |
| 삭제 확인에 **월별 내역도 사라진다**가 적혀 있다 | FR-1008 · SC-1006 |

| 목록에 **상태 필터가 없다** | research 2 |
| 관리 열에 **월별이 없고 삭제가 있다** | research 3 |
| 수단·유형 이름을 **다시 조회해 덮어쓰지 않는다** | FR-1007 |
| 없는 식별자로 모달을 열면 **목록만** 남는다 | §5 |
