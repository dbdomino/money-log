# Feature Specification: 프론트 공통 기반 — 화면 모듈 재구성

**Feature Branch**: `007-frontend-foundation`

**Created**: 2026-09-07

**Status**: Draft

**Input**: `app-mod/money-app` 을 헌장 원칙 I 에 맞게 다시 세운다. 레거시(자체 Entity·Repository·Mapper·MyBatis·`data-mod`/JPA 의존)를 걷어내고 백엔드 API(`:8081/api/v1`)만 호출하는 화면 모듈로 만든다. 화면 31개가 올라설 **공통 기반**이며 개별 화면은 008~012 가 맡는다.

## 이 기능이 다루는 범위

**화면을 만드는 기능이 아니다.** 화면 31개가 공통으로 밟는 바탕을 세운다.

| 구분 | 007 | 008~012 |
|---|---|---|
| 백엔드 호출 | API 클라이언트 · 봉투 해석 · **메서드별 호출 규칙** · 실패의 공통 표시 | 화면별 호출 시점·필드 |
| 목록 | **페이징 환산 공통 처리**(`offset` = 페이지 × `limit`) | 화면별 필터·정렬 |
| 아이콘 | **화면 모듈의 아이콘 경로**로 바이트 전달 | `iconUrl` 을 받아 `<img>` 로 표시 |
| 인증 | 세션 저장·헤더 부착·재발급·인터셉터 | 로그인/로그아웃 **화면** |
| 레이아웃 | `auth`·`main` 두 껍데기·사이드바·모달 셸·확인 다이얼로그 | 그 안의 본문 |
| 정적 자원 | `tokens.css`·`ui.css`·`modal.js` 이식 | 화면별 마크업 |
| URL | 루트·구 URL redirect | 화면 URL 31개 |
| 화면 | **1.6 권한 없음** 1개 | 나머지 30개 |

**1.6 권한 없음(`/error/forbidden`)만 여기서 만든다.** 권한 차단이 착지할 화면이 없으면 인터셉터를 완성할 수 없고, 이 화면은 API 를 부르지 않아 다른 화면과 성격이 다르다. 008 은 1.1~1.5·1.7~1.10 아홉 개를 맡는다.

**화면 상세 명세(`프로젝트설계/기능명세상세-프론트엔드/`)의 골격 채우기는 각 스펙이 자기 범위만 한다.** 007 은 `_공통.md` 와 1.6 문서를 채운다.

## 지금 상태 — 원칙 I 을 어기고 있다

`money-app` 은 아직 전부 레거시다.

| 발견 | 내용 |
|---|---|
| 자체 Entity 12개·Repository·Mapper | `Member`·`Expend`·`Card` 등. 백엔드가 쓰는 `tbl_user_*` 와 이름도 구조도 다른 구 테이블을 가리킨다 |
| 의존 | `data-mod` · `spring-boot-starter-data-jpa` · `mybatis-spring-boot-starter` · `postgresql` |
| 설정 | `spring.profiles.active=postgresql` — DB 에 직접 붙는다 |
| 템플릿 | `home.html`·`signin.html`·`signupsample.html`·`target/default.html` — 샘플 4개뿐 |
| 테스트 | 2개 파일이 **`init` 커밋부터 깨져 있다**. 시험용 `application.yml` 이 메인 설정을 덮어쓰는데 `profiles.active` 도 없고 datasource 줄이 전부 주석이라 `Failed to determine a suitable driver class` 가 난다 |

헌장 원칙 I 은 `money-app → common-mod` 와 **백엔드 API HTTP 호출**만 허용한다. 프론트가 DB 에 직접 붙으면 API 계약이 우회되어 **권한·검증·로깅이 무력화된다** — 백엔드가 002~006 에서 세운 소유자 판정과 에러코드가 전부 우회 가능해진다.

## 이 기능의 핵심 개념

**화면 모듈은 DB 를 모른다.** 데이터는 전부 백엔드 API 로 얻는다. DB 를 꺼도 화면 모듈은 기동해야 하고, 백엔드를 끄면 데이터를 얻을 길이 없어야 한다 — 우회로가 남아 있지 않다는 뜻이다.

**토큰은 서버 세션에 산다.** 화면이 서버 렌더링이고 백엔드 호출도 서버가 하므로, 토큰이 브라우저에만 있으면 서버가 `Authorization` 헤더를 붙일 수 없다. 브라우저로 내려가는 것은 `JSESSIONID` 뿐이고 JWT 원문은 내려가지 않는다.

**봉투는 한 곳에서만 푼다.** 백엔드는 성공·실패 모두 `{ resCode, data }` 로 답한다(헌장 원칙 III). 화면마다 이 형태를 각자 풀면 어느 화면 하나가 `resCode` 확인을 빠뜨렸을 때 **실패가 성공으로 읽히고 빈 화면이 정상처럼 뜬다.**

**봉투에 예외가 둘 있다.** 지출유형 아이콘 조회(003 의 2.10)와 엑셀 양식 다운로드(004 의 3.11)는 본문이 바이너리다. 무조건 봉투로 파싱하면 이 둘이 깨진다.

**화면은 페이지와 딥링크 모달 둘뿐이다.** 목록·허브는 풀페이지, 등록·수정·상세는 부모 URL + `?m=` 로 여는 모달이다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 화면이 DB 대신 백엔드 API 를 본다 (Priority: P1) 🎯 MVP

화면 모듈에서 DB 로 가는 길을 없애고, 데이터를 백엔드 API 로만 가져온다. 백엔드가 준 `{ resCode, data }` 를 한 곳에서 풀어 값 또는 실패 사유를 화면에 넘긴다.

**Why this priority**: 헌장 원칙 I 위반을 걷어내는 것이 이 기능의 존재 이유다. 그리고 이 통로가 없으면 008~012 의 어떤 화면도 데이터를 얻을 수 없다.

**Independent Test**: DB 를 내린 채 화면 모듈을 기동해 정상적으로 뜨는지 보고, 백엔드를 올린 상태에서 API 하나를 호출해 값이 오는지·실패 코드가 그대로 전달되는지 확인한다. 화면 없이 완결된다.

**Acceptance Scenarios**:

1. **Given** DB 가 내려가 있을 때, **When** 화면 모듈을 기동하면, **Then** 정상 기동한다
2. **Given** 백엔드가 성공 봉투를 돌려줄 때, **When** 화면 모듈이 API 를 부르면, **Then** `data` 안의 값이 그대로 전달된다
3. **Given** 백엔드가 실패 봉투(`resCode` 4자리)를 돌려줄 때, **When** 화면 모듈이 API 를 부르면, **Then** 그 `resCode` 와 `data.message` 가 화면으로 전달되고 **성공으로 읽히지 않는다**
4. **Given** 백엔드가 꺼져 있을 때, **When** 화면이 데이터를 필요로 하면, **Then** 사용자가 서버에 닿지 못했음을 읽을 수 있고 **빈 값이 정상처럼 뜨지 않는다**
5. **Given** 아이콘·엑셀처럼 본문이 바이너리인 응답일 때, **When** 화면 모듈이 그것을 받으면, **Then** 봉투 해석을 거치지 않고 바이트 그대로 전달된다

### User Story 2 - 로그인 상태가 유지되고 권한이 지켜진다 (Priority: P1)

로그인하면 그 상태가 서버 세션에 남아 이어지는 화면에서 다시 로그인하지 않아도 된다. 로그인하지 않았거나 권한이 없으면 해당 화면에 들어갈 수 없다.

**Why this priority**: 화면 31개 중 25개가 로그인을 요구하고 3개가 관리자를 요구한다. 이 판정이 없으면 어떤 화면도 안전하게 열 수 없다.

**Independent Test**: 세션에 토큰을 심은 상태와 비운 상태로 보호 URL 에 들어가 결과가 갈리는지 확인한다. 로그인 **화면**(008) 없이 완결된다 — 005·006 이 아직 없는 API 대신 데이터를 직접 심어 시험한 것과 같은 방식이다.

**Acceptance Scenarios**:

1. **Given** 세션이 비어 있을 때, **When** 로그인이 필요한 화면 URL 에 들어가면, **Then** 로그인 화면으로 보내진다
2. **Given** 세션에 유효한 토큰이 있을 때, **When** 같은 URL 에 들어가면, **Then** 그 화면이 열린다
3. **Given** 일반 권한으로 로그인했을 때, **When** 관리자 전용 URL 에 들어가면, **Then** 권한 없음 화면으로 보내진다
4. **Given** 로그인하지 않았을 때, **When** 관리자 전용 URL 에 들어가면, **Then** **권한 없음이 아니라 로그인 화면**으로 보내진다
5. **Given** 세션의 Access 토큰이 만료됐을 때, **When** 화면이 API 를 부르면, **Then** 재발급이 자동으로 일어나 사용자는 **다시 로그인하지 않고** 그 화면을 본다
6. **Given** 다른 곳에서 로그인해 이 세션이 무효가 됐을 때, **When** 화면이 API 를 부르면, **Then** 세션이 지워지고 로그인 화면으로 보내진다
7. **Given** 로그인한 상태에서, **When** 로그아웃하면, **Then** 세션이 지워지고 보호 URL 이 다시 막힌다
8. **Given** 어떤 화면이든, **When** 브라우저가 받은 응답을 살펴보면, **Then** JWT 원문이 들어 있지 않다

### User Story 3 - 모든 화면이 같은 껍데기를 쓴다 (Priority: P2)

로그인 전 화면과 로그인 후 화면이 각각 정해진 레이아웃을 쓰고, 사이드바·모달·확인 다이얼로그가 화면마다 다시 만들어지지 않는다.

**Why this priority**: 008~012 가 각자 껍데기를 만들면 화면 31개의 생김새와 모달 동작이 갈린다. 다만 US1·US2 없이는 그 껍데기 안에 넣을 것이 없다.

**Independent Test**: 껍데기만 쓰는 화면(1.6 권한 없음)과 모달 셸이 붙은 시험용 화면을 열어 레이아웃·사이드바 활성 표시·모달 열고 닫기가 동작하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인 후 화면일 때, **When** 화면을 열면, **Then** 사이드바가 함께 뜨고 **그 화면에 해당하는 메뉴가 활성으로** 표시된다
2. **Given** 일반 권한으로 로그인했을 때, **When** 사이드바를 보면, **Then** 회원 관리 메뉴가 **보이지 않는다**
3. **Given** 부모 페이지가 열려 있을 때, **When** URL 에 `?m=` 딥링크를 넣어 들어가면, **Then** 해당 모달이 열린 채로 뜬다
4. **Given** 모달이 열려 있을 때, **When** 취소·X·Esc·딤 클릭 중 무엇이든 하면, **Then** 모달이 닫힌다
5. **Given** 어떤 화면이든, **When** `?m=` 에 정의되지 않은 값을 넣으면, **Then** 모달이 열리지 않고 **부모 페이지만** 정상으로 뜬다

---

### User Story 4 - 옛 주소로 들어와도 화면에 닿는다 (Priority: P3)

루트 주소와 이전에 쓰던 화면 주소로 들어와도 지금의 화면으로 보내진다.

**Why this priority**: 사용자가 북마크·링크로 들어오는 경로를 살린다. 다만 새 주소만 써도 앱은 완결되므로 마지막이다.

**Independent Test**: 루트와 구 URL 목록에 차례로 들어가 각각 정해진 곳으로 보내지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 상태에서, **When** 루트 주소로 들어가면, **Then** 월별 가계부 화면으로 보내진다
2. **Given** 로그인하지 않았을 때, **When** 루트 주소로 들어가면, **Then** 로그인 화면으로 보내진다
3. **Given** 구 등록 주소(예: 수단 등록의 옛 경로)로 들어갔을 때, **When** 화면이 응답하면, **Then** 부모 목록 + 해당 `?m=` 딥링크로 보내진다

### Edge Cases

- **재발급 직후에도 `1001` 이 오면?** 다시 재발급하지 않는다. 한 번만 시도하고, 그래도 실패하면 세션을 지우고 로그인으로 보낸다 — 재시도를 열어 두면 백엔드가 계속 `1001` 을 줄 때 무한 왕복이 된다.
- **세션은 살아 있는데 백엔드 토큰이 죽었을 때?** 세션 존재만으로 통과시키지 않는다. 백엔드가 `1001`·`1006` 으로 답하는 순간 세션을 지운다.
- **백엔드 토큰은 살아 있는데 세션이 만료됐을 때?** 토큰을 잃은 것이므로 미로그인으로 본다. 백엔드에는 세션이 남아 있지만 화면 모듈이 그것을 꺼낼 방법이 없다.
- **한 화면이 API 를 여러 번 부르는데 그중 하나가 `1001` 이면?** 그 호출에서 재발급이 일어나고 새 토큰이 세션에 반영되어 뒤이은 호출이 새 토큰을 쓴다.
- **백엔드가 봉투가 아닌 것을 돌려줄 때?** 아이콘·엑셀 두 API 는 의도된 예외라 바이트로 다루고, 그 밖의 응답이 봉투가 아니면 실패로 본다.
- **관리자 전용 URL 에 미로그인으로 들어오면?** 로그인 판정이 먼저다 — 권한 없음 화면은 "로그인은 했는데 권한이 모자란" 경우에만 보인다. 순서가 뒤집히면 미로그인 사용자에게 그 URL 이 실재한다는 사실이 드러난다.
- **DB 가 꺼져 있으면?** 화면 모듈은 정상 기동한다. DB 를 모르기 때문이다.

## Requirements *(mandatory)*

### Functional Requirements

**화면 모듈의 경계 (US1)**

- **FR-601**: 화면 모듈은 DB·`data-mod`·JPA·MyBatis 를 의존하지 않아야 한다. 자체 Entity·Repository·Mapper 를 두지 않는다
- **FR-602**: 화면 모듈의 모든 데이터는 백엔드 API 호출로만 얻어야 한다. DB 로 가는 우회로를 남기지 않는다
- **FR-603**: 백엔드 응답의 `{ resCode, data }` 봉투는 **한 곳에서만** 해석해야 한다. 화면·컨트롤러가 각자 풀지 않는다
- **FR-604**: `resCode` 가 `200` 이 아니면 실패로 보고 그 `resCode` 와 `data.message` 를 화면으로 전달해야 한다. 실패를 성공으로 읽지 않는다
- **FR-605**: 본문이 바이너리인 응답 2건(지출유형 아이콘 조회·엑셀 양식 다운로드)은 봉투 해석을 거치지 않고 바이트 그대로 전달해야 한다
- **FR-606**: 백엔드에 닿지 못하면(연결 거부·타임아웃) 사용자에게 그 사실을 알려야 하며, 화면이 빈 값으로 조용히 뜨지 않아야 한다
- **FR-607**: 화면 모듈은 새 에러코드를 정의하지 않는다. 백엔드가 준 코드를 그대로 전달한다
- **FR-608**: 깨져 있던 화면 모듈의 레거시 테스트를 정리해 모듈 테스트가 통과해야 한다
- **FR-609**: 백엔드 호출은 메서드별 규칙을 지켜야 한다 — GET 은 Body 없이 **Path 또는 Query 중 하나만**(혼용 금지), POST 는 Body 만, PATCH 는 Path(키) + Body(변경분), DELETE 는 Path 만. **`PUT` 을 쓰지 않는다.** 유일한 예외는 월별 통계 조회로, Path 연·월 + Query `view` 를 함께 쓴다
- **FR-610**: 목록 화면이 쓸 **페이징 환산을 공통으로** 제공해야 한다. `offset` 은 항상 `limit` 의 배수로 만들고(어기면 `9001` 로 목록이 통째로 실패한다), `limit` 이 바뀌면 첫 페이지로 되돌린다. 화면마다 이 계산을 따로 두지 않는다
- **FR-611**: 지출유형 아이콘을 화면 모듈 경로로 내려줘야 한다. 화면은 백엔드 주소가 아니라 **화면 모듈의 아이콘 경로**를 `<img>` 로 걸고, 화면 모듈이 백엔드에서 받아 바이트 그대로 전달한다 — 브라우저가 `:8081` 을 직접 부르지 않는다는 결정(§Assumptions)의 결과다
- **FR-612**: 실패를 화면에 알리는 방식은 **공통 처리에 맡겨야** 한다. 컨트롤러마다 try-catch 로 응답을 제각각 만들지 않는다 — 화면 31개가 같은 실패를 다르게 보여주면 사용자가 무엇이 잘못됐는지 배울 수 없다

**세션 인증 (US2)**

- **FR-613**: 로그인 성공 시 `accessToken`·`refreshToken` 과 판정에 쓸 회원 정보(아이디·권한)를 **서버 세션에** 담아야 한다
- **FR-614**: 백엔드 호출마다 세션의 `accessToken` 을 `Authorization: Bearer` 로 붙여야 한다
- **FR-615**: `1001` 을 받으면 세션의 `refreshToken` 으로 재발급을 **한 번** 시도하고, 성공하면 새 토큰으로 세션을 덮어쓴 뒤 원래 요청을 다시 불러야 한다
- **FR-616**: 재발급이 실패하거나 `1006` 을 받으면 세션을 무효화하고 로그인 화면으로 보내야 한다
- **FR-617**: 재발급 재시도는 **한 번뿐**이어야 한다. 재발급 직후 요청이 다시 `1001` 이어도 또 재발급하지 않는다
- **FR-618**: 비로그인 허용 URL(화면 1.1~1.6)을 제외한 모든 화면 URL 은 세션에 토큰이 없으면 로그인 화면으로 보내야 한다
- **FR-619**: 관리자 전용 URL(화면 1.8~1.10)은 로그인했으나 권한이 관리자가 아니면 권한 없음 화면으로 보내야 한다
- **FR-620**: 미로그인 상태로 관리자 전용 URL 에 접근하면 권한 없음이 아니라 **로그인 화면**으로 보내야 한다. 로그인 판정이 권한 판정보다 먼저다
- **FR-621**: 로그아웃은 백엔드에서 JWT 를 비활성화한 뒤 **세션을 무효화**해야 한다
- **FR-622**: JWT 원문을 로그·HTML·화면에 남기지 않아야 한다
- **FR-623**: 세션이 만료되어 토큰을 잃으면 미로그인으로 보고 로그인 화면으로 보내야 한다

**공통 껍데기 (US3)**

- **FR-624**: 로그인 전용 레이아웃과 로그인 후 레이아웃 두 가지를 두고, 모든 화면이 둘 중 하나를 써야 한다
- **FR-625**: 로그인 후 레이아웃은 사이드바를 포함하고 현재 화면에 해당하는 메뉴를 **활성으로** 표시해야 한다
- **FR-626**: 일반 권한 회원에게 회원 관리 메뉴를 **보이지 않아야** 한다
- **FR-627**: 등록·수정·상세는 부모 페이지 위에 뜨는 모달이어야 하며 **부모 URL + `?m=`** 딥링크로 열려야 한다
- **FR-628**: 모달은 취소·닫기·Esc·딤 클릭 중 무엇으로도 닫혀야 한다
- **FR-629**: 삭제·회원 정지·할부 중도상환의 확인은 **공통 확인 다이얼로그** 하나를 써야 한다
- **FR-630**: 정의되지 않은 `?m=` 값은 모달을 열지 않고 부모 페이지만 보여야 한다. 오류 화면으로 보내지 않는다
- **FR-631**: 화면기획의 디자인 토큰·공통 스타일·모달 스크립트를 화면 모듈의 정적 자원으로 이식해 전 화면이 같은 것을 써야 한다
- **FR-632**: 권한 없음 화면(1.6)을 만들어 FR-619 의 착지점으로 삼아야 한다

**주소 정리 (US4)**

- **FR-633**: 루트 주소는 로그인했으면 월별 가계부로, 아니면 로그인 화면으로 보내야 한다
- **FR-634**: 구 화면 URL 은 부모 페이지 + 해당 `?m=` 딥링크로 보내야 한다

### 이 기능이 쓰는 에러코드

**새로 정의하는 코드가 없다.** 화면 모듈은 백엔드가 준 코드를 전달만 한다.

| 코드 | 뜻 | 화면 모듈의 반응 |
|---|---|---|
| `200` | 성공 | `data` 를 화면에 넘긴다 |
| `1001` | 인증 실패·Access 만료 | 재발급 1회 → 실패 시 세션 무효화 + 로그인 |
| `1006` | 다른 곳 로그인으로 세션 무효 | 재발급 없이 세션 무효화 + 로그인 |
| 그 밖의 4자리 | 백엔드 비즈니스·검증 실패 | `resCode` 와 `message` 를 화면에 표시 |

**실패도 HTTP 200 이다**(헌장 원칙 III). HTTP 상태로 성공·실패를 가르면 전부 성공으로 읽힌다.

### Key Entities

DB 저장 단위가 없다. 화면 모듈이 들고 있는 상태는 세션 하나뿐이다.

- **로그인 세션**: 백엔드가 발급한 `accessToken`·`refreshToken` 과, 화면 표시·권한 판정에 쓸 회원 아이디·권한. 브라우저에는 세션 식별자만 나가고 토큰은 서버에만 있다. 로그아웃·재로그인·세션 만료로 사라진다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-601**: DB 를 내린 상태에서 화면 모듈이 정상 기동한다 — 화면 모듈이 DB 를 모른다는 증거다
- **SC-602**: 화면 모듈 소스에 `data-mod`·JPA·MyBatis 참조가 **0건**이다
- **SC-603**: 전 모듈 테스트가 한 번에 통과한다 — `init` 커밋부터 깨져 있던 레거시 시험이 정리되어, 모듈을 나눠 돌리지 않아도 된다
- **SC-604**: 로그인이 필요한 화면 URL **전부**를 미로그인으로 열면 예외 없이 로그인 화면으로 보내진다
- **SC-605**: 관리자 전용 URL **전부**를 일반 권한으로 열면 예외 없이 권한 없음 화면으로 보내진다
- **SC-606**: Access 토큰이 만료된 상황에서 사용자가 **다시 로그인하지 않고** 하던 일을 이어서 한다
- **SC-607**: 브라우저가 받은 어떤 응답에도 JWT 원문이 들어 있지 않다
- **SC-608**: 백엔드가 꺼져 있을 때 사용자가 **그 사실을 읽을 수 있고**, 데이터가 없는 화면을 정상으로 오해하지 않는다
- **SC-609**: 백엔드 실패 응답의 `resCode` 가 화면까지 **바뀌지 않고** 도달한다
- **SC-610**: 모달 딥링크로 들어온 URL 이 모달이 열린 화면을 보여주고, 정의되지 않은 값이면 부모 페이지가 정상으로 뜬다

## Assumptions

- **백엔드 002~006 은 이미 서 있다.** API 56건이 `:8081` 에서 동작하며 007 은 그것을 소비만 한다. 백엔드 코드와 `sql/schema-moneylogdb.sql` 은 바뀌지 않는다
- **화면기획 산출물을 그대로 쓴다.** 디자인 토큰·공통 스타일·모달 스크립트는 이미 완성돼 있어 새로 설계하지 않고 경로만 맞춰 이식한다
- **브라우저가 백엔드를 직접 부르지 않는다.** 서버 세션 결정의 결과이며, 그래서 백엔드에 CORS 설정을 더하지 않는다
- **화면 JS 는 토큰을 모른다.** 클라이언트 스크립트는 모달 열고 닫기 같은 화면 조작만 하고 API 를 부르지 않는다
- **레거시 화면 4개는 버린다.** 현재 템플릿(`home`·`signin`·`signupsample`·`target/default`)은 구 테이블을 전제한 샘플이라 살릴 것이 없다
- **한 사용자가 한 브라우저에서 쓴다.** 회원당 활성 세션 1건이라는 백엔드 규칙과 맞물려, 다른 곳에서 로그인하면 이쪽 세션은 `1006` 으로 정리된다
