# Contract: 세션 인증과 권한 판정

**Feature**: 007-frontend-foundation | **관련 FR**: 613~623

## 1. 토큰은 서버 세션에만 산다

브라우저로 내려가는 것은 **`JSESSIONID` 쿠키뿐**이다. JWT 원문은 HTML·JS·로그 어디에도
나타나지 않는다(FR-622·SC-607).

이 결정의 결과가 셋이다.

- 브라우저가 `:8081` 을 직접 부르지 않는다 → 백엔드에 CORS 설정이 필요 없다.
- JWT 가 JS 에서 읽히지 않는다 → XSS 로 토큰이 새지 않는다.
- 화면 JS 는 토큰을 모른다 → `modal.js` 는 화면 조작만 하고 API 를 부르지 않는다.

세션 속성 목록과 수명은 [data-model.md](../data-model.md) § 로그인 세션.
읽고 쓰는 자리는 `LoginSession` **한 클래스뿐**이다.

## 2. 화면 URL 의 세 등급

| 등급 | 화면 | URL |
|---|---|---|
| **비로그인 허용** | 1.1~1.6 | `/auth/login` · `/auth/signup` · `/auth/find-id` · `/auth/find-password` · `/auth/reset-password` · `/error/forbidden` |
| **로그인 필수** | 1.7 및 Phase 2~6 전부 | 위 여섯을 제외한 모든 화면 URL |
| **관리자 필수** | 1.8~1.10 | `/admin/**` |

**비로그인 허용은 여섯 개가 전부다**(FR-618). 목록을 화이트리스트로 두고, 새 URL 이 생기면
기본이 "로그인 필요"가 되게 한다 — 블랙리스트로 두면 008~012 가 화면을 더할 때마다 빠뜨릴 수 있다.

**인터셉터를 타지 않는 경로**: 정적 자원(`/css/**`·`/js/**`·`/images/**`·`/favicon.ico`), **아이콘 프록시(`/expend-groups/icons/**`)**, 오류 착지(`/error`), 그리고 **보낼 곳만 정하는 주소 셋**(`/` · `/mem/ind` · `/mem/login`).

오류 착지를 빼는 이유는 판정이 걸리면 오류 화면이 로그인으로 밀려나 **무엇이 잘못됐는지 사용자에게 영영 보이지 않기** 때문이다.

주소 셋을 빼는 이유는 그것들이 화면이 아니기 때문이다. 본문을 그리지도 백엔드를 부르지도 않고 `Location` 하나만 내보낸다. 특히 **루트를 빼는 것은 요구사항이다**(FR-633) — 로그인 상태에 따라 `/ledger` 와 `/auth/login` 으로 갈라 보내는 판단을 루트가 **직접** 해야 하는데, 판정이 먼저 가로채면 그 분기가 한 번도 실행되지 않는다. `/mem/ind` 는 루트로 보내 같은 분기를 다시 타게 하고, `/mem/login` 은 로그인 화면으로 보낸다. 둘 다 로그인하지 않은 사용자가 북마크로 들어오는 자리라 막으면 갈 곳을 잃는다.

**구 화면 URL 16건은 여기 들어가지 않는다.** 그것들은 보호 화면으로 보내는 주소라 판정을 그대로 탄다 — 미로그인으로 `/payments/new` 에 오면 `/auth/login` 이 먼저다.

아이콘 프록시를 여기 넣는 이유는 정적 자원을 뺀 이유와 같다 — 지출유형이 20개인 화면을 열면 아이콘 요청이 20건 나가는데, 그때마다 `MemberTokenValidate` 가 따라붙으면 화면 한 번에 백엔드 왕복이 40건이 된다. **판정을 건너뛰는 것이 아니다**: 프록시는 세션의 `accessToken` 을 붙여 백엔드를 부르므로 소유자 판정과 토큰 검증을 **백엔드가** 그대로 한다. 세션이 비어 있으면 토큰 없이 호출해 `1001` 이 오고, 프록시는 이미지를 내보내지 않고 404 로 끝낸다.

## 3. 판정 순서 — 로그인이 먼저다

`AuthInterceptor` **하나**가 두 단계를 순서대로 한다. 인터셉터를 둘로 나누지 않는다(research 8).

```
요청
 ├─ 비로그인 허용 URL 인가?  ── 예 ─→ 통과
 │            │ 아니오
 ├─ ① 세션에 accessToken 이 있는가?
 │      │ 없다 ─→ redirect /auth/login              (FR-618·623)
 │      │ 있다
 │      └─ MemberTokenValidate 호출                  (FR-614)
 │             │ 1001 ─→ 재발급 1회 → 실패 시 세션 무효화 + /auth/login
 │             │ 1006 ─→ 세션 무효화 + /auth/login
 │             │ 200
 ├─ ② 관리자 전용 URL 인가?
 │      │ 아니다 ─→ 통과
 │      │ 맞다
 │      └─ role == 1 인가?
 │             │ 예   ─→ 통과
 │             └─ 아니오 ─→ redirect /error/forbidden  (FR-619)
```

**①이 ②보다 먼저인 것이 요구사항이다**(FR-620). 미로그인 사용자가 `/admin/members` 에
들어오면 `/error/forbidden` 이 아니라 `/auth/login` 으로 간다 — 권한 없음 화면을 보여 주면
**그 URL 이 실재한다는 사실이 드러난다**.

`MemberTokenValidate` 를 **세션이 있을 때만** 부르는 이유는 research 9. 세션이 비었으면
토큰 없이 호출해 `1001` 을 받는 것이 확정이라 왕복이 낭비다.

## 4. 재발급 — 한 번뿐

재발급이 일어나는 자리는 둘이다. **인터셉터의 검증 호출**과 **화면이 부르는 각 API 호출**.
둘 다 `BackendApiClient` 를 거치므로 규칙은 하나다.

| 상황 | 동작 |
|---|---|
| `1001` 수신 | 세션 `refreshToken` 으로 `MemberTokenRefresh` 를 **한 번** 부른다 |
| 재발급 성공 | 응답의 `accessToken`·`refreshToken` 을 **둘 다** 세션에 덮어쓰고 원래 요청을 다시 보낸다 |
| 재발급 응답이 `1005` | Refresh 가 만료·무효·해시 불일치. 세션 무효화 → `/auth/login` |
| 재발급 응답이 `1006` | 다른 곳 로그인으로 세션 폐기. 세션 무효화 → `/auth/login` |
| 재발급 응답이 `1004` | 비활성 계정. 세션 무효화 → `/auth/login` |
| 재시도한 요청이 다시 `1001` | **또 재발급하지 않는다.** 세션 무효화 → `/auth/login` (FR-617) |
| 처음부터 `1006` | **재발급을 시도하지 않는다.** 세션 무효화 → `/auth/login` |

**`refreshToken` 을 함께 덮어써야 한다.** 백엔드 `MemberTokenRefresh` 는 Rotation 이라
새 Refresh 를 함께 준다. Access 만 갱신하면 세션에 이미 폐기된 Refresh 가 남아 **다음 재발급이
`1005` 로 실패한다** — "한 번은 되고 두 번째부터 안 되는" 증상이라 원인을 찾기 어렵다.

**재시도를 열어 두면 안 되는 이유**: 백엔드가 계속 `1001` 을 주는 상황에서 무한 왕복이 된다.

### 사용자에게 보이는 문구

세 코드의 처리는 같지만 안내는 갈린다.

| 코드 | 문구 |
|---|---|
| `1006` | 다른 곳에서 로그인되어 로그아웃되었습니다 |
| `1005` | 다시 로그인해 주세요 |
| `1004` | 비활성화된 계정입니다 |

`common-mod` 의 `ErrorCode` 기본 문구가 이미 이렇게 나뉘어 있다. 화면 모듈은 그것을 쓴다.

## 5. 로그인과 로그아웃

**로그인 성공** (`MemberLogin`, 008 이 화면을 만든다)

1. 응답의 `accessToken`·`refreshToken`·`memberId`·`role` 을 세션에 담는다 (FR-613)
2. **세션 id 를 새로 만든다**(session fixation 방어)
3. `/ledger`(월별 가계부)로 보낸다 — 착지는 FR-633 과 같다

**로그아웃**

1. `MemberTokenRevoke` 를 **먼저** 부른다 (세션의 Access 가 아직 필요하다)
2. `session.invalidate()`
3. `/auth/login` 으로 보낸다

**순서를 뒤집으면 백엔드 JWT 가 살아남는다**(FR-621). 세션을 먼저 비우면 `Revoke` 에 쓸
토큰이 없다.

`Revoke` 가 실패해도(이미 폐기된 세션 등) **세션 무효화는 진행한다.** 사용자가 로그아웃을
눌렀는데 화면이 로그인 상태로 남는 쪽이 더 나쁘다.

## 6. 세션 만료

| 항목 | 값 |
|---|---|
| `server.servlet.session.timeout` | **30분** |
| 만료 후 보호 URL 접근 | `/auth/login` (미로그인과 같다 — FR-623) |
| 백엔드 토큰 | **살아 있다.** 화면이 꺼낼 방법이 없을 뿐이다 |

현재 설정은 단위 없는 `60`, 즉 **60초**다. Access 토큰이 1일인데 화면 세션이 1분이면
재발급 흐름이 실제로 관측되지 않는다 — 세션이 먼저 죽는다. 값 근거는 research 12,
`_공통.md` 반영은 선행 개정 4번.

## 7. 시험으로 고정할 것

| 항목 | 근거 |
|---|---|
| 비로그인으로 보호 URL → `/auth/login` **예외 없이** | SC-604 |
| 일반 권한으로 관리자 URL → `/error/forbidden` **예외 없이** | SC-605 |
| **미로그인**으로 관리자 URL → `/error/forbidden` 이 **아니라** `/auth/login` | FR-620 |
| `1001` → 재발급 1회 → 원래 요청 재시도 성공 | SC-606 |
| 재발급 응답의 `refreshToken` 이 세션에 반영됨 | research 7 |
| 재시도 후 다시 `1001` → 두 번째 재발급이 **없음** | FR-617 |
| `1006` → 재발급 시도 **없이** 세션 무효화 | FR-616 |
| 어떤 응답 본문에도 JWT 원문이 없음 | SC-607 |
| 아이콘 프록시 요청에 `MemberTokenValidate` 가 **나가지 않음** (호출 0건) | 위 §2 제외 경로 |

`/auth/login` 과 `/ledger` 는 008·010 이 만들 화면이라 007 시점에는 없다.
**시험은 redirect 대상(Location)을 확인하고, 그 화면이 렌더링되는지는 보지 않는다.**
